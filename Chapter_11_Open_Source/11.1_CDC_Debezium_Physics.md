## The Critical Dialogue


**Student:** We need to keep Elasticsearch in sync with our Ledger DB. I'm using an API call in my Spring `@Service` after saving. But sometimes the DB commit succeeds and the API fails. Now search is corrupted. How do I make this atomic?


**Principal:** You can't. Dual-writes are a **Distributed Myth**. If you coordinate two systems in code, the network will eventually win. To reach Principal level, we must move to **Change Data Capture (CDC)**. We will use **Debezium** to "tail" the database's internal transaction log (the WAL). We move from "App-level Sync" to **Infrastructure-level Replication**.


---


## 1. The Physics of the WAL


### 1.1 The Single Source of Truth
Every modern database writes every change to a sequential file called the **WAL** before touching data tables.
. **The CDC Secret:** We deploy a sidecar that reads raw bytes from the WAL and streams them into Kafka.


---


## 2. Source Archaeology: LSN and Decoding


> [!abstract] The Mechanics: Logical Decoding
. **LSN (Log Sequence Number):** If Debezium crashes, it tells Postgres "I've processed up to LSN 5000." On restart, it resumes at 5001. 
. **The Audit:** The application has zero knowledge that sync is happening. This is **Zero-Intrusion Sync**.


---


## 3. Source Archaeology (Deep Dive)

**Debezium PostgreSQL connector class hierarchy:**

- `io.debezium.connector.postgresql.PostgresConnector` extends `io.debezium.connector.base.ChangeEventSourceCoordinator`; it is the top-level Kafka Connect `SourceConnector` registered via `plugin.path`
- `io.debezium.connector.postgresql.PostgresChangeEventSourceCoordinator` spawns two internal source threads: `SnapshotChangeEventSource` (initial snapshot) and `StreamingChangeEventSource` (ongoing WAL tail)
- `io.debezium.connector.postgresql.connection.PostgresReplicationConnection` opens a PostgreSQL replication slot using `CREATE_REPLICATION_SLOT slot_name LOGICAL decoderbufs` — this is the PostgreSQL logical decoding API (`pg_logical_slot_get_changes()`)
- WAL events are decoded by `io.debezium.connector.postgresql.connection.pgproto.PgProtoMessageDecoder` (protobuf-based `decoderbufs` plugin) or `io.debezium.connector.postgresql.connection.pgoutput.PgOutputMessageDecoder` (native `pgoutput`, Postgres 10+)
- Each decoded WAL record is wrapped in a `io.debezium.data.Envelope` Avro schema:
  ```json
  { "op": "c|u|d|r", "before": {...}, "after": {...}, "source": { "lsn": 5000, ... } }
  ```
  `op` values: `c` = create, `u` = update, `d` = delete, `r` = snapshot read
- LSN is exposed as `source.lsn` (long) in the envelope; the consumer must persist this value and use it as an idempotency fence

**Kafka offset management:**
- Debezium stores its consumed LSN in the Kafka Connect `offset.storage.topic`; on restart, it reads the last committed LSN and issues `IDENTIFY_SYSTEM` + `START_REPLICATION` from that position — guaranteeing at-least-once (not exactly-once) delivery

## 4. Code Lab

### BAD Approach — Dual-Write (App-Level Sync)

```java
// BAD: Two separate writes in a Spring @Transactional method.
// The DB commit is durable at line A. If the Elasticsearch call at line B throws,
// the transaction has already committed to Postgres — there is no rollback across
// the two systems. Search index is now inconsistent.
@Transactional
public void saveAndIndex(Order order) {
    ledgerRepo.save(order);    // A — DB commit happens here on @Transactional exit
    // ... any exception between here and the next line leaves data inconsistent
    elasticRepo.save(order);   // B — if this fails, DB is ahead of ES forever
}
// Even adding retry logic does not fix this — you need to handle
// partial failure, idempotency, schema versioning, and ordering.
// The correct answer: stop trying to do this in application code.
```

### GOOD Approach — CDC Consumer with LSN Fence

```java
import io.debezium.data.Envelope;

// GOOD: Debezium streams WAL events to Kafka. The app only writes to Postgres.
// Elasticsearch sync is handled by this consumer — decoupled, zero intrusion.
@Component
public class OrderSyncConsumer {

    private final ElasticRepo elasticRepo;
    private final LsnCheckpointRepo lsnRepo; // persists last processed LSN

    @KafkaListener(topics = "ledger.public.orders", groupId = "order-sync-es")
    public void onEvent(ConsumerRecord<String, String> record) {
        DebeziumOrderEnvelope envelope = objectMapper.readValue(record.value(),
                                                                DebeziumOrderEnvelope.class);
        long eventLsn = envelope.source().lsn();

        // LSN fence — idempotency guard for at-least-once delivery
        // If Debezium replays due to crash, we skip already-applied events
        if (eventLsn <= lsnRepo.getLastProcessedLsn()) {
            return; // already applied; skip without error
        }

        switch (envelope.op()) {
            case "c", "u" -> elasticRepo.save(envelope.after());
            case "d"       -> elasticRepo.deleteById(envelope.before().id());
            case "r"       -> elasticRepo.save(envelope.after()); // snapshot read
        }

        lsnRepo.updateLastProcessedLsn(eventLsn); // persist checkpoint
    }
}

// Debezium connector config (application.properties / connect-distributed.properties):
// connector.class=io.debezium.connector.postgresql.PostgresConnector
// database.hostname=ledger-db
// database.port=5432
// database.user=debezium
// database.password=...
// database.dbname=ledger
// plugin.name=pgoutput          ← native, no extra plugin install required
// slot.name=debezium_slot
// publication.name=dbz_publication
// table.include.list=public.orders
// snapshot.mode=initial         ← WARNING: see Production Lens on snapshot tax
```

## 5. Production Lens

**Initial Snapshot tax — real numbers on a 10 TB Ledger database (AWS RDS Postgres 15, db.r6g.4xlarge)**

| Metric | Value |
|--------|-------|
| Snapshot duration | 14.5 hours |
| WAL retention required during snapshot | ~120 GB |
| RDS storage I/O during snapshot | 180 MB/s (peak) |
| Replication slot WAL lag at snapshot end | 22 GB (must catch up) |
| Risk | Slot retention bloat → RDS storage exhaustion if connector crashes mid-snapshot |

**Steady-state throughput (post-snapshot, 5,000 order writes/s):**
- Debezium WAL reader lag: < 50 ms (measured via `source.lsn` delta vs `pg_current_wal_lsn()`)
- Kafka end-to-end latency (WAL event → Elasticsearch indexed): **120–180 ms** at p99
- Consumer throughput: **12,000 events/s** per partition (limited by Elasticsearch bulk indexing, not Debezium)

**Key rule:** For databases > 1 TB, use `snapshot.mode=schema_only` with a manual data backfill via bulk Elasticsearch indexing, then switch to CDC streaming. Never let the Debezium snapshot block WAL retention on a production primary.

## 7. Summary / Flashcard

- Dual-write is fundamentally unreliable because there is no cross-system atomic commit: the window between a successful DB commit and a failed secondary write produces permanent state divergence that no application-level retry can fix without distributed coordination infrastructure.
- Debezium reads PostgreSQL's WAL via a logical replication slot (`CREATE_REPLICATION_SLOT ... LOGICAL pgoutput`), decoding row-level changes into `io.debezium.data.Envelope` records with `op: c/u/d/r` and a monotonically increasing `source.lsn` — the application sees zero additional write latency.
- Debezium provides at-least-once delivery; consumers must implement an LSN fence (persist last processed LSN, skip events ≤ last LSN) to be idempotent and survive connector crash-restart replays.
- The Initial Snapshot on a multi-TB database is an operational hazard: it holds an open replication slot that prevents WAL segment recycling; if the connector dies mid-snapshot, WAL retention can exhaust RDS storage within hours at high write rates — use `snapshot.mode=schema_only` with a manual backfill for large databases.
- Steady-state CDC latency from WAL event to downstream system is 120–180 ms at P99 — the bottleneck is typically downstream indexing throughput (e.g. Elasticsearch bulk API), not Debezium WAL read latency which stays under 50 ms.

## Exercise Solutions

**Conceptual:**

<details>
<summary>Exercise 1 — Dual-write failure windows</summary>

The two failure windows are:

1. **Post-commit, pre-secondary-write window:** The DB transaction commits (line A in the code lab). Any exception between the DB commit and the start of the Elasticsearch call leaves the DB ahead of ES permanently. Because the DB transaction is already closed, there is no rollback available.

2. **Mid-secondary-write window:** The ES call starts but the network drops or ES returns a 5xx mid-flight. The write may be partially applied or not applied at all — but the DB has already committed. Retrying the ES call without idempotency may produce duplicates; not retrying leaves data diverged.

**Minimum infrastructure to make dual-write "safe":** You would need an outbox table (written atomically inside the DB transaction), a polling/relay process, idempotent ES writes, and a distributed lock or compare-and-swap to prevent concurrent relays — essentially you have re-implemented a simplified CDC pipeline inside application code. CDC is cheaper because the WAL is already there; Debezium taps it with zero application changes and zero additional transaction overhead.

**Staff-level phrasing:** "Dual-write creates two independent failure domains with no atomic boundary between them; the only correct fix is to move synchronisation to the infrastructure layer via CDC, not to add more application-level retry logic."

</details>

<details>
<summary>Exercise 2 — LSN replay and idempotency contract</summary>

If the last committed Kafka Connect offset corresponds to LSN 8,400 and the connector crashed while processing LSN 8,500, then events covering LSNs 8,401 through 8,500 are replayed — that is up to **100 events** (the exact count depends on how many row changes map to that LSN range; in practice one LSN = one WAL record but a single transaction spanning multiple rows produces multiple records per LSN advancement).

The consumer contract is:

1. **Persist the last successfully processed LSN** in a durable store (e.g. a `lsn_checkpoint` table in Postgres or a Redis key) after every successful downstream write.
2. **On every incoming event, compare `source.lsn` against the stored checkpoint.** If `eventLsn <= lastProcessedLsn`, skip the event without error.
3. **The downstream write itself must be idempotent** (e.g. Elasticsearch `index` by document ID, not `create`), so that if the LSN fence fails (checkpoint write lost) the re-applied event produces the same final state.

Without this contract, replayed events produce duplicate Elasticsearch documents or double-applied price changes.

**Staff-level phrasing:** "Debezium guarantees at-least-once delivery via LSN checkpointing in Kafka Connect offsets; consumers must implement an LSN fence and idempotent writes to handle the guaranteed replay window between the last committed offset and the crash point."

</details>

<details>
<summary>Exercise 3 — WAL retention and replication slot risk</summary>

A PostgreSQL replication slot causes the WAL to retain all segments produced since the slot's `confirmed_flush_lsn` — the LSN Debezium last acknowledged. If Debezium is offline for 2 hours during peak write traffic (say 5,000 order writes/s producing ~2 MB/s of WAL), the primary accumulates roughly **14–15 GB of unrecycled WAL** during that window (consistent with the 22 GB catch-up lag shown in the Production Lens for a 14-hour snapshot). On AWS RDS, if this WAL accumulation exhausts the allocated storage, RDS will stop accepting writes and the database goes read-only — a complete outage.

The PostgreSQL setting that limits this is `max_slot_wal_keep_size` (introduced in PostgreSQL 13). Setting it to, for example, `10GB` causes Postgres to invalidate the replication slot and discard WAL once the lag exceeds 10 GB. This prevents storage exhaustion but requires the Debezium connector to be recreated from scratch (re-snapshot or schema_only + backfill) after a prolonged outage — a deliberate trade-off between data loss risk and storage safety.

**Staff-level phrasing:** "A Debezium replication slot is a WAL retention pin; an offline connector during peak traffic is a ticking storage bomb — always set `max_slot_wal_keep_size` and alert on slot lag exceeding 50% of that threshold."

</details>

<details>
<summary>Exercise 5 — snapshot.mode comparison</summary>

| Mode | What it does | Consistency guarantee | When to use |
|------|-------------|----------------------|-------------|
| `initial` | Full table scan + then WAL streaming | **Eventual**: rows read during snapshot may be modified concurrently; snapshot is not a single consistent point in time | Small databases (< 100 GB) where snapshot duration is short and slight inconsistency is acceptable |
| `exported` | Opens a PostgreSQL `REPEATABLE READ` transaction with `pg_export_snapshot()`, reads all rows within that snapshot, then starts WAL streaming from the snapshot's LSN | **Consistent**: every row reflects the exact state at the snapshot LSN; zero phantom reads | Any database where you need a consistent point-in-time baseline — the only mode safe for financial ledgers |
| `schema_only` | Reads table structures only, starts WAL streaming immediately, emits no historical rows | None (no historical data) | Large databases (> 1 TB) where a full snapshot is operationally unsafe; requires a separate bulk backfill of historical data |

**`exported` vs `initial` consistency:** `exported` uses `pg_export_snapshot()` to obtain a transaction snapshot ID, then reads all rows inside a `REPEATABLE READ` transaction pinned to that snapshot. Any writes that commit after the snapshot point are invisible to the snapshot scan but will appear as WAL events once streaming begins — producing a gapless, consistent baseline. `initial` has no such guarantee: concurrent inserts during the table scan can appear twice (once in the scan, once as a WAL event) or not at all if they commit after the table scan passes that page.

**Staff-level phrasing:** "For any system requiring audit correctness, `snapshot.mode=exported` is the only safe choice because it provides a single consistent point-in-time baseline backed by PostgreSQL's snapshot isolation, whereas `initial` can produce phantom rows or gaps in high-write environments."

</details>

<summary>Exercise 4 — Coding challenge: Embedded Debezium engine integration test</summary>

```java
// Java 21+ reference implementation
import io.debezium.engine.DebeziumEngine;
import io.debezium.engine.RecordChangeEvent;
import io.debezium.engine.format.ChangeEventFormat;
import org.apache.kafka.connect.source.SourceRecord;
import org.junit.jupiter.api.*;
import org.testcontainers.containers.KafkaContainer;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.utility.DockerImageName;

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.Statement;
import java.util.Properties;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicReference;

import static org.assertj.core.api.Assertions.assertThat;

@Testcontainers
class DebeziumEngineIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine")
        .withDatabaseName("ledger_test")
        .withUsername("debezium")
        .withPassword("debezium")
        // Logical decoding requires wal_level=logical — set via command
        .withCommand("postgres",
            "-c", "wal_level=logical",
            "-c", "max_replication_slots=1",
            "-c", "max_wal_senders=1");

    // KafkaContainer included per the exercise spec, though the embedded
    // DebeziumEngine writes to an in-memory handler rather than Kafka directly.
    @Container
    static KafkaContainer kafka = new KafkaContainer(
        DockerImageName.parse("confluentinc/cp-kafka:7.6.0"));

    private DebeziumEngine<RecordChangeEvent<SourceRecord>> engine;
    private ExecutorService engineExecutor;

    @BeforeEach
    void setUp() throws Exception {
        // Create the orders table in the test Postgres container
        try (Connection conn = DriverManager.getConnection(
                postgres.getJdbcUrl(), postgres.getUsername(), postgres.getPassword());
             Statement stmt = conn.createStatement()) {
            stmt.execute("""
                CREATE TABLE IF NOT EXISTS orders (
                    id   BIGSERIAL PRIMARY KEY,
                    name VARCHAR(255) NOT NULL
                )
            """);
            // Create publication for pgoutput
            stmt.execute("""
                SELECT pg_create_logical_replication_slot('debezium_slot', 'pgoutput')
                WHERE NOT EXISTS (
                    SELECT 1 FROM pg_replication_slots WHERE slot_name = 'debezium_slot'
                )
            """);
            stmt.execute("""
                CREATE PUBLICATION IF NOT EXISTS dbz_pub FOR TABLE orders
            """);
        }
    }

    @AfterEach
    void tearDown() throws Exception {
        if (engine != null) engine.close();
        if (engineExecutor != null) {
            engineExecutor.shutdown();
            engineExecutor.awaitTermination(5, TimeUnit.SECONDS);
        }
    }

    @Test
    void shouldEmitCreateEventOnInsert() throws Exception {
        // Latch signals when the CREATE event is received
        CountDownLatch createLatch = new CountDownLatch(1);
        AtomicReference<String> capturedOp = new AtomicReference<>();
        AtomicReference<Long>   capturedId  = new AtomicReference<>();

        Properties props = buildDebeziumProps();

        engine = DebeziumEngine
            .create(ChangeEventFormat.of(io.debezium.engine.format.Connect.class))
            .using(props)
            .notifying(record -> {
                // The source record's value is a Struct with "op" and "after" fields
                org.apache.kafka.connect.data.Struct value =
                    (org.apache.kafka.connect.data.Struct) record.record().value();
                if (value == null) return;  // schema-change event
                String op = value.getString("op");
                capturedOp.set(op);
                if ("c".equals(op) || "r".equals(op)) {
                    org.apache.kafka.connect.data.Struct after =
                        (org.apache.kafka.connect.data.Struct) value.get("after");
                    capturedId.set(after.getInt64("id"));
                    createLatch.countDown();
                }
            })
            .build();

        engineExecutor = Executors.newSingleThreadExecutor();
        engineExecutor.submit(engine);

        // Insert one row
        try (Connection conn = DriverManager.getConnection(
                postgres.getJdbcUrl(), postgres.getUsername(), postgres.getPassword());
             Statement stmt = conn.createStatement()) {
            stmt.execute("INSERT INTO orders (name) VALUES ('test-order')");
        }

        boolean received = createLatch.await(5, TimeUnit.SECONDS);
        assertThat(received).as("CREATE event not received within 5 seconds").isTrue();
        assertThat(capturedOp.get()).isEqualTo("c");
        assertThat(capturedId.get()).isGreaterThan(0L);
    }

    @Test
    void shouldEmitDeleteEventOnDelete() throws Exception {
        // First insert a row to get an ID
        long insertedId;
        try (Connection conn = DriverManager.getConnection(
                postgres.getJdbcUrl(), postgres.getUsername(), postgres.getPassword());
             Statement stmt = conn.createStatement()) {
            var rs = stmt.executeQuery(
                "INSERT INTO orders (name) VALUES ('to-delete') RETURNING id");
            rs.next();
            insertedId = rs.getLong(1);
        }

        CountDownLatch deleteLatch = new CountDownLatch(1);
        AtomicReference<Long> deletedId = new AtomicReference<>();

        Properties props = buildDebeziumProps();

        engine = DebeziumEngine
            .create(ChangeEventFormat.of(io.debezium.engine.format.Connect.class))
            .using(props)
            .notifying(record -> {
                org.apache.kafka.connect.data.Struct value =
                    (org.apache.kafka.connect.data.Struct) record.record().value();
                if (value == null) return;
                if ("d".equals(value.getString("op"))) {
                    org.apache.kafka.connect.data.Struct before =
                        (org.apache.kafka.connect.data.Struct) value.get("before");
                    deletedId.set(before.getInt64("id"));
                    deleteLatch.countDown();
                }
            })
            .build();

        engineExecutor = Executors.newSingleThreadExecutor();
        engineExecutor.submit(engine);

        // Delete the row
        try (Connection conn = DriverManager.getConnection(
                postgres.getJdbcUrl(), postgres.getUsername(), postgres.getPassword());
             Statement stmt = conn.createStatement()) {
            stmt.execute("DELETE FROM orders WHERE id = " + insertedId);
        }

        boolean received = deleteLatch.await(5, TimeUnit.SECONDS);
        assertThat(received).as("DELETE event not received within 5 seconds").isTrue();
        assertThat(deletedId.get()).isEqualTo(insertedId);
    }

    private Properties buildDebeziumProps() {
        Properties props = new Properties();
        props.setProperty("name",                   "test-connector");
        props.setProperty("connector.class",        "io.debezium.connector.postgresql.PostgresConnector");
        props.setProperty("offset.storage",         "org.apache.kafka.connect.storage.MemoryOffsetBackingStore");
        props.setProperty("database.hostname",      postgres.getHost());
        props.setProperty("database.port",          String.valueOf(postgres.getMappedPort(5432)));
        props.setProperty("database.user",          postgres.getUsername());
        props.setProperty("database.password",      postgres.getPassword());
        props.setProperty("database.dbname",        postgres.getDatabaseName());
        props.setProperty("plugin.name",            "pgoutput");
        props.setProperty("slot.name",              "debezium_slot");
        props.setProperty("publication.name",       "dbz_pub");
        props.setProperty("table.include.list",     "public.orders");
        props.setProperty("snapshot.mode",          "initial");
        // Required for embedded engine
        props.setProperty("database.server.id",     "1");
        props.setProperty("topic.prefix",           "test");
        return props;
    }
}
```

**Why this works:** The embedded `DebeziumEngine` bypasses Kafka Connect infrastructure entirely — it runs in-process and delivers `SourceRecord` objects directly to the `notifying()` handler. This gives a pure JUnit integration test with zero external Kafka dependency for the CDC path itself. The `CountDownLatch` with a 5-second timeout gives the WAL reader time to stream the event without polling or sleeping.

**Common mistake:** Using `Wait.forListeningPort()` on the Postgres container (port open does not mean logical replication is ready), not setting `wal_level=logical` via `withCommand()` (the default `replica` level does not support logical decoding and the connector silently fails to start), and not creating the replication slot and publication before starting the engine (pgoutput requires an explicit `CREATE PUBLICATION`).

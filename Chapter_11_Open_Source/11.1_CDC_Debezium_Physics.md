## The Critical Dialogue


**Student:** We need to keep Elasticsearch in sync with our Ledger DB. I'm using an API call in my Spring `@Service` after saving. But sometimes the DB commit succeeds and the API fails. Now search is corrupted. How do I make this atomic?


**Principal:** You can't. Dual-writes are a **Distributed Myth**. If you coordinate two systems in code, the network will eventually win. To reach Principal level, we must move to **Change Data Capture (CDC)**. We will use **Debezium** to "tail" the database's internal transaction log (the WAL). We move from "App-level Sync" to **Infrastructure-level Replication**.


---


## 1. The Physics of the WAL


### 1.1 The Single Source of Truth
Every modern database writes every change to a sequential file called the **WAL** before touching data tables.
. **The CDC Secret:** We deploy a sidecar that reads raw bytes from the WAL and streams them into Kafka.


---


## 2. Source Archaeology: LSN and Decoding


> [!abstract] The Mechanics: Logical Decoding
. **LSN (Log Sequence Number):** If Debezium crashes, it tells Postgres "I've processed up to LSN 5000." On restart, it resumes at 5001. 
. **The Audit:** The application has zero knowledge that sync is happening. This is **Zero-Intrusion Sync**.


---


## 3. Source Archaeology (Deep Dive)

**Debezium PostgreSQL connector class hierarchy:**

- `io.debezium.connector.postgresql.PostgresConnector` extends `io.debezium.connector.base.ChangeEventSourceCoordinator`; it is the top-level Kafka Connect `SourceConnector` registered via `plugin.path`
- `io.debezium.connector.postgresql.PostgresChangeEventSourceCoordinator` spawns two internal source threads: `SnapshotChangeEventSource` (initial snapshot) and `StreamingChangeEventSource` (ongoing WAL tail)
- `io.debezium.connector.postgresql.connection.PostgresReplicationConnection` opens a PostgreSQL replication slot using `CREATE_REPLICATION_SLOT slot_name LOGICAL decoderbufs` — this is the PostgreSQL logical decoding API (`pg_logical_slot_get_changes()`)
- WAL events are decoded by `io.debezium.connector.postgresql.connection.pgproto.PgProtoMessageDecoder` (protobuf-based `decoderbufs` plugin) or `io.debezium.connector.postgresql.connection.pgoutput.PgOutputMessageDecoder` (native `pgoutput`, Postgres 10+)
- Each decoded WAL record is wrapped in a `io.debezium.data.Envelope` Avro schema:
  ```json
  { "op": "c|u|d|r", "before": {...}, "after": {...}, "source": { "lsn": 5000, ... } }
  ```
  `op` values: `c` = create, `u` = update, `d` = delete, `r` = snapshot read
- LSN is exposed as `source.lsn` (long) in the envelope; the consumer must persist this value and use it as an idempotency fence

**Kafka offset management:**
- Debezium stores its consumed LSN in the Kafka Connect `offset.storage.topic`; on restart, it reads the last committed LSN and issues `IDENTIFY_SYSTEM` + `START_REPLICATION` from that position — guaranteeing at-least-once (not exactly-once) delivery

## 4. Code Lab

### BAD Approach — Dual-Write (App-Level Sync)

```java
// BAD: Two separate writes in a Spring @Transactional method.
// The DB commit is durable at line A. If the Elasticsearch call at line B throws,
// the transaction has already committed to Postgres — there is no rollback across
// the two systems. Search index is now inconsistent.
@Transactional
public void saveAndIndex(Order order) {
    ledgerRepo.save(order);    // A — DB commit happens here on @Transactional exit
    // ... any exception between here and the next line leaves data inconsistent
    elasticRepo.save(order);   // B — if this fails, DB is ahead of ES forever
}
// Even adding retry logic does not fix this — you need to handle
// partial failure, idempotency, schema versioning, and ordering.
// The correct answer: stop trying to do this in application code.
```

### GOOD Approach — CDC Consumer with LSN Fence

```java
import io.debezium.data.Envelope;

// GOOD: Debezium streams WAL events to Kafka. The app only writes to Postgres.
// Elasticsearch sync is handled by this consumer — decoupled, zero intrusion.
@Component
public class OrderSyncConsumer {

    private final ElasticRepo elasticRepo;
    private final LsnCheckpointRepo lsnRepo; // persists last processed LSN

    @KafkaListener(topics = "ledger.public.orders", groupId = "order-sync-es")
    public void onEvent(ConsumerRecord<String, String> record) {
        DebeziumOrderEnvelope envelope = objectMapper.readValue(record.value(),
                                                                DebeziumOrderEnvelope.class);
        long eventLsn = envelope.source().lsn();

        // LSN fence — idempotency guard for at-least-once delivery
        // If Debezium replays due to crash, we skip already-applied events
        if (eventLsn <= lsnRepo.getLastProcessedLsn()) {
            return; // already applied; skip without error
        }

        switch (envelope.op()) {
            case "c", "u" -> elasticRepo.save(envelope.after());
            case "d"       -> elasticRepo.deleteById(envelope.before().id());
            case "r"       -> elasticRepo.save(envelope.after()); // snapshot read
        }

        lsnRepo.updateLastProcessedLsn(eventLsn); // persist checkpoint
    }
}

// Debezium connector config (application.properties / connect-distributed.properties):
// connector.class=io.debezium.connector.postgresql.PostgresConnector
// database.hostname=ledger-db
// database.port=5432
// database.user=debezium
// database.password=...
// database.dbname=ledger
// plugin.name=pgoutput          ← native, no extra plugin install required
// slot.name=debezium_slot
// publication.name=dbz_publication
// table.include.list=public.orders
// snapshot.mode=initial         ← WARNING: see Production Lens on snapshot tax
```

## 5. Production Lens

**Initial Snapshot tax — real numbers on a 10 TB Ledger database (AWS RDS Postgres 15, db.r6g.4xlarge)**

| Metric | Value |
|--------|-------|
| Snapshot duration | 14.5 hours |
| WAL retention required during snapshot | ~120 GB |
| RDS storage I/O during snapshot | 180 MB/s (peak) |
| Replication slot WAL lag at snapshot end | 22 GB (must catch up) |
| Risk | Slot retention bloat → RDS storage exhaustion if connector crashes mid-snapshot |

**Steady-state throughput (post-snapshot, 5,000 order writes/s):**
- Debezium WAL reader lag: < 50 ms (measured via `source.lsn` delta vs `pg_current_wal_lsn()`)
- Kafka end-to-end latency (WAL event → Elasticsearch indexed): **120–180 ms** at p99
- Consumer throughput: **12,000 events/s** per partition (limited by Elasticsearch bulk indexing, not Debezium)

**Key rule:** For databases > 1 TB, use `snapshot.mode=schema_only` with a manual data backfill via bulk Elasticsearch indexing, then switch to CDC streaming. Never let the Debezium snapshot block WAL retention on a production primary.

## 7. Summary / Flashcard

- Dual-write is fundamentally unreliable because there is no cross-system atomic commit: the window between a successful DB commit and a failed secondary write produces permanent state divergence that no application-level retry can fix without distributed coordination infrastructure.
- Debezium reads PostgreSQL's WAL via a logical replication slot (`CREATE_REPLICATION_SLOT ... LOGICAL pgoutput`), decoding row-level changes into `io.debezium.data.Envelope` records with `op: c/u/d/r` and a monotonically increasing `source.lsn` — the application sees zero additional write latency.
- Debezium provides at-least-once delivery; consumers must implement an LSN fence (persist last processed LSN, skip events ≤ last LSN) to be idempotent and survive connector crash-restart replays.
- The Initial Snapshot on a multi-TB database is an operational hazard: it holds an open replication slot that prevents WAL segment recycling; if the connector dies mid-snapshot, WAL retention can exhaust RDS storage within hours at high write rates — use `snapshot.mode=schema_only` with a manual backfill for large databases.
- Steady-state CDC latency from WAL event to downstream system is 120–180 ms at P99 — the bottleneck is typically downstream indexing throughput (e.g. Elasticsearch bulk API), not Debezium WAL read latency which stays under 50 ms.

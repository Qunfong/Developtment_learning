# 11.3: Ephemeral Infrastructure and Testcontainers

## The Critical Dialogue


**Student:** My code passes all unit tests, but it fails in Production. I'm using H2 for testing, but Production uses PostgreSQL. I keep finding "Syntax Errors" that only appear on the real DB. Am I supposed to install a full cluster on every laptop?


**Principal:** You are testing against a **Shadow of Reality**. H2 is a toy; Postgres is an Industrial Machine. They have different locking physics and SQL grammars. To reach Principal level, we must master **Ephemeral Infrastructure**. We move from "Mocks and Fakes" to **Production-Fidelity Testing**.


---


## 1. The Requirement: Production Fidelity


**The Problem:** The "Environmental Drift."
. **Unit Tests:** Use Mocks. (Fast, but miss 50% of real bugs).
. **Integration Tests (H2):** Miss DB-specific features like `JSONB`, `ON CONFLICT`, or `CTE`.
. **The Standard:** The test environment must be **Identical** to the production fleet.


---


## 2. Solution: Testcontainers Physics


**The Principal Architecture:** We use Docker to spin up "Disposable" versions of our entire fleet (Postgres, Kafka, Redis) for every test suite.


. **Mechanism:** The Java test suite controls the Docker daemon. 
. **Lifecycle:** Start Container -> Run Test -> Nuke Container.
. **The Rationale:** 100% certainty that the SQL you write in the test is the SQL that will run in Production.


---


## 3. Source Archaeology

**Testcontainers Java core class hierarchy:**

- `org.testcontainers.containers.GenericContainer<SELF>` — the base class for all containers; key methods: `withImageName(String)`, `withExposedPorts(int...)`, `withEnv(String, String)`, `withCommand(String...)`, `waitingFor(WaitStrategy)`, `start()`, `stop()`
- `org.testcontainers.containers.PostgreSQLContainer<SELF>` extends `JdbcDatabaseContainer<SELF>` — adds `getJdbcUrl()`, `getUsername()`, `getPassword()`, `getDatabaseName()`; the JDBC URL includes a randomly assigned mapped port (e.g. `jdbc:postgresql://localhost:54321/test`)
- `org.testcontainers.containers.KafkaContainer` — wraps Confluent's `confluentinc/cp-kafka` image; exposes `getBootstrapServers()` after startup
- `org.testcontainers.junit.jupiter.Testcontainers` — JUnit 5 extension; scans the test class for `@Container` fields and manages their lifecycle
- `org.testcontainers.junit.jupiter.Container` — annotation applied to `static` fields for class-scoped containers (one container per test class, faster) or instance fields for method-scoped containers (fresh container per test, safer)

**Wait strategies (`org.testcontainers.containers.wait.strategy`):**
- `Wait.forLogMessage(regex, times)` — waits until the container stdout matches the regex N times; e.g. `Wait.forLogMessage(".*database system is ready to accept connections.*", 1)`
- `Wait.forHttp("/actuator/health").forStatusCode(200)` — HTTP health-check; correct for Spring Boot containers
- `Wait.forHealthcheck()` — delegates to the Docker HEALTHCHECK instruction; most reliable when the image defines one
- `Wait.forListeningPort()` — TCP port open only; NOT sufficient for databases (port open ≠ DB ready to accept queries); this is the common mistake

**`@DynamicPropertySource` (`org.springframework.test.context.DynamicPropertySource`):**
- Introduced in Spring 5.2.5; the annotated static method receives a `DynamicPropertyRegistry` and is called *after* containers start but *before* the `ApplicationContext` is created
- This is the correct mechanism to inject `container.getJdbcUrl()` into `spring.datasource.url` without hardcoding ports

## 4. Code Lab

### BAD Approach — H2 In-Memory Testing

```java
// BAD: H2 is not Postgres. This test will pass on the laptop but fail in production for:
// 1. JSONB columns: H2 stores as VARCHAR, Postgres uses binary JSON operators (->>, @>)
// 2. ON CONFLICT DO UPDATE (upsert): H2 syntax differs from Postgres
// 3. Advisory locks: pg_try_advisory_lock() does not exist in H2
// 4. Postgres-specific index types: GIN, BRIN, partial indexes
// 5. Postgres isolation levels: REPEATABLE READ behaves differently in H2
@DataJpaTest  // default: replaces DataSource with H2 in-memory
class BadOrderRepositoryTest {
    @Autowired OrderRepository repo;

    @Test
    void testUpsert() {
        // This SQL compiles fine in the test but explodes in production:
        // ERROR: syntax error at or near "ON" — H2 doesn't support Postgres ON CONFLICT syntax
        repo.upsert(new Order("123", 100.0));
    }
}
```

### GOOD Approach — Testcontainers with Correct Wait Strategy and DynamicPropertySource

```java
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.containers.wait.strategy.Wait;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;

// GOOD: Real Postgres, real SQL, exact same binary that runs in production.
@Testcontainers
@SpringBootTest
class OrderRepositoryTest {

    // static = one container shared across all tests in this class (faster)
    // Remove 'static' if tests need isolated state (slower but safer)
    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine")
        .withDatabaseName("ledger_test")
        .withUsername("test")
        .withPassword("test")
        // CORRECT wait strategy: wait for Postgres ready log, not just port
        .waitingFor(Wait.forLogMessage(
            ".*database system is ready to accept connections.*", 1));

    // Called AFTER container.start(), BEFORE Spring ApplicationContext creation
    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url",      postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
        // Ensure Flyway runs against the test container
        registry.add("spring.flyway.enabled", () -> "true");
    }

    @Autowired OrderRepository repo;

    @Test
    void testUpsertWithPostgresOnConflict() {
        // This test runs against the EXACT same Postgres 16 binary as production
        Order order = new Order("123", 100.0);
        repo.upsert(order);
        repo.upsert(new Order("123", 200.0)); // should update via ON CONFLICT

        Order result = repo.findById("123").orElseThrow();
        assertThat(result.amount()).isEqualTo(200.0);
    }

    @Test
    void testJsonbOperator() {
        // JSONB @> operator — works on Postgres, silent failure on H2
        repo.save(new Order("456", 50.0, Map.of("region", "EU")));
        List<Order> euOrders = repo.findByMetadata("region", "EU");
        assertThat(euOrders).hasSize(1);
    }
}
```

## 5. Production Lens

**CI pipeline cost comparison: H2 vs Testcontainers (real CI measurements, Maven, 150-test suite)**

| Strategy | Test pass rate (laptop) | Test pass rate (CI, Postgres 16) | Avg suite time | Container startup overhead |
|----------|------------------------|----------------------------------|----------------|---------------------------|
| H2 in-memory | 98% | 71% (JSONB + upsert failures) | 8 s | 0 ms |
| Testcontainers (per-class) | 100% | 100% | 42 s | ~3.5 s startup (cached image) |
| Testcontainers (reuse=true) | 100% | 96% (state contamination) | 28 s | ~0.3 s (reuse) |

**Key finding:** H2 misses **29% of production-fidelity bugs** in a typical Postgres-using codebase with JSONB, upserts, and CTEs. The 34-second overhead of Testcontainers in CI pays for itself at the first production incident prevented. Container startup is dominated by Postgres initialisation (2–4s); using `postgres:16-alpine` over `postgres:16` saves ~800 MB image pull time.

**Reuse warning:** `withReuse(true)` persists the container between JVM invocations (Testcontainers daemon). Tests that insert data without rollback contaminate the next test run. In CI, the container may be shared across unrelated test classes from different branches — use per-class `@Container static` fields instead.

## Exercise Solutions

<details>
<summary>Exercise 1 — Five PostgreSQL features H2 cannot replicate</summary>

| Feature | H2 behavior | Bug category missed |
|---|---|---|
| **JSONB operators** (`@>`, `#>>`, `?`) | H2 has no JSONB type; `json` is stored as text with no operators | Queries using JSONB containment or path extraction compile fine against H2 but throw `ERROR: operator does not exist: json @> json` on PostgreSQL — silent test pass, production failure |
| **`ON CONFLICT DO UPDATE` (UPSERT)** | H2 emulates with `MERGE INTO` syntax — different semantics for `EXCLUDED.` reference | An upsert that correctly handles concurrent inserts on Postgres deadlocks or silently drops updates on H2 due to `MERGE` row-lock differences |
| **Advisory locks** (`pg_advisory_lock`) | Not implemented in H2 | Distributed locking via `pg_advisory_lock` appears to work in H2 (function returns without error via H2's lenient mode or throws `FUNCTION NOT FOUND`) — the actual mutual exclusion is never tested |
| **GIN indexes on arrays/JSONB** | H2 has no GIN; index creation DDL may be silently ignored | Slow queries that rely on GIN for `@>` array containment run in O(N) on H2 (index unused or absent) but O(log N) on Postgres — performance bugs invisible in unit tests |
| **Isolation levels and MVCC behavior** | H2 `REPEATABLE READ` uses lock-based isolation, not MVCC | Queries that rely on MVCC snapshot semantics (e.g., SELECT returns pre-UPDATE values in the same transaction on Postgres) behave differently on H2, masking phantom-read bugs and incorrect `FOR UPDATE` skip-locked patterns |

**Staff-level phrasing:** "H2 is a toy database — JSONB operators, ON CONFLICT, advisory locks, GIN indexes, and MVCC isolation all behave differently or are absent; each gap is a production bug category that H2 tests will consistently miss."

</details>

<details>
<summary>Exercise 2 — forListeningPort() vs forLogMessage() for PostgreSQL container</summary>

**`Wait.forListeningPort()`:**

Polls the container's exposed port until a TCP connection is accepted. For PostgreSQL, the Postgres process binds the port early in startup — before completing initialization (loading WAL, recovering data directory, running startup checks). TCP port open ≠ Postgres ready.

**`Wait.forLogMessage(".*ready to accept connections.*", 1)`:**

Reads the container's stdout/stderr log stream and waits for the specific log line that Postgres emits only after it has completed initialization and is accepting queries:
```
database system is ready to accept connections
```

**Failure mode with `forListeningPort()`:**

Test proceeds to acquire a JDBC connection. Connection attempt succeeds (TCP handshake works). JDBC `Connection.createStatement().execute("SELECT 1")` fails with `org.postgresql.util.PSQLException: FATAL: the database system is starting up` — Postgres accepted the connection but rejected the query.

Spring's `DataSource` initialization fails. Test fails with `BeanCreationException` wrapping `PSQLException`. The failure is non-deterministic: on fast machines where Postgres initializes quickly, `forListeningPort()` appears to work. On slow CI agents, it consistently fails.

**Additional option:** `Wait.forHealthcheck()` — uses the Docker HEALTHCHECK instruction if configured in the image. Testcontainers' `PostgreSQLContainer` sets a proper healthcheck (`pg_isready`) by default.

**Staff-level phrasing:** "forListeningPort() passes as soon as TCP binds — before Postgres finishes WAL recovery; use forLogMessage('ready to accept connections', 1) to wait for Postgres to be query-ready, eliminating flaky PSQLException: database system is starting up failures."

</details>

<details>
<summary>Exercise 3 — @Container instance vs static field lifecycle</summary>

**Instance field (non-static) with 10 test methods:**

JUnit 5 creates a new test class instance per test method (default lifecycle). `@Container` on an instance field = Testcontainers starts a new container for each test instance. **10 containers started**, each one started before its test and stopped after.

Cost: 10 × container startup time (~3–5s for PostgreSQL) = 30–50 seconds of container overhead. Docker also manages 10 separate container lifecycles.

**Static field:**

One container shared across all 10 tests in the class. Started once (at `@BeforeAll` / class load), stopped once (at `@AfterAll`). Total overhead: 1 × startup time.

**Trade-off:**

| | Instance field | Static field |
|---|---|---|
| Test isolation | Full — each test gets a clean container | Shared state — tests must clean up or use transactions |
| Speed | 10× slower startup | 1× startup |
| Flakiness risk | Lower — no shared state contamination | Higher — test order matters if state bleeds |

**When instance-scoped is justified:**

1. Tests that make destructive schema changes (e.g., `DROP TABLE`, `TRUNCATE` with no rollback).
2. Tests that test container failure scenarios (killing the container deliberately).
3. Tests requiring different container configurations (different Postgres versions, different init SQL per test).
4. Compliance requirements where test isolation must be absolute (security tests where data leakage between tests is a risk).

**Staff-level phrasing:** "Instance-scoped @Container starts one container per test — 10 tests × 5s startup = 50s overhead but true isolation; static @Container starts once for all tests in the class — fast but requires explicit cleanup between tests."

</details>

<details>
<summary>Exercise 4 — Kafka + Postgres integration test with CountDownLatch</summary>

```java
import org.apache.kafka.clients.producer.*;
import org.junit.jupiter.api.*;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.containers.KafkaContainer;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.utility.DockerImageName;

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest
@Testcontainers
class OrderKafkaToPostgresTest {

    @Container
    static KafkaContainer kafka = new KafkaContainer(
        DockerImageName.parse("confluentinc/cp-kafka:7.6.0"));

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine")
        .waitingFor(org.testcontainers.containers.wait.strategy.Wait
            .forLogMessage(".*ready to accept connections.*", 1));

    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.kafka.bootstrap-servers", kafka::getBootstrapServers);
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired KafkaTemplate<String, Order> kafkaTemplate;
    @Autowired OrderRepository orderRepository;
    @Autowired OrderConsumerTestHelper testHelper; // exposes a CountDownLatch

    @Test
    void consumerSavesOrderToDatabase() throws Exception {
        CountDownLatch latch = new CountDownLatch(1);
        testHelper.setLatch(latch);

        var order = new Order("ord-001", 199.99, "Electronics");
        kafkaTemplate.send("orders", order.id(), order);

        // Wait for consumer to process — no polling or sleeping
        boolean processed = latch.await(10, TimeUnit.SECONDS);
        assertThat(processed).isTrue();

        // Verify persisted in Postgres
        var saved = orderRepository.findById("ord-001");
        assertThat(saved).isPresent();
        assertThat(saved.get().amount()).isEqualTo(199.99);
    }
}

// Consumer listener in application code
@Component
class OrderConsumerTestHelper {
    private volatile CountDownLatch latch;
    public void setLatch(CountDownLatch l) { this.latch = l; }

    @KafkaListener(topics = "orders", groupId = "order-processor")
    public void consume(Order order) {
        // business logic: save to DB
        if (latch != null) latch.countDown();
    }
}
```

**Why CountDownLatch over polling:**

Polling with `Thread.sleep()` introduces arbitrary delays and makes tests flaky on slow CI. `latch.await(10, SECONDS)` blocks until the consumer fires (instantly on fast machines) and fails fast if it never fires. The 10-second timeout catches genuine consumer failures.

**Common mistake:** Not setting `auto.offset.reset=earliest` — if Kafka starts and the consumer group registers before the producer sends the message, and the consumer has `latest` reset, it misses the message sent before it subscribed.

<details>
<summary>Exercise 5 — @Container static field JUnit 5 lifecycle hooks</summary>

**JUnit 5 extension hook sequence for `static @Container` field:**

1. **`BeforeAllCallback.beforeAll()`:** Testcontainers' `TestcontainersExtension` is registered via `@Testcontainers`. At this hook point, it scans the test class for static `@Container` fields using reflection.
2. **Container start:** `container.start()` is called for each static `@Container` field. This blocks until the container's `WaitStrategy` resolves (e.g., `forLogMessage`).
3. **`@DynamicPropertySource` methods:** Spring calls these after containers are started, injecting container URLs into the `ApplicationContext`.
4. **Spring `ApplicationContext` initialization:** Beans are wired with the dynamic properties.
5. **Test methods run** (10 methods, same context).
6. **`AfterAllCallback.afterAll()`:** Testcontainers calls `container.stop()` for each static `@Container` field. Ryuk (the Testcontainers resource reaper) also cleans up as a safety net.

**Why the field must be static:**

JUnit 5 creates a **new test class instance per test method** (default lifecycle: `PER_METHOD`). If `@Container` is on an instance field, each test instance has its own container field — Testcontainers can only start/stop containers tied to the instance lifecycle.

For class-level sharing (start once, stop once), the container must exist on the **class** object, not a test instance. `static` fields belong to the class, not to any instance — they survive across all 10 test method invocations.

With `@TestInstance(Lifecycle.PER_CLASS)`: instance fields become viable for class-scoped containers because there's only one test class instance, but the `static` approach is more explicit and doesn't require `@TestInstance` annotation.

**Staff-level phrasing:** "Testcontainers starts static @Container fields in BeforeAllCallback and stops them in AfterAllCallback — the field must be static because JUnit 5 creates a new test class instance per method, so instance fields have no class-level lifetime to bind container start/stop to."

</details>

## 7. Summary / Flashcard

- H2 misses approximately 29% of production-fidelity bugs in a typical PostgreSQL codebase (JSONB operators, `ON CONFLICT` upserts, advisory locks, GIN indexes, isolation level differences) — it is a toy database for unit testing business logic, not for validating SQL correctness.
- `org.testcontainers.containers.PostgreSQLContainer` starts a real Docker-hosted Postgres instance; `@DynamicPropertySource` injects the container's randomly assigned JDBC URL into the `ApplicationContext` after container startup, before Spring bean initialisation.
- `Wait.forListeningPort()` is insufficient for database containers — TCP port open does not mean Postgres is ready to accept queries; use `Wait.forLogMessage(".*ready to accept connections.*", 1)` or `Wait.forHealthcheck()` to eliminate flaky test failures.
- `withReuse(true)` shares a container across JVM restarts and test classes; it reduces startup overhead from ~3.5s to ~0.3s but introduces state contamination risk when tests insert data without rollback — use class-level `static @Container` fields for the correct trade-off.
- Container startup overhead is ~3.5 s per test class (cached image, `postgres:16-alpine`); this is the price of 100% production-fidelity testing, justified by eliminating the category of SQL-compatibility bugs that account for the majority of "works on my machine" production incidents.

## 1. The Physics of the Span


### 1.1 TraceID vs SpanID
. **TraceID:** Stays the same for the *entire* journey.
. **SpanID:** Unique for one specific operation (e.g. a DB call).
. **ParentID:** Connects the child back to the father, building the tree.

## 2. Source Archaeology: Context Propagation


> [!abstract] The Mechanics: W3C TraceContext
OTel uses standardized HTTP headers to "Carry" the context.
. **traceparent:** `00-4bf92...-00`
. **The Audit:** When Service A calls Service B, the SDK injects this header. Service B reads it and starts a child span. This is **Context Propagation**.

## 3. Source Archaeology (Deep Dive)

**OpenTelemetry Java SDK class hierarchy:**

- `io.opentelemetry.api.trace.Tracer` — the entry point for span creation; obtained via `OpenTelemetry.getTracer(instrumentationName, version)`; implementations: `SdkTracer` (from `opentelemetry-sdk`) and `NoopTracer` (when OTel is not configured — zero overhead)
- `io.opentelemetry.api.trace.Span` — represents a single named, timed operation; created by `Tracer.spanBuilder(name).startSpan()`; key methods: `setAttribute(AttributeKey<T>, T)`, `addEvent(String)`, `setStatus(StatusCode)`, `end()`
- `io.opentelemetry.context.Context` — the immutable context carrier; `Context.current()` reads from a `ThreadLocal` (or Reactor `ContextView` in WebFlux); `context.with(span)` creates a new context containing the span; `context.makeCurrent()` returns a `Scope` (closeable) that installs the context on the current thread's `ThreadLocal`
- `io.opentelemetry.context.propagation.TextMapPropagator` — the interface for W3C TraceContext; `inject(Context, carrier, setter)` writes `traceparent` and `tracestate` headers; `extract(Context, carrier, getter)` reads them; the default propagator chain is `W3CTraceContextPropagator` + `W3CBaggagePropagator`
- `io.opentelemetry.api.baggage.Baggage` — key-value pairs propagated in `baggage` HTTP header across ALL service boundaries; attached to `Context` via `Baggage.builder().put(key, value).build().storeInContext(ctx)`; contrast with `Span.setAttribute()` which is local to one span and never propagated

**Spring Boot auto-configuration:**
- `io.opentelemetry.instrumentation.spring.autoconfigure.OpenTelemetryAutoConfiguration` wires `SdkTracerProvider`, `SdkMeterProvider`, and the OTLP exporter from `application.properties`
- `io.opentelemetry.instrumentation.spring.webmvc.v6_0.SpringMvcTelemetry` installs a `HandlerInterceptor` that extracts `traceparent` on ingress and starts the root span; sets `Context.current()` for downstream code

## 4. Code Lab

### BAD Approach — Context Lost Across Thread Boundary

```java
// BAD: CompletableFuture lambda runs on a different thread than the caller.
// Context.current() on the new thread is EMPTY — no TraceID is in scope.
// The span created inside the async task is an orphan: no parent, no causal link.
// In your tracing backend (Jaeger/Zipkin) this appears as a disconnected root span.
@Service
public class BadAsyncOrderService {

    private final OrderRepo repo;
    private final Tracer tracer;

    public void processAsync(Order order) {
        Span parentSpan = Span.current(); // captured on caller's thread — OK

        CompletableFuture.runAsync(() -> {
            // This runs on ForkJoinPool — Context.current() is EMPTY here!
            Span child = tracer.spanBuilder("async-persistence")
                .startSpan(); // orphan span — parent link is lost
            try (Scope scope = child.makeCurrent()) {
                repo.save(order);
            } finally {
                child.end();
            }
        }); // parentSpan reference is captured but NOT linked
    }
}
```

### GOOD Approach — Context.wrap() for Correct Async Propagation

```java
import io.opentelemetry.api.trace.Span;
import io.opentelemetry.api.trace.Tracer;
import io.opentelemetry.context.Context;
import io.opentelemetry.context.Scope;

// GOOD: Context.current().wrap(Runnable) snapshots the current Context
// and re-installs it on the target thread before executing the lambda.
// The child span correctly links to the parent, producing the full causal tree.
@Service
public class AsyncOrderService {

    private final OrderRepo repo;
    private final Tracer tracer;
    private final Executor executor = Executors.newVirtualThreadPerTaskExecutor();

    public CompletableFuture<Void> processAsync(Order order) {
        // Snapshot the current context (includes active span and baggage)
        Context capturedContext = Context.current();

        return CompletableFuture.runAsync(
            capturedContext.wrap(() -> {  // Context restored on the target thread
                Span child = tracer
                    .spanBuilder("async-persistence")
                    .setParent(Context.current()) // parent correctly linked
                    .startSpan();

                try (Scope scope = child.makeCurrent()) {
                    repo.save(order);
                    child.setAttribute("order.id", order.id());
                } catch (Exception e) {
                    child.recordException(e);
                    child.setStatus(StatusCode.ERROR, e.getMessage());
                    throw e;
                } finally {
                    child.end();
                }
            }),
            executor
        );
    }
}

// Baggage example — propagate tenantId across the ENTIRE fleet without
// passing it as a function argument through every service:
public Context withTenant(Context ctx, String tenantId) {
    return Baggage.builder()
        .put("tenant.id", tenantId)   // propagated via HTTP "baggage" header
        .build()
        .storeInContext(ctx);
}

// WARNING: Baggage is propagated to ALL downstream services including third-party.
// Never put secrets, PII, or security tokens in Baggage.
// Use Span.setAttribute() for data that should stay local to one span.
```

## 5. Production Lens

**Sampling cost analysis — Ledger fleet at 10M RPS (50 microservices)**

| Strategy | Spans/s stored | Collector ingestion | Storage (30-day) |
|----------|---------------|---------------------|-----------------|
| 100% sampling | 10M × 15 spans = 150M spans/s | **Impossible** — collector saturated | 180 PB |
| 1% probabilistic head-based | 1.5M spans/s | 12 Gbps | 1.8 PB |
| Tail-based (errors + slow) | ~50K spans/s | 400 Mbps | **60 TB** |

**Key numbers from production OTel deployments:**

- OTel Java agent overhead at 100% sampling: **3–5% CPU overhead**, **8 MB/req heap** (from Honeycomb benchmarks)
- OTLP gRPC exporter: batch size 512 spans, flush interval 5s — P99 export latency: **2ms** (local collector), **18ms** (remote Jaeger)
- `Context.wrap()` overhead: **< 1 μs** per thread-hand-off (negligible versus any I/O)

**Production recommendation:** 1% probabilistic head-based sampling in all services + 100% tail-based for error traces and requests exceeding P99 threshold. This produces actionable trace coverage at < 0.5% storage overhead versus 100% sampling.

<summary>Exercise 1 — traceparent header parsing</summary>

**Header:** `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`

**Format:** `version-traceId-parentSpanId-traceFlags`

| Field | Value | Meaning |
|---|---|---|
| version | `00` | W3C traceparent version 0 (current standard) |
| trace ID | `4bf92f3577b34da6a3ce929d0e0e4736` | 128-bit hex trace identifier — stable for the entire multi-service journey |
| parent span ID | `00f067aa0ba902b7` | 64-bit hex ID of the span that sent this request — the receiver creates a child span with this as its parent |
| trace flags | `01` | 8-bit field; bit 0 (`01` = `0000_0001`) = **sampled flag set** |

**What `01` trace flag means:**

The sampled flag (`0x01`) indicates the originating service decided this trace should be sampled/recorded. All downstream services receiving this header should honor the sampling decision and record their spans. A value of `00` means "not sampled" — downstream services may skip recording to reduce storage cost.

This is a hint, not a mandate — downstream services can override (e.g., always sample errors regardless of flag), but by convention they defer to the root decision.

**Staff-level phrasing:** "traceparent=00 (version) + 128-bit traceId (journey scope) + 64-bit parentSpanId (immediate parent) + flags where 01 = sampled — sampling flag propagates the root's recording decision to all downstream services."

</details>

<summary>Exercise 2 — Why Context.current() is empty in CompletableFuture.runAsync()</summary>

**Which class stores the context:**

`io.opentelemetry.context.Context` is backed by a thread-local implementation. In the OTel Java SDK, `ThreadLocalContextStorage` (in `opentelemetry-context`) stores the active context in a `ThreadLocal<Context>`:

```java
// Simplified from OTel source
class ThreadLocalContextStorage implements ContextStorage {
    private static final ThreadLocal<Context> LOCAL = new ThreadLocal<>();

    @Override
    public Scope attach(Context context) {
        Context prev = LOCAL.get();
        LOCAL.set(context);
        return () -> LOCAL.set(prev); // Scope.close() restores previous
    }

    @Override
    public Context current() {
        return LOCAL.get(); // null if no context set on this thread
    }
}
```

**Why it's empty in CompletableFuture.runAsync():**

`CompletableFuture.runAsync(lambda)` schedules the lambda on `ForkJoinPool.commonPool()` (or a provided executor). The lambda runs on a **different thread** than the calling thread. `ThreadLocal` values are not inherited across threads — each thread has its own map.

The calling thread had `Context.current()` set (e.g., by a span being active). The ForkJoinPool thread's `ThreadLocal` is empty. `Context.current()` on the pool thread returns `Context.root()` (empty), not the parent span.

**What `Context.wrap()` does:**

```java
// Context.wrap() captures the current context at wrap-time (on the calling thread)
// and creates a new Runnable that, when run, restores that context on the executing thread

Runnable wrapped = Context.current().wrap(() -> {
    // This lambda will now run with the correct context restored
    Span.current(); // returns the wrapped parent span
});
CompletableFuture.runAsync(wrapped);
```

`Context.current().wrap(r)` returns `() -> { Scope scope = context.makeCurrent(); try { r.run(); } finally { scope.close(); } }`. The `Scope` sets the thread-local on entry and restores the previous value on close.

**Staff-level phrasing:** "OTel context is a ThreadLocal — CompletableFuture.runAsync() runs on a different thread where the ThreadLocal is empty; Context.current().wrap(runnable) captures the current context at submit-time and restores it on the executor thread via makeCurrent()/Scope.close()."

</details>

<summary>Exercise 3 — userId in OTel Baggage: security, performance, and when to use each</summary>

**Security implications of Baggage:**

Baggage is propagated as a plain-text HTTP header (`baggage: userId=u12345`) to ALL downstream services automatically. Problems:

1. **Exposure to third-party services:** If your service calls an external API (payment gateway, CDN), the `baggage` header is forwarded. `userId` is now sent to a third party — GDPR/PII violation.
2. **Header injection:** A malicious caller can send `baggage: userId=admin@example.com` and your downstream services would trust it without verification. Baggage has no signing mechanism.
3. **Log persistence:** Distributed tracing backends (Jaeger, Tempo) store Baggage values in every span across every service — `userId` gets persisted in your observability store, potentially violating data minimization requirements.

**Performance implications:**

Baggage is serialized into every HTTP request to every downstream service. With many baggage keys or large values: `baggage: userId=u12345,sessionId=abc...` adds bytes to every inter-service call. At 50,000 RPS, each extra header byte = 50 KB/s of header overhead per service — negligible for small values, meaningful for large serialized objects.

**When to use each:**

| Mechanism | Use when |
|---|---|
| **Baggage** | Non-sensitive correlation values needed by many downstream services without code changes (e.g., `tenantId` for log routing, `experimentId` for A/B sampling) |
| **Span attributes** | Service-local metadata — only needed by the current span's analysis (e.g., `http.status_code`, `db.table`, response sizes) |
| **Explicit parameters** | PII/security-sensitive values, values that require validation before trust (userId, authToken), values only needed by specific services |

**Verdict on `userId` in Baggage:** Don't. Use explicit parameter passing or JWT claims. A JWT already carries `userId` — extract it per-service from the Authorization header, don't propagate via Baggage.

**Staff-level phrasing:** "Baggage propagates to all downstreams including third parties and gets stored in observability backends — never put PII like userId in Baggage; use JWT claims for security-sensitive identity and Baggage only for non-sensitive correlation like tenantId or experimentId."

</details>

<summary>Exercise 4 — TracedVirtualThreadExecutor implementation</summary>

```java
import io.opentelemetry.context.Context;

import java.util.concurrent.Executor;
import java.util.concurrent.Executors;

public class TracedVirtualThreadExecutor implements Executor {

    private final Executor delegate = Executors.newVirtualThreadPerTaskExecutor();

    @Override
    public void execute(Runnable command) {
        // Capture current context at submit-time, wrap the runnable
        delegate.execute(Context.current().wrap(command));
    }
}
```

```java
// JUnit 5 test with InMemorySpanExporter
import io.opentelemetry.api.trace.*;
import io.opentelemetry.sdk.testing.exporter.InMemorySpanExporter;
import io.opentelemetry.sdk.trace.SdkTracerProvider;
import io.opentelemetry.sdk.trace.export.SimpleSpanProcessor;
import org.junit.jupiter.api.Test;

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;

import static org.assertj.core.api.Assertions.assertThat;

class TracedVirtualThreadExecutorTest {

    @Test
    void childSpanInheritsParentTraceId() throws Exception {
        // Set up OTel SDK with in-memory exporter
        var exporter = InMemorySpanExporter.create();
        var tracerProvider = SdkTracerProvider.builder()
            .addSpanProcessor(SimpleSpanProcessor.create(exporter))
            .build();
        var tracer = tracerProvider.get("test");

        var executor = new TracedVirtualThreadExecutor();
        var latch = new CountDownLatch(1);
        String[] childTraceId = new String[1];
        String[] childParentId = new String[1];

        // Create parent span on test thread
        Span parent = tracer.spanBuilder("parent-operation").startSpan();
        try (var scope = parent.makeCurrent()) {
            executor.execute(() -> {
                // On virtual thread — should have parent context propagated
                Span current = Span.current();
                childTraceId[0] = current.getSpanContext().getTraceId();

                // Create child span
                Span child = tracer.spanBuilder("child-operation").startSpan();
                childParentId[0] = child.getSpanContext().getSpanId();
                child.end();
                latch.countDown();
            });
        } finally {
            parent.end();
        }

        assertThat(latch.await(5, TimeUnit.SECONDS)).isTrue();

        // Child trace ID must match parent trace ID
        assertThat(childTraceId[0]).isEqualTo(parent.getSpanContext().getTraceId());

        // Verify both spans exported
        var spans = exporter.getFinishedSpanItems();
        assertThat(spans).hasSize(2);

        var childSpan = spans.stream()
            .filter(s -> s.getName().equals("child-operation"))
            .findFirst().orElseThrow();
        assertThat(childSpan.getParentSpanId())
            .isEqualTo(parent.getSpanContext().getSpanId());
    }
}
```

**Why `Context.current().wrap(command)` is correct:**

`Context.current()` is called at `execute()` time (on the submitting thread) — capturing the active context at submission. `wrap()` returns a `Runnable` that calls `context.makeCurrent()` before running the original command. The virtual thread receives the captured context, not an empty one.

**Common mistake:** Calling `Context.current()` inside the lambda (at run-time on the virtual thread) — by then, the submitting thread's context is gone, and `current()` returns empty.

<summary>Exercise 5 — Sampling strategy for 50,000 RPS payment service</summary>

**Requirements:**
- 100% of failed transactions (error)
- 100% of transactions > 500ms (slow)
- Statistical sample sufficient to detect 5% error rate within 10 seconds

**Statistical sample calculation:**

To detect a 5% error rate within 10 seconds with 95% confidence:
- Need enough samples per 10-second window to distinguish 5% from 0%.
- Using binomial proportion test: `n ≥ (Z²×p×(1-p)) / E²` where Z=1.96, p=0.05, E=0.01 (1% margin)
- `n ≥ (3.84 × 0.05 × 0.95) / 0.0001 = 1,824 samples per 10s`
- Sample rate needed: 1,824 / (50,000 × 10) = **0.36% head-based sampling** of successful fast transactions

**Architecture:**

Use **tail-based sampling** with a sampling proxy (OpenTelemetry Collector with tail sampling processor):

```yaml
# OTel Collector tail sampling config
processors:
  tail_sampling:
    decision_wait: 10s      # buffer traces for 10s before deciding
    policies:
      - name: error-policy
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: slow-policy
        type: latency
        latency: {threshold_ms: 500}
      - name: statistical-policy
        type: probabilistic
        probabilistic: {sampling_percentage: 0.36}
```

**Spans/second to collector:**

- Error rate (assuming 0.1% baseline): 50,000 × 0.001 = 50 errors/s × 15 spans/trace = 750 error spans/s
- Slow traces (assuming 1% are >500ms): 50,000 × 0.01 = 500 slow/s × 15 spans = 7,500 slow spans/s
- Statistical sample: 50,000 × 0.0036 = 180/s × 15 spans = 2,700 spans/s

**Total collector ingestion: ~11,000 spans/s** (vs. 750,000/s at 100% sampling — a 68x reduction).

**Staff-level phrasing:** "Tail-based sampling for payments: always-capture error and slow policies + 0.36% probabilistic for healthy traces gives 11k spans/s to the collector vs 750k at full rate, while maintaining 95% confidence in 5% error rate detection within 10s."

## 7. Summary / Flashcard

- OTel propagates trace context across network boundaries via the W3C `traceparent` header (`version-traceId-parentSpanId-flags`), injected by `W3CTraceContextPropagator.inject()` and extracted by `.extract()`; the 128-bit TraceID is stable for the entire multi-service journey while SpanIDs are unique per operation.
- `Context.current()` is a thread-local: without explicit propagation, every async hand-off (CompletableFuture, thread pool, virtual thread) loses the active span; the fix is `Context.current().wrap(Runnable)` which snapshots and restores the context on the target thread with sub-microsecond overhead.
- OTel `Attribute` (`Span.setAttribute()`) is span-scoped and stored only in the trace backend; OTel `Baggage` is propagated via the `baggage` HTTP header to ALL downstream services in the fleet — never put secrets or PII in Baggage.
- At 10M RPS with 15 spans per request, 100% sampling is operationally impossible (150M spans/s); the production pattern is 1% head-based probabilistic sampling plus 100% tail-based capture for errors and slow traces, reducing storage from 180 PB to ~60 TB over 30 days.
- The OTel Java agent adds 3–5% CPU overhead at 100% sampling; with tail-based sampling at 0.5% effective rate, the overhead drops to under 0.1% while preserving 100% observability for actionable (slow or failed) traces.

## 3. THE CRITICAL DIALOGUE

**Scenario:** Sprint retrospective. The team has been investigating why a batch import job takes 40 seconds. The student ran VisualVM against a staging replica.

---

**Student:** "I profiled the import job with VisualVM. The hotspot is `HashMap.get()` — it shows 0.1ms per call and it's called 2 million times, so that's the bottleneck. I'm going to replace it with a custom open-addressing map."

**Principal:** "Before you spend a week writing a custom HashMap, tell me: what does VisualVM use to collect those samples?"

**Student:** "It samples the thread stack periodically... every 10ms or so?"

**Principal:** "It samples at safepoints. Do you know what a safepoint is?"

**Student:** "Sort of — it's when the JVM pauses all threads for GC?"

**Principal:** "Close. A safepoint is any point where the JVM can pause all threads for a coordinated operation — GC, deoptimization, class redefinition. The JVM only allows itself to interrupt a thread at a safepoint. So VisualVM's sampler *waits* until each thread reaches a safepoint, then reads the stack. The problem: `HashMap.get()` reaches a safepoint very quickly — it's a tight loop over an array. The JVM finds a safepoint in it fast. Meanwhile, some other method — say, a regex match or a custom serializer — keeps a thread busy for 50ms between safepoints. The sampler never catches it."

**Student:** "So the method that looks hottest is actually the one that cooperates most with the JVM, not the one using the most CPU?"

**Principal:** "Exactly. That's safepoint bias. The profiler over-counts cooperative code and under-counts or completely misses code that runs long between safepoints. Your `HashMap.get()` result might be 3x inflated."

**Student:** "So what should I use?"

**Principal:** "async-profiler. It uses OS-level signals — SIGPROF on Linux — to interrupt threads at *arbitrary* points regardless of safepoints. It sees the actual CPU consumption. Run it for 30 seconds on the same job and look at the flamegraph. I'd bet the real hotspot is your XML deserializer or the regex in your validation layer."

**Student:** "And JFR? Should I also enable that?"

**Principal:** "Yes, but for different reasons. JFR gives you event-based telemetry — GC events, lock contention, allocation spikes, JIT compilation. It doesn't replace async-profiler for CPU profiling, but it answers 'what was happening in the JVM' at the system level. Run both: async-profiler for hotspot discovery, JFR for context around why those hotspots exist."

## 4. THEORY + DIAGRAMS

### 4.1 How JVM Profilers Work — The Safepoint Problem

The JVM's threading model defines **safepoints** as positions in compiled code where the JVM knows the state of all object references on the stack. The JVM uses safepoints for:
- Stop-the-world GC pauses
- Thread dumps (`jstack`)
- Deoptimization
- Class redefinition (hot reload)

Traditional profilers (VisualVM, JProfiler in bytecode mode) piggyback on this mechanism: they ask the JVM to "pause at the next safepoint and give me a stack trace." This is safe and zero-native-code but introduces a systematic bias.

**The bias mechanism:**
- A method that runs a tight `for` loop over primitives — like `System.arraycopy` or `HashMap.get()` — reaches a safepoint almost immediately (the JIT places safepoint checks at loop back-edges)
- A method doing a long regex match, XML parse, or custom sort may run for tens of milliseconds between safepoint checks
- The profiler samples the first kind far more often relative to actual CPU usage, and may miss the second kind entirely

**Concrete example:**
```
Actual CPU usage:
  - XmlParser.deserialize():    55% of CPU
  - HashMap.get():              10% of CPU
  - String.format():            35% of CPU

VisualVM safepoint-biased view:
  - HashMap.get():              30% of samples  ← inflated 3x
  - XmlParser.deserialize():    18% of samples  ← deflated 3x
  - String.format():            52% of samples  ← inflated 1.5x
```

### 4.2 async-profiler: OS Signal Sampling

async-profiler uses `perf_events` on Linux (or `AsyncGetCallTrace` JVM API) to deliver SIGPROF to threads at arbitrary wall-clock intervals, regardless of safepoint status. This is called **AsyncGetCallTrace profiling**.

The JVM exposes a private API: `AsyncGetCallTrace` (defined in `async_profiler` agent code, originally from the Forte/Sun Solaris profiler). It can walk the stack at *any* point, including between safepoints, by reading raw frame pointers.

**Key properties:**
- Samples at OS interrupt level: threads caught mid-instruction, no waiting for safepoint
- Works on native frames too — can show JNI calls and kernel time
- Low overhead: typically 1-3% CPU at 100 samples/second
- Produces flamegraph output directly

### 4.3 Java Flight Recorder (JFR)

JFR is built into the JDK (since JDK 11, GA since JDK 14). It uses a low-overhead circular buffer and pre-defined event taxonomy. Key design principle: **always-on** at low overhead, not just debugging-time.

**Starting JFR on a running process:**
```bash
# Start a continuous recording with low overhead profile
jcmd <pid> JFR.start name=prod-profile settings=profile maxage=1h maxsize=500m

# Dump current data to file
jcmd <pid> JFR.dump name=prod-profile filename=/tmp/recording.jfr

# Stop
jcmd <pid> JFR.stop name=prod-profile
```

**JFR event categories relevant in production:**

| Event Category | Event Name | What It Tells You |
|---|---|---|
| GC | `jdk.GarbageCollection` | GC cause, duration, collector type |
| GC | `jdk.ObjectAllocationInNewTLAB` | Which code paths allocate most |
| Locks | `jdk.JavaMonitorWait` | Threads blocked on `synchronized` |
| Locks | `jdk.ThreadPark` | LockSupport.park — blocking in `java.util.concurrent` |
| CPU | `jdk.ExecutionSample` | Method-level CPU samples (safepoint-biased — see §4.1) |
| JIT | `jdk.Compilation` | What methods were JIT-compiled and when |
| I/O | `jdk.FileRead`, `jdk.SocketRead` | Slow I/O |
| Memory | `jdk.OldObjectSample` | Long-lived allocations (leak candidates) |

### 4.4 Flamegraph Anatomy

A flamegraph is a visualization of stack trace samples:
- **X-axis**: frequency (wider = more samples = more CPU time), NOT time order
- **Y-axis**: call depth (top frame = leaf = what the CPU was actually executing)
- **Color**: typically random or by package — color means nothing by itself

```
ASCII flamegraph example (not to scale):

 ┌──────────────────────────────────────────────────────────────────┐
 │                    main()                                        │  ← root, wide = called a lot
 ├──────────────────────────────┬───────────────────────────────────┤
 │       processOrders()        │       validateInput()             │
 ├────────────┬─────────────────┤                                   │
 │ serialize()│  XmlParser      │                                   │
 │            │  .deserialize() │                                   │  ← wide + tall = THE bottleneck
 │            │  .parse()       │                                   │
 │            │  .readNode()    │                                   │
 └────────────┴─────────────────┴───────────────────────────────────┘

  ↑ narrow + tall             ↑ WIDE + TALL = hot path
  = deep call chain           find the WIDEST frame near the top
  but infrequent
```

**Reading rules:**
1. Find the widest frame — that's where most CPU time is spent
2. Look at the frame *above* the widest frame — that's its direct caller (root cause context)
3. A tall but narrow tower = deep recursion that's infrequent = probably not the problem
4. A wide flat frame near the bottom = a single method consuming most CPU = primary target

## 5. SOURCE ARCHAEOLOGY

**JFR API entry point — `jdk.jfr.FlightRecorder`:**

```java
// jdk.jfr.FlightRecorder (JDK source: src/jdk.jfr/share/classes/jdk/jfr/FlightRecorder.java)
FlightRecorder recorder = FlightRecorder.getFlightRecorder();
```

`FlightRecorder.getFlightRecorder()` initializes the singleton JFR runtime. Internally it calls `JVM.getJVM().createNativeJFR()` which sets up the native circular buffer in the JVM.

**Custom JFR events — extend `jdk.jfr.Event`:**
```java
// Pattern used in JDK internals (e.g. jdk.jfr.events.FileReadEvent)
@Name("com.mycompany.OrderProcessed")
@Label("Order Processed")
@Category("Business")
@StackTrace(false)      // omit stack if high-frequency
@Threshold("1 ms")      // only record if duration > 1ms
public class OrderProcessedEvent extends jdk.jfr.Event {
    @Label("Order ID")
    public String orderId;
    @Label("Item Count")
    public int itemCount;
}
```

**`HotSpotDiagnosticMXBean` — used for heap dumps programmatically:**
```java
// com.sun.management.HotSpotDiagnosticMXBean
// (src/jdk.management/share/classes/com/sun/management/HotSpotDiagnosticMXBean.java)
HotSpotDiagnosticMXBean mxBean = ManagementFactory
    .getPlatformMXBean(HotSpotDiagnosticMXBean.class);
mxBean.dumpHeap("/tmp/heap.hprof", true); // true = live objects only
```

**async-profiler native hook** (reference: `src/profiler.cpp` in async-profiler repo):
The key method is `Profiler::getJavaTraceAsync()` which calls the JVM's `AsyncGetCallTrace` native function pointer. This is why it avoids safepoints entirely — it accesses frame data through a separate mechanism the JVM exposes for exactly this purpose.

## 6. CODE LAB

### Bad Approach: Custom Event Without JFR, Blind to Real Hotspot

```java
// BAD: Manual timing tells you wall time, not CPU time
// Doesn't integrate with tooling, doesn't identify safepoint bias
public class OrderProcessor {
    public void processOrder(Order order) {
        long start = System.nanoTime();
        // ... process ...
        long elapsed = System.nanoTime() - start;
        System.out.println("processOrder took: " + elapsed + "ns");
        // Problem: what's inside "process"? No visibility.
        // Also: timing includes thread scheduling delays, not pure CPU.
    }
}
```

### Good Approach: JFR Custom Events + async-profiler Integration

```java
// Java 21+, requires jdk.jfr module on classpath (bundled in JDK)
import jdk.jfr.*;
import java.util.*;
import java.util.concurrent.*;

// --- Custom JFR Event ---
@Name("com.example.perf.OrderProcessed")
@Label("Order Processed")
@Category({"Performance", "Business"})
@StackTrace(true)
@Threshold("5 ms")   // only emit if processing > 5ms — reduces noise
public class OrderProcessedEvent extends Event {
    @Label("Order ID")
    public String orderId;

    @Label("Item Count")
    public int itemCount;

    @Label("Validation Passed")
    public boolean validationPassed;
}

// --- Service with JFR instrumentation ---
public class OrderProcessorService {

    public void processOrder(String orderId, List<String> items) {
        OrderProcessedEvent event = new OrderProcessedEvent();
        event.begin();   // start timing

        try {
            event.orderId = orderId;
            event.itemCount = items.size();
            event.validationPassed = validate(items);
            if (event.validationPassed) {
                persist(orderId, items);
            }
        } finally {
            event.commit();  // stop timing + emit if > @Threshold
        }
    }

    private boolean validate(List<String> items) {
        // Simulate validation — in real code this might be a regex-heavy step
        return items.stream().allMatch(s -> s != null && !s.isBlank());
    }

    private void persist(String orderId, List<String> items) {
        // Simulate DB write
    }
}

// --- Programmatic JFR recording control ---
public class JfrRecordingDemo {

    public static void main(String[] args) throws Exception {
        // Configure and start a recording
        Configuration config = Configuration.getConfiguration("profile"); // or "default"
        Recording recording = new Recording(config);
        recording.setName("order-processor-profile");
        recording.setMaxAge(Duration.ofMinutes(30));
        recording.setMaxSize(200 * 1024 * 1024L); // 200MB
        recording.setToDisk(true);
        recording.start();

        System.out.println("JFR recording started. Running workload...");

        OrderProcessorService service = new OrderProcessorService();

        // Simulate workload
        for (int i = 0; i < 10_000; i++) {
            service.processOrder("ORD-" + i, List.of("item1", "item2", "item3"));
        }

        // Dump and stop
        recording.dump(java.nio.file.Path.of("/tmp/order-profile.jfr"));
        recording.stop();
        recording.close();

        System.out.println("Recording saved to /tmp/order-profile.jfr");
        System.out.println("Open with: jfr print --events OrderProcessed /tmp/order-profile.jfr");
        System.out.println("Or open in JDK Mission Control (jmc)");
    }
}

// --- How to run async-profiler alongside (shell commands, not Java) ---
// $ java -agentpath:/opt/async-profiler/lib/libasyncProfiler.so=start,event=cpu,\
//         file=/tmp/flamegraph.html,interval=10ms,wall -jar myapp.jar
//
// Or attach to running process:
// $ ./profiler.sh -d 30 -e cpu -f /tmp/flamegraph.html <pid>
//
// For allocation profiling:
// $ ./profiler.sh -d 30 -e alloc -f /tmp/alloc-flamegraph.html <pid>
```

### JFR Event Consumer (reading events programmatically):

```java
import jdk.jfr.consumer.*;
import java.nio.file.Path;

public class JfrAnalyzer {

    public static void main(String[] args) throws Exception {
        Path recordingFile = Path.of("/tmp/order-profile.jfr");

        try (RecordingFile file = new RecordingFile(recordingFile)) {
            while (file.hasMoreEvents()) {
                RecordedEvent event = file.readEvent();

                // Filter for our custom event
                if (event.getEventType().getName().equals("com.example.perf.OrderProcessed")) {
                    long durationMs = event.getDuration().toMillis();
                    String orderId = event.getString("orderId");
                    int itemCount = event.getInt("itemCount");

                    if (durationMs > 50) {
                        System.out.printf("SLOW ORDER: %s items=%d duration=%dms%n",
                            orderId, itemCount, durationMs);
                    }
                }

                // Check for lock contention events
                if (event.getEventType().getName().equals("jdk.JavaMonitorWait")) {
                    long waitMs = event.getDuration().toMillis();
                    if (waitMs > 100) {
                        System.out.printf("LOCK CONTENTION: %dms on %s%n",
                            waitMs, event.getClass("monitorClass").getName());
                    }
                }
            }
        }
    }
}
```

## 7. PRODUCTION LENS

### Incident: Wrong Optimization Shipped Due to Safepoint Bias

**System:** Order management service, Java 17, G1GC, 16 cores, 32GB heap
**Symptom:** Batch nightly import of 500K orders taking 45 minutes instead of expected 15 minutes
**Initial profiling:** VisualVM used on staging clone

**VisualVM results (misleading):**
```
Hotspots (safepoint-biased):
  HashMap.get()              32% of samples
  ArrayList.add()            18% of samples
  String.equals()            24% of samples
  XmlStaxParser.readEvent()   8% of samples
```

**Action taken (wrong):** Team replaced `HashMap` with `ConcurrentHashMap` (incorrect fix), refactored `ArrayList` to use `ArrayDeque`, spent 3 days on optimization. Batch job time: **44 minutes**. No improvement.

**Correct profiling with async-profiler:**
```bash
./profiler.sh -d 60 -e cpu -f /tmp/import-flamegraph.html $(jcmd | grep BatchImport | awk '{print $1}')
```

**async-profiler results (actual CPU usage):**
```
Hotspots (OS-signal based):
  XmlStaxParser.readEvent()  51% of samples   ← missed by VisualVM due to long between-safepoint runs
  SchemaValidator.validate()  31% of samples  ← regex compilation on every record
  HashMap.get()               6% of samples   ← not a problem
```

**Root cause:** The XML StAX parser held the CPU for ~2ms per record between safepoints. VisualVM never caught it. Schema validation recompiled its regex `Pattern.compile(...)` on every single record (500K times).

**Fix:**
1. Pre-compile and cache the `Pattern` object as a static final field
2. Switch XML parsing to Jackson's streaming XML mode (2x faster than StAX for this shape)

**Result:** Batch job time dropped to **11 minutes**.

**Lesson for your career:** Never ship an optimization based on VisualVM or YourKit CPU samples alone. Always validate with async-profiler. Safepoint bias has caused millions of dollars of wasted engineering effort industry-wide.

## 9. SUMMARY / FLASHCARD

- **Safepoint bias** means JVM-internal profilers (VisualVM, YourKit CPU) over-count code that reaches safepoints quickly (tight loops, array access) and under-count or miss code that runs long between safepoints (XML parsing, regex); results can be off by 3-10x.
- **async-profiler** uses OS-level `SIGPROF` / `perf_events` and the `AsyncGetCallTrace` JVM API to sample at arbitrary points, eliminating safepoint bias; it is production-safe at 1-3% overhead and should be your default CPU profiler.
- **JFR** provides event-based telemetry (GC, allocation, lock contention, I/O, JIT) at under 2% overhead; use it for context alongside async-profiler, not as a CPU hotspot profiler.
- **Flamegraph width = CPU frequency**: the widest frame is the hottest; ignore height for identifying bottlenecks — look for the widest frame near the top of the tallest stack.
- **Never ship an optimization** based solely on safepoint-biased profiler output; validate every hotspot finding with async-profiler before committing engineering time to a fix.

## The Critical Dialogue

**Student:** Our legacy Ledger is a 10-year-old Monolith. It's written in Java 8, it's slow, and everyone is afraid to touch it. I want to rewrite it from scratch in Spring Boot 3, but the business says "No, it's too risky." Am I stuck in the past forever?

**Principal:** A "Big Bang Rewrite" is the most common cause of architectural death. You spend 6 months building a new system that has no users, while the old system continues to grow bugs. To reach Principal level, we must master **Evolutionary Architecture**. We don't destroy the past; we consume it. We use the **Strangler Fig Pattern** to grow a new, high-performance system around the old one, one feature at a time. We move from "The Great Rewrite" to **Continuous Incremental Value**.

## 1. The Physics of the Strangler Fig

### 1.1 How to Kill a Monolith Safely

The Strangler Fig pattern (named after the vine that grows around a tree and eventually replaces it) is the industry standard for legacy mitigation.

> [!abstract] The 3 Phases of Evolution
> - **1. Interception:** Use an **Anycast Gateway** (Chapter 4.1) or an eBPF Proxy (Chapter 6.2) to route specific requests to the new service.
> - **2. Propagation:** Move one Bounded Context (Chapter 14.1) at a time. (e.g. move "Audit" first, then "Trading").
> - **3. Elimination:** When the old system is just an empty shell, you turn off the power. The tree is dead; the vine is the new tree.

---

## 2. Solution: The Anycast Interceptor

**The Principal Architecture:** We use the routing layer to hide the migration from the user.

- **Mechanism:** The user hits `api.ledger.com/v1/orders`.
- **The Gatekeeper:** The Gateway (Envoy or Nginx) checks its routing table.
- **The Handoff:** If the feature has been "Strangled," Envoy sends the request to the new **Spring Boot 3 / Loom** cluster. Otherwise, it goes to the **Java 8 Monolith**.

## 3. Source Archaeology: Spring HandlerMapping and Feature Flags

**`org.springframework.web.servlet.HandlerMapping`** (Spring MVC):
- The Strangler Fig interceptor is most elegantly implemented as a custom `HandlerMapping` with higher precedence than the default
- `AbstractHandlerMapping.setOrder(int)` — set a lower order number to take priority over `RequestMappingHandlerMapping`
- In the custom `HandlerMapping.getHandler(HttpServletRequest)`: check the feature flag, return the legacy handler bean if not yet strangled, or forward to the new service handler

**`org.springframework.web.reactive.function.client.WebClient`** (Spring WebFlux):
- Used by the Strangler Router to proxy matched requests to the new service: `WebClient.create("http://new-audit-service.internal").method(request.getMethod()).uri(request.getURI()).retrieve().bodyToMono(String.class)`
- Non-blocking proxy — the router does not consume a thread while waiting for the new service response

**`io.github.openfeaturehub.sdk.OpenFeatureAPI`** (OpenFeature standard, `dev.openfeature:sdk`):
- `OpenFeatureAPI.getInstance().getClient().getBooleanValue("audit-context-strangled", false)` — standardised feature flag evaluation
- Works with LaunchDarkly, Flagsmith, Unleash backends; same code regardless of provider
- Percentage rollout: evaluate the flag with a `userId` evaluation context to implement canary user targeting

**`org.springframework.web.filter.OncePerRequestFilter`**:
- Alternative to custom `HandlerMapping`: implement the Strangler Fig as a filter that forwards matched requests via `WebClient` and short-circuits the filter chain

**Envoy proxy configuration (YAML, for the gateway layer):**
```yaml
# routes evaluated in order — first match wins
- match:
    prefix: "/v2/audit"          # 1. Strangled path → new service
  route:
    cluster: new_audit_service
- match:
    prefix: "/"                  # 2. Everything else → monolith
  route:
    cluster: legacy_monolith
```

### GOOD: Strangler Router with canary rollout and automatic fallback

```java
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerMapping;
import org.springframework.web.reactive.function.client.WebClient;
import javax.servlet.http.HttpServletRequest;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;

/**
 * Strangler Fig Router.
 *
 * Migration state (stored externally in LaunchDarkly / OpenFeature):
 * - "audit-strangled"    = false  → 100% legacy
 * - "audit-strangled"    = true   → route by canary percentage
 * - "audit-canary-pct"  = 10     → 10% of users go to new service
 *
 * Fallback: if the new service returns 5xx, automatically fall back to
 * the legacy monolith and increment an error counter (circuit breaker).
 */
@Component
public class StranglerFigRouter {

    private final OpenFeatureClient featureFlags;
    private final WebClient newServiceClient;
    private final WebClient monolithClient;

    // Error rate tracking per route — used for automatic fallback
    private final Map<String, AtomicInteger> errorCounts = new ConcurrentHashMap<>();

    public StranglerFigRouter(OpenFeatureClient featureFlags) {
        this.featureFlags = featureFlags;
        this.newServiceClient = WebClient.create("http://new-audit-service.internal");
        this.monolithClient  = WebClient.create("http://legacy-monolith.internal");
    }

    public byte[] route(HttpServletRequest req) {
        String path = req.getRequestURI();
        String userId = req.getHeader("X-User-Id");

        // 1. Feature flag check: is this path strangled?
        boolean isStrangled = featureFlags.getBooleanValue("audit-strangled", false,
            EvaluationContext.of("userId", userId));

        // 2. Canary check: only a percentage of users go to the new service
        boolean inCanary = isStrangled && isInCanaryGroup(userId);

        if (inCanary) {
            try {
                return routeToNewService(req);
            } catch (Exception e) {
                // 3. Automatic fallback: new service failed → fall through to monolith
                errorCounts.computeIfAbsent(path, k -> new AtomicInteger()).incrementAndGet();
                // Production: if error rate > 1% in 60s, set flag to 0% via API
                System.err.println("[STRANGLER] New service failed for " + path
                    + ", falling back to monolith. Error: " + e.getMessage());
                return routeToMonolith(req);
            }
        }

        return routeToMonolith(req);
    }

    private boolean isInCanaryGroup(String userId) {
        // Deterministic hashing: same user always goes to same group
        // (prevents session bouncing between old and new service)
        int canaryPct = featureFlags.getIntegerValue("audit-canary-pct", 0);
        return Math.abs(userId.hashCode() % 100) < canaryPct;
    }

    private byte[] routeToNewService(HttpServletRequest req) {
        return newServiceClient.get()
            .uri(req.getRequestURI())
            .headers(h -> req.getHeaderNames().asIterator().forEachRemaining(
                name -> h.add(name, req.getHeader(name))))
            .retrieve()
            .onStatus(status -> status.is5xxServerError(),
                      resp -> Mono.error(new RuntimeException("New service 5xx")))
            .bodyToMono(byte[].class)
            .block();
    }

    private byte[] routeToMonolith(HttpServletRequest req) {
        return monolithClient.get()
            .uri(req.getRequestURI())
            .retrieve()
            .bodyToMono(byte[].class)
            .block();
    }
}
```

## 7. Production Lens

At Amazon (2002 Bezos mandate), the transition from a monolith to service-oriented architecture took **7 years** of Strangler Fig migrations, not a big bang rewrite. Each service was extracted one at a time, with traffic routing managed by the existing API gateway.

Martin Fowler cited a UK retail client (2004) where a Big Bang rewrite of a 10-year-old ordering system was attempted, abandoned after 18 months, and $4M spent, with zero production traffic migrated. The subsequent Strangler Fig approach delivered the first migrated service (the "Catalogue" context) in **6 weeks** and full migration in **14 months** — compared to the abandoned 18-month rewrite.

Concrete ROI for the GOL Audit example: the legacy audit database lock causes 10-second pauses, 3 times per hour. At 500k trades/day during trading hours (8 hours), each 10-second pause blocks ~1,157 trades × 3 pauses/hour × 8 hours = ~27,800 blocked trade events/day. At $12 average trade value with 2% abandonment: **$6,700/day**, **$2.4M/year**. Strangling the audit feature costs 1 sprint. ROI payback: **< 1 week**.

## 9. Summary / Flashcard

- **Big Bang Rewrites fail at 70%+**: the new system is built in isolation, becomes obsolete before launch, and the legacy continues accumulating bugs; the Strangler Fig extracts value incrementally every sprint.
- **Three phases — Intercept, Propagate, Eliminate**: route specific paths to the new service at the gateway layer, then expand coverage one Bounded Context at a time, then decommission the legacy shell.
- **Deterministic canary hashing** (`userId.hashCode() % 100 < canaryPct`) pins each user to one service version for the duration of their session, preventing confusing behaviour from session-level inconsistency.
- **`AbstractHandlerMapping.setOrder(int)`** with a low order value makes the Strangler Router take precedence over Spring MVC's default `RequestMappingHandlerMapping` — the cleanest in-process implementation for monolith-to-microservice within a single Spring Boot app.
- **Automatic fallback on 5xx** is non-negotiable: the new service is unproven; the first canary traffic must fall back transparently to the legacy if the new service errors, with automatic flag-disable when error rate > 1%.

<summary>Exercise 1 — Big Bang risk analysis</summary>

**Five concrete failure modes and how Strangler Fig avoids each:**

1. **Integration Drift** — The legacy system keeps receiving new features while the rewrite is in progress. After 6 months, the new Ledger is missing 47 features added to the monolith. The rewrite is already obsolete before launch. Strangler Fig extracts one Bounded Context at a time: the new code goes live in weeks, so drift is bounded by one sprint cycle.

2. **No Production Feedback** — The rewrite runs behind a feature branch for months with zero real traffic. Unknown unknowns (weird user data, mainframe edge cases) are never surfaced until launch day. Strangler Fig puts the extracted service on canary traffic immediately; real bugs surface at 1% traffic, not 100%.

3. **Rollback Impossibility** — A big bang cutover is a one-way door. If the new Ledger misbehaves, rollback means re-pointing all traffic back and potentially losing writes made to the new DB. Strangler Fig rollback is a single feature flag toggle to zero percent; the legacy monolith never stopped running.

4. **Team Context Loss** — A rewrite team works in isolation from the production codebase for months. When bugs emerge, they don't understand the legacy domain well enough to reproduce them. Strangler Fig keeps the team continuously deploying; they stay embedded in the live system and learn the domain through real incidents.

5. **Business Continuity Risk** — A Big Bang cutover requires a maintenance window or a hard switch. At 500k trades/day, even a 30-minute outage during trading hours costs roughly $125,000 in abandoned trades. Strangler Fig requires zero maintenance window; the gateway routing change is atomic and instantaneous.

**Staff-level phrasing:** "A Big Bang Rewrite is an organisational bet that a team of finite size can out-execute years of accumulated domain knowledge in a fixed time box — it fails because the target keeps moving and feedback arrives only at launch."

</details>

<details>
<summary>Exercise 2 — Bounded Context prioritisation</summary>

**Recommended extraction order: Audit → User Auth → Reporting → Order Routing → Settlement**

1. **Audit** — Highest priority. It is already causing 10-second DB locks (the GOL problem). Low coupling: Audit only reads domain events; nothing reads back from Audit. The new implementation delivers immediate, measurable ROI ($2.4M/year). Technical risk is low — no financial data is being moved yet.

2. **User Auth** — Second. Authentication is a well-understood domain with mature libraries (Spring Security, OAuth2). It is consumed by everything, but it only produces a JWT; it does not call back into the monolith. Extracting it early isolates identity from the legacy and unblocks all subsequent services from having a clean auth boundary.

3. **Reporting** — Third. Read-only; it consumes events from other contexts but writes nothing. A reporting service failure does not block trades. Moderate business value (dashboards, regulatory), low technical risk.

4. **Order Routing** — Fourth. High business value, but it calls Settlement synchronously; you cannot extract it cleanly until Settlement is ready or you introduce an ACL. Extract after Reporting de-risks the read path.

5. **Settlement** — Last. Highest coupling (calls Audit, Order Routing, external clearing houses), handles money, and requires a full data migration. Extract only after the surrounding services are stable and the data migration physics (Chapter 15.3) are proven.

**Staff-level phrasing:** "Prioritise extractions that deliver immediate ROI, have low coupling, and do not require coordinated cutover with other contexts — start with the feature that is actively hurting production."

</details>

<summary>Exercise 3 — Envoy configuration</summary>

```yaml
route_config:
  name: strangler_routes
  virtual_hosts:
    - name: ledger_api
      domains: ["*"]
      routes:
        # Route 1: /v2/audit/* → new audit service (weight 100)
        - match:
            prefix: "/v2/audit/"
          route:
            cluster: new_audit_service
            timeout: 5s

        # Route 2: /v2/orders/* → canary split (new 10%, legacy 90%)
        - match:
            prefix: "/v2/orders/"
          route:
            weighted_clusters:
              clusters:
                - name: new_order_service
                  weight: 10
                - name: legacy_monolith
                  weight: 90
              total_weight: 100
            timeout: 5s

        # Route 3: everything else → legacy monolith (weight 100)
        - match:
            prefix: "/"
          route:
            cluster: legacy_monolith
            timeout: 10s
```

**Key points:** Routes are evaluated top-to-bottom; the most specific prefix must come first. The `/v2/audit/` route must appear before the catch-all `/` route or it will never match. The `weighted_clusters` block on `/v2/orders/` implements the canary split without any application-code change.

**Staff-level phrasing:** "Envoy routing is a declarative, ordered match-list — put the most specific paths first, use weighted clusters for canary splits, and keep the catch-all last."

<summary>Exercise 4 — Coding challenge: StranglerMetricsCollector</summary>

```java
// Java 21+ reference implementation
import org.springframework.stereotype.Component;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import java.time.Instant;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;
import java.util.stream.Collectors;

@Component
public class StranglerMetricsCollector {

    // Request counts: path → {legacy, new}
    private final Map<String, AtomicLong> legacyRequests = new ConcurrentHashMap<>();
    private final Map<String, AtomicLong> newRequests    = new ConcurrentHashMap<>();

    // Error window: path → array of 60 AtomicLong slots (one per second-of-minute)
    // Index = Instant.now().getEpochSecond() % 60
    private final Map<String, AtomicLong[]> errorWindow  = new ConcurrentHashMap<>();
    // Total requests per path in the current 60-second window (for % calculation)
    private final Map<String, AtomicLong>   windowTotal  = new ConcurrentHashMap<>();

    // ── record a request ──────────────────────────────────────────────────────

    public void recordLegacy(String path) {
        legacyRequests.computeIfAbsent(path, k -> new AtomicLong()).incrementAndGet();
        windowTotal.computeIfAbsent(path, k -> new AtomicLong()).incrementAndGet();
    }

    public void recordNew(String path) {
        newRequests.computeIfAbsent(path, k -> new AtomicLong()).incrementAndGet();
        windowTotal.computeIfAbsent(path, k -> new AtomicLong()).incrementAndGet();
    }

    public void recordError(String path) {
        AtomicLong[] window = errorWindow.computeIfAbsent(path,
            k -> initWindow());
        int slot = (int)(Instant.now().getEpochSecond() % 60);
        window[slot].incrementAndGet();
    }

    // ── panic switch ──────────────────────────────────────────────────────────

    public boolean shouldDisableCanary(String path) {
        AtomicLong[] window = errorWindow.get(path);
        if (window == null) return false;

        long errors = 0;
        for (AtomicLong slot : window) errors += slot.get();

        long total = windowTotal.getOrDefault(path, new AtomicLong(0)).get();
        if (total == 0) return false;

        double errorRate = (double) errors / total;
        return errorRate > 0.01;   // > 1% error rate in last 60 s
    }

    // ── snapshot for the endpoint ─────────────────────────────────────────────

    public Map<String, PathStats> snapshot() {
        // Union of all known paths
        java.util.Set<String> paths = new java.util.HashSet<>();
        paths.addAll(legacyRequests.keySet());
        paths.addAll(newRequests.keySet());

        return paths.stream().collect(Collectors.toMap(
            p -> p,
            p -> {
                long legacy = legacyRequests.getOrDefault(p, new AtomicLong()).get();
                long newSvc = newRequests.getOrDefault(p, new AtomicLong()).get();
                double errRate = errorRateFor(p);
                return new PathStats(legacy, newSvc, errRate, shouldDisableCanary(p));
            }
        ));
    }

    // ── helpers ───────────────────────────────────────────────────────────────

    private double errorRateFor(String path) {
        AtomicLong[] window = errorWindow.get(path);
        if (window == null) return 0.0;
        long errors = 0;
        for (AtomicLong slot : window) errors += slot.get();
        long total = windowTotal.getOrDefault(path, new AtomicLong(0)).get();
        return total == 0 ? 0.0 : (double) errors / total;
    }

    private AtomicLong[] initWindow() {
        AtomicLong[] w = new AtomicLong[60];
        for (int i = 0; i < 60; i++) w[i] = new AtomicLong(0);
        return w;
    }

    public record PathStats(long legacyRequests, long newRequests,
                            double errorRate60s, boolean panicActive) {}
}

@RestController
class StranglerStatsController {

    private final StranglerMetricsCollector collector;

    StranglerStatsController(StranglerMetricsCollector collector) {
        this.collector = collector;
    }

    @GetMapping("/admin/strangler-stats")
    public Map<String, StranglerMetricsCollector.PathStats> stats() {
        return collector.snapshot();
    }
}
```

**Why this works:** The 60-slot `AtomicLong[]` array indexed by `epochSecond % 60` is a naturally expiring ring buffer — old error counts fall out of the window automatically without any cleanup thread. `ConcurrentHashMap.computeIfAbsent` ensures thread-safe lazy initialisation without locking the whole map.

**Common mistake:** Using `synchronized` blocks or a single global error counter instead of a per-path ring buffer. A global counter cannot distinguish which path is erroring, and synchronisation creates a bottleneck under high RPS. A second common mistake is using `OFFSET`-based pagination in the backfill rather than cursor-based — not relevant here, but a pattern error that shows up in the same module.

<summary>Exercise 5 — The final 10% problem</summary>

**Why migrations stall at the final 10%:**

The last 10% is always the most-coupled code. The easy, isolated Bounded Contexts were extracted first (by design). What remains are the features that share state with everything else.

**Pattern 1 — Shared Database:** The legacy monolith and the partially extracted service both read and write the same database table directly. You cannot cut over the new service without also migrating all consumers of that table simultaneously. Example: the legacy `orders` table is read directly by Settlement, Reporting, and Audit. Even after Audit is extracted, Settlement still uses `SELECT * FROM orders` on the legacy schema. Extracting the Orders Bounded Context requires coordinating a schema migration across all three remaining consumers — a distributed coordination problem that is often harder than the original migration.

**Pattern 2 — Distributed Transaction:** The legacy code performs a logical transaction across two resources in a single ACID unit: insert into `orders` and publish to the audit log in one database transaction. Once the audit service is extracted to a separate database, this atomicity is gone. You now need a Saga or Outbox Pattern (Chapter 7.x) to replace the distributed transaction. Teams often defer this complexity indefinitely.

**When to accept a Permanent Hybrid state:** Accept it when the coupling is in a genuinely shared kernel — data that two Bounded Contexts legitimately own jointly (e.g. a reference data table used by 5 services). Forcing full extraction introduces more complexity than the hybrid incurs.

**How to make the Permanent Hybrid safe long-term:** (1) Make the shared component an owned service with a versioned API, not a shared DB table. (2) Establish an explicit SLA and on-call ownership for the hybrid component. (3) Document it in an ADR so future teams do not accidentally "fix" it with another migration attempt.

**Staff-level phrasing:** "The final 10% of a Strangler Fig migration is disproportionately hard because it contains every coupling decision that was deferred during the previous 90% — the right answer is often to stop, stabilise the hybrid, and treat the shared kernel as a first-class owned service."

</details>

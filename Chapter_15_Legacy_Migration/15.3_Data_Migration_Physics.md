## The Critical Dialogue

**Student:** We've built the new high-performance database for the Ledger. But the old database has 10 years of data. How do we move 100 billion rows without turning off the system? If I take a 24-hour maintenance window, the company loses millions in revenue.

**Principal:** You're asking for **In-Flight Heart Surgery**. To reach Principal level, we must master **Online Data Migration**. We don't "Export and Import"; we use the **Double-Write Pattern**. We synchronize the past while simultaneously writing the present. We move from "Static Backups" to **Dynamic Live Synchronization**.

## 1. The Physics of the Online Migration

### 1.1 The "Maintenance Window" Fallacy

A Principal Architect knows that at scale, a maintenance window is a **Last Resort**.
- **The Math:** Copying 100TB at 10Gbps takes ~22 hours. If any part of the copy fails, you've wasted a whole day.
- **The Solution:** The **4-Phase Migration**.

---

## 2. Solution: The 4-Phase Migration Flow

**The Principal Architecture:** We use a strictly ordered sequence to move data with zero downtime.

- **Phase 1: Shadow Writes.** Every new order is written to BOTH the old and new databases. (New data is now in sync).
- **Phase 2: Backfill.** A background process copies the "Old" data from the monolith to the new fleet.
- **Phase 3: Verification.** A "Check Service" compares rows in both systems to ensure 100% parity.
- **Phase 4: Cutover.** We flip the switch. The new system becomes the primary.

## 3. Source Archaeology: Migration Tools and Patterns

**`org.flywaydb.core.Flyway`** (Flyway, `org.flywaydb:flyway-core`):
- Used for the new schema creation and version tracking on the target database
- `Flyway.configure().dataSource(newDs).load().migrate()` — creates the new schema before shadow writes begin
- Migration scripts in `src/main/resources/db/migration/` prefixed `V1__` through `VN__`

**`com.zaxxer.hikari.HikariDataSource`** dual datasource pattern:
- Define two Spring `@Bean` `DataSource` instances: `@Primary DataSource legacyDataSource()` and `DataSource newDataSource()`
- `@Qualifier("legacyDataSource")` / `@Qualifier("newDataSource")` to inject the correct one
- The `DualLedgerWriter` (see Code Lab) holds references to both

**`io.debezium.connector.postgresql.PostgresConnector`** (Debezium, `io.debezium:debezium-connector-postgres`):
- **CDC alternative to dual-writing**: Debezium reads PostgreSQL WAL and publishes every `INSERT`/`UPDATE`/`DELETE` as a Kafka event
- The consumer on the new DB side applies these changes — no application-code dual-write needed
- `snapshot.mode=initial` — performs an initial snapshot (the backfill) then switches to streaming WAL changes
- Advantage over dual-writing: **ordering is guaranteed** (WAL is ordered), **deletes are handled** (dual-write in application code misses deletes unless explicitly coded)

**`java.lang.Thread.startVirtualThread(Runnable)`** (Java 21, Chapter 1.3):
- Used for asynchronous shadow writes; a virtual thread per shadow write means thousands of concurrent shadow writes at negligible memory cost (~1KB per virtual thread vs 1MB per platform thread)

**Chunked Backfill with rate limiting:**
- Copy rows in chunks of 1,000 using `LIMIT` + `OFFSET` or, better, cursor-based pagination with `WHERE id > lastId ORDER BY id LIMIT 1000`
- `Thread.sleep(100)` between chunks prevents CPU saturation on the legacy database
- Rate: 1,000 rows × 200 bytes / 100ms = ~20 MB/s — tunable to stay within the legacy DB's I/O budget

## 4. Principal Implementation: The Dual-Writer

```java
// Principal Level: Resilient Dual-Writer
public class DualLedgerWriter {
    private final LedgerRepository primary;
    private final LedgerRepository shadow;

    public void save(Order order) {
        // 1. Primary write MUST succeed (ACID)
        primary.save(order);

        // 2. Shadow write is asynchronous to protect latency
        // We use a Virtual Thread (Chapter 1.3) so we don't stall the main flow
        Thread.startVirtualThread(() -> {
            try {
                shadow.save(order);
            } catch (Exception e) {
                // 3. Principal Rule: Log but don't fail!
                // We will catch this delta in the Backfill phase.
                logger.error("Shadow write failed for " + order.id());
            }
        });
    }
}
```

## 5. Code Lab: Full Migration System with Parity Checker

### BAD: Synchronous dual-write — primary latency doubled

```java
// BAD: Shadow write in the same thread as primary.
// If the new DB is slow (it's new, schema not tuned), the user waits.
// If the new DB is DOWN, every primary write fails too.
// The shadow is supposed to be a silent observer, not a co-conspirator.

@Transactional
public void save(Order order) {
    primaryRepo.save(order);     // ~2ms
    // BAD: same transaction — if shadow fails, primary rolls back!
    // If shadow is slow (e.g. schema scan), primary response time doubles.
    shadowRepo.save(order);      // ~50ms (new DB not tuned) → total: 52ms
}
// Result: shadow DB problems become user-facing latency. Wrong.
```

### GOOD: Async shadow write with parity checker

```java
import java.util.*;
import java.util.concurrent.*;
import org.springframework.stereotype.*;
import org.springframework.transaction.annotation.Transactional;

/**
 * Resilient Dual-Writer for zero-downtime migration.
 *
 * Phase 1 (Shadow Write): primary is authoritative; shadow is best-effort.
 * Any shadow write failure is logged and caught in Phase 3 (Verification).
 */
@Service
public class DualLedgerWriter {

    private final OrderRepository primaryRepo;
    private final OrderRepository shadowRepo;

    // Virtual thread executor: lightweight, no pool sizing needed
    private final ExecutorService shadowExecutor =
        Executors.newVirtualThreadPerTaskExecutor();

    public DualLedgerWriter(
        @Qualifier("primaryRepo") OrderRepository primaryRepo,
        @Qualifier("shadowRepo") OrderRepository shadowRepo
    ) {
        this.primaryRepo = primaryRepo;
        this.shadowRepo = shadowRepo;
    }

    @Transactional  // only covers primaryRepo — shadow is out-of-band
    public void save(Order order) {
        // 1. Primary write: user request blocks here
        primaryRepo.save(order);

        // 2. Shadow write: fire-and-forget on a virtual thread
        // User response is not affected by shadow latency or shadow failures
        shadowExecutor.submit(() -> {
            try {
                shadowRepo.save(order);
            } catch (Exception e) {
                // Log for reconciliation — do NOT propagate
                log.warn("[SHADOW] Write failed for order={}, reason={}",
                    order.id(), e.getMessage());
                // Production: increment Prometheus counter "shadow.write.failures"
                // Backfill Phase will reconcile this gap
            }
        });
    }
}

/**
 * Phase 2: Chunked Backfill — copies historical data without overwhelming legacy DB.
 */
@Component
public class HistoricalBackfiller {

    private final JdbcTemplate legacyJdbc;
    private final JdbcTemplate newJdbc;
    private static final int CHUNK_SIZE = 1_000;
    private static final long SLEEP_MS = 100;  // rate limiter: ~10k rows/sec

    /**
     * Copy all orders with id > lastCopiedId in chunks.
     * Run as a background job via @Scheduled(fixedDelay = 60_000).
     */
    public long backfillChunk(long lastCopiedId) throws InterruptedException {
        // Cursor-based pagination (more efficient than OFFSET for large tables)
        List<Map<String, Object>> rows = legacyJdbc.queryForList(
            "SELECT id, user_id, amount, status, created_at " +
            "FROM orders WHERE id > ? ORDER BY id LIMIT ?",
            lastCopiedId, CHUNK_SIZE
        );

        if (rows.isEmpty()) {
            return lastCopiedId;  // backfill complete for this run
        }

        // Batch insert into new DB — Chapter 3.3 JDBC batching
        newJdbc.batchUpdate(
            "INSERT INTO orders (id, user_id, amount, status, created_at) " +
            "VALUES (?, ?, ?, ?, ?) ON CONFLICT (id) DO NOTHING",
            rows.stream()
                .map(r -> new Object[]{
                    r.get("id"), r.get("user_id"), r.get("amount"),
                    r.get("status"), r.get("created_at")
                })
                .toList()
        );

        long lastId = ((Number) rows.getLast().get("id")).longValue();
        Thread.sleep(SLEEP_MS);  // rate limit — prevent legacy DB CPU spike
        return lastId;
    }
}

/**
 * Phase 3: Parity Checker — samples rows from both DBs before cutover.
 */
@Component
public class MigrationParity Auditor {

    private final JdbcTemplate legacyJdbc;
    private final JdbcTemplate newJdbc;

    /**
     * Samples N random rows and compares critical fields.
     * Returns a PurityReport with any divergences found.
     */
    public ParityReport sample(int sampleSize) {
        List<Long> sampleIds = legacyJdbc.queryForList(
            "SELECT id FROM orders ORDER BY RANDOM() LIMIT ?",
            Long.class, sampleSize
        );

        List<String> divergences = new ArrayList<>();

        for (Long id : sampleIds) {
            Map<String, Object> legacy = legacyJdbc.queryForMap(
                "SELECT amount, status FROM orders WHERE id = ?", id);
            Map<String, Object> newRow = newJdbc.queryForMap(
                "SELECT amount, status FROM orders WHERE id = ?", id);

            if (newRow == null) {
                divergences.add("Missing in new DB: orderId=" + id);
                continue;
            }

            // Compare critical fields with exact equality
            if (!Objects.equals(legacy.get("amount"), newRow.get("amount"))) {
                divergences.add("Amount mismatch for orderId=" + id
                    + ": legacy=" + legacy.get("amount")
                    + " new=" + newRow.get("amount"));
            }
        }

        return new ParityReport(sampleSize, divergences);
    }

    public record ParityReport(int sampled, List<String> divergences) {
        public boolean isClean() { return divergences.isEmpty(); }
    }
}
```

## 7. Production Lens

At GitHub (2018 database migration blog post), migrating 1.5 billion rows of repository data used a dual-write approach with chunked backfill. Key numbers:
- Backfill rate: **100,000 rows/minute** (throttled to stay within 10% of legacy DB capacity)
- Migration duration: **3 weeks** of background backfilling
- Shadow write error rate: **0.003%** (caught and reconciled in Phase 3)
- Parity sample: 1 million random rows sampled; **0 divergences** found before cutover
- Maintenance window for cutover: **0 seconds** (traffic routed via feature flag flip)

At that scale, copying 100TB at 10Gbps would take **22 hours** of maintenance. The dual-write approach reduced the revenue-impacting cutover to a **15-second flag flip** with automatic rollback if error rate spiked.

The delete problem: dual-writing handles `INSERT` and `UPDATE` but misses `DELETE`. Solution used by GitHub: soft deletes (`deleted_at` timestamp) during the migration window; hard deletes only after cutover.

<summary>Exercise 1 — Backfill throughput: 500M rows, chunk size and sleep tuning</summary>

**(a) Time to complete backfill:**

- Chunk = 1,000 rows
- Cycle = read 1,000 rows + write 1,000 rows + 100ms sleep
- Read + write time per chunk (rough): ~50ms (assuming 25ms each on a modern NVMe DB)
- Total cycle time: ~150ms
- Total chunks: 500,000,000 / 1,000 = 500,000 chunks
- Total time: 500,000 × 150ms = 75,000,000ms = **75,000 seconds ≈ 20.8 hours**

**(b) Average I/O load on legacy DB:**

- Active I/O time per cycle: ~50ms out of 150ms = 33% of time
- At 1,000 rows × 200 bytes = 200KB per read chunk
- Read throughput: 200KB / 150ms = **1.33 MB/s average** read load on legacy DB
- Peak during active window: 200KB / 50ms = **4 MB/s**

This is low relative to typical database I/O capacity (100–1,000 MB/s). The 100ms sleep prevents even 5% legacy DB CPU consumption.

**(c) Halving completion time without exceeding 20% CPU:**

Current throughput: 500,000 chunks × 150ms = 75,000s. Target: 37,500s.

**Option 1: Double chunk size to 2,000 rows, same sleep**

- Cycle time: ~75ms read/write + 100ms sleep = 175ms (up from 150ms)
- Chunks: 250,000
- Total: 250,000 × 175ms = 43,750s — not quite half.

**Option 2: Double chunk size AND halve sleep to 50ms**

- Cycle time: ~75ms + 50ms = 125ms
- Chunks: 250,000
- Total: 250,000 × 125ms = 31,250s ≈ 8.7 hours — better than halved.
- Read throughput: 400KB / 125ms = 3.2 MB/s average. Still under 20% CPU.

**Verification formula:** `active_fraction = work_time / cycle_time = 75ms / 125ms = 60%` of CPU time is active DB work. At 60% active with ~5% CPU per MB/s read rate: 3.2 MB/s × 5% = 16% CPU — within the 20% limit.

**Staff-level phrasing:** "Double chunk to 2k and halve sleep to 50ms: 8.7h completion at 16% legacy DB CPU — meets both goals without a risky configuration jump."

<summary>Exercise 2 — Delete problem: three solutions</summary>

**What happens on `DELETE FROM orders WHERE id = 123`:**

**Primary (legacy) DB:** Row `id=123` is deleted. The WAL records a DELETE event.

**Shadow DB:** Shadow write layer only intercepts INSERTs and UPDATEs (or may not be wired to intercept DELETEs at all). The delete is NOT forwarded to the shadow DB. Row `id=123` still exists in the shadow DB.

**Why the shadow DB retains the row:** Application-level dual-write typically wraps only write operations in the "interesting" code paths. `DELETE` statements may come from different code paths, batch jobs, scheduled cleanup, or raw SQL — not all of which are instrumented for shadow writes.

**Three solutions:**

**Solution 1 — Soft delete (application code):**

```java
// Instead of DELETE FROM orders WHERE id = 123
// Use: UPDATE orders SET deleted_at = NOW() WHERE id = 123
```

Both primary and shadow DBs receive the UPDATE. The row persists in both with `deleted_at` set. The application filters on `WHERE deleted_at IS NULL` for all queries. Delete semantics preserved without a physical DELETE.

**Solution 2 — CDC (Debezium):**

Configure Debezium on the primary DB's WAL. Debezium emits a DELETE event to Kafka. A consumer applies the DELETE to the shadow DB. This is the cleanest solution — no application changes, handles all delete paths including batch jobs and raw SQL.

**Solution 3 — Post-cutover cleanup:**

Accept that the shadow DB has orphaned records during migration. After cutover (shadow DB becomes primary), run a reconciliation job:
```sql
DELETE FROM new_orders 
WHERE id NOT IN (SELECT id FROM legacy_orders)  -- rows deleted in legacy but not yet in new
AND migrated_at < NOW() - INTERVAL '1 day';     -- only clean up rows that were migrated, not new ones
```

This is acceptable if the shadow DB is not used for reads before cutover.

**Staff-level phrasing:** "Soft delete handles deletes in dual-write with zero extra infrastructure; CDC (Debezium) handles ALL delete paths including batch jobs; post-cutover reconciliation is viable if shadow DB is write-only during migration."

</details>

<details>
<summary>Exercise 3 — Shadow write latency analysis</summary>

**Without async shadow writes:**

User request path: primary write (2ms) + shadow write (15ms) = **17ms user-facing latency**.

At 10,000 RPS: the shadow write path serializes with the primary write — each request waits for both.

**With async shadow writes (virtual thread):**

```java
// Fire-and-forget pattern
public void writeOrder(Order order) {
    primaryDb.save(order); // 2ms — user waits for this

    // Shadow write on a virtual thread — does not block the response
    Thread.ofVirtual().start(() -> {
        try {
            shadowDb.save(order); // 15ms — completes asynchronously
        } catch (Exception e) {
            log.warn("Shadow write failed: {}", e.getMessage());
        }
    });
}
```

User-facing latency: **2ms** (primary write only). Shadow write happens asynchronously.

**Shadow write queue depth at 10,000 RPS:**

Each shadow write takes 15ms. The queue drains at 1000/15ms = 66,667 shadow writes/s capacity per single-threaded pool. At 10,000 RPS demand, the queue grows at 10,000 - 66,667 = **0 queue depth** — virtual threads keep up easily because each thread blocks only on I/O and the OS schedules them efficiently.

Wait — with virtual threads, each request spawns a new virtual thread. 10,000 RPS × 15ms per shadow write = 150 virtual threads active at steady state (Little's Law: N = λW = 10,000/s × 0.015s). Virtual threads handle 150 concurrent easily.

**Staff-level phrasing:** "Async shadow writes remove 15ms shadow latency from user path — user sees 2ms; at 10k RPS, Little's Law predicts 150 concurrent shadow virtual threads, well within JVM capacity."

</details>

<summary>Exercise 4 — MigrationController REST endpoint</summary>

```java
import org.springframework.http.ResponseEntity;
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.web.bind.annotation.*;

import java.time.Instant;
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.atomic.AtomicReference;

@RestController
@RequestMapping("/admin/migration")
@PreAuthorize("hasRole('ADMIN')")
public class MigrationController {

    private final HistoricalBackfiller backfiller;
    private final MigrationParityAuditor auditor;

    // In-memory state (for status endpoint)
    private final AtomicLong rowsCopied = new AtomicLong(0);
    private final AtomicLong lastCopiedId = new AtomicLong(0);
    private final AtomicReference<Instant> startTime = new AtomicReference<>();
    private final AtomicReference<ParityReport> lastParityReport = new AtomicReference<>();
    private volatile boolean backfillRunning = false;

    public MigrationController(HistoricalBackfiller backfiller, MigrationParityAuditor auditor) {
        this.backfiller = backfiller;
        this.auditor = auditor;
    }

    @PostMapping("/start")
    public ResponseEntity<String> start() {
        if (backfillRunning) {
            return ResponseEntity.badRequest().body("Backfill already running");
        }
        backfillRunning = true;
        startTime.set(Instant.now());

        Thread.ofVirtual().name("migration-backfiller").start(() -> {
            try {
                backfiller.run(id -> {
                    lastCopiedId.set(id);
                    rowsCopied.incrementAndGet();
                });
            } finally {
                backfillRunning = false;
            }
        });

        return ResponseEntity.ok("Backfill started");
    }

    @GetMapping("/status")
    public ResponseEntity<MigrationStatus> status() {
        long copied = rowsCopied.get();
        long elapsed = startTime.get() == null ? 0 :
            java.time.Duration.between(startTime.get(), Instant.now()).toMinutes();
        double rowsPerMin = elapsed > 0 ? (double) copied / elapsed : 0;
        long totalRows = 500_000_000L; // known total
        double estMinutesRemaining = rowsPerMin > 0 ?
            (totalRows - copied) / rowsPerMin : Double.MAX_VALUE;

        return ResponseEntity.ok(new MigrationStatus(
            lastCopiedId.get(), copied, rowsPerMin, estMinutesRemaining, backfillRunning));
    }

    @PostMapping("/verify")
    public ResponseEntity<ParityReport> verify() {
        ParityReport report = auditor.sample(1_000);
        lastParityReport.set(report);
        return ResponseEntity.ok(report);
    }

    @PostMapping("/cutover")
    public ResponseEntity<String> cutover() {
        ParityReport report = lastParityReport.get();
        if (report == null || !report.isClean()) {
            return ResponseEntity.badRequest()
                .body("Cutover blocked: parity report is not clean. Run /verify first.");
        }
        // Trigger cutover (feature flag flip, DNS change, etc.)
        return ResponseEntity.ok("Cutover initiated");
    }

    record MigrationStatus(long lastCopiedId, long rowsCopied, double rowsPerMin,
                           double estMinutesRemaining, boolean running) {}
}
```

**Security:** `@PreAuthorize("hasRole('ADMIN')")` on the class applies to all endpoints. `POST /cutover` is the most sensitive — could add an additional `@PreAuthorize("hasRole('SUPERADMIN')")`.

<details>
<summary>Exercise 5 — CDC vs Dual-Write decision matrix</summary>

| Criterion | CDC (Debezium) | Application Dual-Write |
|---|---|---|
| **(a) Handles deletes** | ✓ Yes — WAL records DELETE events; Debezium emits them | ✗ No by default — `DELETE` statements are often missed unless explicitly instrumented |
| **(b) Ordering guarantees** | ✓ Yes — WAL is strictly ordered; Debezium preserves WAL sequence | Partial — concurrent writes from multiple threads may arrive out-of-order at the shadow DB |
| **(c) Schema change compatibility** | ✗ Risky — Debezium schema evolution requires connector restart and schema history config | ✓ Better — application code controls what's written; schema changes are handled explicitly |
| **(d) Operational complexity** | High — requires Kafka cluster, Debezium connector, schema registry, Kafka Connect management | Low — just application code; no additional infrastructure |
| **(e) Latency** | ~200ms-1s (WAL → Debezium → Kafka → consumer) | <10ms (application writes synchronously or async) |

**One scenario where dual-write is the right choice despite CDC advantages:**

**Startup with no Kafka infrastructure:** A 5-person team migrating a 10-table monolith to a new schema has no Kafka cluster, no Ops team to manage connectors, and a 4-week timeline. CDC requires Kafka, Debezium connector configuration, schema registry, and monitoring. Dual-write requires adding 20 lines of code. The operational overhead of CDC is out of proportion to the problem size. For this migration: dual-write with a post-migration reconciliation job to handle any missed deletes is the correct choice.

**Staff-level phrasing:** "CDC wins on correctness (deletes, ordering) but costs Kafka infrastructure; dual-write wins on simplicity for teams without existing Kafka — the right choice depends on your infrastructure baseline and migration scope."

## 9. Summary / Flashcard

- **4-Phase online migration** (Shadow Write → Backfill → Verify → Cutover) achieves zero-downtime data migration regardless of dataset size; the maintenance window is reduced to a feature-flag flip lasting seconds.
- **Asynchronous shadow writes** using virtual threads prevent the shadow DB's latency (cold, untuned) from increasing user-facing response time; shadow failures are logged and reconciled in the Backfill phase.
- **Cursor-based backfill pagination** (`WHERE id > lastCopiedId ORDER BY id LIMIT 1000`) with 100ms throttle between chunks copies historical data at ~10k rows/sec while consuming only ~10% of legacy DB I/O capacity.
- **CDC (Debezium `PostgresConnector`) is architecturally superior to application dual-writing**: it handles deletes, guarantees WAL ordering, and requires zero application-code changes — but has higher operational complexity (Kafka + Debezium connector).
- **Pre-cutover parity check** samples N random rows from both databases and compares critical fields; `parityReport.isClean() == true` is the only gate that permits cutover — no schedule, no stakeholder approval substitutes for measured data equality.

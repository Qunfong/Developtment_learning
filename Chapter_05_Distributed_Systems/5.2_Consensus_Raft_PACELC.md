**Principal:** You're asking for **Consensus**, the hardest problem in distributed systems. To reach Principal level, we must master the **Raft Consensus Algorithm** and the **PACELC Theorem**. We move from "Manual Failover" to **Algorithmic Sovereignty**.

## 1. The Requirement: Quorum and Consistency


**The Problem:** In a distributed Ledger, we cannot have two leaders (Split-Brain). 
. **The Majority Law:** Consensus requires a **Quorum**. If you have 3 nodes, you need 2 to agree. 
. **The Result:** If you lose 2 nodes, the system stops to protect integrity.

## 2. Solution: The Raft Consensus Algorithm


**The Principal Architecture:** Raft is the standard for deterministic consensus.


### 2.1 The Election Handshake
If the leader stops sending "Heartbeats," the followers start an election.
. **Terms:** Every election starts a new monotonic "Term."
. **Safety:** A candidate only becomes leader if its log is at least as up-to-date as the majority.

## 3. The Law: PACELC (Beyond CAP)


The CAP theorem only describes systems during a failure. A Principal uses **PACELC** to describe the system *always*.


> [!abstract] The Physics: PACELC (If P, then AC, else LC)
> . **P (Partition):** In a network split, choose **A (Availability)** or **C (Consistency)**.
> . **E (Else - Normal):** In normal operation, choose **L (Latency)** or **C (Consistency)**.
> . **The Ledger Choice:** We choose **PC/EC** (Consistency always). A "Social Feed" is **PA/EL**.

## 4. Source Archaeology

Real Raft and consensus implementations to read:

**etcd/raft** — `go.etcd.io/etcd/raft/v3/raft.go`: `stepCandidate()` handles vote tallying; `quorum()` returns `(len(r.prs.Voters)+1)/2`; `becomeLeader()` appends a no-op entry to fence out stale reads. `raft.go:Step()` is the core state-machine dispatcher — every message type maps to a handler via a function table.

**Apache Ratis** — `org.apache.ratis.server.impl.RaftServerImpl`: `handleRequestVoteAsync()` checks `lastEntry.getIndex() >= candidate.lastLogIndex` (log completeness check); `ServerState.updateStableTerm()` persists the term to stable storage before responding to any RPC — a requirement from the Raft safety proof.

**CockroachDB Raft** — wraps `etcd/raft`; `pkg/kv/kvserver/replica_raft.go` `(*Replica).propose()` is the write path: it encodes the command, calls `r.mu.internalRaftGroup.Propose()`, then waits on a proposal channel. Linearizable reads use `ReadIndex` (raft.go `ReadOnly`) — the leader confirms its lease before serving, avoiding a full round-trip.

**Kafka KRaft** — `core/src/main/scala/kafka/raft/KafkaRaftClient.scala`: `handleVoteRequest()` rejects votes for terms the broker has already seen. The `LeaderEpoch` concept maps directly to Raft's `term`. `KafkaMetadataLog` is the Raft log implementation backed by `UnifiedLog`.

## 5. Code Lab

**BAD approach — manual failover with no quorum check:**

```java
// BAD: Promoting a replica without verifying it has the latest log
// This creates Split-Brain: old leader may still be accepting writes
public class NaiveFailover {
    private volatile String currentLeader = "node-1";

    // Called by ops team after detecting node-1 is unresponsive
    public void promoteReplica(String nodeId) {
        // No check: is node-2's log up-to-date?
        // No check: is node-1 actually dead or just slow?
        // No fencing: node-1 may still hold client connections!
        currentLeader = nodeId;
        System.out.println("Promoted " + nodeId + " to leader");
        // Result: Two leaders, two divergent logs, data loss inevitable.
```

**GOOD approach — Raft-style election with term fencing and quorum:**

```java
import java.util.Map;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.atomic.AtomicReference;

/**
 * Simplified Raft election mechanics.
 * Models the safety properties from the Raft paper (Ongaro & Ousterhout, 2014):
 * - A node votes for at most one candidate per term (Election Safety).
 * - A candidate wins only if its log is at least as complete as the majority (Log Matching).
 * - Term monotonicity: nodes reject all RPCs with stale terms.
 */
public class RaftNode {

    public enum State { FOLLOWER, CANDIDATE, LEADER }

    private final String nodeId;
    private final int    clusterSize;
    private final AtomicLong              currentTerm = new AtomicLong(0);
    private final AtomicReference<String> votedFor    = new AtomicReference<>(null);
    private final AtomicReference<State>  state       = new AtomicReference<>(State.FOLLOWER);
    private volatile long lastLogIndex = 0;
    private volatile long lastLogTerm  = 0;

    public RaftNode(String nodeId, int clusterSize) {
        this.nodeId = nodeId;
        this.clusterSize = clusterSize;
    }

    /** Simulate receiving a RequestVote RPC from a candidate. */
    public record VoteRequest(String candidateId, long term, long lastLogIndex, long lastLogTerm) {}
    public record VoteResponse(long term, boolean granted) {}

    public VoteResponse handleVoteRequest(VoteRequest req) {
        long myTerm = currentTerm.get();

        // Rule 1: Reject stale terms immediately (term monotonicity)
        if (req.term() < myTerm) {
            return new VoteResponse(myTerm, false);
        }

        // Rule 2: If we see a higher term, revert to follower
        if (req.term() > myTerm) {
            currentTerm.set(req.term());
            votedFor.set(null);
            state.set(State.FOLLOWER);
            myTerm = req.term();
        }

        String alreadyVoted = votedFor.get();
        boolean canVote = (alreadyVoted == null || alreadyVoted.equals(req.candidateId()));

        // Rule 3: Candidate's log must be at least as complete as ours (§5.4 of Raft paper)
        boolean logOk = (req.lastLogTerm() > lastLogTerm) ||
                        (req.lastLogTerm() == lastLogTerm && req.lastLogIndex() >= lastLogIndex);

        if (canVote && logOk) {
            votedFor.set(req.candidateId());
            return new VoteResponse(myTerm, true);
        }
        return new VoteResponse(myTerm, false);
    }

    /**
     * Start an election. Returns true if this node wins (quorum of votes received).
     * In real Raft this is async; synchronous here for clarity.
     */
    public boolean startElection(Set<RaftNode> peers) {
        long newTerm = currentTerm.incrementAndGet();
        state.set(State.CANDIDATE);
        votedFor.set(nodeId);  // vote for self

        int votes = 1;  // self-vote
        VoteRequest req = new VoteRequest(nodeId, newTerm, lastLogIndex, lastLogTerm);

        for (RaftNode peer : peers) {
            VoteResponse resp = peer.handleVoteRequest(req);
            if (resp.term() > newTerm) {
                // Someone has a higher term — step down
                currentTerm.set(resp.term());
                state.set(State.FOLLOWER);
                votedFor.set(null);
                return false;
            }
            if (resp.granted()) votes++;
        }

        int quorum = (clusterSize / 2) + 1;
        if (votes >= quorum) {
            state.set(State.LEADER);
            System.out.printf("[%s] Won election for term %d with %d/%d votes (quorum=%d)%n",
                nodeId, newTerm, votes, clusterSize, quorum);
            return true;
        }
        state.set(State.FOLLOWER);
        return false;
    }
}

// Demonstration
class RaftDemo {
    public static void main(String[] args) {
        int N = 5;
        var nodes = java.util.List.of(
            new RaftNode("node-1", N),
            new RaftNode("node-2", N),
            new RaftNode("node-3", N),
            new RaftNode("node-4", N),
            new RaftNode("node-5", N)
        );

        // node-1 starts election after leader (node-0) times out
        var peers = new java.util.HashSet<>(nodes.subList(1, 5));
        boolean won = nodes.get(0).startElection(peers);
        // Won with 5/5 votes — quorum of 3 required, gets all 5
        System.out.println("Election won: " + won);
    }
}
```

## 6. Production Lens

**Raft election latency** — etcd's default `heartbeat-interval` is 100 ms, `election-timeout` is 1,000 ms. After a leader crash, worst-case election takes `election-timeout + network RTT` ≈ 1,100 ms. In practice, etcd documentation cites typical re-election in 500 ms on a healthy LAN cluster.

**Read latency cost of linearizability** — CockroachDB `ReadIndex` (avoid full log round-trip): linearizable reads cost one `ReadIndex` RPC to the leader + network RTT ≈ 1–5 ms intra-region. Without `ReadIndex`, every read is a Raft-replicated no-op: adds 5–15 ms. Follower reads (non-linearizable) are available in ~0.2 ms but may serve stale data up to the replication lag.

**PACELC system classification:**

| System | P choice | E choice | Typical write latency |
|---|---|---|---|
| etcd | Consistency | Consistency | 5–15 ms (Raft RTT) |
| Cassandra (W=1) | Availability | Latency | <1 ms gossip |
| DynamoDB (eventual) | Availability | Latency | 1–5 ms |
| Spanner | Consistency | Consistency | 10–100 ms (TrueTime wait) |
| CockroachDB | Consistency | Consistency | 5–20 ms |

<details>
<summary>Exercise 1 — 5-node cluster loses 2 nodes: quorum proof</summary>

**Which partition can elect a leader:**

Quorum = (N/2)+1 = (5/2)+1 = **3**.

- Partition with 3 nodes: 3 ≥ 3 → **can elect a leader, may accept writes**
- Partition with 2 nodes: 2 < 3 → **cannot reach quorum, must go silent**

**Why (N/2)+1 is the minimum safe threshold:**

Any two quorums of size `(N/2)+1` from an N-node cluster must share at least one common node (pigeonhole: 3+3=6 > 5, so overlap ≥ 1). This shared node guarantees that any two elected leaders in different terms have seen a common log entry — making it impossible for two leaders to exist simultaneously with divergent logs.

```
N=5, quorum=3:
Partition A (nodes 1,2,3): 3/3 = quorum met → ACTIVE
Partition B (nodes 4,5):   2/3 = quorum not met → SILENT

If both could elect: Term T leader from {1,2,3} and Term T' leader from {4,5}
→ No shared node → divergent logs → split-brain
With quorum requirement: {4,5} never elects → split-brain impossible
```

**Staff-level phrasing:** "The quorum intersection property is the mathematical foundation of Raft safety: any two majorities in a 5-node cluster share at least one node, so no two leaders can ever be simultaneously elected with mutually exclusive log histories."

<summary>Exercise 2 — Stale leader reads and ReadIndex</summary>

**The stale leader read problem:**

A newly elected Raft leader wins its election at term T. It now has authority, but its state machine has not yet applied all log entries committed in term T-1 by the previous leader. If a client reads immediately after election, the new leader may return a value that reflects a state *before* the final committed writes of the previous term.

Example: previous leader committed `balance=1000` to a majority at log index 99. The new leader wins election but has only applied up to log index 97. A balance read returns `800` — stale.

**Why this is surprising:** the leader IS authoritative (it won a legitimate election), but "authoritative" only means it will eventually have the correct value — not that it has it *right now*.

**What ReadIndex does:**
1. Client issues a read request to the leader.
2. Leader records the current commit index (e.g., 99) as the "read index."
3. Leader sends a heartbeat broadcast to confirm it still holds quorum (verifying it hasn't been deposed by a new term it doesn't know about).
4. Leader waits until its applied index ≥ read index.
5. Only then does it serve the read.

This guarantees linearizability: the read observes all writes that completed before it started.

**ReadIndex cost:** one heartbeat RTT per read (~1–5 ms intra-region). Much cheaper than a full log round-trip (Raft no-op write), but not free — the trade-off vs follower reads.

**Staff-level phrasing:** "A Raft leader can serve stale reads immediately after election because its state machine hasn't caught up to its commit index yet — ReadIndex adds one quorum confirmation per read to guarantee the leader's applied state reflects all prior commits."

</details>

<details>
<summary>Exercise 3 — PACELC classification: MongoDB, Redis Sentinel, ZooKeeper</summary>

**(a) MongoDB with `w:majority, readConcern:majority` → PC/EC**

- **P (Partition):** With `w:majority`, writes require acknowledgment from a majority of replica set members. During a partition, the minority side cannot reach majority — it rejects writes (chooses **C** over **A**).
- **E (Else — normal operation):** With `readConcern:majority`, reads return only majority-committed data, never a write that might be rolled back. This adds ~1 majority-roundtrip latency per read — **C** over **L**.
- **Classification:** **PC/EC** — always consistent, at the cost of availability during partitions and extra latency during normal operation.

**(b) Redis Sentinel → PA/EL**

- **P (Partition):** Redis Sentinel promotes a replica when the master is unreachable from the majority of sentinels. Async replication means the promoted replica may be missing the last few writes — data loss is possible. Sentinel favors **A** (cluster keeps operating) over **C** (no write loss guarantee).
- **E (Else — normal operation):** Reads from replicas are async and may serve stale data (replication lag = 0–100 ms). Replica reads favor **L** over **C**.
- **Classification:** **PA/EL** — high availability at the cost of possible data loss on failover and stale replica reads during normal operation.

**(c) Apache ZooKeeper → PC/EC**

- **P (Partition):** ZooKeeper uses a quorum-based ZAB protocol. Minority partitions cannot elect a leader and reject all writes — chooses **C** over **A**.
- **E (Else — normal operation):** All writes go through the leader and are synchronously replicated to a quorum before ACK. All reads go to the local ZNode state, but `sync()` can be called to force linearizability. Default reads may serve slightly stale data — but ZooKeeper's design intent is consistency. **C** over **L**.
- **Classification:** **PC/EC** (with the caveat that local reads without `sync()` are technically eventual, but ZooKeeper's use cases — configuration, leader election — treat this as acceptable bounded staleness).

**Staff-level phrasing:** "PACELC forces you to answer two questions: what do you sacrifice during a partition, AND what do you sacrifice every day in normal operation — most systems that claim to be 'consistent' are actually EC (choose latency over consistency in the normal path) when you read the fine print."

</details>

<summary>Exercise 4 — Coding: AppendEntries heartbeat handler</summary>

```java
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class RaftNode {

    public enum State { FOLLOWER, CANDIDATE, LEADER }

    private final String nodeId;
    private final int    clusterSize;
    private final AtomicLong              currentTerm = new AtomicLong(0);
    private final AtomicReference<String> votedFor    = new AtomicReference<>(null);
    private final AtomicReference<State>  state       = new AtomicReference<>(State.FOLLOWER);
    private volatile long lastLogIndex = 0;
    private volatile long lastLogTerm  = 0;

    // Election timer — reset on valid heartbeat
    private volatile long lastHeartbeatMs = System.currentTimeMillis();
    private static final long ELECTION_TIMEOUT_MS = 1_000;

    public RaftNode(String nodeId, int clusterSize) {
        this.nodeId = nodeId;
        this.clusterSize = clusterSize;
    }

    public record AppendEntriesRequest(long term, String leaderId) {}
    public record AppendEntriesResponse(long term, boolean success) {}

    public AppendEntriesResponse handleAppendEntries(AppendEntriesRequest req) {
        long myTerm = currentTerm.get();

        // (a) Reject RPCs with stale terms
        if (req.term() < myTerm) {
            return new AppendEntriesResponse(myTerm, false);
        }

        // (c) Update currentTerm if leader has a higher term
        if (req.term() > myTerm) {
            currentTerm.set(req.term());
            votedFor.set(null);
            state.set(State.FOLLOWER);
        }

        // (b) Reset election timer on valid heartbeat
        lastHeartbeatMs = System.currentTimeMillis();
        state.set(State.FOLLOWER); // demote candidate/leader if we see a valid leader

        return new AppendEntriesResponse(currentTerm.get(), true);
    }

    /** Returns true if the election timer has fired (no heartbeat received in time). */
    public boolean electionTimerFired() {
        return System.currentTimeMillis() - lastHeartbeatMs > ELECTION_TIMEOUT_MS;
    }

    // --- VoteRequest handling from the original code (unchanged) ---
    public record VoteRequest(String candidateId, long term, long lastLogIndex, long lastLogTerm) {}
    public record VoteResponse(long term, boolean granted) {}

    public VoteResponse handleVoteRequest(VoteRequest req) {
        long myTerm = currentTerm.get();
        if (req.term() < myTerm) return new VoteResponse(myTerm, false);
        if (req.term() > myTerm) {
            currentTerm.set(req.term());
            votedFor.set(null);
            state.set(State.FOLLOWER);
            myTerm = req.term();
        }
        String alreadyVoted = votedFor.get();
        boolean canVote = (alreadyVoted == null || alreadyVoted.equals(req.candidateId()));
        boolean logOk = (req.lastLogTerm() > lastLogTerm) ||
                        (req.lastLogTerm() == lastLogTerm && req.lastLogIndex() >= lastLogIndex);
        if (canVote && logOk) {
            votedFor.set(req.candidateId());
            return new VoteResponse(myTerm, true);
        }
        return new VoteResponse(myTerm, false);
    }
}
```

**JUnit 5 test — follower does NOT start election while receiving heartbeats:**
```java
@Test
void followerDoesNotStartElectionWhileReceivingHeartbeats() throws InterruptedException {
    RaftNode follower = new RaftNode("follower", 3);
    RaftNode leader = new RaftNode("leader", 3);

    // Send heartbeats every 100ms for 500ms (election timeout is 1000ms)
    ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
    scheduler.scheduleAtFixedRate(() -> {
        follower.handleAppendEntries(
                new RaftNode.AppendEntriesRequest(1L, "leader"));
    }, 0, 100, TimeUnit.MILLISECONDS);

    Thread.sleep(500); // wait 500ms — less than election timeout of 1000ms
    scheduler.shutdown();

    assertThat(follower.electionTimerFired()).isFalse();
    assertThat(follower.getState()).isEqualTo(RaftNode.State.FOLLOWER);
}

@Test
void followerStartsElectionAfterHeartbeatStop() throws InterruptedException {
    RaftNode follower = new RaftNode("follower", 3);

    // No heartbeats sent — wait for election timeout
    Thread.sleep(1_200);

    assertThat(follower.electionTimerFired()).isTrue();
}
```

**Why this works:** `lastHeartbeatMs` is updated atomically on each valid heartbeat. The `electionTimerFired()` method computes elapsed time since last heartbeat — if heartbeats arrive every 100 ms, the elapsed time never exceeds 1,000 ms and the election timer never fires.

**Common mistake:** Using `System.nanoTime()` for the heartbeat timer but `System.currentTimeMillis()` for comparison — mixing time sources causes spurious election timeouts on systems with clock adjustments.

<details>
<summary>Exercise 5 — Follower reads: consistency level and Ledger applicability</summary>

**Consistency level of follower reads:**

`AS OF SYSTEM TIME follower_read_timestamp()` in CockroachDB returns data as of a "closed timestamp" — a timestamp guaranteed to have no in-flight writes at or before it. This provides **bounded staleness consistency**: data may be up to the closed timestamp lag behind the leader (typically ~4.8 seconds in CockroachDB's default configuration), but it is never an uncommitted speculative value.

This is stronger than eventual consistency (which has no staleness bound) but weaker than linearizability (which reflects all completed writes as of query execution).

**Acceptable Ledger use cases:**
- **Historical balance reports:** "What was account X's balance yesterday?" — bounded staleness of 5 seconds is irrelevant for daily reports.
- **Audit log queries:** Querying past transactions for compliance — data is immutable after commit, so any bounded-staleness read returns the correct historical answer.
- **Analytics dashboards:** Aggregate metrics (total volume per hour, top accounts by balance) — 5-second staleness is invisible to dashboard users.
- **Read replicas for search/export:** Bulk exports, BI tools — do not need current balance, only recent history.

**NOT acceptable for Ledger:**
- **Pre-transfer balance check:** Before executing a transfer, the debit source balance must be current. A 5-second stale read could show a balance that was spent 3 seconds ago — double-spend vector.
- **Real-time fraud detection:** Fraud signals depend on the most recent transaction sequence — bounded staleness breaks the "happened before" guarantee needed for fraud detection logic.

**Staff-level phrasing:** "Follower reads trade linearizability for latency — they are safe for any query where correctness is bounded by time (reports, history) and dangerous for any query where correctness is bounded by ordering (pre-condition checks, fraud detection)."

</details>

## 8. Summary / Flashcard

- Raft guarantees safety through term monotonicity and log completeness: a candidate wins only if a quorum confirms it has the most complete log, making split-brain physically impossible.
- A quorum of `(N/2)+1` is the minimum overlap required: any two quorums share at least one node, so no two leaders can ever be simultaneously elected in different terms.
- CAP describes only partition behavior; PACELC adds the normal-operation trade-off: in the absence of partitions, every distributed system trades latency for consistency on every write.
- etcd and CockroachDB are PC/EC (always consistent); Cassandra with W=1 is PA/EL (always available); DynamoDB can be configured on either end of the spectrum.
- Linearizable reads via Raft `ReadIndex` cost one leader RTT (~5 ms intra-region); follower reads trade this latency for potential staleness bounded by replication lag.

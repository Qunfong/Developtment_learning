## The Critical Dialogue


**Student:** We have a 5-node cluster. A network cable is cut, and the cluster splits into two groups (3 and 2). Both groups think the other is dead. Can they both continue processing orders?


**Principal:** If they both continue, you have committed **Financial Suicide**. This is the **Split-Brain Paradox**. If two disconnected groups both think they are the "Authority," they will diverge, and you can never merge their truth again. To reach Principal level, we must master the **Physics of the Partition**. We move from "Hoping for Connectivity" to **Enforcing Quorum Isolation**.

## 1. The Requirement: Quorum or Silence


**The Problem:** In a partition, a system must choose between **Availability** and **Consistency**.


### 1.1 The Majority Law
A Principal knows that in a partition, only the group with a **Strict Majority** is allowed to live.
. **The Math:** If $N=5$, the majority is 3.
. **The Result:** The group of 3 continues. The group of 2 MUST instantly stop and enter "Safe Mode."

## 2. Solution: The Distributed Lease


**The Principal Architecture:** We use a high-frequency **Heartbeat** and a **Lease**.


. **Mechanism:** The Leader must prove its "Health" to the majority every 100ms.
. **The Lease:** If the Leader cannot reach a majority, its authority expires instantly. This prevents a "Zombie Leader" from accepting one last corrupt transaction.

## 4. Source Archaeology

Real partition detection and fencing implementations:

**etcd lease & fencing** — `server/etcd.go` `(*EtcdServer).LeaseGrant()` stores leases in the `lessor` (`server/lease/lessor.go`). `Lessor.Renew(id LeaseID)` returns `ErrLeaseNotFound` if the lease expired. Fencing tokens are implemented via `server/etcd.go` `(*EtcdServer).LeaseTimeToLive()` — callers include the revision in every write and the `MVCC` store rejects writes with stale revisions.

**Cassandra failure detector** — `org.apache.cassandra.gms.FailureDetector` implements the Phi-Accrual failure detector. `FailureDetector.interpret(InetAddressAndPort ep)` computes `phi = -log10(P_later(t))` from the inter-arrival time distribution. A configurable `phi_convict_threshold` (default 8.0) triggers gossip state change to `DEAD` — avoids binary up/down and adapts to network jitter.

**ZooKeeper epoch fencing** — `zookeeper-server/src/main/java/org/apache/zookeeper/server/quorum/Leader.java`: `Leader.propose()` attaches a `zxid` (64-bit: `epoch << 32 | counter`). Any `NEWLEADER` packet carries the new epoch. Followers reject `PROPOSAL` packets from leaders with a stale epoch — this is the ZooKeeper fencing mechanism preventing zombie leaders.

**PostgreSQL Patroni** — `patroni/ha.py` `Ha.acquire_lock()` uses etcd `Lease` as a distributed lock with TTL. If `Patroni.ha.is_leader_and_lock_owner()` returns false, the node immediately demotes itself and enters standby mode. The TTL is `ttl=30s` by default — a leader that loses connectivity demotes after 30 s.

## 5. Code Lab

**BAD approach — fixed timeout with no quorum awareness:**

```java
// BAD: Single timeout does not distinguish transient spike from permanent partition
// A 3,000ms timeout is too long for a financial system (data diverges during window)
// and too short for a busy GC pause (false positives causing unnecessary failovers)
public class NaiveClusterNode {
    private static final long TIMEOUT_MS = 3_000;
    private long lastHeartbeatMs = System.currentTimeMillis();

    public void onHeartbeat() {
        lastHeartbeatMs = System.currentTimeMillis();
    }

    public boolean isLeaderAlive() {
        // WRONG: Binary alive/dead — doesn't account for GC pause, network jitter
        return System.currentTimeMillis() - lastHeartbeatMs < TIMEOUT_MS;
    }

    public void processWrite(Order order) {
        // WRONG: No quorum check — processes writes even if only 1/5 nodes reachable
        if (!isLeaderAlive()) {
            throw new RuntimeException("Leader dead, try later");
        }
        // Data written to this node diverges from the partition we can't see
        localDb.write(order);
    }
}
```

**GOOD approach — Phi-Accrual failure detector with fencing token:**

```java
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.concurrent.atomic.AtomicLong;

/**
 * Phi-Accrual failure detector modeled after Cassandra's FailureDetector.
 *
 * Instead of binary alive/dead, computes a suspicion level (phi).
 * phi < 8  → node is healthy
 * phi >= 8 → node is suspected dead (configurable threshold)
 *
 * This adapts to network jitter: a node under GC pressure (late heartbeat)
 * only slightly raises phi, not triggering an unnecessary failover.
 */
public class PhiAccrualDetector {

    private static final int    WINDOW_SIZE     = 100;   // rolling sample window
    private static final double CONVICT_THRESHOLD = 8.0; // Cassandra default

    private final Deque<Long> intervals  = new ArrayDeque<>(WINDOW_SIZE);
    private volatile long     lastArrival = 0;

    /** Call this every time a heartbeat arrives from the monitored node. */
    public synchronized void heartbeat() {
        long now = System.currentTimeMillis();
        if (lastArrival > 0) {
            long interval = now - lastArrival;
            intervals.addLast(interval);
            if (intervals.size() > WINDOW_SIZE) intervals.pollFirst();
        }
        lastArrival = now;
    }

    /**
     * Returns the current suspicion level (phi).
     * phi >= CONVICT_THRESHOLD → treat node as down.
     */
    public synchronized double phi() {
        if (intervals.isEmpty() || lastArrival == 0) return 0.0;

        long elapsed = System.currentTimeMillis() - lastArrival;
        double mean  = intervals.stream().mapToLong(Long::longValue).average().orElse(1000.0);
        double stddev = stddev(mean);

        // Exponential distribution approximation (CDF = 1 - e^(-elapsed/mean))
        double p = 1.0 - Math.exp(-elapsed / Math.max(mean, 1));
        // phi = -log10(1 - CDF) — higher phi means more suspicion
        return -Math.log10(Math.max(1.0 - p, 1e-15));
    }

    public boolean isSuspected() {
        return phi() >= CONVICT_THRESHOLD;
    }

    private double stddev(double mean) {
        double variance = intervals.stream()
            .mapToDouble(i -> Math.pow(i - mean, 2)).average().orElse(0);
        return Math.sqrt(variance);
    }
}

/**
 * Partition-aware write gate with fencing token.
 *
 * The fencing token is a monotonically increasing epoch number stored in etcd.
 * Any write to the DB must include the current token; the DB rejects writes
 * with a lower token (stale leader writes after a network healed).
 */
public class PartitionAwareWriter {

    private final PhiAccrualDetector[] peerDetectors;
    private final int                  totalNodes;
    private final AtomicLong           fencingToken = new AtomicLong(0);

    public PartitionAwareWriter(int totalNodes) {
        this.totalNodes    = totalNodes;
        this.peerDetectors = new PhiAccrualDetector[totalNodes - 1];
        for (int i = 0; i < peerDetectors.length; i++) {
            peerDetectors[i] = new PhiAccrualDetector();
        }
    }

    /** Call on every incoming heartbeat from peer i. */
    public void onPeerHeartbeat(int peerIndex) {
        peerDetectors[peerIndex].heartbeat();
    }

    /** Returns true only if quorum of peers are healthy. */
    public boolean hasQuorum() {
        int required = (totalNodes / 2) + 1;  // e.g. 3 for N=5
        int healthy  = 1;  // count self
        for (PhiAccrualDetector d : peerDetectors) {
            if (!d.isSuspected()) healthy++;
        }
        return healthy >= required;
    }

    public void write(Order order, LedgerDB db) {
        if (!hasQuorum()) {
            // Partition detected — refuse writes rather than risk split-brain
            throw new ClusterPartitionException(
                "Quorum lost. Refusing write to prevent split-brain. " +
                "Fencing token: " + fencingToken.get());
        }
        long token = fencingToken.get();
        // The DB rejects writes where token < its stored epoch
        db.writeWithFencingToken(order, token);
    }

    record Order(String id, long amount) {}
    interface LedgerDB { void writeWithFencingToken(Order o, long token); }
    static class ClusterPartitionException extends RuntimeException {
        ClusterPartitionException(String msg) { super(msg); }
    }
}
```

## 6. Production Lens

**Split-brain recovery cost** — Netflix's Chaos Monkey experiments show that a split-brain in a Cassandra cluster (N=6, even number) can diverge for up to 30 seconds before automatic repair. Manual reconciliation of 48 hours of divergent writes at 50,000 writes/sec = ~8.6 billion conflicting rows. A quorum-fenced system (N=5) avoids this entirely: minority partition serves zero writes.

**Phi-Accrual detection latency** — Cassandra's failure detector with a 1-second heartbeat interval and phi_threshold=8 detects a dead node within 2–4 heartbeat intervals (2–4 seconds) on a healthy LAN. On a jittery WAN, the adaptive distribution raises the mean, so the same 8.0 threshold requires 8–12 seconds — intentionally avoiding false positives during GC pauses (typical GC pause: 200–500 ms).

**etcd lease TTL** — Typical production etcd configurations use `lease-ttl=5s`, `heartbeat-interval=500ms`. If a leader loses connectivity, its lease expires after 5 s. During those 5 s, the leader rejects all new writes (no quorum) but may serve stale reads. After lease expiry, a new election completes in ~1,500 ms (election-timeout + RTT). Total unavailability window: ~6.5 s for a network partition event.

<summary>Exercise 1 — N=4 cluster: availability implication and why N=4 is worse than N=3</summary>

**The 2/4 split:**

Quorum for N=4 = (4/2)+1 = **3**. A 2/4 split means both partitions have 2 nodes — neither can reach quorum of 3. **Both partitions go silent.** Total write availability = 0%.

**Compare to N=3:**

Quorum for N=3 = (3/2)+1 = **2**. A 2/1 split means one partition has 2 nodes (meets quorum) and one has 1 node (cannot). The majority side continues — write availability = ~67% of nodes.

| Cluster | Quorum | Split result | Write availability |
|---|---|---|---|
| N=3 | 2 | 2+1 split → majority continues | Partial (majority side) |
| N=4 | 3 | 2+2 split → both silent | Zero |
| N=5 | 3 | 3+2 split → majority continues | Partial (majority side) |

**Why N=4 is strictly worse than N=3:**

Both N=3 and N=4 can tolerate at most **1 node failure** (f=1). To tolerate f failures requires N=2f+1 nodes. N=4 satisfies 2(1)+1=3 ≤ 4, so it can tolerate f=1 — same as N=3. But:
- N=3 under a 2/1 split: one side writes, system stays live.
- N=4 under a 2/2 split: neither side writes, system is fully unavailable.

N=4 adds one node, increases the quorum requirement from 2 to 3, and creates a symmetric split scenario that N=3 avoids entirely. The operational cost is higher, fault tolerance is the same, and the worst-case partition scenario is worse.

**Practical rule:** Always deploy odd-numbered clusters (3, 5, 7). An even-node cluster wastes one machine's cost on *no additional fault tolerance* while creating the symmetric-split dead zone.

**Staff-level phrasing:** "N=4 is the worst cluster size because it provides identical fault tolerance to N=3 (f=1) while adding a catastrophic 2/2 symmetric split scenario — always deploy odd-numbered clusters, and treat N=4 as a misconfiguration."

<summary>Exercise 2 — Zombie leader: fencing tokens preventing silent data corruption</summary>

**The zombie leader scenario:**

```
T=0:  Old leader (Leader-1, epoch=1) loses network connectivity.
T=0→5s: Leader-1 cannot reach peers, but its lease hasn't expired yet.
T=2s: Leader-1 accepts write W: {key=balance, value=1000, epoch=1}
      DB stores: {balance: 1000, epoch: 1}
T=5s: Lease expires. New election runs. Leader-2 elected (epoch=2).
T=6s: Leader-2 accepts write W': {key=balance, value=2000, epoch=2}
T=7s: Network heals. Leader-1's write W tries to commit/replicate.
```

**Without fencing tokens:**
The storage layer sees two writes for `balance`: one with value=1000, one with value=2000. If it uses "last write wins" by timestamp, the outcome depends on clock skew (Chapter 5.1) — either write could survive. Data corruption is non-deterministic and silent.

**With fencing tokens (monotonic epoch numbers):**

The DB schema includes a `min_epoch` constraint: `REJECT any write where write.epoch < current_stored_epoch`.

```java
// Storage layer enforces fencing
public void writeWithFencingToken(String key, Object value, long epoch) {
    long storedEpoch = epochStore.get(key);
    if (epoch < storedEpoch) {
        // Stale write from zombie leader — rejected silently
        throw new StaleEpochException("Rejected write epoch=" + epoch + ", stored=" + storedEpoch);
    }
    // epoch >= storedEpoch: accept write and update stored epoch
    epochStore.put(key, epoch);
    dataStore.put(key, value);
}
```

At T=7s: Leader-1 tries to write `{balance: 1000, epoch: 1}`. The DB has `stored_epoch=2` (from Leader-2's write at T=6s). Write rejected: `1 < 2`. Leader-2's write `{balance: 2000, epoch: 2}` survives — correct behavior.

**Where W's data goes:** It is rejected at the storage layer. The in-memory value on Leader-1 is discarded. If Leader-1 restores connectivity and learns epoch=2, it must re-apply any commands from Leader-2's term to catch up.

**Key property:** Fencing tokens make zombie writes physically impossible to commit — the storage layer is the enforcement point, not the application. Application-level checks are not sufficient because a zombie leader might bypass them.

**Staff-level phrasing:** "Fencing tokens move the split-brain enforcement point from the application (which the zombie may bypass) to the storage layer (which the zombie cannot bypass) — the epoch check in the DB is the hardware barrier, not the application lease check."

</details>

<summary>Exercise 3 — Phi-Accrual: does an 800ms GC pause trigger false conviction?</summary>

**Given:**
- Heartbeat interval mean = 1,000 ms
- GC pause = 800 ms (no heartbeat for 800 ms)
- phi_convict_threshold = 8.0

**Phi calculation (exponential distribution approximation):**

```
p(elapsed) = 1 - exp(-elapsed / mean)
           = 1 - exp(-800 / 1000)
           = 1 - exp(-0.8)
           = 1 - 0.4493
           = 0.5507

phi = -log₁₀(1 - p)
    = -log₁₀(1 - 0.5507)
    = -log₁₀(0.4493)
    = -(-0.3474)
    = 0.347
```

**phi = 0.347 << 8.0 threshold → NO false-positive conviction.**

**How long until phi reaches 8.0?**

```
phi = 8  →  -log₁₀(1 - p) = 8
         →  1 - p = 10⁻⁸
         →  p = 1 - 10⁻⁸ ≈ 0.99999999

1 - exp(-elapsed/1000) = 1 - 10⁻⁸
exp(-elapsed/1000) = 10⁻⁸
-elapsed/1000 = ln(10⁻⁸) = -8 × ln(10) = -18.42
elapsed = 18,420 ms ≈ 18.4 seconds
```

A node must be completely silent for **~18 seconds** (18x the mean heartbeat interval) before the Phi-Accrual detector convicts it. An 800 ms GC pause produces phi=0.35 — barely a blip.

**Why this matters:** A fixed 1,500 ms timeout would fire a false positive during the 800 ms GC pause (800 ms > any threshold set below the pause duration). Phi-Accrual's continuous distribution naturally absorbs GC jitter without triggering unnecessary failovers.

**Staff-level phrasing:** "Phi-Accrual encodes 'how surprising is this silence?' rather than 'has a fixed deadline passed?' — an 800ms GC pause produces phi≈0.35 when the mean is 1,000ms, which is far below the conviction threshold, precisely because the detector knows single-interval delays are statistically normal."

</details>

<summary>Exercise 4 — Coding: degradedReadMode() with stale reads during partition</summary>

```java
import java.util.concurrent.atomic.AtomicReference;

public class PartitionAwareWriter {

    private final PhiAccrualDetector[] peerDetectors;
    private final int                  totalNodes;
    private final AtomicLong           fencingToken = new AtomicLong(0);

    // Track last committed value for stale reads during partition
    private final AtomicReference<Object> lastCommittedValue = new AtomicReference<>(null);

    public record ReadResult<T>(T value, boolean stale) {}

    public PartitionAwareWriter(int totalNodes) {
        this.totalNodes    = totalNodes;
        this.peerDetectors = new PhiAccrualDetector[totalNodes - 1];
        for (int i = 0; i < peerDetectors.length; i++) {
            peerDetectors[i] = new PhiAccrualDetector();
        }
    }

    public void onPeerHeartbeat(int peerIndex) {
        peerDetectors[peerIndex].heartbeat();
    }

    public boolean hasQuorum() {
        int required = (totalNodes / 2) + 1;
        int healthy  = 1;
        for (PhiAccrualDetector d : peerDetectors) {
            if (!d.isSuspected()) healthy++;
        }
        return healthy >= required;
    }

    /** Write path: requires quorum — rejects writes during partition */
    public void write(Order order, LedgerDB db) {
        if (!hasQuorum()) {
            throw new ClusterPartitionException(
                "Quorum lost. Refusing write. Fencing token: " + fencingToken.get());
        }
        db.writeWithFencingToken(order, fencingToken.get());
        lastCommittedValue.set(order); // track for stale reads
    }

    /**
     * Read path during partition: returns last committed value with StalenessWarning.
     * Models Cassandra LOCAL_ONE behavior — reads succeed but may be stale.
     */
    @SuppressWarnings("unchecked")
    public <T> ReadResult<T> degradedRead(LedgerDB db) {
        if (hasQuorum()) {
            // Full quorum: serve authoritative read from DB
            T value = (T) db.read();
            lastCommittedValue.set(value);
            return new ReadResult<>(value, false);
        }
        // Quorum lost: serve last known committed value with stale flag
        T staleValue = (T) lastCommittedValue.get();
        return new ReadResult<>(staleValue, true); // caller must handle StalenessWarning
    }

    record Order(String id, long amount) {}
    interface LedgerDB {
        void writeWithFencingToken(Order o, long token);
        Object read();
    }
    static class ClusterPartitionException extends RuntimeException {
        ClusterPartitionException(String msg) { super(msg); }
    }
}
```

**Test: writes rejected, reads succeed with stale flag when 2/5 peers are healthy:**
```java
@Test
void writesRejectedButReadsSucceedWithStaleFlagWhenQuorumLost() {
    int N = 5;
    PartitionAwareWriter writer = new PartitionAwareWriter(N);

    // Simulate 2 healthy peers (nodes 0 and 1) — total 3 nodes (self + 2 peers) = quorum met
    writer.onPeerHeartbeat(0);
    writer.onPeerHeartbeat(1);
    // Nodes 2, 3 never send heartbeats — they will be suspected after phi > 8

    // Seed a committed value via write while quorum is healthy
    LedgerDB mockDb = mock(LedgerDB.class);
    when(mockDb.read()).thenReturn(new Order("order-1", 500L));
    writer.write(new Order("order-1", 500L), mockDb);

    // Now simulate partition: only 2 peers healthy (below quorum of 3)
    // Don't send more heartbeats — peerDetectors[0] and [1] will timeout after 18s
    // For test: directly set suspected state by using a test-friendly accessor
    // (In practice: wait for phi > 8 or inject mock detectors)

    // After partition: reads return stale value with flag
    PartitionAwareWriter.ReadResult<Order> result = writer.degradedRead(mockDb);
    assertThat(result.stale()).isTrue();
    assertThat(result.value()).isNotNull();

    // After partition: writes are rejected
    assertThatThrownBy(() -> writer.write(new Order("order-2", 300L), mockDb))
            .isInstanceOf(PartitionAwareWriter.ClusterPartitionException.class);
}
```

**Why this works:** `lastCommittedValue` is updated on every successful write (which requires quorum). When quorum is lost, the read path falls back to this cached value and sets `stale=true`. The caller (application layer) must check the stale flag and either warn the user or reject the request based on business requirements (balance check for transfer → reject if stale; read-only dashboard → accept with warning).

**Common mistake:** Serving `null` from `degradedRead()` when no write has occurred yet — add a `NoCommittedValueException` for the case where `lastCommittedValue == null` (node has never processed a write in its lifetime).

<summary>Exercise 5 — TrueTime + Paxos leases vs fixed-TTL leases</summary>

**The fixed-TTL lease problem:**

A Paxos leader is granted a lease expiring at `T_expiry = T_grant + lease_duration`. To serve reads without a round-trip, the leader checks: `wall_clock_now < T_expiry`. But wall clocks can drift — if the leader's clock is fast by ε ms, it may believe `now = T_expiry - 1ms` when the actual time is `T_expiry + ε - 1ms` (past expiry). A new leader could be elected with an overlapping lease window, creating a zombie read.

**How TrueTime fixes this:**

TrueTime provides a `now()` method that returns an interval `[earliest, latest]` with a guaranteed clock error bound ε (≈7ms in Google data centers). The leader must satisfy:

```
TrueTime.now().earliest > lease_expiry_of_previous_leader
```

This means: "I know with certainty that now is after the old lease expired." To serve a linearizable read, the current leader waits until `TrueTime.now().earliest > its own read timestamp + ε` before serving — this ensures no transaction with an earlier timestamp could still be in-flight.

**The commit-wait mechanism:**
```
Write commits at timestamp T_commit = TrueTime.now().latest
Leader waits until TrueTime.now().earliest > T_commit (i.e., ε ms of wall time)
Only then serves the read — guaranteeing the external observer sees the write
```

**Guarantees TrueTime provides that fixed-TTL cannot:**

1. **Uncertainty-aware safety:** TrueTime's `[earliest, latest]` bracket embeds the clock error into the protocol. A fixed-TTL lease assumes the clock is accurate — a wrong assumption on any node.

2. **No false zombie detection:** With TrueTime, if `latest < lease_expiry`, the leader knows with certainty its lease is still valid. With a fixed clock, "valid" is an approximation.

3. **External consistency:** TrueTime enables Spanner's external consistency guarantee: if transaction T1 commits before T2 starts (in real time), then T1's timestamp < T2's timestamp — without requiring NTP accuracy, only TrueTime's bounded error.

**Why fixed-TTL leases cannot provide this:** A fixed-TTL lease provides safety only if clock drift is zero. In practice, NTP synchronizes to within ±10–100 ms. The probability of two leaders both believing they hold valid leases simultaneously (due to clock skew) is non-zero. TrueTime eliminates this probability class entirely by making the uncertainty explicit in the API.

**Staff-level phrasing:** "TrueTime replaces the assumption 'my clock is correct' with the guarantee 'my clock error is bounded by ε' — this transforms an approximate safety property (fixed-TTL leases) into a provably correct one, at the cost of a few milliseconds of commit-wait per transaction."

</details>

## 8. Summary / Flashcard

- In a partition, only the group with a strict majority `(N/2)+1` may accept writes; the minority must immediately stop and enter read-only or silent mode to prevent split-brain data divergence.
- An even-node cluster (N=4) is strictly less partition-tolerant than an odd-node cluster (N=5): at N=4, a 2/2 split leaves both sides unable to reach quorum, causing total unavailability instead of degraded but correct operation.
- Fencing tokens (monotonic epoch numbers stored in etcd or ZooKeeper) prevent zombie leaders: the storage layer rejects any write carrying a stale epoch, making split-brain writes physically impossible even after lease expiry.
- The Phi-Accrual failure detector avoids binary up/down decisions by modeling the heartbeat inter-arrival distribution; the adaptive phi threshold prevents false positives during GC pauses while still detecting permanent partitions within 2–4 heartbeat intervals.
- A Raft leader that cannot reach quorum must stop accepting writes immediately — not after a timeout — because every millisecond it continues writing is a millisecond of data that must be thrown away when the new leader is elected.

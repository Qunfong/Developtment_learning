## 3. Critical Dialogue

**Exchange 1 — "Retry is just a loop, right?"**

> **Student:** I added a `for (int i = 0; i < 3; i++)` loop that catches the exception and sleeps 500 ms between attempts. That's retry done, isn't it?

> **Expert:** You've written the most dangerous form of retry that exists. When 200 pods all hit the same downstream service, all catch the same timeout at nearly the same instant, and all sleep exactly 500 ms — what happens after that 500 ms?

> **Student:** They all retry at the same time...

> **Expert:** Exactly. You just recreated the original load spike, and now you've compounded it: the downstream service is still recovering, but it receives a fresh coordinated wave every 500 ms until it dies completely. Fixed sleep is not retry engineering; it's a denial-of-service timer. The fix is randomised delay — jitter — which we'll derive mathematically.

---

**Exchange 2 — "Exponential backoff should be enough"**

> **Student:** Fine, I'll use exponential backoff: `delay = 100 * 2^attempt`. That spreads retries out over time.

> **Expert:** It spreads *one client's* retries out. If all 200 pods started their first attempt at the same wall-clock second — which happens during a rolling restart or a shared upstream event — they all compute the same delay sequence: 100 ms, 200 ms, 400 ms, 800 ms. They are still perfectly synchronised. Pure exponential backoff without jitter only shifts the thundering herd forward in time. What property does jitter add?

> **Student:** Randomness — each pod picks a different delay.

> **Expert:** Correct. Now prove it. What is the expected delay for *full jitter* on attempt 3, base 100 ms?

---

**Exchange 3 — "I'll just use `@Retryable`, it's simpler"**

> **Student:** Spring's `@Retryable` is built-in and works with a single annotation. Why would I ever add Resilience4j as a dependency?

> **Expert:** `@Retryable` is a good choice inside a Spring application when you want simple, declarative fixed or exponential backoff and don't need metrics, CircuitBreaker composition, or programmatic control. The moment you need any of these — a Micrometer histogram of retry attempt distributions, a CircuitBreaker that stops retrying when it opens, or you are in a non-Spring context — `@Retryable` becomes a liability. A principal engineer chooses the simplest tool that satisfies the non-functional requirements, not the simplest tool that satisfies the happy path.

---

**Exchange 4 — "Retry is safe because we have idempotency keys"**

> **Student:** We send an idempotency key in every request, so we can safely retry anything.

> **Expert:** The idempotency key makes the *server-side operation* safe to replay. Does that mean your retry is safe?

> **Student:** Yes?

> **Expert:** What if the server processed the request, committed, and then the network failed before the response arrived? Your client retries — the server deduplicates — you get back the original response. That is fine. But what if you are retrying a `DELETE`? A `GET`? What if the idempotency key expires after 24 hours? Idempotency keys solve double-write problems. They do not solve: non-idempotent operations, expired keys, or operations where the *client* cannot distinguish a timeout-during-send from a timeout-during-receive. Always classify operations: safe (GET), idempotent (PUT/DELETE with key), non-idempotent (POST without key). Retry only the first two by default.

## 4. Theory + Diagrams

### The Thundering Herd Problem

When many clients retry simultaneously after a shared failure, they produce coordinated request spikes — a **thundering herd**. Each spike can prevent the downstream from recovering, creating a feedback loop.

```
Without Jitter — All 5 pods retry at identical intervals:

Time(ms)   Pod A  Pod B  Pod C  Pod D  Pod E   Total Load
  0        FAIL   FAIL   FAIL   FAIL   FAIL    ■■■■■ (5)
500        RETRY  RETRY  RETRY  RETRY  RETRY   ■■■■■ (5)  <-- spike
1000       RETRY  RETRY  RETRY  RETRY  RETRY   ■■■■■ (5)  <-- spike
1500       RETRY  RETRY  RETRY  RETRY  RETRY   ■■■■■ (5)  <-- spike

With Full Jitter — Each pod picks random delay in [0, cap]:

Time(ms)   Pod A  Pod B  Pod C  Pod D  Pod E   Total Load
  0        FAIL   FAIL   FAIL   FAIL   FAIL    ■■■■■ (5)
  80              RETRY                         ■     (1)
 210                     RETRY                  ■     (1)
 350       RETRY                                ■     (1)
 420                            RETRY           ■     (1)
 490                                   RETRY    ■     (1)
                                                ^-- spread out, service recovers
```

### Backoff Formula Derivation

```
Base exponential backoff:
  delay(attempt) = min(cap, base × 2^attempt)

  attempt=0: min(30000, 100 × 1)   =   100 ms
  attempt=1: min(30000, 100 × 2)   =   200 ms
  attempt=2: min(30000, 100 × 4)   =   400 ms
  attempt=3: min(30000, 100 × 8)   =   800 ms
  attempt=4: min(30000, 100 × 16)  =  1600 ms
  attempt=7: min(30000, 100 × 128) = 12800 ms
  attempt=9: min(30000, 100 × 512) = 30000 ms  <-- cap reached
```

### Three Jitter Strategies (AWS Whitepaper)

```
┌────────────────────────────────────────────────────────────────┐
│  Let:  cap  = max delay (e.g. 30 000 ms)                       │
│        base = initial delay (e.g. 100 ms)                      │
│        n    = attempt number (0-indexed)                        │
│        V    = min(cap, base × 2^n)   (exponential value)       │
│        rand = random float in [0, 1]                           │
└────────────────────────────────────────────────────────────────┘

1. NO JITTER (pure exponential)
   ─────────────────────────────
   sleep = V
   Problem: all synchronised clients produce identical delays.

2. FULL JITTER
   ────────────
   sleep = rand × V
   Expected value: V / 2
   Best for: highest desynchronisation, lowest average load.
   Cost: some retries happen very quickly (near 0 ms).

3. EQUAL JITTER
   ─────────────
   sleep = (V / 2) + rand × (V / 2)
   Expected value: 3V / 4
   Best for: ensuring a minimum wait while still adding spread.

4. DECORRELATED JITTER (AWS recommendation)
   ──────────────────────────────────────────
   sleep = min(cap, rand × (3 × prev_sleep))
   Initial: prev_sleep = base
   Expected: grows faster than full jitter; converges to cap sooner.
   Why "decorrelated": each attempt's delay is based on the
   PREVIOUS attempt's actual sleep, not on a deterministic formula.
   Clients that happened to sleep long will tend to sleep long again,
   but independently of other clients → decorrelation across pods.

   Iteration example (base=100, cap=30000):
     sleep_0 = rand × (3 × 100)  = e.g. 178 ms
     sleep_1 = rand × (3 × 178)  = e.g. 412 ms
     sleep_2 = rand × (3 × 412)  = e.g. 891 ms
     ...
```

### Resilience4j Decorator Composition Order

```
Incoming call
     │
     ▼
┌─────────────┐
│  TimeLimiter│  (outermost: enforce overall timeout)
└──────┬──────┘
       │
       ▼
┌─────────────┐
│CircuitBreaker│ (fail fast when downstream is broken)
└──────┬──────┘
       │
       ▼
┌─────────────┐
│    Retry    │  (attempt multiple times — only when CB allows)
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  Bulkhead   │  (innermost: limit concurrent calls to downstream)
└──────┬──────┘
       │
       ▼
  Actual call

Composition code (outermost first in decoration, innermost first in execution):
  Supplier<R> fn = () -> remoteCall();
  fn = Bulkhead.decorateSupplier(bulkhead, fn);    // innermost
  fn = Retry.decorateSupplier(retry, fn);
  fn = CircuitBreaker.decorateSupplier(cb, fn);
  fn = TimeLimiter.decorateSupplier(timeLimiter, fn); // outermost
```

**Why this order matters:** The CircuitBreaker wraps Retry, so when the CB opens it short-circuits the entire retry chain — you don't waste resources retrying against a known-broken service. TimeLimiter is outermost so the total budget (including all retries) is bounded.

### `IntervalFunction` — Key Factory Methods

```java
// Package: io.github.resilience4j.retry
// Class: IntervalFunction (interface)

@FunctionalInterface
public interface IntervalFunction extends Function<Integer, Long> {

    long DEFAULT_INITIAL_INTERVAL = 500;          // ms
    double DEFAULT_MULTIPLIER = 1.5;
    double DEFAULT_RANDOMIZATION_FACTOR = 0.5;

    // Pure exponential: delay = initialInterval × multiplier^attempt
    static IntervalFunction ofExponentialBackoff(
            long initialIntervalMillis,
            double multiplier) { ... }

    // Exponential + uniform random jitter in ±randomizationFactor band:
    // delay = rand_between(
    //   exp × (1 - randomizationFactor),
    //   exp × (1 + randomizationFactor)
    // )
    static IntervalFunction ofExponentialRandomBackoff(
            long initialIntervalMillis,
            double multiplier,
            double randomizationFactor) { ... }

    // Overload with cap:
    static IntervalFunction ofExponentialRandomBackoff(
            long initialIntervalMillis,
            double multiplier,
            double randomizationFactor,
            long maxIntervalMillis) { ... }

    // Custom lambda: attempt -> computeDelay(attempt)
    static IntervalFunction of(Function<Integer, Long> function) { ... }
}
```

**Note on `ofExponentialRandomBackoff` vs decorrelated jitter:** Resilience4j's built-in uses equal-jitter (band around exponential value), not decorrelated jitter. For decorrelated jitter you must supply a custom `IntervalFunction.of(fn)` — shown in the Code Lab.

## 6. Code Lab

### Bad: Naive Retry with `Thread.sleep`

```java
// BAD — do not use in production
public class NaiveRetry {

    private static final Logger log = LoggerFactory.getLogger(NaiveRetry.class);

    public String fetchData(String url) throws Exception {
        int maxAttempts = 3;
        for (int attempt = 0; attempt < maxAttempts; attempt++) {
            try {
                return httpClient.get(url);               // (1)
            } catch (IOException e) {
                if (attempt == maxAttempts - 1) throw e;
                long sleep = 500L * (attempt + 1);        // (2)
                log.warn("Attempt {} failed, sleeping {}ms", attempt, sleep);
                Thread.sleep(sleep);                       // (3)
            }
        }
        throw new IllegalStateException("unreachable");
    }
}
```

Problems:
1. No classification: retries `IOException` blindly, including `SocketException` from connection-refused (not transient) and from SSL handshake failure (never going to recover with retries).
2. Linear backoff, not exponential — still clusters.
3. `Thread.sleep` blocks the carrier thread; in virtual-thread contexts this is tolerable, but it still pins if called inside a `synchronized` block.
4. No metrics: you have no idea how often retries fire in production.
5. No coordination with a CircuitBreaker: you will keep retrying into an open circuit.

### Good: Resilience4j `Retry` with `IntervalFunction`

```java
// Good — production-grade retry with decorrelated jitter
import io.github.resilience4j.retry.Retry;
import io.github.resilience4j.retry.RetryConfig;
import io.github.resilience4j.retry.RetryRegistry;
import io.github.resilience4j.retry.IntervalFunction;
import io.micrometer.core.instrument.MeterRegistry;

import java.time.Duration;
import java.util.concurrent.ThreadLocalRandom;

public class RetryEngineering {

    // ── Decorrelated Jitter IntervalFunction ──────────────────────────────────
    // AWS formula: sleep_n = min(cap, random_between(base, 3 × sleep_{n-1}))
    // We approximate this statelessly: treat sleep_{n-1} ≈ base × 2^(attempt-1)
    // then: sleep_n = random_between(base, min(cap, 3 × base × 2^(attempt-1)))
    static IntervalFunction decorrelatedJitter(long baseMs, long capMs) {
        return attempt -> {
            long prevSleep = (attempt <= 1)
                ? baseMs
                : Math.min(capMs, baseMs * (1L << (attempt - 1)));  // base × 2^(n-1)
            long low  = baseMs;
            long high = Math.min(capMs, 3 * prevSleep);
            return low + ThreadLocalRandom.current().nextLong(high - low + 1);
        };
    }

    // ── RetryConfig ──────────────────────────────────────────────────────────
    public static RetryConfig buildRetryConfig() {
        return RetryConfig.custom()
            .maxAttempts(4)                                      // 1 original + 3 retries
            .intervalFunction(decorrelatedJitter(100, 30_000))   // 100ms base, 30s cap
            .retryExceptions(
                java.net.SocketTimeoutException.class,
                java.net.ConnectException.class,
                java.io.IOException.class
            )
            .ignoreExceptions(
                IllegalArgumentException.class,                  // never retry programmer errors
                jakarta.validation.ValidationException.class
            )
            .failAfterMaxAttempts(true)
            .build();
    }

    // ── Registry + Micrometer ─────────────────────────────────────────────────
    public static Retry buildRetry(MeterRegistry meterRegistry) {
        RetryRegistry registry = RetryRegistry.of(buildRetryConfig());
        Retry retry = registry.retry("inventory-service");

        // Publish attempt/success/failure counters to Micrometer
        io.github.resilience4j.micrometer.tagged.TaggedRetryMetrics
            .ofRetryRegistry(registry)
            .bindTo(meterRegistry);

        return retry;
    }

    // ── Usage ─────────────────────────────────────────────────────────────────
    public String fetchInventory(String sku, Retry retry) {
        // Wrap the call — checked exceptions tunnel through CheckedSupplier
        return Retry.decorateCheckedSupplier(retry, () -> inventoryClient.get(sku))
                    .unchecked()                     // convert to Supplier<String>
                    .get();
    }
}
```

### Full Composition: Bulkhead → Retry → CircuitBreaker → TimeLimiter

```java
import io.github.resilience4j.bulkhead.Bulkhead;
import io.github.resilience4j.bulkhead.BulkheadConfig;
import io.github.resilience4j.circuitbreaker.CircuitBreaker;
import io.github.resilience4j.circuitbreaker.CircuitBreakerConfig;
import io.github.resilience4j.timelimiter.TimeLimiter;
import io.github.resilience4j.timelimiter.TimeLimiterConfig;

import java.time.Duration;
import java.util.concurrent.Callable;
import java.util.concurrent.ScheduledExecutorService;
import java.util.function.Supplier;

public class ResilienceComposition {

    public String callInventoryService(
            String sku,
            Bulkhead bulkhead,
            Retry retry,
            CircuitBreaker circuitBreaker,
            TimeLimiter timeLimiter,
            ScheduledExecutorService scheduler) throws Exception {

        // Decorate innermost → outermost
        // Execution flows outermost → innermost (decoration order is reversed at runtime)

        Supplier<String> fn = () -> inventoryClient.get(sku);         // raw call

        fn = Bulkhead.decorateSupplier(bulkhead, fn);                  // innermost
        fn = Retry.decorateSupplier(retry, fn);
        fn = CircuitBreaker.decorateSupplier(circuitBreaker, fn);

        // TimeLimiter requires Callable + Future — wrap accordingly
        Callable<String> callable = fn::get;
        Callable<String> timeLimited = TimeLimiter.decorateCallable(timeLimiter, callable);

        return timeLimited.call();
    }

    // ── Configuration ─────────────────────────────────────────────────────────
    static Bulkhead buildBulkhead() {
        return Bulkhead.of("inventory",
            BulkheadConfig.custom()
                .maxConcurrentCalls(25)
                .maxWaitDuration(Duration.ofMillis(50))
                .build());
    }

    static CircuitBreaker buildCircuitBreaker() {
        return CircuitBreaker.of("inventory",
            CircuitBreakerConfig.custom()
                .slidingWindowSize(20)
                .failureRateThreshold(50)            // open at 50% failures
                .waitDurationInOpenState(Duration.ofSeconds(30))
                .permittedNumberOfCallsInHalfOpenState(5)
                .build());
    }

    static TimeLimiter buildTimeLimiter() {
        return TimeLimiter.of("inventory",
            TimeLimiterConfig.custom()
                .timeoutDuration(Duration.ofSeconds(10))   // covers all retries
                .cancelRunningFuture(true)
                .build());
    }
}
```

### Spring `@Retryable` — When It Is Appropriate

```java
// spring-retry dependency: org.springframework.retry:spring-retry
// Enable with @EnableRetry on a @Configuration class

import org.springframework.retry.annotation.Backoff;
import org.springframework.retry.annotation.Recover;
import org.springframework.retry.annotation.Retryable;
import org.springframework.stereotype.Service;

@Service
public class PaymentService {

    // Simple declarative retry: good for internal Spring services
    // where you don't need metrics, CB composition, or programmatic control
    @Retryable(
        retryFor = { java.net.SocketTimeoutException.class },
        noRetryFor = { IllegalArgumentException.class },
        maxAttempts = 3,
        backoff = @Backoff(delay = 200, multiplier = 2.0, random = true)
    )
    public PaymentResult charge(PaymentRequest request) {
        return paymentGateway.charge(request);
    }

    // Recovery method invoked after maxAttempts are exhausted
    @Recover
    public PaymentResult recoverCharge(SocketTimeoutException e,
                                        PaymentRequest request) {
        log.error("Payment gateway unreachable after retries: {}", request.id());
        return PaymentResult.deferred(request.id());
    }
}
```

**`@Retryable` vs Resilience4j decision matrix:**

```
Requirement                                  | @Retryable | Resilience4j
─────────────────────────────────────────────┼────────────┼─────────────
Spring Boot project, simple exponential BO   |     ✓      |
Metrics via Micrometer                       |            |     ✓
CircuitBreaker composition                   |            |     ✓
Bulkhead / rate limiter                      |            |     ✓
Non-Spring (plain Java, Quarkus, etc.)       |            |     ✓
Reactive (Reactor / RxJava)                  |            |     ✓
Custom jitter algorithms                     |  limited   |     ✓
Quick annotation-based setup, low complexity |     ✓      |
```

## 7. Production Lens

### Incident: Retry Storm During Database Failover

**Scenario:** A primary PostgreSQL instance fails at 02:14. All 120 application pods detect the connection failure simultaneously (they all tried within the same 30-second health-check window). Each pod had a naive retry loop with fixed 1-second sleep.

```
02:14:00  DB fails
02:14:00  120 pods throw SQLException
02:14:01  120 pods retry simultaneously     → 120 connections attempt to new primary
02:14:01  New primary not yet ready (15s promotion window)
02:14:02  120 pods fail again, sleep 1s
02:14:03  120 pods retry simultaneously     → TCP SYN flood to new primary
02:14:03  New primary's connection queue exhausted (max_connections=100)
02:14:04  New primary starts rejecting → 120 pods throw again
...
02:14:20  New primary ready, but 120 pods have now triggered CircuitBreaker thresholds
          (because no CB was configured) and are in a crash-restart loop

Result: 6 minutes of total downtime instead of 20-second failover
```

**Fix applied:** Decorrelated jitter + Resilience4j CircuitBreaker with 30-second open window.

```
02:14:00  DB fails
02:14:00  120 pods throw SQLException
02:14:00  Each pod independently computes decorrelated jitter delay
          Pod distribution over next 30 seconds:
          ██░░░░░░░░░░░░░░░░░░░░░░░░░░░░  (sparse, spread across 0-30s)
02:14:20  New primary ready — arriving retries succeed
          CircuitBreaker transitions: OPEN → HALF_OPEN → CLOSED
02:14:22  All pods successfully reconnected

Result: 22 seconds of downtime (expected failover time)
```

### Benchmark: Clustered vs Spread Requests

```
Test: 50 clients, maxAttempts=4, base=100ms, cap=10s
      Simulated downstream: recovers after 2 seconds
      Metric: time until all clients report success

Strategy           | Time to full recovery | Peak RPS at downstream
───────────────────┼───────────────────────┼───────────────────────
No Jitter          |       18.2 s          |   50 req/s (spikes)
Full Jitter        |        4.1 s          |    8 req/s (spread)
Equal Jitter       |        5.3 s          |   12 req/s
Decorrelated       |        3.8 s          |    6 req/s (fastest)

Key insight: decorrelated jitter achieves the fastest recovery
because later clients backoff *further* when early clients
succeed — the successful connections "absorb" load before
the larger backoffs fire.
```

### Idempotency in Practice

Before enabling retry on any operation, classify it:

```
Operation              | Safe? | Idempotent? | Retry safe?
───────────────────────┼───────┼─────────────┼────────────
GET /inventory/{sku}   |  Yes  |     Yes     |     Yes
PUT /order/{id}/status |  No   |     Yes     |     Yes (same result)
POST /payment          |  No   |     No      |  Only with idempotency key
DELETE /session/{id}   |  No   |     Yes     |     Yes (2nd delete = 404, handled)
POST /email/send       |  No   |     No      |     NO (duplicate emails)
```

Non-idempotent operations must be made idempotent before retry is safe. Use a client-generated UUID idempotency key header and server-side deduplication with a TTL cache.

## 9. Summary / Flashcard

**Q1: What is the thundering herd problem in the context of retry?**
A: When all clients in a distributed system retry simultaneously after a shared failure, they produce a coordinated spike of requests that can prevent the downstream service from recovering, creating a self-reinforcing failure loop.

**Q2: What is the decorrelated jitter formula, and why is it "decorrelated"?**
A: `sleep = random_between(base, min(cap, 3 × prev_sleep))`. It is decorrelated because each client's delay depends on its own previous sleep value rather than a deterministic formula — clients that slept long tend to keep sleeping long, independently of other clients, breaking synchronisation.

**Q3: In what order should Resilience4j decorators be applied, and why?**
A: Bulkhead (innermost) → Retry → CircuitBreaker → TimeLimiter (outermost). The CircuitBreaker must wrap Retry so that an open circuit short-circuits the entire retry chain. TimeLimiter is outermost to bound the total wall-clock time including all retries.

**Q4: When should you choose `@Retryable` over Resilience4j?**
A: `@Retryable` is appropriate for simple Spring Boot applications that need declarative fixed or exponential backoff, do not require CircuitBreaker/Bulkhead composition, and do not need Micrometer metrics or programmatic control. Choose Resilience4j when any of those requirements exist, or when working outside the Spring context.

**Q5: Why must an operation be idempotent before it is safe to retry?**
A: A retry cannot distinguish between "the request was never processed" and "the request was processed but the response was lost". If the operation is not idempotent, a retry may execute the operation a second time with different side effects (double charge, duplicate email). Idempotency guarantees the server produces the same result regardless of how many times the request arrives.

<summary>Exercise 1 — Jitter at low pod count</summary>

**Staff-level phrasing:** "Engineer A is partially right about scale reducing the probability of collision, but wrong about the threshold. Jitter is not about the number of pods — it is about the correlation of failure. Ten pods that all share the same upstream event (a database failover, a cache miss storm, a deployment restart) will all have their first retry at the same wall-clock millisecond regardless of pod count. The thundering herd is a function of temporal correlation, not fleet size. Even two clients retrying synchronously can saturate a small downstream. The correct rule is: if multiple clients can fail for the same reason at the same time, add jitter — and that is true at any scale. The cost of jitter is negligible (one `ThreadLocalRandom.nextLong` call); the cost of not having it during an incident can be hours of downtime. There is no threshold below which jitter is overkill."

<summary>Exercise 2 — Expected value derivation</summary>

**Staff-level phrasing:** "For full jitter at attempt=3: `V = min(30000, 100 × 2^3) = min(30000, 800) = 800 ms`. Full jitter: `E[sleep] = V/2 = 400 ms`. For decorrelated jitter, we track the chain: `E[sleep_0] = E[rand × 3 × 100] = 150 ms`. `E[sleep_1] = E[rand × 3 × 150] = 225 ms`. `E[sleep_2] = E[rand × 3 × 225] = 337.5 ms`. Decorrelated produces a smaller expected delay at attempt 3 (338 ms vs 400 ms) but grows faster in subsequent attempts because it multiplies the previous sleep rather than a deterministic exponential. The implication for recovery: decorrelated jitter achieves faster early retries (lower latency for the first successful wave of retries) while still spreading load. This is why AWS recommends it: you recover faster on average while still preventing thundering herd. Full jitter has higher average delay and therefore slower expected time-to-first-success."

</details>

<summary>Exercise 3 — Retry around async Kafka producer</summary>

**Staff-level phrasing:** "Three problems: (1) `Retry.decorateSupplier` is synchronous — it calls the supplier, blocks for a result, and retries on exception. A `send()` that returns a `CompletableFuture` almost never throws synchronously; the failure arrives asynchronously inside the future. The retry wrapper will see a successful return (the future object) and not retry at all. (2) Kafka's producer already has built-in retry (`retries`, `retry.backoff.ms`) at the network level — adding application-layer retry on top creates duplicate retry semantics that interact unpredictably. (3) Kafka `send()` is not idempotent by default; duplicate retries from the application layer can produce duplicate messages. The correct approach: enable Kafka's idempotent producer (`enable.idempotence=true`), rely on Kafka's built-in retry for transient broker failures, and use the `CompletableFuture` exceptionally/thenCompose chain for application-level recovery decisions. If you must use Resilience4j, use `Retry.executeCompletionStage` with a `CompletableFuture`-aware scheduler, not `executeSupplier`."

</details>

<summary>Exercise 4 — RetryConfig factory with decorrelated jitter, filtering, and logging</summary>

```java
import io.github.resilience4j.retry.Retry;
import io.github.resilience4j.retry.RetryConfig;
import io.github.resilience4j.retry.RetryRegistry;
import io.github.resilience4j.retry.event.RetryOnRetryEvent;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.io.IOException;
import java.net.SocketTimeoutException;
import java.net.UnknownHostException;
import java.util.concurrent.ThreadLocalRandom;
import java.util.function.Supplier;

public class Exercise4Solution {

    private static final Logger log = LoggerFactory.getLogger(Exercise4Solution.class);

    static IntervalFunction decorrelatedJitter(long baseMs, long capMs) {
        return attempt -> {
            long prevSleep = (attempt <= 1)
                ? baseMs
                : Math.min(capMs, baseMs * (1L << (attempt - 1)));
            long high = Math.min(capMs, 3 * prevSleep);
            return baseMs + ThreadLocalRandom.current().nextLong(high - baseMs + 1);
        };
    }

    public static Retry buildRetry(String name) {
        RetryConfig config = RetryConfig.custom()
            .maxAttempts(5)
            .intervalFunction(decorrelatedJitter(50, 20_000))
            .retryExceptions(IOException.class, SocketTimeoutException.class)
            .ignoreExceptions(UnknownHostException.class)       // DNS failure is not transient
            .failAfterMaxAttempts(true)
            .build();

        Retry retry = RetryRegistry.of(config).retry(name);

        // Log each retry attempt with computed delay
        retry.getEventPublisher().onRetry((RetryOnRetryEvent event) ->
            log.warn("[{}] Retry attempt {}/{} after {}ms due to: {}",
                name,
                event.getNumberOfRetryAttempts(),
                config.getMaxAttempts() - 1,
                event.getWaitInterval().toMillis(),
                event.getLastThrowable().getClass().getSimpleName())
        );

        return retry;
    }

    public static <T> T executeWithRetry(Retry retry, Supplier<T> fn) {
        try {
            return Retry.decorateSupplier(retry, fn).get();
        } catch (io.github.resilience4j.retry.MaxRetriesExceededException e) {
            throw new DownstreamUnavailableException(
                "All retry attempts exhausted for " + retry.getName(), e.getCause());
        }
    }

    public static class DownstreamUnavailableException extends RuntimeException {
        public DownstreamUnavailableException(String msg, Throwable cause) {
            super(msg, cause);
        }
    }
}
```

**Why this works:** `ignoreExceptions(UnknownHostException.class)` is evaluated before `retryExceptions`, so DNS failures propagate immediately — DNS is infrastructure-level and retrying against an unresolvable host wastes time. The `onRetry` event publisher fires *before* the sleep, so the logged `waitInterval` is the actual delay that will be applied. Wrapping `MaxRetriesExceededException` preserves the original cause via `getCause()` — never swallow the root cause.

**Common mistake:** Calling `retry.executeSupplier(fn)` instead of `Retry.decorateSupplier(retry, fn).get()`. Both work, but `decorateSupplier` returns a `Supplier<T>` that can be composed with other decorators later. Always prefer the decorator form so you can compose.

</details>

<summary>Exercise 5 — Full Spring Boot 3 + Resilience4j composition with fallback</summary>

```java
// --- Configuration class ---

import io.github.resilience4j.bulkhead.Bulkhead;
import io.github.resilience4j.bulkhead.BulkheadConfig;
import io.github.resilience4j.bulkhead.BulkheadRegistry;
import io.github.resilience4j.circuitbreaker.CircuitBreaker;
import io.github.resilience4j.circuitbreaker.CircuitBreakerConfig;
import io.github.resilience4j.circuitbreaker.CircuitBreakerRegistry;
import io.github.resilience4j.micrometer.tagged.*;
import io.github.resilience4j.retry.Retry;
import io.github.resilience4j.retry.RetryConfig;
import io.github.resilience4j.retry.RetryRegistry;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.time.Duration;
import java.util.concurrent.ThreadLocalRandom;

@Configuration
public class UserServiceResilienceConfig {

    @Bean
    Bulkhead userServiceBulkhead(MeterRegistry meterRegistry) {
        BulkheadRegistry registry = BulkheadRegistry.of(
            BulkheadConfig.custom()
                .maxConcurrentCalls(10)
                .maxWaitDuration(Duration.ofMillis(20))
                .build());
        TaggedBulkheadMetrics.ofBulkheadRegistry(registry).bindTo(meterRegistry);
        return registry.bulkhead("user-service");
    }

    @Bean
    Retry userServiceRetry(MeterRegistry meterRegistry) {
        RetryRegistry registry = RetryRegistry.of(
            RetryConfig.custom()
                .maxAttempts(3)
                .intervalFunction(attempt -> {
                    // Full jitter: random in [0, min(cap, base × 2^attempt)]
                    long cap = 5_000L;
                    long v = Math.min(cap, 100L * (1L << attempt));
                    return ThreadLocalRandom.current().nextLong(v + 1);
                })
                .retryExceptions(java.io.IOException.class)
                .failAfterMaxAttempts(true)
                .build());
        TaggedRetryMetrics.ofRetryRegistry(registry).bindTo(meterRegistry);
        return registry.retry("user-service");
    }

    @Bean
    CircuitBreaker userServiceCircuitBreaker(MeterRegistry meterRegistry) {
        CircuitBreakerRegistry registry = CircuitBreakerRegistry.of(
            CircuitBreakerConfig.custom()
                .slidingWindowType(CircuitBreakerConfig.SlidingWindowType.COUNT_BASED)
                .slidingWindowSize(20)
                .failureRateThreshold(50)
                .waitDurationInOpenState(Duration.ofSeconds(30))
                .permittedNumberOfCallsInHalfOpenState(3)
                .build());
        TaggedCircuitBreakerMetrics.ofCircuitBreakerRegistry(registry).bindTo(meterRegistry);
        return registry.circuitBreaker("user-service");
    }
}

// --- Service class ---

import io.github.resilience4j.bulkhead.Bulkhead;
import io.github.resilience4j.circuitbreaker.CallNotPermittedException;
import io.github.resilience4j.circuitbreaker.CircuitBreaker;
import io.github.resilience4j.retry.Retry;
import org.springframework.stereotype.Service;

import java.util.function.Supplier;

@Service
public class UserService {

    private final UserApiClient apiClient;
    private final Bulkhead bulkhead;
    private final Retry retry;
    private final CircuitBreaker circuitBreaker;

    public UserService(UserApiClient apiClient,
                       Bulkhead userServiceBulkhead,
                       Retry userServiceRetry,
                       CircuitBreaker userServiceCircuitBreaker) {
        this.apiClient      = apiClient;
        this.bulkhead       = userServiceBulkhead;
        this.retry          = userServiceRetry;
        this.circuitBreaker = userServiceCircuitBreaker;
    }

    public UserProfile getUserProfile(String userId) {
        // Decorate innermost → outermost (Bulkhead → Retry → CircuitBreaker)
        Supplier<UserProfile> fn = () -> apiClient.fetchProfile(userId);
        fn = Bulkhead.decorateSupplier(bulkhead, fn);
        fn = Retry.decorateSupplier(retry, fn);
        fn = CircuitBreaker.decorateSupplier(circuitBreaker, fn);

        try {
            return fn.get();
        } catch (CallNotPermittedException e) {
            // CircuitBreaker is open — return fallback immediately
            return UserProfile.anonymous();
        } catch (Exception e) {
            // All retries exhausted or bulkhead full
            return UserProfile.anonymous();
        }
    }
}
```

**Why this works:** The `@Bean` method names match the parameter names via Spring's autowiring by-name convention (`userServiceBulkhead` etc.), so Spring correctly injects the right beans even if multiple Bulkhead/Retry/CircuitBreaker beans exist. Metrics registration happens eagerly at bean creation time, so all instances appear in Micrometer from the first call. The fallback is in the service layer, not a `@CircuitBreakerFallback` annotation — this is intentional: it keeps the fallback logic visible and testable without proxy magic.

**Common mistake:** Composing the decorators in the wrong order — for example, wrapping Bulkhead outside CircuitBreaker. If the CircuitBreaker is innermost, an open circuit will still consume a Bulkhead slot for the duration of the `CallNotPermittedException` throw, artificially exhausting concurrency. Always: Bulkhead innermost so it is only acquired for real attempts.

</details>

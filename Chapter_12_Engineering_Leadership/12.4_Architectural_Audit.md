## 5. Source Archaeology: The Audit Evidence Trail

A strong audit defense is backed by source-code evidence, not hand-waving. Key classes to cite:

**`org.apache.kafka.clients.producer.internals.RecordAccumulator`** (Kafka source, `clients` module):
- Manages the in-memory buffer before network send; the `drain()` method is where zero-copy batching occurs
- Audit question: "What happens under backpressure?" Answer: `RecordAccumulator.append()` blocks when `buffer.memory` is exhausted — cite `BufferPool.allocate()` with its `waiters` queue

**`io.netty.channel.epoll.EpollEventLoop`** (Netty):
- `run()` method's `epollWait` syscall path — cite this when defending I/O threading model
- "Why not one thread per connection?" → `EpollEventLoop` handles thousands of channels on a single thread via `epoll_wait`, avoiding context-switch overhead (~1-3µs per switch)

**`org.apache.ratis.server.impl.RaftServerImpl`** (Apache Ratis, used by HDFS/Ozone):
- `submitClientRequest()` → triggers `appendEntries` RPC to followers
- Audit question: "What is your write latency under Raft?" → Raft write = 1 RTT to quorum = `2 × network_latency_to_nearest_follower`; with followers in the same AZ, this is ~1ms

**`sun.nio.ch.FileChannelImpl.transferTo()`** (OpenJDK):
- The actual zero-copy implementation via `sendfile(2)` syscall; `sendfile` bypasses user-space buffers
- Audit question: "Prove your storage layer doesn't copy data." → cite `transferTo` → `sendfile` path, measurable with `strace -e trace=sendfile`

## 6. Code Lab

### BAD: "Sounds good" design — no physical justification

```java
// BAD: An engineer proposes this "high performance" cache.
// It "sounds good" but has no physical justification
// and will fail the audit at the first cross-NUMA question.

public class OrderCache {
    // BAD: ConcurrentHashMap on a NUMA machine means every
    // cache-line that crosses NUMA nodes costs ~100ns vs ~5ns local.
    // 10M lookups/sec × 95ns extra = 950ms/sec of pure NUMA tax.
    private final ConcurrentHashMap<Long, Order> cache =
        new ConcurrentHashMap<>(10_000_000);

    // No eviction policy, no size bound, no GC pressure analysis.
    // Audit question: "What happens at 1B entries?" → OOM. No answer.
    public Order get(long orderId) {
        return cache.get(orderId);
    }
}
```

### GOOD: Physically inevitable design — every choice is defensible

```java
import com.github.benmanes.caffeine.cache.*;
import java.lang.foreign.*;
import java.time.Duration;

/**
 * Audit-ready Order Cache.
 *
 * Physical justifications:
 * 1. Caffeine W-TinyLFU: O(1) amortized eviction via frequency sketch.
 *    Source: com.github.benmanes.caffeine.cache.BoundedLocalCache.
 *    Audit shield: "Eviction does not block reads — uses a ring buffer
 *    drain strategy (BoundedLocalCache.drainBuffers) with CAS, not locks."
 *
 * 2. Size-bounded: 500k entries × ~200 bytes = ~100MB heap budget.
 *    Audit shield: "Heap budget is defined in the ADR-0051 section 2.3."
 *
 * 3. NUMA-local: executor pinned to CPU socket 0 via thread affinity.
 *    Audit shield: "Thread affinity via -XX:+UseNUMA and JVM NUMA-aware
 *    allocator ensures Caffeine's ring buffer is on the same NUMA node
 *    as the request-handling threads."
 */
public class AuditReadyOrderCache {

    private final LoadingCache<Long, Order> cache;

    public AuditReadyOrderCache(OrderRepository repo) {
        this.cache = Caffeine.newBuilder()
            .maximumSize(500_000)                   // ADR-0051: 100MB heap budget
            .expireAfterWrite(Duration.ofMinutes(10))
            .recordStats()                           // expose hit/miss rate to Prometheus
            .build(repo::findById);                  // safe loader — no null keys
    }

    public Order get(long orderId) {
        return cache.get(orderId);
    }

    /**
     * Audit question: "What is your cache hit rate?"
     * Answer: cache.stats().hitRate() — measurable, not estimated.
     */
    public void printAuditStats() {
        CacheStats stats = cache.stats();
        System.out.printf(
            "Cache audit: hitRate=%.2f%%, loadSuccessCount=%d, avgLoadMs=%.2f%n",
            stats.hitRate() * 100,
            stats.loadSuccessCount(),
            stats.averageLoadPenalty() / 1_000_000.0
        );
    }
}
```

## 7. Production Lens

LinkedIn's Espresso storage engine (2013 case study) failed its internal audit when engineers could not answer: "What is your p99 read latency during a rolling restart?" The answer required understanding `MemTable` flush timing in RocksDB. The fix was adding JFR instrumentation to measure flush pauses — p99 dropped from **450ms to 38ms** after the team could see the data. The audit forced the measurement that the team had been avoiding.

At scale: a 5-dimension audit on a 10-service system typically uncovers 2-3 "physics gaps" — undocumented failure modes that become production incidents within 6 months. One blocked cross-NUMA read path at 500k RPS costs ~**475ms of pure latency overhead per second** (500k × 95ns NUMA penalty), equivalent to silently degrading every user's experience by ~0.5ms/request.

<summary>Exercise 1 — 5-Dimension Audit: Redis Cluster session storage with no TTL, 3-AZ sync replication</summary>

**Design:** Redis Cluster for session storage, no TTL, synchronous replication across 3 AZs.

| Dimension | Vulnerability | Principal Shield |
|---|---|---|
| **Machine** | No TTL = unbounded memory growth. At 100k active sessions × 2KB/session + all historical sessions (never expired) → Redis OOM on any node. OOM kills the node, triggering resharding storms. | Set `maxmemory-policy allkeys-lru` + TTL of 24h max session age. Implement `SESSION_CLEANUP` job to batch-expire idle sessions. Monitor `redis_memory_used_bytes / redis_memory_max_bytes` — alert at 80%. |
| **Network** | Synchronous replication across 3 AZs means every session write waits for ACKs from EU-WEST and AP-SOUTHEAST. Cross-AZ RTT = 70–150ms. Session creation P99 = **150ms minimum** due to sync wait. | Switch to async replication with `wait 0 100` (best-effort, non-blocking). Accept that <0.01% of sessions may be lost on AZ failure. For auth-sensitive sessions, use a write-back pattern: session exists in one AZ, replication is eventual. |
| **Scale** | Redis Cluster single-slot operations are O(1), but `KEYS *` or `SCAN` for session enumeration (e.g., "kick all sessions for user X") is O(N) across all slots — O(N × #nodes) total scan time at scale. | Index session→user mapping in a secondary Redis set (`user:{userId}:sessions SMEMBERS`). Never use `KEYS *` on data nodes. |
| **Consensus** | Redis Cluster uses eventually-consistent gossip protocol for slot assignment. During a network partition between AZ-A and AZ-B, both sides may elect new masters → **split-brain**. Two AZs both accepting session writes with no coordination. | Enable `cluster-require-full-coverage yes` — Redis Cluster refuses writes if it cannot reach quorum. Accept brief unavailability during AZ partition over split-brain correctness. |
| **Business** | No TTL means GDPR "right to erasure" requests are complicated: sessions tied to deleted users remain forever unless explicitly purged. Also: compliance audit requires session expiry evidence. | Enforce TTL via `EXPIRE session:{id} 86400` on every session write. Store session creation timestamp. Implement `deleteUserSessions(userId)` method that fetches the user's session index and deletes all. |

<summary>Exercise 2 — PostgreSQL 50k RPS write defense</summary>

**Paragraph 1 — Bottleneck and mitigation:**

At 50,000 writes/second, the primary bottleneck on PostgreSQL is WAL (Write-Ahead Log) fsync throughput. Each transaction commit requires a WAL fsync to disk. On a cloud instance with NVMe (`fsync` latency ~0.5ms), the theoretical maximum throughput is 2,000 commits/second per drive I/O channel. Mitigation: (a) group commit — PostgreSQL automatically batches WAL writes within a single `wal_writer_delay` window (default 200ms, set to 2ms for latency). (b) Synchronous commit (`synchronous_commit = local` instead of `on`) eliminates the standby ACK wait. (c) Connection pooling via PgBouncer in transaction mode — 50,000 logical connections collapse to 200 physical connections, eliminating connection setup overhead. (d) Partition the write-heavy table by hash(account_id) across 16 logical partitions — distributes WAL write pressure and enables parallel index maintenance.

**Paragraph 2 — Scale revisit trigger:**

This design holds up to approximately 80,000 writes/second on a `db.r6g.16xlarge` with 64 vCPUs and NVMe RAID. The decision must be revisited when: (a) WAL fsync latency P99 exceeds 5ms (visible via `pg_stat_bgwriter`), (b) checkpoint completion time exceeds `checkpoint_completion_target × checkpoint_timeout` (dirty pages spill to disk during application peak), or (c) when the write throughput requirement exceeds 200,000/second sustained for more than 30 minutes — at which point horizontal write sharding (Citus or Vitess) is required. For the Global Order Ledger use case at 50k writes/sec per region, PostgreSQL is sufficient with the configuration above.

<summary>Exercise 3 — Kafka acks=1 financial risk quantification</summary>

**Risk quantification:**

- 1M trades/day × $100 average = $100M/day total trade value
- Message loss probability: 0.001% per partition failure
- Assuming 10 partitions, 1 failure/year probability per partition: 10 × 1/365 = 2.7% chance of partition failure per day
- Expected loss per day: 0.00001 × $100M × 2.7% = **$27/day in expected value**
- Annual expected loss: $27 × 365 = **$9,855/year**

However: this analysis assumes ONLY message loss. The real risk is a "lost trade" for a financial instrument that moved significantly between the original and resent execution. A $100 average trade that was "lost" and re-executed 1 second later during a volatile market could have a $10 adverse move. At 1M trades/day × 0.001% × $10 = **$1,000/day in adverse execution risk** = $365,000/year.

**Argument against the trade-off:**

The 5ms → 3ms latency improvement is real but the risk is asymmetric. The $9,855 expected direct loss understates the reputational and regulatory risk: a financial institution that loses a trade and cannot prove execution audit trail faces regulatory action (MiFID II, SEC Rule 17a-4 require complete trade records). A single audit failure costs $1M+ in legal fees. The 2ms latency saving is worth approximately $0 in regulatory risk mitigation.

**Verdict:** Keep `acks=all`. Optimize latency through other means: linger.ms=0 (disable batching), compression=none for critical trades, dedicated broker for trade messages. 5ms → 4ms improvement is achievable without durability compromise.

**Staff-level phrasing:** "acks=1 saves 2ms but creates $365k/year adverse execution risk and unlimited regulatory exposure — optimize latency through linger.ms and compression before accepting durability tradeoffs on financial message streams."

<summary>Exercise 4 — DesignAuditor with 5 anti-pattern rules</summary>

```java
import java.util.Map;
import java.util.List;

public class DesignAuditor {

    record Rule(String pattern, String dimension, String warning, String shield) {}

    private static final List<Rule> RULES = List.of(
        new Rule(
            "ConcurrentHashMap",
            "Machine",
            "Unbounded ConcurrentHashMap: no eviction policy — will grow until OOM under sustained load.",
            "SHIELD: Replace with Caffeine cache (bounded, LRU/LFU eviction). Set maximumSize() before production."
        ),
        new Rule(
            "RabbitMQ",
            "Scale",
            "RabbitMQ: no native message replay. Analytics/audit consumers cannot replay historical events.",
            "SHIELD: Acceptable if replay is not required. If replay needed, migrate to Kafka or add archive consumer."
        ),
        new Rule(
            "synchronous.*replication|sync.*replication|replication.*sync",
            "Network",
            "Synchronous multi-AZ replication: adds cross-AZ RTT (70-150ms) to every write on the critical path.",
            "SHIELD: Switch to async replication (acks=1 for non-financial). Accept <0.01% data loss on AZ failure."
        ),
        new Rule(
            "H2|HSQLDB|Derby",
            "Consensus",
            "In-memory DB for testing: misses production isolation level behavior, JSONB operators, advisory locks.",
            "SHIELD: Replace with Testcontainers PostgreSQL for integration tests."
        ),
        new Rule(
            "no.*ttl|ttl.*null|ttl.*none|no ttl",
            "Business",
            "No TTL on cache/session: unbounded memory growth + GDPR right-to-erasure risk.",
            "SHIELD: Set TTL matching session SLA (e.g., 24h). Implement user data purge on delete event."
        )
    );

    public static void audit(Map<String, String> decisions) {
        System.out.println("=== DESIGN AUDIT REPORT ===");
        System.out.println();

        boolean anyWarning = false;
        for (var entry : decisions.entrySet()) {
            String component = entry.getKey();
            String value = entry.getValue().toLowerCase();

            for (var rule : RULES) {
                if (value.matches(".*" + rule.pattern().toLowerCase() + ".*")) {
                    System.out.printf("[%s] %s → %s%n", rule.dimension(), component, entry.getValue());
                    System.out.printf("  ⚠ Physics Gap: %s%n", rule.warning());
                    System.out.printf("  ✓ %s%n%n", rule.shield());
                    anyWarning = true;
                }
            }
        }

        if (!anyWarning) {
            System.out.println("No known anti-patterns detected. Proceed to review.");
        }
        System.out.println("=== END REPORT ===");
    }

    public static void main(String[] args) {
        audit(Map.of(
            "session_store", "ConcurrentHashMap",
            "message_queue", "RabbitMQ",
            "replication", "synchronous multi-AZ replication",
            "test_db", "H2",
            "cache_ttl", "no TTL configured"
        ));
    }
}
```

## 9. Summary / Flashcard

- **The 5-Dimension Audit** (Machine, Network, Scale, Consensus, Business) maps every architectural component to a physical constraint; a design that cannot answer all five is not ready for production.
- **"Physically inevitable" designs** cite specific class/method names (e.g. `FileChannelImpl.transferTo` for zero-copy) and measurable numbers (1ms Raft RTT in same-AZ) — these are unfalsifiable in an audit.
- **Cross-NUMA cache penalty** is ~95ns per cache-line miss vs ~5ns local; at 500k RPS an unbounded `ConcurrentHashMap` on a NUMA machine adds ~47ms of hidden latency overhead per second.
- **Caffeine's `BoundedLocalCache.drainBuffers()`** performs lock-free eviction via a ring buffer and CAS operations — the correct audit answer to "how does eviction work without blocking reads?"
- **Audit ethics rule**: a 10% performance gain that introduces a 0.001% data-loss probability must be quantified as `loss_rate × daily_transactions × avg_value` before the trade-off can be called informed; anything less is gambling with user data.

## 1. The Physics of Business: Cloud Economics

### 1.1 The Unit Cost

- **The Math:** If a Ledger order takes 1MB and we have 1B orders, that is 1TB of RAM. At AWS prices (`r6g.large`: ~$0.1008/hr for 16GB), that's **$7,200/month** for idle memory across 100 pods.
- **The ROI:** If a refactor reduces memory by 50%, you just handed the company **$43,200/year** in pure OPEX savings — before touching latency or throughput.

### 1.2 The GC Tax Formula

```
Monthly Revenue Loss = Daily_Transactions × Bounce_Rate_During_GC × Avg_Order_Value × 30
```

Example: 500k tx/day × 2% bounce × $5 avg = **$150k/year** in abandoned transactions.

## 4. Source Archaeology: Where the Numbers Come From

Real cost data is not guesswork — it is computed from measurable JVM internals.

**`java.lang.management.MemoryMXBean`** (`java.management` module):
- `getHeapMemoryUsage()` → `MemoryUsage.getUsed()` gives live heap bytes at runtime
- `getNonHeapMemoryUsage()` → captures Metaspace + direct buffer overhead

**`java.lang.management.GarbageCollectorMXBean`**:
- `getCollectionTime()` / `getCollectionCount()` → derive average pause duration per GC cycle
- Combine with `getLastGcInfo()` from `com.sun.management.GarbageCollectorMXBean` (HotSpot extension) to get per-collection start/end times

**Practical approach:** instrument a staging run with JFR (`jcmd <pid> JFR.start`), export the `jdk.GCPhasePause` event, correlate pause times with your APM bounce rate — that correlation *is* your Slide 1 number.

## 5. Code Lab

### BAD: Heap-Based Order Object — invisible memory tax

```java
// BAD: Each Order lives on the GC-managed heap.
// At 1M concurrent orders, this is ~1GB of GC pressure.
public class Order {
    private final long orderId;
    private final BigDecimal amount;     // 40 bytes on heap
    private final Instant createdAt;    // 24 bytes on heap
    // ... 20 more fields = ~400 bytes per Order
}

// Usage: 1_000_000 orders × 400 bytes = ~400MB live set
// GC must scan all 400MB every minor collection → stop-the-world pauses
List<Order> activeOrders = new ArrayList<>(1_000_000);
```

### GOOD: Off-Heap Arena — GC-invisible, zero pause impact

```java
import java.lang.foreign.*;
import java.lang.foreign.MemoryLayout.*;

// GOOD: Orders stored in a MemorySegment outside the GC heap.
// Java 21 Panama API (java.lang.foreign).
public class OffHeapOrderStore implements AutoCloseable {

    // Layout: orderId(8) + amount_unscaled(8) + amount_scale(4) + epochMillis(8) = 28 bytes
    private static final MemoryLayout LAYOUT = MemoryLayout.structLayout(
        ValueLayout.JAVA_LONG.withName("orderId"),
        ValueLayout.JAVA_LONG.withName("amountUnscaled"),
        ValueLayout.JAVA_INT.withName("amountScale"),
        ValueLayout.JAVA_LONG.withName("epochMillis"),
        MemoryLayout.paddingLayout(4)   // align to 8 bytes → 32 bytes/record
    );

    private static final VarHandle VH_ORDER_ID =
        LAYOUT.varHandle(PathElement.groupElement("orderId"));

    private final Arena arena = Arena.ofShared();
    private final MemorySegment segment;
    private final int capacity;

    public OffHeapOrderStore(int capacity) {
        this.capacity = capacity;
        // Allocate 32 bytes × capacity OUTSIDE the Java heap
        this.segment = arena.allocate(LAYOUT.byteSize() * capacity);
    }

    public void writeOrderId(int slot, long id) {
        VH_ORDER_ID.set(segment, (long) slot * LAYOUT.byteSize(), id);
    }

    @Override public void close() { arena.close(); }
}

// Result: 1_000_000 orders × 32 bytes = 32MB, completely invisible to GC.
// Minor GC time: ~0ms for off-heap data vs ~80ms for equivalent heap data.
```

- **Memory OPEX**: 1M on-heap order objects at 400 bytes each = 400MB live set; at AWS r6g.large rates across 100 pods, trimming that by 50% saves ~$158k/year.
- **GC-to-Revenue bridge**: `Monthly Revenue Loss = daily_tx × bounce_rate_during_GC × avg_order_value × 30` — this single formula converts a JVM metric into a CFO-readable number.

<summary>Exercise 1 — Unit Cost Calculation</summary>

**(a) Total heap required:**
200M orders/day is a throughput number, not a concurrent count. To find peak concurrent orders, estimate the in-flight window. A common assumption is a 5-second processing window:
`200M orders/day ÷ 86,400 sec/day × 5 sec = ~11,574 concurrent orders`
But the exercise is likely asking for the raw storage implication, so treat 200M as the live set for worst-case sizing:
`200M orders × 600 bytes = 120,000 MB = ~117 GB of heap`

**(b) Monthly pod cost:**
`r6g.xlarge` = $0.2016/hr
`50 pods × $0.2016/hr × 24 hrs × 30 days = $7,257.60/month`

**(c) OPEX saving from halving object size:**
Halving from 600 bytes to 300 bytes halves the heap requirement. If the 117 GB requirement drove the pod count, a 50% reduction in memory demand could reduce the pod fleet proportionally — saving roughly **$3,628/month or ~$43,500/year**. Even without reducing pod count, you free headroom that defers the next scaling event.

**Staff-level phrasing:** "A 300-byte object refactor eliminates $43k in annual RAM OPEX on our current fleet and defers the next pod-count scaling event by an estimated two quarters."

<summary>Exercise 2 — GC Bounce Math</summary>

**Step 1 — Pauses per day:**
4 pauses/minute × 60 minutes × 24 hours = **5,760 GC pauses/day**

**Step 2 — Requests affected per pause:**
1M transactions/day ÷ 86,400 sec = ~11.57 tx/sec
Each 150ms pause affects: `11.57 tx/sec × 0.15 sec = ~1.74 in-flight transactions per pause`
`5,760 pauses × 1.74 in-flight = ~10,022 transactions exposed to GC per day`

**Step 3 — Abandonment:**
`10,022 × 0.5% = ~50 abandoned transactions/day`

**Step 4 — Annual revenue loss:**
`50 abandoned/day × $12 avg × 365 days = **$219,000/year**`

This is a conservative model using average in-flight exposure. Under burst load the figure is higher. The key insight: 0.5% of 10k exposed transactions is 50 lost — not 0.5% of 1M total.

**Staff-level phrasing:** "Our 150ms GC pauses abandon roughly 50 transactions per day — $219k/year in lost revenue — which a single-sprint off-heap migration eliminates entirely."

<summary>Exercise 4 — GcCostMonitor (coding challenge)</summary>

```java
import java.lang.management.GarbageCollectorMXBean;
import java.lang.management.ManagementFactory;
import java.util.List;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

/**
 * GcCostMonitor — polls GC stats every 5 seconds and estimates revenue loss.
 *
 * Revenue loss formula: $10/ms of GC pause per 1,000 RPS.
 * Adjust RPS via the constant below for your environment.
 *
 * Run: java GcCostMonitor
 */
public class GcCostMonitor {

    private static final double COST_PER_MS_PER_1K_RPS = 10.0;
    private static final int ASSUMED_RPS = 5_000; // tune to your service

    // Snapshot from previous poll to compute deltas
    private static long prevTotalPauseMs = 0;
    private static long prevTotalCollections = 0;

    public static void main(String[] args) throws InterruptedException {
        List<GarbageCollectorMXBean> gcBeans =
            ManagementFactory.getGarbageCollectorMXBeans();

        System.out.println("GcCostMonitor started. Polling every 5 seconds...");
        System.out.printf("Assumed RPS: %,d | Cost model: $%.0f/ms/1k-RPS%n%n",
            ASSUMED_RPS, COST_PER_MS_PER_1K_RPS);

        var scheduler = Executors.newSingleThreadScheduledExecutor();
        scheduler.scheduleAtFixedRate(() -> poll(gcBeans), 0, 5, TimeUnit.SECONDS);

        // Run for demonstration; in production, keep alive indefinitely
        TimeUnit.MINUTES.sleep(Long.MAX_VALUE);
    }

    private static void poll(List<GarbageCollectorMXBean> gcBeans) {
        long totalPauseMs = 0;
        long totalCollections = 0;

        for (GarbageCollectorMXBean gc : gcBeans) {
            long ct = gc.getCollectionTime();
            long cc = gc.getCollectionCount();
            if (ct > 0) {
                totalPauseMs += ct;
                totalCollections += cc;
            }
        }

        long deltaPauseMs = totalPauseMs - prevTotalPauseMs;
        long deltaCollections = totalCollections - prevTotalCollections;

        prevTotalPauseMs = totalPauseMs;
        prevTotalCollections = totalCollections;

        if (deltaCollections == 0) {
            System.out.println("[GC-COST] No GC activity in last 5 seconds.");
            return;
        }

        double avgPauseMs = (double) deltaPauseMs / deltaCollections;
        // Collections per 5-second window → per minute
        double collectionsPerMin = deltaCollections * (60.0 / 5.0);
        // Revenue loss: $10/ms × (RPS/1000) × total pause ms in this window
        double revenueLossPerHr = deltaPauseMs * COST_PER_MS_PER_1K_RPS
            * (ASSUMED_RPS / 1_000.0) * (3600.0 / 5.0);

        System.out.printf("[GC-COST] Pause: %.1fms | Collections/min: %.1f | Estimated revenue loss/hr: $%.2f%n",
            avgPauseMs, collectionsPerMin, revenueLossPerHr);
    }
}
```

**Why this works:** Using delta values between polls rather than cumulative totals gives you the *current* GC rate, not an average since JVM start. The revenue loss scales linearly with RPS — at 5,000 RPS (5× 1k units), a 10ms pause costs $500/hr in the model. Adjust `ASSUMED_RPS` to match your load-test baseline.

**Common mistake:** Reading `getCollectionTime()` without computing deltas. Cumulative totals tell you lifetime GC cost, not current GC pressure — a JVM that had heavy GC an hour ago but is healthy now will still show a large cumulative number, giving a false alarm.

<summary>Exercise 5 — ADR Consequences Section (off-heap Panama)</summary>

**ADR-XXXX: Use Off-Heap Panama MemorySegment for Active Order Storage**

**Consequences:**

Migrating active orders from heap-based Java objects to Panama `MemorySegment` arenas eliminates GC visibility for the hot data set, reducing p99 GC pause times from ~80ms to under 2ms at 1M concurrent orders. The annual OPEX reduction on a 100-pod fleet is approximately $158k. However, two significant costs are accepted: first, **debugging complexity increases substantially** — off-heap data is invisible to heap profilers (VisualVM, JProfiler, Eclipse MAT), requiring custom tooling or raw memory inspection to diagnose corruption; second, **developer ergonomics regress** — the Panama API (`VarHandle`, `MemoryLayout`, `Arena`) has a steeper learning curve than standard Java objects, increasing onboarding time for new team members and raising the risk of layout offset bugs that produce silent data corruption rather than a clean `NullPointerException`. Both risks are mitigated by thorough `VarHandle` unit tests and mandatory ADR documentation for any layout change.

**Staff-level phrasing:** "We trade heap-profiler visibility and developer ergonomics for $158k/year in OPEX savings and sub-2ms GC pauses — a defensible exchange documented in this ADR so future teams understand what was given up."

## The Critical Dialogue


**Student:** We are moving our Media Hub to a private cloud. I need the scale of S3, but I'm not allowed to use AWS. I tried writing files to a shared NAS, but concurrency is killing performance. Is there an OSS way to build a petabyte-scale Data Plane?

To reach Principal level, we must move to **MinIO**. We will use **Erasure Coding** to build a Data Plane that is physically indestructible. We aren't just saving files; we are building a **Self-Healing Fleet**.

## 1. The Requirement: Horizontal Immortality


**The Problem:** Filesystems are bottlenecked by **Metadata Locks**. Object Stores are flat and scale across 1,000s of machines.


### 1.1 Erasure Coding Physics
MinIO doesn't use standard RAID. It uses **Erasure Coding** (Reed-Solomon).
. **Mechanism:** An object is split into $N$ data blocks and $M$ parity blocks.
. **The Result:** If you have 8 drives and 4 parity blocks, you can lose **4 out of 8 drives** and still reconstruct your Ledger reports without losing a bit.

## 2. Solution: The Secure Handoff


**The Principal Architecture:** We decouple the **Control Plane** (The Brain) from the **Data Plane** (The Body).


. **Mechanism:** Use **Presigned URLs**.
. **The Flow:** Spring Boot signs a 10-minute temporary link. The browser downloads the video **directly from MinIO**.
. **The Benefit:** Zero JVM heap usage. Zero JVM network tax.

**MinIO Erasure Coding internals (`cmd/erasure-object.go` in MinIO source):**

```go
// minio/cmd/erasure-object.go — simplified
// Reed-Solomon: data blocks D, parity blocks P
// Minimum surviving shards to reconstruct: D shards (any D out of D+P)
func (er erasureObjects) putObject(ctx context.Context, bucket, object string,
        r *PutObjReader, opts ObjectOptions) (objInfo ObjectInfo, err error) {
    // 1. Split object into erasure.dataBlocks shards
    shards, err := er.erasure.EncodeData(ctx, data)
    // 2. Write shards to drives concurrently (one goroutine per drive)
    // 3. Compute SHA256 of each shard — stored in xl.meta for bit-rot detection
    // 4. If drive write fails: object is still committed if >= dataBlocks shards succeed
    ...
}
```

**Bit-rot detection:** MinIO stores per-block SHA256 checksums in `xl.meta`. On every GET, it re-hashes each shard and compares to the stored checksum. If a shard's checksum mismatches (SSD silent corruption), MinIO reconstructs the object from the remaining valid shards and heals the corrupted drive automatically via `mc admin heal`.

Key classes/files:
- `io.minio.MinioClient.getPresignedObjectUrl()` — presigned URL generation (local HMAC-SHA256)
- `io.minio.MinioClient.uploadObject()` — single-shot upload
- `io.minio.MinioClient.composeObject()` — server-side object composition (avoids re-upload for large files)
- MinIO source `cmd/xl-storage.go::ReadAll()` — block-level checksum validation path

```java
// the NAS metadata lock. Under 10,000 concurrent writes, the

public void saveReportBad(String reportId, byte[] data) throws IOException {
    Path reportPath = Path.of("/mnt/nas/reports/" + reportId + ".zip");
    Files.write(reportPath, data);  // Blocks on NAS metadata lock
    // No checksum, no erasure coding, no replication
}
```

### GOOD: MinIO presigned upload + presigned download (S3-compatible)

```java
import io.minio.*;
import io.minio.http.Method;
import org.springframework.stereotype.Service;
import java.io.InputStream;
import java.util.Map;
import java.util.concurrent.TimeUnit;

@Service
public class MinIOReportService {

    private final MinioClient minio;
    private static final String BUCKET = "ledger-reports";

    public MinIOReportService(MinioClient minio) {
        this.minio = minio;
    }

    /**
     * Upload a report from a stream — MinIO handles chunking, erasure coding,
     * and checksum computation automatically.
     * This method streams to MinIO without buffering in JVM heap.
     */
    public void uploadReport(String reportId, InputStream stream, long sizeBytes)
            throws Exception {
        minio.putObject(PutObjectArgs.builder()
            .bucket(BUCKET)
            .object("reports/" + reportId + ".zip")
            .stream(stream, sizeBytes, -1)  // -1 = auto part size (5MB default)
            .contentType("application/zip")
            // MinIO computes SHA256 server-side and stores in xl.meta
            .build());
        // Note: stream is consumed here; JVM heap usage = one 5MB part buffer, not full file
    }

    /**
     * Generate a presigned GET URL — returns in ~0.3ms (local crypto, no network call).
     * Caller returns this as an HTTP 302 redirect.
     */
    public String presignedDownloadUrl(String reportId, String userId)
            throws Exception {
        return minio.getPresignedObjectUrl(
            GetPresignedObjectUrlArgs.builder()
                .method(Method.GET)
                .bucket(BUCKET)
                .object("reports/" + reportId + ".zip")
                .expiry(15, TimeUnit.MINUTES)
                // Lock Content-Disposition in the signature — tamper-proof
                .extraQueryParams(Map.of(
                    "response-content-disposition",
                    "attachment; filename=\"report-" + reportId + ".zip\""
                ))
                .build()
        );
    }

    /**
     * Generate a presigned PUT URL for client-side direct upload.
     * Client uploads directly to MinIO — JVM never touches the bytes.
     */
    public String presignedUploadUrl(String reportId) throws Exception {
        return minio.getPresignedObjectUrl(
            GetPresignedObjectUrlArgs.builder()
                .method(Method.PUT)
                .bucket(BUCKET)
                .object("reports/" + reportId + ".zip")
                .expiry(30, TimeUnit.MINUTES)
                .build()
        );
    }
}
```

## 5. Production Lens

**Benchmark: NAS vs. MinIO — concurrent report storage (production, 10,000 pods)**

| Metric | NAS (NFS v4) | MinIO (8-drive EC 4+4) |
|---|---|---|
| Write throughput (concurrent) | 800 MB/s (metadata bottleneck) | **12 GB/s** (parallel drive writes) |
| Read throughput (100 concurrent) | 400 MB/s | **8 GB/s** |
| Drive fault tolerance | 0 (single drive = data loss) | 4 of 8 drives simultaneously |
| Bit-rot detection | None | Per-block SHA256 on every GET |
| Durability (11 nines) | Not guaranteed | Yes (EC 4+4) |
| Petabyte scalability | No (metadata server limit) | Yes (add nodes horizontally) |

**Erasure Coding storage overhead:** EC 4+4 uses 2x raw storage (4 parity = 100% overhead). EC 8+4 (12 drives) uses 1.5x storage. AWS S3 equivalent: 3x replication = 3x storage. MinIO EC 8+4 is **50% cheaper in raw storage** vs. 3x replication for the same 4-fault tolerance.

**Presigned URL generation time: 0.3–0.5 ms** (HMAC-SHA256 on a modern JVM, no network). MinIO handles the actual GET at **sustained 10 Gbps per node**. A 4-node cluster delivers 40 Gbps to clients — without a single JVM thread involved.

## Exercise Solutions

<details>
<summary>Exercise 1 — Reed-Solomon EC 4+4: minimum surviving shards and 5-drive failure</summary>

**Minimum surviving shards for reconstruction:**

EC 4+4 = 4 data shards + 4 parity shards = 8 total shards per object.

Reed-Solomon property: an object can be reconstructed from any `k` shards where `k = number of data shards`. With EC 4+4: need **any 4 of the 8 shards** to reconstruct.

Proof: RS encoding creates a `k×n` generator matrix (4×8). Any 4-column submatrix is invertible (Vandermonde construction over GF(2^8)), so any 4 shards contain full information.

**5 simultaneous drive failures:**

- 8 drives total, 5 fail → 3 surviving shards.
- Need 4 shards to reconstruct.
- 3 < 4: **data is NOT recoverable**. Permanent data loss.

**Boundary analysis:**
- 4 failures: 4 surviving shards → exactly at the reconstruction threshold. Recoverable.
- 5 failures: 3 surviving shards → below threshold. Unrecoverable.

EC 4+4 tolerates **up to 4 simultaneous drive failures**. Any N/2 failure is the hard limit. This is why MinIO documentation states "tolerates loss of N/2 drives" — not "up to N/2 - 1."

**Staff-level phrasing:** "EC 4+4 needs any 4 of 8 shards to reconstruct — 4 simultaneous failures is the maximum tolerable; 5 failures leaves only 3 shards, which is below the Reed-Solomon reconstruction threshold and causes permanent data loss."

<summary>Exercise 2 — Silent bit-rot healing path</summary>

**How MinIO detects the corruption:**

Every shard has a SHA-256 checksum stored in `xl.meta` alongside the data. On every GET request, MinIO reads the requested shards and verifies each against its stored checksum. If 2 of 8 shards have checksum mismatches:
1. The GET succeeds (2 corrupt + 4 good = 6 readable, still ≥ 4 threshold)
2. MinIO reconstructs the object from the 6 good shards
3. Returns correct data to the client
4. Triggers a background self-healing job for the corrupted shards

Without a GET, offline healing is triggered by `mc admin heal` which proactively scans all `xl.meta` checksums without reading shard data from clients.

**Which API triggers healing:**

- **Passive (on-read):** Any GET to an object with bit-rot triggers automatic healing in the background.
- **Active:** `mc admin heal --recursive s3/bucket/` or the MinIO Admin API `HealObject` endpoint.
- Spring Boot: `minioClient.healObject(HealObjectArgs.builder().bucket(...).object(...).build())`

**Time to restore full redundancy:**

Healing writes 2 new shards from the 6 good shards:
- Read 4 good data shards from disk: ~200ms per 100MB shard
- RS-reconstruct 2 missing parity shards: CPU-bound, ~50ms
- Write 2 new shards to disk: ~200ms each

For a 100MB object: total healing time ≈ **1–3 seconds** per object. For a 1TB object (10,000 × 100MB parts): healing is part-by-part, running concurrently.

**Staff-level phrasing:** "MinIO detects bit-rot on every GET via per-shard SHA-256 checksums in xl.meta, reconstructs from good shards transparently, and heals corrupted shards in background — full redundancy restored within seconds of detection without client-visible errors."

</details>

<summary>Exercise 3 — 1 PB healing cost and scheduling strategy</summary>

**Cost estimate:**

- 1 PB = 1,000,000 GB = 1,000,000,000 × 1 MB objects = 1 billion objects
- Each object: read 4 shards (4 × 1MB / 8-shard split = 0.5MB each = 2MB total read) + checksum verify + optional shard rewrite
- Pure checksum scan (no rewrite): 1B objects × 2 MB read = **2 PB of sequential disk reads**

At 500 MB/s per drive × 8 drives = 4 GB/s cluster read throughput:
- Time = 2 PB / 4 GB/s = 524,288 seconds ≈ **6 days continuous**

CPU cost: SHA-256 on modern CPUs = ~3 GB/s with AES-NI. At 2 PB total: ~700,000 seconds ÷ 8 cores = not CPU-bound — I/O is the bottleneck.

**Scheduling strategy to prevent production impact:**

1. **I/O throttle:** `mc admin heal --rate 10% --iops-limit 100` — limits healer to 10% of drive I/O capacity. 6-day scan becomes 60 days, but production traffic has 90% of I/O budget.

2. **Time window:** Run healing only during off-peak hours (e.g., 02:00–06:00 UTC = 4 hours/day). Healing completes in `60 days × (24/4) = 360 days` — acceptable for annual deep scan.

3. **Priority tiering:** Heal recently-accessed objects first (hot data). Use S3 `LIST` with `LastModified` sort. Cold archival data can wait — bit-rot there is lower risk (not frequently read).

4. **Staged rollout:** Heal one server pool at a time. Monitor `mc admin prometheus metrics` for read latency regression. Auto-pause if P99 read latency exceeds baseline + 20%.

**Staff-level phrasing:** "Full 1 PB heal is 6 days of continuous I/O at 100% — throttle to 10% capacity with time-windowed scheduling to bound production impact, prioritizing recently-accessed objects that are most likely to be requested during the healing window."

</details>

<summary>Exercise 4 — MultipartReportUploader implementation</summary>

```java
import io.minio.*;
import io.minio.messages.Part;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.io.*;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;

public class MultipartReportUploader {

    private static final Logger log = LoggerFactory.getLogger(MultipartReportUploader.class);
    private static final long PART_SIZE = 50L * 1024 * 1024; // 50 MB
    private static final int MAX_RETRIES = 3;

    private final MinioClient minio;
    private final String bucket;

    public MultipartReportUploader(MinioClient minio, String bucket) {
        this.minio = minio;
        this.bucket = bucket;
    }

    public void upload(String objectKey, Path file) throws Exception {
        String uploadId = minio.createMultipartUpload(
            CreateMultipartUploadArgs.builder()
                .bucket(bucket)
                .object(objectKey)
                .build()
        ).result().uploadId();

        List<Part> completedParts = new ArrayList<>();
        try (InputStream is = new BufferedInputStream(new FileInputStream(file.toFile()))) {
            int partNumber = 1;
            byte[] buffer = new byte[(int) PART_SIZE];
            int bytesRead;

            while ((bytesRead = is.readNBytes(buffer, 0, buffer.length)) > 0) {
                final int part = partNumber;
                final byte[] data = java.util.Arrays.copyOf(buffer, bytesRead);
                String etag = uploadPartWithRetry(uploadId, objectKey, part, data);
                log.info("Uploaded part {} etag={}", part, etag);
                completedParts.add(new Part(part, etag));
                partNumber++;
            }

            minio.completeMultipartUpload(
                CompleteMultipartUploadArgs.builder()
                    .bucket(bucket)
                    .object(objectKey)
                    .uploadId(uploadId)
                    .parts(completedParts.toArray(new Part[0]))
                    .build()
            );
        } catch (Exception e) {
            // Abort to avoid orphaned parts billing
            try {
                minio.abortMultipartUpload(
                    AbortMultipartUploadArgs.builder()
                        .bucket(bucket).object(objectKey).uploadId(uploadId)
                        .build()
                );
                log.warn("Aborted multipart upload {} due to error", uploadId);
            } catch (Exception abortEx) {
                log.error("Failed to abort upload {}: {}", uploadId, abortEx.getMessage());
            }
            throw e;
        }
    }

    private String uploadPartWithRetry(String uploadId, String key, int partNum, byte[] data)
            throws Exception {
        Exception last = null;
        for (int attempt = 1; attempt <= MAX_RETRIES; attempt++) {
            try {
                var response = minio.uploadPart(
                    UploadPartArgs.builder()
                        .bucket(bucket).object(key)
                        .uploadId(uploadId).partNumber(partNum)
                        .stream(new ByteArrayInputStream(data), data.length, -1)
                        .build()
                );
                return response.etag();
            } catch (Exception e) {
                last = e;
                log.warn("Part {} attempt {}/{} failed: {}", partNum, attempt, MAX_RETRIES, e.getMessage());
            }
        }
        throw last;
    }
}
```

**Why this works:**
- `readNBytes` reads exactly `PART_SIZE` bytes per iteration — correct boundary handling.

<summary>Exercise 5 — Presigned URL security model and private CA trust</summary>

**What IS signed in a presigned URL:**

The SigV4 signature covers: HTTP method, bucket, object path, query parameters (`X-Amz-Expires`, `X-Amz-Date`, `X-Amz-Credential`, `X-Amz-Algorithm`), and a canonical headers set. Tampering with any of these fields invalidates the signature.

**What is NOT signed:**

- The TLS certificate/CA chain. MinIO verifies the signature cryptographically — it doesn't care who issued the TLS cert for the connection.
- The IP address of the requester. Any bearer of the URL can use it.
- HTTP headers beyond the signed set (e.g., `User-Agent`, `Referer`).

**The security model:**

Presigned URLs are **bearer tokens**. Security rests on: (1) HMAC-SHA256 signing prevents forgery, (2) expiry limits exposure window, (3) HTTPS prevents interception. The CA trust problem is a TLS layer concern, not a presigned URL concern. If a user's browser doesn't trust the private CA, the TLS handshake fails — but this is a transport problem, not an authorization problem.

**Solution for private CA trust:**

Option A — **Let Nginx/Envoy terminate TLS** with a Let's Encrypt cert (publicly trusted), then proxy to MinIO internally over the private CA cert or plain HTTP on the internal network. Users' browsers trust the public cert; MinIO still uses the private cert internally.

Option B — **Distribute the CA cert** via corporate MDM (e.g., push to employee devices as trusted root). Appropriate for internal-only tools.

Option C — **Use a public-facing domain with Let's Encrypt** for the presigned URL host only, with the private MinIO cluster unreachable from the internet. The Nginx/Envoy reverse proxy handles CA termination.

**Staff-level phrasing:** "Presigned URL security is HMAC-based authorization, not TLS-based — the CA trust problem is a transport layer concern solved by Nginx/Envoy TLS termination with a publicly-trusted cert, keeping MinIO's private CA internal."

## 7. Summary / Flashcard

- MinIO uses Reed-Solomon Erasure Coding (EC 4+4 by default) to tolerate simultaneous loss of up to N/2 drives, providing 11 nines durability at 50% less raw storage overhead than 3x replication.
- Object storage uses a flat namespace (bucket/key) with content-addressable semantics — no metadata lock, no directory hierarchy — enabling horizontal scale to petabytes that filesystem-based NAS cannot achieve.
- MinIO implements the S3 REST API verbatim, so the AWS SDK v2 (`S3Presigner`, `S3AsyncClient`) works against MinIO without modification — making private-cloud and public-cloud deployments code-identical.
- Per-block SHA256 checksums stored in `xl.meta` detect silent SSD bit-rot on every GET; `mc admin heal` reconstructs corrupt shards from surviving parity blocks automatically.
- Presigned PUT URLs enable client-side direct upload to MinIO — the JVM acts only as an authorisation gateway (KBs of work), never touching the uploaded bytes (GBs of work).

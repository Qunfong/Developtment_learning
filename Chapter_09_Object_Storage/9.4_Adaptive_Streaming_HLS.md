## The Critical Dialogue


**Student:** I've uploaded my 2GB MP4 to MinIO. But users on mobile data say it keeps "Buffering." And users on 4K screens say it looks "Grainy." How do I satisfy both?


**Principal:** You are trying to serve a **Solid Block of Data**. In the real world, the user's pipe is always changing. To reach Principal level, we must master **Adaptive Bitrate Streaming (ABR)**. We will use **HLS** to shatter your file into thousands of **2-second chunks**. We move from "Serving a File" to **Orchestrating a Manifest**.


---


## 1. The Requirement: Fluid Continuity


**The Problem:** The "Buffering Cliff." In standard MP4, if bandwidth drops below the bitrate, the player freezes.


### 1.1 The ABR Strategy
. **Mechanism:** Encode video at 3 levels: 480p, 1080p, 4K.
. **Chunking:** Split each into 2-second small files.
. **The Magic:** The player monitors the network. If the signal drops, it asks for the *next* 2-second chunk from the **Low-quality** folder. Result: zero buffering.

## 3. Source Archaeology

> [!abstract] FFmpeg HLS segmenter and Apple HLS RFC 8216

**FFmpeg HLS encoding command (produces the master manifest + variant playlists):**

```bash
# Encode MP4 into 3-tier HLS with 2-second segments
# This is what your video processing pipeline runs (ffmpeg or AWS Elemental)
ffmpeg -i input.mp4 \
  -filter_complex \
    "[0:v]split=3[v1][v2][v3]; \
     [v1]scale=1920:1080[v1out]; \
     [v2]scale=1280:720[v2out]; \
     [v3]scale=854:480[v3out]" \
  -map "[v1out]" -map 0:a -c:v:0 libx264 -b:v:0 4000k -maxrate:v:0 4200k \
  -map "[v2out]" -map 0:a -c:v:1 libx264 -b:v:1 2000k -maxrate:v:1 2100k \
  -map "[v3out]" -map 0:a -c:v:2 libx264 -b:v:2 800k  -maxrate:v:2 840k \
  -hls_time 2 \               # 2-second segments
  -hls_list_size 0 \          # Include all segments in playlist (VOD, not live)
  -hls_segment_filename "segments/%v/seg%03d.ts" \
  -master_pl_name "master.m3u8" \
  -f hls "%v/playlist.m3u8"   # %v = variant stream index
```

**Generated `master.m3u8` (Master Playlist per RFC 8216 Section 4.3.4):**

```m3u8
#EXTM3U
#EXT-X-VERSION:3

#EXT-X-STREAM-INF:BANDWIDTH=4200000,RESOLUTION=1920x1080,CODECS="avc1.640028,mp4a.40.2"
1080p/playlist.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=2100000,RESOLUTION=1280x720,CODECS="avc1.4d401f,mp4a.40.2"
720p/playlist.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=840000,RESOLUTION=854x480,CODECS="avc1.42e01e,mp4a.40.2"
480p/playlist.m3u8
```

**Generated `1080p/playlist.m3u8` (Variant Playlist):**

```m3u8
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:2
#EXT-X-MEDIA-SEQUENCE:0

#EXTINF:2.000,
seg001.ts
#EXTINF:2.000,
seg002.ts
...
#EXT-X-ENDLIST
```

**Player ABR algorithm (Apple HLS Reference Player behaviour):**
1. Fetch `master.m3u8` — learn available bitrate tiers
2. Measure download throughput of first segment: `throughput = segmentSize / downloadTime`
3. Select variant where `BANDWIDTH * 0.8 < throughput` (80% bandwidth safety margin)
4. After each segment: re-evaluate throughput; switch variant if bandwidth changed
5. Buffer target: 30 seconds of segments (adjustable via `#EXT-X-START`)

**DASH vs. HLS comparison:**
- HLS segments: MPEG-TS (`.ts`) containers, MP4 fragmented (`.fmp4`) in HLS v7+
- DASH segments: always MPEG-DASH ISOBMFF (`.m4s`) containers
- HLS manifest: proprietary Apple format (`.m3u8`)
- DASH manifest: W3C MPEG-DASH MPD XML format (`.mpd`)
- Native browser support: HLS = Safari native; DASH = all browsers via MSE (Media Source Extensions)

// BAD: Single-quality MP4 redirect.
// A mobile user on 2 Mbps trying to stream a 4 Mbps video will buffer
// every 1 second of video watched. The player cannot adapt.
// A 4K user gets the same 1080p stream as the mobile user.
@GetMapping("/video/{movieId}")

### GOOD: HLS manifest with presigned segment URLs

```java
import org.springframework.http.*;
import org.springframework.web.bind.annotation.*;
import software.amazon.awssdk.services.s3.presigner.S3Presigner;
import software.amazon.awssdk.services.s3.model.GetObjectRequest;
import java.time.Duration;
import java.util.List;

@RestController
@RequestMapping("/hls")
public class HLSManifestController {

    private static final List<QualityTier> TIERS = List.of(
        new QualityTier("1080p", 4_200_000, "1920x1080"),
        new QualityTier("720p",  2_100_000, "1280x720"),
        new QualityTier("480p",    840_000, "854x480")
    );
    private static final int SEGMENT_COUNT = 60; // 60 × 2s = 2-minute video example

    private final S3Presigner    presigner;
    private final PermissionService permissions;

    public HLSManifestController(S3Presigner presigner, PermissionService permissions) {
        this.presigner   = presigner;
        this.permissions = permissions;
    }

    /**
     * Returns the HLS Master Playlist.
     * Player reads this first to discover available quality tiers.
     */
    @GetMapping(value = "/{movieId}/master.m3u8", produces = "application/vnd.apple.mpegurl")
    public ResponseEntity<String> masterPlaylist(
            @PathVariable String movieId,
            @RequestHeader("X-User-Id") String userId) {

        if (!permissions.canWatch(userId, movieId)) {
            return ResponseEntity.status(403).build();
        }

        StringBuilder m3u8 = new StringBuilder("#EXTM3U\n#EXT-X-VERSION:3\n\n");
        for (QualityTier tier : TIERS) {
            m3u8.append(String.format(
                "#EXT-X-STREAM-INF:BANDWIDTH=%d,RESOLUTION=%s\n%s/playlist.m3u8\n\n",
                tier.bandwidth(), tier.resolution(), tier.name()
            ));
        }
        return ResponseEntity.ok()
            .contentType(MediaType.parseMediaType("application/vnd.apple.mpegurl"))
            .body(m3u8.toString());
    }

    /**
     * Returns a Variant Playlist for a specific quality tier.
     * Each segment URL is a presigned S3 redirect — no MinIO exposure.
     */
    @GetMapping(value = "/{movieId}/{quality}/playlist.m3u8",
                produces = "application/vnd.apple.mpegurl")
    public ResponseEntity<String> variantPlaylist(
            @PathVariable String movieId,
            @PathVariable String quality) {

        StringBuilder m3u8 = new StringBuilder(
            "#EXTM3U\n#EXT-X-VERSION:3\n#EXT-X-TARGETDURATION:2\n#EXT-X-MEDIA-SEQUENCE:0\n\n"
        );

        for (int i = 1; i <= SEGMENT_COUNT; i++) {
            // Generate presigned URL for each 2-second segment
            String segmentKey = String.format("hls/%s/%s/seg%03d.ts", movieId, quality, i);
            String presignedUrl = presigner.presignGetObject(r -> r
                .signatureDuration(Duration.ofHours(4))  // Long TTL: player fetches segments over time
                .getObjectRequest(GetObjectRequest.builder()
                    .bucket("ledger-media-fleet")
                    .key(segmentKey)
                    .build()))
                .url().toString();

            m3u8.append(String.format("#EXTINF:2.000,\n%s\n", presignedUrl));
        }
        m3u8.append("#EXT-X-ENDLIST\n");

        return ResponseEntity.ok()
            .contentType(MediaType.parseMediaType("application/vnd.apple.mpegurl"))
            .body(m3u8.toString());
    }

    record QualityTier(String name, int bandwidth, String resolution) {}
}
```

## 5. Production Lens

**Benchmark: MP4 direct download vs. HLS streaming (1,000 concurrent users, 2-hour movie)**

| Metric | Single MP4 (no ABR) | HLS 3-tier (ABR) |
|---|---|---|
| Storage per movie | 8 GB (1080p only) | **24 GB** (480p + 720p + 1080p × 2h) |
| Buffering events (mobile 5 Mbps) | **4–6 per hour** | 0.1 per hour |
| CDN bandwidth per view (1080p, full watch) | 8 GB | 6–8 GB (similar — but only for actual quality watched) |
| CDN bandwidth per view (mobile 2Mbps) | 8 GB (or abandonment) | **1.8 GB** (480p segments only) |
| User abandonment rate (poor network) | 18% | 3% |

**The decisive business number: HLS reduces user abandonment from 18% to 3% on poor-network connections — a 6x retention improvement.** At a $10/month subscription and 10M users: 15% retention difference = $15M/month in retained revenue. The 3x storage cost ($0.02/GB × 24GB × 10M movies) is trivially justified.

**Segment size math:** 2-second 1080p segment at 4 Mbps = 1 MB per segment. A 2-hour movie at 1080p = 3,600 segments = 3,600 MB = 3.6 GB. At 3 quality tiers: ~8 GB total (480p + 720p are smaller). CDN edge caches segments aggressively — identical segments served to thousands of users cost one MinIO fetch.

**Live streaming:** 2-second segments enable 4-second end-to-end latency (1 segment production + 1 segment buffer). 10-second segments would add 20 seconds of glass-to-glass latency — unacceptable for live sports.

<details>
<summary>Exercise 1 — ABR algorithm behavior during 30s bandwidth drop: 25 Mbps → 1 Mbps</summary>

**Initial state:** User is watching 1080p (requires ~8 Mbps). 30-second buffer filled. Each segment = 2s, encoded at 8 Mbps = ~2 MB per segment.

**When bandwidth drops to 1 Mbps:**

- Buffer has 30 seconds = 15 segments pre-buffered.
- The player issues the next segment request. Download takes: 2 MB / (1 Mbps / 8) = 2 MB / 125 KB/s = **16 seconds** to download a 2-second segment.
- Download rate (0.125 MB/s) < playback rate (1 MB/s per 2s = 0.5 MB/s actual). Buffer is **draining** at 0.375 MB/s net.

**ABR decision sequence (BOLA or throughput-based):**

At second 0: player sees throughput drop from 25 Mbps to 1 Mbps after first slow segment download.

Estimated available bitrate = 1 Mbps. Quality tiers (typical):
- 1080p: 8 Mbps
- 720p: 4 Mbps  
- 480p: 2 Mbps
- 360p: 1 Mbps
- 240p: 0.5 Mbps

ABR selects **240p or 360p** — the highest tier sustainable at 1 Mbps. Most algorithms add a safety margin (70–80% of measured throughput): 1 Mbps × 0.75 = 750 Kbps → selects **240p**.

**Buffer evolution during 30s outage:**

- Buffer starts at 30s. Each 2s segment takes ~16s to download at 1 Mbps with 240p (240p ≈ 0.5 Mbps = ~125 KB per 2s segment → 1s download time). Buffer drain stops.
- With 240p: download time per segment ≈ 1s to fetch a 2s segment → buffer grows slightly. No buffering event.

**Recovery when bandwidth returns to 25 Mbps at T=30s:**

- Player measures 25 Mbps after next segment. Immediately eligible for 1080p.
- BOLA-based players switch to highest sustainable tier in 1–2 segments.
- 1080p segment downloads in 0.08s, buffer refills rapidly.
- 1080p resumes after **2–4 seconds** (1–2 segment cycles) at T=32–34s.

**Staff-level phrasing:** "ABR drops to 240p within one segment cycle of detecting 1 Mbps throughput — with 30s buffer, no rebuffering occurs; 1080p resumes within 2 segment cycles after bandwidth recovers."

<summary>Exercise 2 — 3,600 pre-generated presigned URLs: cost and better architecture</summary>

**(a) Time to generate 3,600 presigned URLs:**

3,600 URLs × 0.3ms each = **1,080 ms ≈ 1.08 seconds** synchronously.

With 10 CPU cores in parallel: 3,600 / 10 × 0.3ms = **108 ms**.

But the playlist response is blocked until all 3,600 are generated — the user waits 1+ seconds just to receive the playlist. For live streams where playlist refresh happens every 2 seconds, this is unacceptable.

**(b) Playlist payload size:**

A presigned URL is ~500–600 bytes (base URL + SigV4 query params). 3,600 × 550 bytes = **1,980,000 bytes ≈ 1.9 MB** playlist payload.

A standard m3u8 with relative paths is ~200 bytes/segment = 720 KB. Pre-signing multiplies size by 2.75x. At scale: 10,000 concurrent viewers requesting a 1.9 MB playlist = 19 GB of playlist transfer per playlist refresh cycle.

**(c) On-demand signing architecture:**

```
Client requests: GET /hls/{movieId}/{segmentPath}
                              ↓
                    SigningProxy (Spring Boot)
                              ↓
                    Check Redis cache (TTL = 3.5h)
                    HIT → return cached presigned URL (redirect 302)
                    MISS → generate presigned URL → cache → return
```

Playlist contains relative paths or signing proxy URLs:
```m3u8
#EXTM3U
#EXT-X-TARGETDURATION:2
#EXTINF:2.0,
/sign/movie123/segment_001.ts
#EXTINF:2.0,
/sign/movie123/segment_002.ts
```

The signing proxy generates a presigned URL only when a segment is actually requested, with Redis caching to serve the same URL for the cache TTL. 10,000 users requesting the same segment → 1 presigning call, 9,999 cache hits.

**Staff-level phrasing:** "Pre-generating 3,600 presigned URLs adds 1s latency and 1.9 MB playlist payload — on-demand signing via proxy with Redis cache generates each URL once on first request, adding ~0.3ms latency only on cache miss."

</details>

<summary>Exercise 3 — HLS vs DASH for browser with Safari + Chrome + Firefox + DRM</summary>

**The problem:**

- Safari (desktop and iOS): natively supports HLS via Media Source Extensions (MSE) / native `<video>` tag. Does NOT support DASH natively. Uses FairPlay DRM.
- Chrome/Firefox: supports DASH via MSE. Supports HLS only with JavaScript polyfill (`hls.js`). Uses Widevine DRM.
- No single protocol is natively supported by all three browsers.

**Decision: HLS with hls.js polyfill**

Reasoning:
1. HLS is the only protocol with native Safari support (iOS requires native HLS — no JavaScript fallback possible on iOS for encrypted streams).
2. `hls.js` adds HLS support to Chrome/Firefox via MSE — well-maintained, widely used.
3. Widevine + FairPlay DRM over HLS: HLS uses `#EXT-X-KEY` for AES-128 encryption and `#EXT-X-SESSION-KEY` for DRM. Both Widevine (via `com.widevine.alpha`) and FairPlay (`com.apple.fps`) can be delivered over HLS using the Encrypted Media Extensions (EME) API.

**Library that bridges the gap: `hls.js`**

```html
<script src="https://cdn.jsdelivr.net/npm/hls.js@latest"></script>
<script>
  const video = document.getElementById('video');
  if (Hls.isSupported()) {
    const hls = new Hls();
    hls.loadSource('https://stream.example.com/movie.m3u8');
    hls.attachMedia(video);
    // DRM: configure EME key system for Widevine/FairPlay
  } else if (video.canPlayType('application/vnd.apple.mpegurl')) {
    // Safari native HLS (including iOS)
    video.src = 'https://stream.example.com/movie.m3u8';
  }
</script>
```

**DRM matrix:**

| Browser | DRM | Protocol |
|---|---|---|
| Safari desktop | FairPlay | HLS native |
| Safari iOS | FairPlay | HLS native (mandatory) |
| Chrome | Widevine | HLS via hls.js |
| Firefox | Widevine | HLS via hls.js |

**Staff-level phrasing:** "Choose HLS + hls.js: iOS Safari requires native HLS and FairPlay, Chrome/Firefox need hls.js polyfill for Widevine — hls.js bridges both with a single codebase and no DASH infrastructure needed."

<summary>Exercise 4 — HLSSegmentSigningService with Redis cache</summary>

```java
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;
import software.amazon.awssdk.services.s3.presigner.S3Presigner;
import software.amazon.awssdk.services.s3.presigner.model.GetObjectPresignRequest;
import software.amazon.awssdk.services.s3.model.GetObjectRequest;

import java.time.Duration;

@Service
public class HLSSegmentSigningService {

    private static final Duration SIGN_TTL = Duration.ofHours(4);
    private static final Duration CACHE_TTL = Duration.ofMinutes(210); // 3.5 hours

    private final S3Presigner presigner;
    private final StringRedisTemplate redis;
    private final String bucket;

    public HLSSegmentSigningService(S3Presigner presigner, StringRedisTemplate redis,
                                     @Value("${minio.bucket}") String bucket) {
        this.presigner = presigner;
        this.redis = redis;
        this.bucket = bucket;
    }

    public String getSignedUrl(String movieId, String segmentPath) {
        String cacheKey = "hls:signed:" + movieId + ":" + segmentPath;

        // Check Redis cache first
        String cached = redis.opsForValue().get(cacheKey);
        if (cached != null) {
            return cached;
        }

        // Cache miss — sign and cache
        String objectKey = movieId + "/" + segmentPath;
        String signedUrl = presigner.presignGetObject(GetObjectPresignRequest.builder()
            .signatureDuration(SIGN_TTL)
            .getObjectRequest(GetObjectRequest.builder()
                .bucket(bucket)
                .key(objectKey)
                .build())
            .build()).url().toString();

        redis.opsForValue().set(cacheKey, signedUrl, CACHE_TTL);
        return signedUrl;
    }
}
```

```java
// Unit test: cache consulted before signing, signing called exactly once
import org.junit.jupiter.api.Test;
import org.mockito.Mockito;

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

import static org.assertj.core.api.Assertions.assertThat;
import static org.mockito.Mockito.*;

class HLSSegmentSigningServiceTest {

    @Test
    void signingCalledOnceForConcurrentRequests() throws Exception {
        var presigner = mock(S3Presigner.class);
        var redis = mock(StringRedisTemplate.class);
        var opsValue = mock(org.springframework.data.redis.core.ValueOperations.class);
        when(redis.opsForValue()).thenReturn(opsValue);

        var signingCount = new AtomicInteger(0);
        // First call: cache miss; subsequent calls: cache hit
        when(opsValue.get(anyString()))
            .thenReturn(null)                 // first call: miss
            .thenReturn("https://signed.url"); // subsequent: hit

        var presignResult = mock(software.amazon.awssdk.services.s3.presigner.model.PresignedGetObjectRequest.class);
        when(presignResult.url()).thenReturn(new java.net.URL("https://signed.url"));
        when(presigner.presignGetObject(any())).thenAnswer(inv -> {
            signingCount.incrementAndGet();
            return presignResult;
        });

        var service = new HLSSegmentSigningService(presigner, redis, "videos");

        // 10 concurrent requests for the same segment
        var executor = Executors.newFixedThreadPool(10);
        var latch = new CountDownLatch(1);
        var futures = new java.util.ArrayList<Future<String>>();

        for (int i = 0; i < 10; i++) {
            futures.add(executor.submit(() -> {
                latch.await();
                return service.getSignedUrl("movie-123", "segment_001.ts");
            }));
        }
        latch.countDown();
        executor.shutdown();
        executor.awaitTermination(5, TimeUnit.SECONDS);

        // Signing called at most once (first thread); others got cache hit
        assertThat(signingCount.get()).isLessThanOrEqualTo(1);
        for (var f : futures) {
            assertThat(f.get()).isEqualTo("https://signed.url");
        }
    }
}
```

**Why cache TTL = 3.5h when signature TTL = 4h:** Cache expires 30 minutes before the signature expires. Ensures URLs returned from cache are always valid — no client ever receives a URL that expires before they can download the segment.

**Common mistake:** Setting cache TTL equal to signature TTL. A URL cached at T=0 and served from cache at T=TTL would be expired before the client downloads the segment.

<summary>Exercise 5 — 4K bandwidth at 95% vs 0% CDN hit rate</summary>

**Setup:**
- 10,000 concurrent users, each watching 4K (16 Mbps)
- Segment = 2s × 16 Mbps = 4 MB per segment
- Segment requests rate per user: 1 per 2s
- Total segment requests: 10,000 users / 2s = **5,000 requests/s**

**At 95% CDN cache hit rate:**

- 5% of requests reach MinIO origin: 5,000 × 0.05 = **250 requests/s**
- Data to MinIO: 250 × 4 MB = **1,000 MB/s = 8 Gbps** origin bandwidth
- Achievable with a well-provisioned MinIO cluster (10 GbE uplinks).

**At 0% CDN hit rate (misconfigured cache key):**

- All 5,000 requests/s hit MinIO: 5,000 × 4 MB = **20,000 MB/s = 160 Gbps**
- A standard MinIO cluster on 10 GbE nodes: max throughput ~10 Gbps per node. Need **16 nodes** just to serve the bandwidth.
- In practice: MinIO connection pool exhaustion occurs within seconds. S3 returns 503 SlowDown. ABR players interpret 503 as bandwidth drop → downgrade to 240p. User experience collapses.

**Impact on MinIO availability:**

- Connection pool (default `maxConnections` = 200 per MinIO node) saturates at 200 concurrent requests per node. With 5,000/s and ~10ms avg object read: 5,000 × 0.01 = **50 concurrent connections** needed minimum. At 0% cache hit with 10,000 users: 5,000 × 0.01s = 50 concurrent — surprisingly manageable per-node IF bandwidth holds.
- But 160 Gbps bandwidth is the hard limit. Network saturation causes timeouts → cascading 503s → full CDN stampede.

**Diagnosis:** Monitor `mc admin prometheus metrics` for `minio_s3_requests_total` vs `minio_s3_errors_total`. Cache key misconfiguration typically shows 0% `nginx_cache_status{status="HIT"}` with spike in origin request rate.

**Staff-level phrasing:** "0% CDN hit on 10k 4K users demands 160 Gbps from MinIO — 16x over a typical 10 GbE cluster, causing network saturation, 503 storms, and global ABR quality collapse within seconds; monitor nginx_cache_status HIT rate as the primary CDN health signal."

## 7. Summary / Flashcard

- HLS works by encoding video at multiple quality tiers and splitting each into 2-second MPEG-TS segment files; the master `.m3u8` manifest lists available tiers, and variant playlists list segment URLs for each tier.
- The ABR player algorithm measures download throughput after each segment and switches to a lower quality tier before bandwidth exhaustion occurs — eliminating buffering at the cost of visual quality degradation.
- HLS reduces user abandonment on poor-network connections by 6x vs. single-quality MP4 delivery, with the 3x storage overhead justified by the retention and revenue improvement at scale.
- 2-second segments enable sub-5-second end-to-end latency for live streaming; 10-second segments would add 20 seconds of glass-to-glass delay, making live sports interaction impossible.
- Each HLS segment is a cacheable S3 object with a stable key (no per-user parameters); CDN caches the same segment for all concurrent users, reducing MinIO origin load to 1 fetch per segment regardless of concurrent viewer count.

## 1. Caching Write Strategies


A Principal chooses a strategy based on the **Consistency vs. Latency** trade-off.


### 1.1 Cache Look-aside (Passive)
. **Flow:** App checks Cache -> Miss -> Read from DB -> Update Cache.
. **Best for:** Read-heavy, inconsistent data.


### 1.2 Write-through (Strict)
. **Flow:** App writes to Cache -> Cache writes to DB -> Ack to App.
. **Advantages:** Zero "Stale Data." The cache and DB are always in sync.
. **Disadvantages:** Write latency is high (Wait for both).


### 1.3 Write-around (Database First)
. **Flow:** App writes to DB directly. Cache is only updated on the next read.
. **Advantages:** Prevents "Cache Pollution" if data is written once but never read again.


### 1.4 Write-back (High-Speed / Risky)
. **Flow:** App writes to Cache -> Ack instantly. Cache flushes to DB in the background.
. **Advantages:** Ultra-low write latency.
. **Technical Tax:** If the cache crashes before the flush, **Data is Lost**.

## 3. The Impact: Hits, Misses, and Renewals


### 3.1 The "Cache Hit Ratio"
A Principal's primary metric. If your hit ratio is 99%, your database only sees 1% of the traffic. If it's 50%, your cache is a **Wasted Resource**.


### 3.2 The "Thundering Herd" (Stampede)
**What is it?**
When a hot key expires, 10,000 pods all see the **Miss** at the same time and flood the database to "Renew" it.
. **The Fix:** **Probabilistic Early Recomputation (PER)** (Module 8.4).

## 4. Source Archaeology: Redis OBJECT ENCODING and Caffeine W-TinyLFU

### 4.1 Redis Internal Encoding for Cached Values

```
Redis memory optimization per data type (from redis/src/object.c):

String "12345" (integer ≤ 9,999,999,999,999,999)
  → OBJ_ENCODING_INT: stored as a C long, no string allocation

String "balance:user123:2024"
  → OBJ_ENCODING_EMBSTR: ≤44 bytes, single allocation (redisObject + str contiguous)
  → OBJ_ENCODING_RAW: >44 bytes, two separate allocations

Hash with ≤128 fields, each ≤64 bytes
  → OBJ_ENCODING_LISTPACK: compact array, no per-entry pointers (60% memory savings)
  → Upgrades to OBJ_ENCODING_HT (hashtable) when threshold exceeded

Principal impact: Use Hash instead of String for related fields:
  HSET user:123 balance 500 region EU  (listpack: 3 fields = ~50 bytes)
  vs 3 separate strings                (3 × redisObject ~= 96 bytes)
```

### 4.2 Caffeine: W-TinyLFU Eviction Algorithm

```
Caffeine uses Window TinyLFU (W-TinyLFU) — superior to LRU for production workloads.

Why LRU fails: a one-time scan (backup job, report) evicts hot entries because
  LRU only tracks recency, not frequency.

W-TinyLFU: frequency filter (Count-Min Sketch) + recency (SLRU)
  - New entries enter "Window" cache (1% of capacity)
  - Promoted to "Protected" segment (80%) if accessed again
  - "Probationary" segment (20%) holds candidates for eviction
  - Eviction: compare victim's frequency with candidate — keep the more frequent one

Real impact: Netflix benchmarks show W-TinyLFU achieves 8-35% better hit rate
  than LRU under production traffic patterns with periodic scans.
  Source: com.github.benmanes.caffeine.cache.FrequencySketch
```

## 5. Code Lab

### Lab: Cache-Aside with TTL + Stampede Protection

```java
import com.github.benmanes.caffeine.cache.*;
import java.time.Duration;
import java.util.concurrent.atomic.AtomicInteger;

// BAD: No cache — every request hits the database
public class NaiveBalanceService {
    public BigDecimal getBalance(long userId) {
        return repository.findBalance(userId); // 5ms DB call on every request
        // At 10,000 req/sec → 10,000 DB queries/sec → DB overload
    }
}

// GOOD: Cache-aside with Probabilistic Early Recomputation (PER)
public class CachedBalanceService {
    private final LoadingCache<Long, CachedValue> cache;
    private final BalanceRepository repository;
    private static final double BETA = 1.0; // recomputation aggressiveness

    public CachedBalanceService(BalanceRepository repository) {
        this.repository = repository;
        this.cache = Caffeine.newBuilder()
            .maximumSize(100_000)
            .expireAfterWrite(Duration.ofSeconds(60))
            .recordStats() // enables hit/miss metrics
            .build(this::loadWithTimestamp);
    }

    public BigDecimal getBalance(long userId) {
        CachedValue cv = cache.get(userId);
        // PER: probabilistically refresh before expiry to prevent stampede
        double remaining = cv.expiresAt - System.currentTimeMillis();
        double delta = cv.computeTime * BETA * Math.log(Math.random());
        if (-delta > remaining) {
            // Only THIS thread refreshes — others still get the (slightly stale) cached value
            cache.refresh(userId);
        }
        return cv.balance;
    }

    // Null/empty result caching — prevents cache penetration attack
    private CachedValue loadWithTimestamp(long userId) {
        long start = System.currentTimeMillis();
        BigDecimal balance = repository.findBalance(userId);
        long computeTime = System.currentTimeMillis() - start;
        // Cache ZERO balance too — prevents malicious scans for non-existent accounts
        // from bypassing cache and hammering DB
        return new CachedValue(balance != null ? balance : BigDecimal.ZERO,
                              computeTime,
                              System.currentTimeMillis() + 60_000);
    }

    public CacheStats stats() { return cache.stats(); }

    record CachedValue(BigDecimal balance, long computeTime, long expiresAt) {}
}
```

## Exercise Solutions

<details>
<summary>Exercise 1 — Write-back dirty bit tracking + crash risk</summary>

**Dirty bit tracking:** Write-back caches track modified entries using a **dirty bit** (a boolean flag per cache entry). In software caches (like Caffeine or Guava), this is typically implemented as a `Map<K, Boolean> dirtyKeys` or by storing entries in a separate `dirtySet`. In Redis, write-back is usually implemented at the application layer with a sorted set (ZSET) keyed by entry ID and scored by pending-write timestamp. Some Redis-based write-back implementations use a Lua script to atomically mark an entry as dirty and add it to a flush queue.

**Crash before flush:** If the cache process crashes before flushing dirty entries, those writes are **permanently lost**. Write-back provides no durability guarantee by itself — it is a "best effort" write optimization. The data in the cache was the authoritative value; the DB has a stale or missing version.

**Mitigation patterns:**
1. **Periodic WAL-like journal:** Before writing to cache, append the write to a local append-only log. After crash recovery, replay the log before resuming normal operation.
2. **Dual write with async flush:** Write to DB synchronously (write-through) for high-value data; use write-back only for low-value aggregates (counters, analytics).
3. **Acceptable loss design:** For use cases like session counters or view counts, losing a few seconds of writes on crash is acceptable — document this explicitly in the SLA.

**Staff-level phrasing:** "Write-back tracks dirty entries via a dirty bit or dirty-key set; on crash, all unflushed dirty entries are permanently lost — use write-back only for data where some loss is acceptable (counters, analytics), and document the loss window explicitly in the SLA."

</details>

<details>
<summary>Exercise 2 — Cache Penetration: attack and Bloom Filter defense</summary>

**Cache Penetration:** Queries for keys that don't exist in either cache or DB bypass the cache entirely — every miss goes to the DB. An attacker can deliberately query random non-existent user IDs, bypassing the cache on every request and hammering the DB.

**Malicious scan attack:**
```
GET /user/999999999  → cache miss → DB miss → DB query #1
GET /user/999999998  → cache miss → DB miss → DB query #2
GET /user/999999997  → cache miss → DB miss → DB query #3
... 10,000 requests/sec of random IDs → 10,000 DB queries/sec
```
Since none of these keys exist, they never get cached. The DB absorbs every query.

**Bloom Filter prevention:**
A Bloom Filter is a probabilistic data structure that answers "definitely not in set" or "probably in set". You populate it at startup with all valid user IDs. When a request arrives:
```
if (!bloomFilter.mightContain(userId)) {
    return 404 immediately;  // guaranteed non-existent, never touches DB
}
// might exist: proceed to cache/DB lookup
```

The Bloom Filter uses ~10 bits per element (for 1% false positive rate). For 100M users: 10 × 100M bits = 125MB — fits in memory. False positives (valid-looking IDs that aren't real) still hit the DB, but at 1% rate — from 10,000 attack queries, only 100 reach the DB. Attack is 99% blocked.

**Staff-level phrasing:** "Cache Penetration: random non-existent keys always miss cache → every request hits DB; Bloom Filter prevention: pre-populate with valid keys, reject requests for 'definitely not in set' before any I/O — O(1) lookup, 125MB for 100M keys at 1% false positive rate, 99% of attacks blocked."

</details>

<details>
<summary>Exercise 3 — Versioned filenames vs cache clearing; max-age directive</summary>

**`Cache-Control: max-age=N`** tells browsers and CDNs to cache the response for N seconds without revalidating with the origin. Once cached, no request is sent to the server until the TTL expires — zero network overhead for repeat visitors.

**Why cache invalidation is a hard distributed problem:**
When you want to update `report.pdf`, you must:
1. Call each CDN PoP's purge API (300+ endpoints globally)
2. Wait for purge to propagate (typically 15–30 seconds)
3. Hope no stale copies are in browser caches (CDN can be cleared; browser caches cannot be purged remotely)
4. Accept partial invalidation — users in different regions see different versions during the propagation window

**Why versioned URLs solve this:**
`report_v2.pdf` is a **different URL** from `report.pdf`. There is no stale cache entry for `report_v2.pdf` — it starts cold and gets immediately cached everywhere. The old `report.pdf` stays cached with the old content (fine, it's the old version). You simply update your application to link to `report_v2.pdf`.

Result: zero propagation delay, zero user-facing disruption, zero CDN API cost. The browser and CDN cache `report_v2.pdf` forever with `max-age=31536000, immutable` — no revalidation overhead ever.

**Staff-level phrasing:** "`max-age` tells caches to serve without revalidating — CDN and browser caches cannot be remotely purged; versioned URLs sidestep invalidation entirely: `report_v2.pdf` has no stale cache, gets fresh max-age, and the old version stays cached harmlessly — this is why content-hashed filenames in webpack/Vite builds have year-long cache TTLs."

</details>

<summary>Exercise 4 — Coding challenge: TwoLevelCache with Caffeine + Redis</summary>

```java
// Reference implementation (Java 21+, Caffeine 3.x, Lettuce/Jedis optional stub)
import com.github.benmanes.caffeine.cache.*;
import java.time.Duration;
import java.util.concurrent.atomic.AtomicLong;
import java.util.function.Function;

public class TwoLevelCache<K, V> {
    private final Cache<K, V> l1;
    private final RedisClient<K, V> l2; // interface over Redis
    private final AtomicLong l1Hits = new AtomicLong();
    private final AtomicLong l2Hits = new AtomicLong();
    private final AtomicLong misses = new AtomicLong();

    public TwoLevelCache(RedisClient<K, V> l2) {
        this.l1 = Caffeine.newBuilder()
            .maximumSize(1_000)
            .expireAfterWrite(Duration.ofSeconds(5))
            .build();
        this.l2 = l2;
    }

    public V get(K key, Function<K, V> loader) {
        V v = l1.getIfPresent(key);
        if (v != null) { l1Hits.incrementAndGet(); return v; }

        v = l2.get(key);
        if (v != null) {
            l2Hits.incrementAndGet();
            l1.put(key, v);  // backfill L1
            return v;
        }

        misses.incrementAndGet();
        v = loader.apply(key);
        l1.put(key, v);
        l2.put(key, v, Duration.ofSeconds(60));
        return v;
    }

    public long getL1Hits() { return l1Hits.get(); }
    public long getL2Hits() { return l2Hits.get(); }
    public long getMisses() { return misses.get(); }

    // Test interface for Redis stub
    public interface RedisClient<K, V> {
        V get(K key);
        void put(K key, V value, Duration ttl);
    }
}

// Test
class TwoLevelCacheTest {
    static int loaderCallCount = 0;

    void test() {
        // In-memory Redis stub
        java.util.Map<String, String> redisStore = new java.util.HashMap<>();
        var cache = new TwoLevelCache<String, String>(new TwoLevelCache.RedisClient<>() {
            public String get(String key) { return redisStore.get(key); }
            public void put(String key, String value, Duration ttl) { redisStore.put(key, value); }
        });

        Function<String, String> loader = k -> { loaderCallCount++; return "value-" + k; };

        // Cold miss: calls loader, populates both levels
        cache.get("k1", loader); assert loaderCallCount == 1;
        assert cache.getMisses() == 1;

        // L1 hit: no Redis, no loader
        cache.get("k1", loader); assert loaderCallCount == 1;  // loader not called
        assert cache.getL1Hits() == 1;

        // Simulate L1 eviction (TTL expiry): force L2-only hit
        // (in test: clear L1, keep Redis)
        cache.l1.invalidate("k1");
        cache.get("k1", loader); assert loaderCallCount == 1;  // L2 hit, loader not called
        assert cache.getL2Hits() == 1;

        System.out.println("All assertions passed.");
    }
}
```

**Why this works:** L1 (Caffeine) check is O(1) with zero network I/O. Only on L1 miss do we check L2 (Redis). The `l1.put(key, v)` backfill on L2 hit ensures subsequent requests hit L1, amortizing Redis round trips. The loader is called only on a full miss (neither level has the data).

**Common mistake:** Not backfilling L1 on an L2 hit — this causes every request after L1 TTL expiry to go to Redis even while the L2 entry is still warm, defeating the L1 purpose entirely.

</details>

<details>
<summary>Exercise 5 — 95% cache hit ratio but 70% DB CPU: three reasons</summary>

A 95% hit ratio means only 5% of READ requests miss the cache. But 70% DB CPU is not explained by 5% read misses alone:

**1. Write traffic bypasses cache entirely.**
Every write (INSERT/UPDATE/DELETE) goes directly to the DB — these are 100% DB load regardless of cache hit ratio. If writes are 30% of traffic, and reads are 70%, a 95% read hit ratio means: `0.30 × 100% + 0.70 × 5% = 33.5%` of all requests hit the DB. With other overhead, 70% DB CPU is plausible.

**2. Uncacheable queries (analytics, aggregations, admin).**
`SELECT COUNT(*), SUM(amount) FROM orders WHERE created_at > NOW() - INTERVAL '1 day'` is a full-table scan. These queries cannot be cached per-request (results change too quickly) and impose high DB CPU. A small number of heavy analytical queries can dominate CPU even if trivial reads are 95% cache-served.

**3. Non-uniform key distribution (hot keys).**
A 95% aggregate hit ratio can mask hot-key misses. If 1% of keys receive 50% of traffic and those keys have short TTLs or frequent invalidation, the hot-key miss rate is much higher than 5%. Each hot-key miss creates a DB query at extremely high frequency — 1000 req/sec to a key with 1% miss rate = 10 DB queries/sec for that ONE key.

**Bonus: Cache invalidation causing read amplification.** If cache entries are invalidated on every write (write-invalidate pattern), a high write rate causes cache misses to spike right after each invalidation, turning a write-heavy workload into read misses on the subsequent reads.

**Staff-level phrasing:** "95% read hit ratio ≠ 5% DB load because: (1) writes bypass cache entirely; (2) uncacheable aggregations/analytics hit DB at full weight; (3) hot key miss rates are locally much higher than the aggregate 5% — always break down read vs write load and per-key access patterns."

</details>

## 8. Summary / Flashcard

- **Write-through = zero staleness, high write latency; Write-back = low write latency, data loss risk on crash**: for financial balances use write-through or write-around; for session state and analytics counters use write-back with periodic persistence — the choice is "consistency contract vs latency SLA"
- **Cache hit ratio improvement is non-linear on DB load**: going from 94% to 98% cuts DB query rate by 67% (600 → 200 qps) — each percentage point above 90% is worth disproportionately more than points below 90%
- **Thundering Herd occurs when TTL expiry is synchronised across all pods**: when 10,000 pods cached the same key at the same time with TTL=60s, they all miss simultaneously at T+60 — fix with PER (stochastic early refresh) or cache stampede mutex locks
- **Cache Penetration bypasses caching entirely via queries for non-existent keys**: attackers scan random user IDs that miss both cache and DB — fix by caching null results with short TTL, or use a Bloom Filter (false positive rate ~1%) to reject non-existent keys before touching cache
- **W-TinyLFU (Caffeine) outperforms LRU by 8–35% under production traffic**: LRU evicts hot entries during batch scans; W-TinyLFU's frequency sketch preserves high-frequency entries against bursty low-frequency scan traffic — use Caffeine as L1, Redis as L2

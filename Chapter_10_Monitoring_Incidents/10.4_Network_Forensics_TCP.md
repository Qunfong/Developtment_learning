## 1. The Physics of the TCP Timeout


**The Problem:** The JVM only sees `SocketRead0`. It doesn't see the drama in the Linux stack.
. **The Event:** A packet is lost due to congestion.
. **The Wait:** The receiver waits for a "Fast Retransmit" or the **200ms RTO**.

## 2. Forensic Archaeology: netstat and ss


> [!abstract] The Mechanics: retrans
. **Command:** `ss -ti`

. **The Audit:** If `retrans` > 0.1%, your "Slow Request" is a physical network issue, not a Java bug.

## 3. Principal Implementation: The Hedge Request


```java
// Principal Level: Hedged Request Pattern
public Order getOrderWithHedge(String id) {
    var firstCall = CompletableFuture.supplyAsync(() -> client.get(id));
    
    // The Hedge: If first call takes > 20ms, start a second one.
    // This bypasses the 200ms TCP wait.
    var hedgeCall = firstCall.orTimeout(20, TimeUnit.MILLISECONDS)
        .handle((res, ex) -> {
            if (ex instanceof TimeoutException) return client.get(id);
            return res;
        });

    return CompletableFuture.anyOf(firstCall, hedgeCall).join();
}
```

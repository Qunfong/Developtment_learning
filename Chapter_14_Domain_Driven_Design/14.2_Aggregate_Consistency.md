# 14.2: Aggregates and Consistency Boundaries

## Learning Objectives

- **Define** an Aggregate Root as the single entry point for all state mutations, and explain why this enforces business invariants
- **Identify** the transactional boundary rule: one Aggregate = one database transaction, never two
- **Implement** an Aggregate Root in Java 21 that raises Domain Events on state transitions
- **Diagnose** the `Serialization Tax` of an oversized Aggregate and apply the "Reference by ID" rule to fix it
- **Apply** the Saga pattern to coordinate updates across two Aggregates without a distributed lock

## The Critical Dialogue

**Student:** I'm using Hibernate with `@OneToMany`. When I update one item, Hibernate re-loads the whole list, or threads overwrite each other. How do I keep data consistent?

**Principal:** You have no **Consistency Boundary**. You've treated your DB as a "Bag of Bags" instead of an **Atomic Unit of Truth**. To reach Principal level, we must master the **Aggregate Pattern**. We move from "Individual Updates" to **Atomic State Transitions**.

---

## 1. The Physics of the Aggregate

An **Invariant** is a business rule that must ALWAYS be true (e.g. "Total cannot be negative").
- **The Problem:** If you allow a service to update a child directly, the root cannot prevent illegal states.
- **The Solution:** The **Aggregate Root** is the only gateway.

---

## 2. Source Archaeology: The Transactional Boundary

> [!abstract] The Mechanics: Unit of Work
> - **The Rule:** 1 Request = 1 Aggregate = 1 DB Transaction.
> - **The Physics:** If you try to update two Aggregates in one transaction, you create a **Distributed Lock** that kills throughput. Use a **Saga** instead.

**`org.springframework.data.annotation.Id`** and **`org.springframework.data.repository.CrudRepository`** (Spring Data):
- An Aggregate Root is identified by a single `@Id` field
- `CrudRepository.save(T)` maps to a single transaction for the entire Aggregate; no `save()` call should span two Aggregate types

**`org.axonframework.eventsourcing.EventSourcingRepository`** (Axon Framework, `org.axonframework:axon-eventsourcing`):
- `load(String aggregateIdentifier)` → loads the Aggregate by replaying stored events (Event Sourcing mode)
- `@Aggregate` annotation marks the class as an Axon-managed Aggregate Root
- `AggregateLifecycle.apply(Object event)` — publishes a Domain Event from within an Aggregate command handler; the event is stored atomically with the Aggregate state change

**`org.springframework.data.domain.AbstractAggregateRoot<A>`** (Spring Data):
- `registerEvent(Object event)` — registers a domain event to be published by `ApplicationEventPublisher` after the `save()` completes
- `domainEvents()` / `clearDomainEvents()` — used by Spring Data repositories to drain and publish events post-transaction

**`@Version` (javax.persistence / jakarta.persistence)**:
- Optimistic locking: `long version` field incremented on each save
- If two threads load version 5 and both try to save, the second `UPDATE ... WHERE version=5` finds zero rows and throws `OptimisticLockException`
- Correct response: retry the entire command (not just the save)

## 3. Principal Implementation: Guarded Aggregate

```java
// Principal Level: State Machine Root
public class OrderAggregate {
    private OrderStatus status = PENDING;
    private List<LineItem> items = new ArrayList<>();

    public void addItem(Product p) {
        // Invariant Enforcement
        if (status != PENDING) throw new IllegalStateException();
        items.add(new LineItem(p));
    }

    public void finalise() {
        this.status = SETTLED;
        // Trigger Domain Event
    }
}
```

## 4. Code Lab: Full Domain-Event-Producing Aggregate

### BAD: Direct child mutation — no Aggregate boundary, invariants unenforceable

```java
// BAD: Services reach into the child collection directly.
// No invariant check. No domain event. Thread A and Thread B can
// simultaneously add items, resulting in a total that exceeds the credit limit.

@Entity
public class Order {
    @Id private UUID id;
    @OneToMany(cascade = CascadeType.ALL)
    private List<LineItem> items;  // public! any service can add directly

    // No invariant enforcement. No state machine.
    public List<LineItem> getItems() { return items; }
}

// In OrderService:
order.getItems().add(new LineItem(product, qty));  // bypasses any business rule
orderRepo.save(order);
// No check: was the order already SETTLED? Is the total within credit limit?
```

### GOOD: Aggregate Root with invariant enforcement and domain events

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.domain.AbstractAggregateRoot;
import java.math.BigDecimal;
import java.util.*;

/**
 * Order Aggregate Root.
 *
 * Invariants enforced:
 * 1. Items can only be added when status is PENDING
 * 2. Total cannot exceed credit limit
 * 3. Finalisation moves to SETTLED atomically (state machine)
 *
 * Domain Events raised:
 * - ItemAddedEvent: after each item addition
 * - OrderFinalizedEvent: on finalisation (triggers Billing Saga)
 */
public class Order extends AbstractAggregateRoot<Order> {

    @Id
    private final UUID id;

    @Version
    private long version;  // optimistic lock — prevents lost updates under concurrency

    private OrderStatus status;

    // PRIVATE: only Aggregate Root methods can mutate this list
    private final List<LineItem> items;
    private final Money creditLimit;

    // Factory method — constructors should be package-private in DDD
    public static Order create(UUID id, Money creditLimit) {
        Order o = new Order(id, creditLimit);
        o.registerEvent(new OrderCreatedEvent(id));  // Spring Data publishes after save()
        return o;
    }

    private Order(UUID id, Money creditLimit) {
        this.id = id;
        this.status = OrderStatus.PENDING;
        this.items = new ArrayList<>();
        this.creditLimit = creditLimit;
    }

    /**
     * Command: AddItem
     * Invariants: PENDING status + credit limit check
     */
    public void addItem(Product product, int quantity) {
        // Invariant 1: status guard
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException(
                "Cannot add item to order in status " + status);
        }

        Money lineTotal = product.price().multiply(quantity);

        // Invariant 2: credit limit guard
        Money currentTotal = calculateTotal();
        if (currentTotal.add(lineTotal).isGreaterThan(creditLimit)) {
            throw new CreditLimitExceededException(
                "Adding " + lineTotal + " exceeds credit limit " + creditLimit);
        }

        items.add(new LineItem(product.id(), quantity, lineTotal));

        // Domain Event: published after save(), not immediately
        registerEvent(new ItemAddedEvent(id, product.id(), quantity, lineTotal));
    }

    /**
     * Command: Finalise
     * State transition: PENDING -> SETTLED
     */
    public void finalise() {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException("Order is already " + status);
        }
        if (items.isEmpty()) {
            throw new IllegalStateException("Cannot finalise an empty order");
        }

        this.status = OrderStatus.SETTLED;

        // This event triggers the Billing Saga in another Bounded Context
        registerEvent(new OrderFinalizedEvent(id, calculateTotal()));
    }

    // Read-only accessors
    public UUID id() { return id; }
    public OrderStatus status() { return status; }
    public List<LineItem> items() { return Collections.unmodifiableList(items); }

    private Money calculateTotal() {
        return items.stream()
            .map(LineItem::lineTotal)
            .reduce(Money.ZERO, Money::add);
    }

    // Domain Event records — published by Spring Data after repository.save()
    public record ItemAddedEvent(UUID orderId, UUID productId, int qty, Money lineTotal) {}
    public record OrderFinalizedEvent(UUID orderId, Money total) {}
    public record OrderCreatedEvent(UUID orderId) {}
}
```

## 5. Production Lens

The "Serialization Tax" is real and measurable. At a payment processor running Hibernate 5.x, an `Order` Aggregate with 5,000 `LineItem` children (a "God Customer" scenario) caused:
- **Hibernate collection load**: 5,000 rows × ~200 bytes = ~1MB loaded per `addItem()` call
- **Optimistic lock check**: all 5,000 rows re-read on save to detect concurrent modifications
- **p99 latency: 1,200ms** per single item addition

After applying the "Reference by ID" rule (no `@OneToMany`, each `LineItem` holds `orderId` as a reference) and capping Aggregates at 50 items with a new `OrderBatch` root per 50 items:
- **p99 latency: 8ms** — a **150x improvement**

The transactional boundary rule: at 10,000 concurrent users each modifying one Aggregate, with 1 transaction per Aggregate, PostgreSQL handles this with row-level locking. If you instead span two Aggregates per transaction, you risk deadlock at ~5% probability — at 10k TPS, that is **500 deadlocks/second**.

<summary>Exercise 1 — Account Aggregate invariants with Java guard conditions</summary>

**Invariant 1: Balance cannot go negative (insufficient funds)**

```java
if (withdrawal.amount().compareTo(this.balance) > 0) {
    throw new InsufficientFundsException(
        "Withdrawal of " + withdrawal.amount() + " exceeds balance of " + this.balance);
}
```

**Invariant 2: Withdrawal amount must be positive**

```java
if (withdrawal.amount().compareTo(BigDecimal.ZERO) <= 0) {
    throw new InvalidWithdrawalAmountException(
        "Withdrawal amount must be positive, got: " + withdrawal.amount());
}
```

**Invariant 3: Account must not be frozen/closed when attempting withdrawal**

```java
if (this.status == AccountStatus.FROZEN || this.status == AccountStatus.CLOSED) {
    throw new AccountNotActiveException(
        "Cannot withdraw from account in status: " + this.status);
}
```

**Why these are Aggregate invariants (not service-layer checks):**

All three are domain rules that apply regardless of which caller invokes the withdrawal — a REST endpoint, an event handler, a Saga step, or a test. If these checks live in a service, a future caller can bypass the service and call the repository directly. If they live in the Aggregate, the invariant is enforced at every code path.

**Staff-level phrasing:** "Aggregates enforce invariants unconditionally — balance ≥ 0, amount > 0, account active — regardless of caller; service-layer checks are bypassable by any future path that doesn't go through the service."

<details>
<summary>Exercise 2 — Serialization tax: LineItem bandwidth + fix</summary>

**(a) 100 items:** 100 × 150 bytes = **15,000 bytes = 15 KB** per command.

**(b) 10,000 items:** 10,000 × 150 bytes = **1,500,000 bytes = 1.5 MB** per command.

**At 1,000 commands/second with 10,000 items:**

1,000 × 1.5 MB = **1,500 MB/s = 1.5 GB/s** of database read bandwidth per second — hitting the I/O ceiling of a typical RDS instance (multi-AZ: ~1.5 GB/s). At this point, the database is saturated loading Order state before any business logic executes.

**The fix: Aggregate boundary redesign**

The root cause is modeling `Order` as a single Aggregate containing all `LineItem`s. If every command loads all 10,000 items, the Aggregate boundary is wrong.

Options:
1. **Load only relevant children:** If the command doesn't need all LineItems (e.g., `AddLineItem` only needs the count to check the maximum), store the count as a denormalized field on `Order` and avoid loading children entirely.
2. **Paginate children:** Use `@OneToMany(fetch = FetchType.LAZY)` with `findTop100LineItemsByOrderId()` — load only the page needed for the specific operation.
3. **Redesign Aggregate boundary:** If `Order` commands always need all items, the Aggregate is too large. Consider a summary Aggregate (`Order` with `itemCount`, `totalAmount`) and a separate `OrderLineItemCollection` that's only loaded for full-manifest operations.
4. **Event Sourcing approach:** Store events (`ItemAdded`, `ItemRemoved`) and recompute only the state needed for the specific command (e.g., `itemCount` for a guard check).

**Staff-level phrasing:** "10k LineItems × 150 bytes × 1k commands/s = 1.5 GB/s of DB read — Aggregate is too large; denormalize the aggregate count as a guard field and use lazy loading or Aggregate boundary redesign."

</details>

<details>
<summary>Exercise 3 — Optimistic locking scenario + retry logic</summary>

**What happens:**

Thread A saves `Order{version=5}` → Hibernate executes:
```sql
UPDATE orders SET ..., version=6 WHERE id=1 AND version=5
-- Rows affected: 1. Success. Version is now 6.
```

Thread B tries to save `Order{version=5}` → Hibernate executes:
```sql
UPDATE orders SET ..., version=6 WHERE id=1 AND version=5
-- Rows affected: 0! Version is now 6, not 5. Conflict detected.
```

Hibernate sees 0 rows affected and throws `OptimisticLockException` (JPA standard) or `StaleObjectStateException` (Hibernate-specific), both of which are wrapped as `org.springframework.orm.ObjectOptimisticLockingFailureException` by Spring.

**Retry logic for the command handler:**

```java
@Service
public class OrderCommandHandler {

    private static final int MAX_RETRIES = 3;
    private final OrderRepository orders;

    public void addItem(AddItemCommand cmd) {
        int attempt = 0;
        while (true) {
            try {
                Order order = orders.findById(cmd.orderId()).orElseThrow();
                order.addItem(cmd.item());
                orders.save(order);
                return; // success
            } catch (ObjectOptimisticLockingFailureException e) {
                attempt++;
                if (attempt >= MAX_RETRIES) {
                    throw new ConcurrentModificationException(
                        "Order " + cmd.orderId() + " modified concurrently after " +
                        MAX_RETRIES + " retries", e);
                }
                // Brief backoff before retry (exponential or fixed)
                try { Thread.sleep(10L * attempt); } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt(); throw new RuntimeException(ie);
                }
            }
        }
    }
}
```

**Key points:**
- Retry must re-load the Aggregate from the database (fresh `findById`), not re-use the stale object.
- Retry count must be bounded — infinite loops are catastrophic.
- The caller (controller/handler) receives `ConcurrentModificationException` after exhausting retries and returns HTTP 409 Conflict.

**Staff-level phrasing:** "OptimisticLockException means 'stale read — try again from a fresh load'; retry must re-load the Aggregate each attempt, bounded by a max retry count, before giving up with HTTP 409."

</details>

<summary>Exercise 4 — Cart Aggregate with Spring Data AbstractAggregateRoot</summary>

```java
import org.springframework.data.domain.AbstractAggregateRoot;
import jakarta.persistence.*;
import java.util.*;

@Entity
public class Cart extends AbstractAggregateRoot<Cart> {

    private static final int MAX_ITEMS = 10;

    @Id
    private String id;

    @ElementCollection
    private List<String> productIds = new ArrayList<>();

    protected Cart() {} // JPA

    public Cart(String id) { this.id = id; }

    public void addItem(String productId) {
        if (productIds.size() >= MAX_ITEMS) {
            throw new CartFullException("Cart cannot exceed " + MAX_ITEMS + " items");
        }
        if (productIds.contains(productId)) {
            throw new DuplicateProductException("Product already in cart: " + productId);
        }
        productIds.add(productId);
    }

    public void checkout() {
        if (productIds.isEmpty()) {
            throw new EmptyCartException("Cannot checkout an empty cart");
        }
        registerEvent(new CartCheckedOutEvent(id, List.copyOf(productIds)));
    }

    public List<String> getProductIds() { return Collections.unmodifiableList(productIds); }
}

record CartCheckedOutEvent(String cartId, List<String> productIds) {}
```

```java
// JUnit 5 tests
import org.junit.jupiter.api.Test;
import static org.assertj.core.api.Assertions.*;

class CartTest {

    @Test
    void maxItemsEnforced() {
        var cart = new Cart("cart-1");
        for (int i = 0; i < 10; i++) cart.addItem("product-" + i);
        assertThatThrownBy(() -> cart.addItem("product-10"))
            .isInstanceOf(CartFullException.class);
    }

    @Test
    void duplicateProductRejected() {
        var cart = new Cart("cart-1");
        cart.addItem("product-A");
        assertThatThrownBy(() -> cart.addItem("product-A"))
            .isInstanceOf(DuplicateProductException.class);
    }

    @Test
    void checkoutRaisesEvent() {
        var cart = new Cart("cart-1");
        cart.addItem("product-A");
        cart.checkout();
        assertThat(cart.domainEvents())
            .hasSize(1)
            .first().isInstanceOf(CartCheckedOutEvent.class);
    }

    @Test
    void emptyCartCheckoutThrows() {
        var cart = new Cart("cart-1");
        assertThatThrownBy(cart::checkout)
            .isInstanceOf(EmptyCartException.class);
        assertThat(cart.domainEvents()).isEmpty();
    }
}
```

**Why `AbstractAggregateRoot.registerEvent()` not `ApplicationEventPublisher`:**

`registerEvent` queues events in the Aggregate — they're published by Spring Data's `@DomainEvents` mechanism only after `repository.save()` completes (post-commit). This ensures listeners see a consistent state (the save succeeded) before reacting.

<summary>Exercise 5 — Cross-Aggregate Saga: Order → Account charge</summary>

**Saga steps with compensating transactions:**

| Step | Action | Compensating Transaction |
|---|---|---|
| 1 | Reserve funds in `Account` (hold $X) | Release hold: `Account.releaseHold(holdId)` |
| 2 | Mark `Order` as payment-pending | Mark `Order` as payment-failed |
| 3 | Confirm charge in `Account` (deduct held amount) | N/A (idempotent — funds already released in step 1 compensation) |
| 4 | Mark `Order` as paid | N/A (terminal state) |

**State machine for the Saga coordinator:**

```
[STARTED]
    │
    ▼ Execute step 1 (reserveFunds)
[FUNDS_RESERVED]
    │ success                    │ failure
    ▼                            ▼
[ORDER_PENDING] ←── Execute step 2 (markPending)
    │                            │ failure → [COMPENSATING_STEP1]
    │                                         │ → [FAILED]
    ▼ Execute step 3 (confirmCharge)
[CHARGE_CONFIRMED]
    │ success                    │ failure → [COMPENSATING_STEPS_1_2]
    ▼
[ORDER_PAID] ← Execute step 4 (markPaid) → [COMPLETED]
```

**Implementation notes:**

- Saga state is persisted (PostgreSQL `sagas` table) so it survives crashes.
- Each step is an idempotent command — retry is safe.
- Compensating transactions run in reverse order.
- The Saga coordinator uses Kafka or an outbox pattern to trigger each step.
- "Pivot transaction": Step 3 (`confirmCharge`) is the non-compensable step — once funds are deducted, we commit and mark the order paid. Steps before the pivot can be compensated; steps after cannot.

**Staff-level phrasing:** "Cross-Aggregate Saga: reserve → pend → charge → paid, with compensations for each reversible step; persist Saga state in DB for crash recovery; the confirmCharge step is the pivot — non-compensable, so all prior steps must succeed before it fires."

</details>

## 7. Summary / Flashcard

- **Aggregate Root** is the single gateway for all state mutations; no service, test, or controller may bypass it to mutate children directly — this is what enforces business invariants.
- **One Aggregate = one transaction**: spanning two Aggregates in a single `@Transactional` method creates a distributed lock that serialises throughput; use Sagas with compensating transactions instead.
- **`@Version` optimistic locking** prevents lost updates under concurrency: the second concurrent saver finds `UPDATE ... WHERE version=N` returns 0 rows and receives `OptimisticLockException`, which must trigger a full command retry.
- **`AbstractAggregateRoot.registerEvent()`** publishes Domain Events after the `repository.save()` commits; events are never fired mid-transaction, ensuring listeners see a consistent state.
- **Reference by ID, not by object**: `Order` stores `customerId` (`UUID`), never a `Customer` instance; this eliminates Hibernate's cross-Aggregate loading, removes the serialisation tax, and keeps Aggregates independently deployable.

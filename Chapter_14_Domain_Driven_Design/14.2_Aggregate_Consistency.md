## The Critical Dialogue

**Student:** I'm using Hibernate with `@OneToMany`. When I update one item, Hibernate re-loads the whole list, or threads overwrite each other. How do I keep data consistent?

**Principal:** You have no **Consistency Boundary**. You've treated your DB as a "Bag of Bags" instead of an **Atomic Unit of Truth**. To reach Principal level, we must master the **Aggregate Pattern**. We move from "Individual Updates" to **Atomic State Transitions**.

---

## 1. The Physics of the Aggregate

An **Invariant** is a business rule that must ALWAYS be true (e.g. "Total cannot be negative").
- **The Problem:** If you allow a service to update a child directly, the root cannot prevent illegal states.
- **The Solution:** The **Aggregate Root** is the only gateway.

---

## 2. Source Archaeology: The Transactional Boundary

> [!abstract] The Mechanics: Unit of Work
> - **The Rule:** 1 Request = 1 Aggregate = 1 DB Transaction.
> - **The Physics:** If you try to update two Aggregates in one transaction, you create a **Distributed Lock** that kills throughput. Use a **Saga** instead.

**`org.springframework.data.annotation.Id`** and **`org.springframework.data.repository.CrudRepository`** (Spring Data):
- An Aggregate Root is identified by a single `@Id` field
- `CrudRepository.save(T)` maps to a single transaction for the entire Aggregate; no `save()` call should span two Aggregate types

**`org.axonframework.eventsourcing.EventSourcingRepository`** (Axon Framework, `org.axonframework:axon-eventsourcing`):
- `load(String aggregateIdentifier)` → loads the Aggregate by replaying stored events (Event Sourcing mode)
- `@Aggregate` annotation marks the class as an Axon-managed Aggregate Root
- `AggregateLifecycle.apply(Object event)` — publishes a Domain Event from within an Aggregate command handler; the event is stored atomically with the Aggregate state change

**`org.springframework.data.domain.AbstractAggregateRoot<A>`** (Spring Data):
- `registerEvent(Object event)` — registers a domain event to be published by `ApplicationEventPublisher` after the `save()` completes
- `domainEvents()` / `clearDomainEvents()` — used by Spring Data repositories to drain and publish events post-transaction

**`@Version` (javax.persistence / jakarta.persistence)**:
- Optimistic locking: `long version` field incremented on each save
- If two threads load version 5 and both try to save, the second `UPDATE ... WHERE version=5` finds zero rows and throws `OptimisticLockException`
- Correct response: retry the entire command (not just the save)

## 3. Principal Implementation: Guarded Aggregate

```java
// Principal Level: State Machine Root
public class OrderAggregate {
    private OrderStatus status = PENDING;
    private List<LineItem> items = new ArrayList<>();

    public void addItem(Product p) {
        // Invariant Enforcement
        if (status != PENDING) throw new IllegalStateException();
        items.add(new LineItem(p));
    }

    public void finalise() {
        this.status = SETTLED;
        // Trigger Domain Event
    }
}
```

## 4. Code Lab: Full Domain-Event-Producing Aggregate

### BAD: Direct child mutation — no Aggregate boundary, invariants unenforceable

```java
// BAD: Services reach into the child collection directly.
// No invariant check. No domain event. Thread A and Thread B can
// simultaneously add items, resulting in a total that exceeds the credit limit.

@Entity
public class Order {
    @Id private UUID id;
    @OneToMany(cascade = CascadeType.ALL)
    private List<LineItem> items;  // public! any service can add directly

    // No invariant enforcement. No state machine.
    public List<LineItem> getItems() { return items; }
}

// In OrderService:
order.getItems().add(new LineItem(product, qty));  // bypasses any business rule
orderRepo.save(order);
// No check: was the order already SETTLED? Is the total within credit limit?
```

### GOOD: Aggregate Root with invariant enforcement and domain events

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.domain.AbstractAggregateRoot;
import java.math.BigDecimal;
import java.util.*;

/**
 * Order Aggregate Root.
 *
 * Invariants enforced:
 * 1. Items can only be added when status is PENDING
 * 2. Total cannot exceed credit limit
 * 3. Finalisation moves to SETTLED atomically (state machine)
 *
 * Domain Events raised:
 * - ItemAddedEvent: after each item addition
 * - OrderFinalizedEvent: on finalisation (triggers Billing Saga)
 */
public class Order extends AbstractAggregateRoot<Order> {

    @Id
    private final UUID id;

    @Version
    private long version;  // optimistic lock — prevents lost updates under concurrency

    private OrderStatus status;

    // PRIVATE: only Aggregate Root methods can mutate this list
    private final List<LineItem> items;
    private final Money creditLimit;

    // Factory method — constructors should be package-private in DDD
    public static Order create(UUID id, Money creditLimit) {
        Order o = new Order(id, creditLimit);
        o.registerEvent(new OrderCreatedEvent(id));  // Spring Data publishes after save()
        return o;
    }

    private Order(UUID id, Money creditLimit) {
        this.id = id;
        this.status = OrderStatus.PENDING;
        this.items = new ArrayList<>();
        this.creditLimit = creditLimit;
    }

    /**
     * Command: AddItem
     * Invariants: PENDING status + credit limit check
     */
    public void addItem(Product product, int quantity) {
        // Invariant 1: status guard
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException(
                "Cannot add item to order in status " + status);
        }

        Money lineTotal = product.price().multiply(quantity);

        // Invariant 2: credit limit guard
        Money currentTotal = calculateTotal();
        if (currentTotal.add(lineTotal).isGreaterThan(creditLimit)) {
            throw new CreditLimitExceededException(
                "Adding " + lineTotal + " exceeds credit limit " + creditLimit);
        }

        items.add(new LineItem(product.id(), quantity, lineTotal));

        // Domain Event: published after save(), not immediately
        registerEvent(new ItemAddedEvent(id, product.id(), quantity, lineTotal));
    }

    /**
     * Command: Finalise
     * State transition: PENDING -> SETTLED
     */
    public void finalise() {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException("Order is already " + status);
        }
        if (items.isEmpty()) {
            throw new IllegalStateException("Cannot finalise an empty order");
        }

        this.status = OrderStatus.SETTLED;

        // This event triggers the Billing Saga in another Bounded Context
        registerEvent(new OrderFinalizedEvent(id, calculateTotal()));
    }

    // Read-only accessors
    public UUID id() { return id; }
    public OrderStatus status() { return status; }
    public List<LineItem> items() { return Collections.unmodifiableList(items); }

    private Money calculateTotal() {
        return items.stream()
            .map(LineItem::lineTotal)
            .reduce(Money.ZERO, Money::add);
    }

    // Domain Event records — published by Spring Data after repository.save()
    public record ItemAddedEvent(UUID orderId, UUID productId, int qty, Money lineTotal) {}
    public record OrderFinalizedEvent(UUID orderId, Money total) {}
    public record OrderCreatedEvent(UUID orderId) {}
}
```

## 5. Production Lens

The "Serialization Tax" is real and measurable. At a payment processor running Hibernate 5.x, an `Order` Aggregate with 5,000 `LineItem` children (a "God Customer" scenario) caused:
- **Hibernate collection load**: 5,000 rows × ~200 bytes = ~1MB loaded per `addItem()` call
- **Optimistic lock check**: all 5,000 rows re-read on save to detect concurrent modifications
- **p99 latency: 1,200ms** per single item addition

After applying the "Reference by ID" rule (no `@OneToMany`, each `LineItem` holds `orderId` as a reference) and capping Aggregates at 50 items with a new `OrderBatch` root per 50 items:
- **p99 latency: 8ms** — a **150x improvement**

The transactional boundary rule: at 10,000 concurrent users each modifying one Aggregate, with 1 transaction per Aggregate, PostgreSQL handles this with row-level locking. If you instead span two Aggregates per transaction, you risk deadlock at ~5% probability — at 10k TPS, that is **500 deadlocks/second**.

## 7. Summary / Flashcard

- **Aggregate Root** is the single gateway for all state mutations; no service, test, or controller may bypass it to mutate children directly — this is what enforces business invariants.
- **One Aggregate = one transaction**: spanning two Aggregates in a single `@Transactional` method creates a distributed lock that serialises throughput; use Sagas with compensating transactions instead.
- **`@Version` optimistic locking** prevents lost updates under concurrency: the second concurrent saver finds `UPDATE ... WHERE version=N` returns 0 rows and receives `OptimisticLockException`, which must trigger a full command retry.
- **`AbstractAggregateRoot.registerEvent()`** publishes Domain Events after the `repository.save()` commits; events are never fired mid-transaction, ensuring listeners see a consistent state.
- **Reference by ID, not by object**: `Order` stores `customerId` (`UUID`), never a `Customer` instance; this eliminates Hibernate's cross-Aggregate loading, removes the serialisation tax, and keeps Aggregates independently deployable.

## The Critical Dialogue

**Student:** In our Ledger, we just overwrite the balance: `UPDATE users SET balance = 100`. Why store every single transaction as an "Event"?

**Principal:** You are destroying **Evidence**. An `UPDATE` is a destructive mutation—it tells you the state, but deletes the *history*. To reach Principal level, we must master **Event Sourcing**. We move from "Storing State" to **Storing the Stream of Facts**. History is the only truth.

---

## 1. The Requirement: Absolute Auditability

**The Problem:** The "Lost Context."
- **Mutation:** `$100 -> $50`. (Why?).
- **Event Sourcing:** `OrderPlaced($50)` + `Fee($10)`.

### 1.1 Append-only Physics

Sequential I/O (appending) is **100x faster** than Random I/O (B-Tree updates). When `UPDATE` runs against a B-Tree page, it must:
1. Traverse the tree to the page (~4-8 I/Os)
2. Read the page into the buffer pool
3. Modify it in-place
4. Write the WAL entry (another I/O)
5. Write the dirty page back

Appending an event: one sequential write to the WAL. No read, no traversal, no in-place modification.

---

## 2. Solution: The Replay and Snapshot

- **Mechanism:** The state is the sum of all past events.
- **The Replay:** Reconstruct balance by replaying events from T=0.
- **Snapshot:** Cache the state every 1,000 events to keep replay fast.

## 3. Source Archaeology: Axon Framework Event Sourcing

**`org.axonframework.eventsourcing.EventSourcingRepository`** (Axon Framework `org.axonframework:axon-eventsourcing`):
- `load(String aggregateIdentifier)` → calls `EventStore.readEvents(aggregateIdentifier)` to get the event stream, then calls each `@EventSourcingHandler` method in sequence to reconstruct state
- `save(AnnotatedAggregateRoot)` → appends new `DomainEventMessage` entries to the `EventStore` atomically; no `UPDATE`, only `INSERT`

**`@Aggregate`** (Axon):
- Marks a class as an Axon-managed Aggregate; Axon's `AggregateLifecycle` intercepts `apply()` calls
- `AggregateLifecycle.apply(Object event)` — stores the event AND calls the corresponding `@EventSourcingHandler` in the same transaction, ensuring state is always consistent with the event log

**`@EventSourcingHandler`** (Axon):
- The method that mutates Aggregate state when an event is applied — called both during `apply()` (command handling) and during `load()` (replay)
- Must be **side-effect free** — no external I/O inside `@EventSourcingHandler`; only set `this.field = event.value()`

**`org.axonframework.eventsourcing.SnapshotTriggerDefinition`**:
- `EventCountSnapshotTriggerDefinition(snapshotter, threshold)` — triggers a snapshot after N events
- Snapshots are stored in `SnapshotEventStore`; on `load()`, Axon reads the latest snapshot and only replays events after it

**`org.axonframework.serialization.upcasting.Upcaster`**:
- `SingleEventUpcaster` — the interface to implement when an event schema changes; receives the old `IntermediateEventRepresentation` and produces the new one
- Registered in `EventUpcasterChain`; applied automatically during event replay

**`EventStorageEngine` implementations:**
- `JdbcEventStorageEngine` — stores events in a relational DB; one row per event, sequential insert
- `AxonServerEventStore` — distributed event store with partitioning; supports global event ordering

## 4. Code Lab: Event-Sourced Aggregate with Snapshot

### BAD: Mutable state, no history — update destroys the audit trail

```java
// BAD: Classic mutable entity. 
// After executing these three operations, the database contains only "balance=30".
// Who transferred $50? When? Was it authorised? Unknown. Evidence destroyed.

@Entity
public class Account {
    @Id private UUID id;
    private BigDecimal balance;

    public void deposit(BigDecimal amount) {
        // No event. No history. No audit. Just a number changing.
        this.balance = this.balance.add(amount);
    }

    public void withdraw(BigDecimal amount) {
        if (amount.compareTo(balance) > 0) throw new InsufficientFundsException();
        this.balance = this.balance.subtract(amount);
    }
}

// In production: balance goes from 100 -> 150 -> 80 -> 30.
// Auditor asks: "Where did the $70 go?"
```

### GOOD: Axon Framework event-sourced Account

```java
import org.axonframework.commandhandling.CommandHandler;
import org.axonframework.eventsourcing.EventSourcingHandler;
import org.axonframework.modelling.command.*;
import org.axonframework.spring.stereotype.Aggregate;
import java.math.BigDecimal;
import java.util.UUID;
import static org.axonframework.modelling.command.AggregateLifecycle.apply;

/**
 * Event-Sourced Account Aggregate.
 *
 * Key properties:
 * - State is derived ONLY from replayed events — no mutable fields written directly
 * - @EventSourcingHandler mutates state; @CommandHandler validates and applies events
 * - Snapshot triggered every 50 events via EventCountSnapshotTriggerDefinition
 * - All @EventSourcingHandler methods are side-effect free (no I/O)
 */
@Aggregate(snapshotTriggerDefinition = "accountSnapshotTrigger")
public class AccountAggregate {

    @AggregateIdentifier
    private UUID accountId;
    private BigDecimal balance;
    private AccountStatus status;

    // Required no-arg constructor for Axon framework replay
    protected AccountAggregate() {}

    // ===== Command Handlers =====

    @CommandHandler
    public AccountAggregate(OpenAccountCommand cmd) {
        // Validate: is the initial balance valid?
        if (cmd.initialBalance().compareTo(BigDecimal.ZERO) < 0) {
            throw new IllegalArgumentException("Initial balance cannot be negative");
        }
        // Emit fact — state is set in @EventSourcingHandler, not here
        apply(new AccountOpenedEvent(cmd.accountId(), cmd.initialBalance()));
    }

    @CommandHandler
    public void handle(DepositMoneyCommand cmd) {
        if (status != AccountStatus.ACTIVE) {
            throw new IllegalStateException("Account is " + status);
        }
        // No state mutation here — only emit the fact
        apply(new MoneyDepositedEvent(accountId, cmd.amount(), balance.add(cmd.amount())));
    }

    @CommandHandler
    public void handle(WithdrawMoneyCommand cmd) {
        if (status != AccountStatus.ACTIVE) throw new IllegalStateException("Account " + status);
        if (cmd.amount().compareTo(balance) > 0) {
            throw new InsufficientFundsException(balance, cmd.amount());
        }
        apply(new MoneyWithdrawnEvent(accountId, cmd.amount(), balance.subtract(cmd.amount())));
    }

    // ===== Event Sourcing Handlers — pure state setters, NO side effects =====

    @EventSourcingHandler
    public void on(AccountOpenedEvent event) {
        this.accountId = event.accountId();
        this.balance = event.initialBalance();
        this.status = AccountStatus.ACTIVE;
    }

    @EventSourcingHandler
    public void on(MoneyDepositedEvent event) {
        // State is the running balance from the event stream
        this.balance = event.balanceAfter();
    }

    @EventSourcingHandler
    public void on(MoneyWithdrawnEvent event) {
        this.balance = event.balanceAfter();
    }

    // Getters for queries (never for mutations)
    public BigDecimal getBalance() { return balance; }
}
```

```java
// Snapshot configuration — triggers after every 50 events
@Configuration
public class AxonConfig {
    @Bean
    public SnapshotTriggerDefinition accountSnapshotTrigger(Snapshotter snapshotter) {
        // After 50 events, Axon stores a snapshot.
        // On next load, Axon reads snapshot + only events after it.
        // Replay time: bounded at O(50) events, not O(all events since creation).
        return new EventCountSnapshotTriggerDefinition(snapshotter, 50);
    }
}
```

## 5. Production Lens

| Approach | Write throughput | Read latency (1k events) | Audit capability |
|:---|---:|---:|:---|
| `UPDATE balance` (B-Tree) | ~5,000 TPS | ~2 ms | None — history destroyed |
| Event append (sequential WAL) | ~500,000 TPS | ~50 ms (replay) | Complete — every fact stored |
| Event append + Snapshot (50 events) | ~500,000 TPS | ~3 ms | Complete — snapshot + delta |

**Real numbers:** PostgreSQL WAL append throughput on NVMe SSD: ~500k inserts/sec for single-row event records. Compare to `UPDATE` on a btree index: ~5,000-50,000 updates/sec depending on page contention. Sequential I/O advantage: ~100x for write throughput.

Axon Server (commercial event store) benchmarks (Axon 4.7, 2023): **200k events/sec** sustained write throughput on a 3-node cluster, **<5ms p99** for event append, **<10ms p99** for Aggregate load with snapshots.

## Exercise Solutions

<details>
<summary>Exercise 1 — Append vs Update performance: throughput and storage</summary>

**Throughput comparison:**

- Append (WAL sequential write): 0.1ms per event → **10,000 events/s** maximum single-threaded throughput.
- B-Tree UPDATE: 2ms per update → **500 updates/s** maximum single-threaded.

At 10,000 operations/second: event sourcing can handle this workload with a single thread. B-Tree UPDATE would require 20 concurrent writers just to keep up — and concurrent B-Tree updates create lock contention on leaf pages, reducing effective throughput further.

**Storage cost difference per year:**

- Event store (100M rows + 10,000 new events/s):
  - New events per year: 10,000 × 86,400 × 365 = **315 billion events**
  - At 200 bytes each: 315B × 200 bytes = **63 TB/year**
  
- Traditional UPDATE (no event history):
  - Only current state stored — no growth from historical events.
  - Storage stays roughly constant (row count stable, not growing).

**The trade-off:** Event sourcing sacrifices storage for auditability and replay. 63 TB/year at $0.023/GB-month (S3 Intelligent-Tiering) = **$1,449/month = $17,388/year**. For a financial ledger where audit trail is legally required, this cost is justified. For ephemeral user sessions, it is not.

**Staff-level phrasing:** "Event appends are 20x faster than B-Tree updates (0.1ms vs 2ms) but consume 63 TB/year at 10k events/s — justified for audit-required domains; traditional CRUD is cheaper for ephemeral data."

</details>

<details>
<summary>Exercise 2 — Replay time with and without snapshots</summary>

**Without snapshots:**

10,000 events × 0.05ms per event = **500ms = 0.5 seconds** to reload an Account.

At 1,000 accounts loaded/s (e.g., during a peak): 1,000 × 500ms = 500 CPU-seconds/s — impossible. The system falls over at any meaningful load without snapshots.

**With snapshot every 100 events:**

- Latest snapshot at event 9,900 (or nearest prior multiple of 100).
- Events replayed after snapshot: at most 99 events (from snapshot to latest).
- Replay time: 99 × 0.05ms = **4.95ms ≈ 5ms maximum**.

This is the "bounded replay" guarantee: regardless of how long the Account has been alive or how many events it has accumulated, the maximum reload time is constant: `snapshot_threshold × event_replay_ms = 100 × 0.05ms = 5ms`.

**Why snapshot every 100 events (not 1,000):**

- At 1,000 events between snapshots: max replay = 50ms — acceptable for a batch load, but too slow for real-time command handling where the target is <10ms per operation.
- At 10 events: snapshot overhead becomes too high (frequent Postgres writes for snapshot state).
- 100 events is the sweet spot: 5ms max replay, moderate snapshot write frequency.

**Staff-level phrasing:** "Without snapshots: 10k events × 0.05ms = 500ms per load — catastrophic at scale; snapshot every 100 events bounds max replay to 5ms regardless of aggregate age."

</details>

<summary>Exercise 3 — Upcasting MoneyWithdrawnEvent v1 → v2</summary>

**Upcasting interface (Axon Framework):**

```java
import org.axonframework.serialization.upcasting.event.SingleEventUpcaster;
import org.axonframework.serialization.upcasting.event.IntermediateEventRepresentation;

@Component
public class MoneyWithdrawnEventUpcaster extends SingleEventUpcaster {

    @Override
    protected boolean canUpcast(IntermediateEventRepresentation ir) {
        return ir.getType().getName().equals("MoneyWithdrawnEvent") &&
               ir.getType().getRevision().equals("1.0");
    }

    @Override
    protected IntermediateEventRepresentation doUpcast(IntermediateEventRepresentation ir) {
        // Read v1 fields
        // Add v2 fields with defaults for historical events
        return ir.upcastPayload(
            new XStreamSerializer().deserialize(...), // read v1
            Object.class,
            payload -> {
                // Inject defaults for new required fields
                payload.getNode("currency").setValue("USD");   // historical default
                payload.getNode("reason").setValue("LEGACY");  // reason unknown for old events
                return payload;
            }
        ).withRevision("2.0");
    }
}
```

**What `doUpcast()` does:**

Reads the v1 event from the serialized form (JSON/XStream), adds the missing fields (`currency="USD"`, `reason="LEGACY"`) with sensible defaults for historical events where the original reason is unknown, and returns a v2-compatible representation.

**No data migration required:**

Upcasting happens at read time — the 5M historical v1 events in the database are unchanged. When replayed, the upcaster transforms each v1 event to v2 in memory before passing it to the `@EventSourcingHandler`. No bulk UPDATE or migration script needed.

**What breaks without the upcaster:**

When the application loads historical v1 events and tries to deserialize them into `MoneyWithdrawnEvent v2` (which has required `currency` and `reason` fields), deserialization fails with `com.fasterxml.jackson.databind.exc.MismatchedInputException: Missing required creator property 'currency'`. Every historical replay fails. The entire event store becomes unreadable.

**Staff-level phrasing:** "Upcaster transforms v1 events to v2 at read-time with no DB migration — without it, v2 deserialization fails for all 5M historical events, making the event store unreadable."

<summary>Exercise 4 — SimpleBankEventStore implementation</summary>

```java
import java.util.*;
import java.util.concurrent.CopyOnWriteArrayList;

public class SimpleBankEventStore {

    // Each entry: either a domain event or a snapshot marker
    private sealed interface Entry permits Entry.Event, Entry.Snapshot {
        String aggregateId();
        record Event(String aggregateId, Object payload) implements Entry {}
        record Snapshot(String aggregateId, Object state) implements Entry {}
    }

    private final CopyOnWriteArrayList<Entry> log = new CopyOnWriteArrayList<>();

    public void appendEvent(String aggregateId, Object event) {
        log.add(new Entry.Event(aggregateId, event));
    }

    public void appendSnapshot(String aggregateId, Object snapshotState) {
        log.add(new Entry.Snapshot(aggregateId, snapshotState));
    }

    public List<Object> loadEvents(String aggregateId) {
        var entries = log.stream()
            .filter(e -> e.aggregateId().equals(aggregateId))
            .toList();

        // Find the last snapshot index
        int lastSnapshotIndex = -1;
        for (int i = entries.size() - 1; i >= 0; i--) {
            if (entries.get(i) instanceof Entry.Snapshot) {
                lastSnapshotIndex = i;
                break;
            }
        }

        // Return events after the last snapshot (or all events if no snapshot)
        return entries.subList(lastSnapshotIndex + 1, entries.size())
            .stream()
            .filter(e -> e instanceof Entry.Event)
            .map(e -> ((Entry.Event) e).payload())
            .toList();
    }
}
```

```java
// JUnit 5 test for thread safety and snapshot behavior
import org.junit.jupiter.api.Test;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;
import static org.assertj.core.api.Assertions.assertThat;

class SimpleBankEventStoreTest {

    @Test
    void snapshotTruncatesLoadedEvents() {
        var store = new SimpleBankEventStore();
        store.appendEvent("acc-1", "event-1");
        store.appendEvent("acc-1", "event-2");
        store.appendSnapshot("acc-1", "snapshot-state");
        store.appendEvent("acc-1", "event-3");
        store.appendEvent("acc-1", "event-4");

        assertThat(store.loadEvents("acc-1")).containsExactly("event-3", "event-4");
    }

    @Test
    void concurrentAppendsAreSafe() throws Exception {
        var store = new SimpleBankEventStore();
        int threads = 10;
        var latch = new CountDownLatch(1);
        var counter = new AtomicInteger(0);
        var executor = Executors.newVirtualThreadPerTaskExecutor();

        for (int i = 0; i < threads; i++) {
            final int idx = i;
            executor.submit(() -> {
                try {
                    latch.await();
                    store.appendEvent("acc-1", "event-" + idx);
                    counter.incrementAndGet();
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
        }
        latch.countDown();
        executor.shutdown();
        executor.awaitTermination(5, TimeUnit.SECONDS);

        assertThat(store.loadEvents("acc-1")).hasSize(10);
        assertThat(counter.get()).isEqualTo(10);
    }
}
```

**Why `CopyOnWriteArrayList` is thread-safe here:**

`add()` on `CopyOnWriteArrayList` is atomic — it creates a new copy of the array with the new element appended. Concurrent `add()` calls serialize at the lock. `stream()` reads from a snapshot of the list taken at stream creation — safe for concurrent reads.

**Limitation:** `CopyOnWriteArrayList` is O(N) per write due to array copying. Production event stores use an append-only PostgreSQL table with advisory locks per aggregate, not CopyOnWriteArrayList.

<details>
<summary>Exercise 5 — Command vs Event classification</summary>

| Item | Classification | Why |
|---|---|---|
| (a) `TransferMoneyRequest` | **Command** | Imperative — "please do this." Has intent. Can be rejected. Future tense: "transfer this money." The system decides whether to honor it. |
| (b) `MoneyTransferredFact` | **Event** | Declarative — "this happened." Past tense. Immutable. Cannot be un-done by the event store. Describes a state change that already occurred. |
| (c) `CancelOrderRequest` | **Command** | Intent to cancel. The business may reject it ("order already shipped" → cannot cancel). Imperative mood. |
| (d) `OrderCancellationFailedNotification` | **Event** | A fact about a failure — "the cancellation attempt resulted in failure." Past tense. Immutable. Consumers react to it but cannot change it. |
| (e) `UserRegistrationForm` | **Command** | A form submission is an intent — "register this user." The system validates and may reject it (duplicate email, weak password). Not yet committed to the domain. |

**Semantic difference between a Command that fails vs an Event that "fails":**

**Command failure:** A command that fails produces NO event (or a rejection event like `CancellationFailedNotification`). The failure is the normal path — business rules rejected the intent. The state does NOT change. `CancelOrderRequest` fails → no `OrderCancelledEvent` is published → `Order` remains in its current state.

**Event "failure":** Events cannot fail in the technical sense — they are already committed facts. An `OrderCancelledEvent` represents that cancellation happened. If downstream processing fails (e.g., a refund service crashes), that failure produces a NEW event (`RefundFailedEvent`), not a reversal of the original. The event store is append-only — you cannot "un-publish" an event.

**Staff-level phrasing:** "Commands are rejected (no event published, state unchanged); events are permanent facts — downstream failures produce new compensating events, never deletions of the original event."

</details>

## 7. Summary / Flashcard

- **Event Sourcing stores facts, not state**: `MoneyWithdrawnEvent(amount=50)` is immutable and permanent; an `UPDATE balance=50` destroys the why — the event store is the only source of truth for both current state and history.
- **Append-only I/O is ~100x faster than in-place B-Tree updates**: sequential WAL writes achieve ~500k events/sec; random-access B-Tree updates peak at ~5,000-50,000 updates/sec on the same hardware.
- **`@EventSourcingHandler` must be side-effect free**: it is called both during `apply()` (command time) and during `load()` (replay time); any external I/O inside it will fire on every replay, corrupting external systems.
- **Snapshots bound replay cost to O(threshold)**: `EventCountSnapshotTriggerDefinition(snapshotter, 50)` ensures that no Aggregate ever replays more than 50 events, regardless of how old it is.
- **Upcasting handles schema evolution**: `SingleEventUpcaster` transforms historical event representations at read time, eliminating the need for data migrations on the event store — historical data is never modified, only interpreted differently.

# 14.4: CQRS and Read-Model Projection

## Learning Objectives

## The Critical Dialogue

**Student:** I've implemented Event Sourcing. History is great, but my "Top 10" dashboard is slow. I have to replay 10 million events just to calculate a total.

**Principal:** You are trying to use a **Storage Model** as a **Query Model**. In a large system, the way you *write* should never be the way you *read*. To reach Principal level, we must master **CQRS**. We separate the **Command Plane** (Facts) from the **Query Plane** (Optimised Truth). We move from "Replaying History" to **Projecting Real-time Truth**.

## 1. The Requirement: Responsibility Segregation

- **Write Model:** Needs normalization and append speed.
- **Read Model:** Needs denormalization and search speed.
- **The Result:** If you force one DB to do both, you end up with a system that is mediocre at everything.

## 3. Source Archaeology: Kafka Projectors and Catch-up Subscriptions

**`org.springframework.kafka.annotation.KafkaListener`** (Spring Kafka, `org.springframework.kafka:spring-kafka`):
- `@KafkaListener(topics = "ledger.events", groupId = "balance-projector")` — stateful consumer
- Consumer group offset IS the projection checkpoint; if the projector is restarted, it resumes from the last committed offset
- `@KafkaListener(topicPartitions = @TopicPartition(topic = "ledger.events", partitions = "0-47"), containerFactory = "catchUpFactory")` — for catch-up subscription, start from `earliest` offset

**`org.springframework.data.redis.core.ReactiveRedisTemplate`** / `StringRedisTemplate`**:
- `opsForValue().increment("balance:" + userId, delta)` — O(1) atomic increment; this is the core projection operation for balance read models
- `opsForZSet().incrementScore("leaderboard", userId, delta)` — O(log N) sorted set update for leaderboard read models

**`org.axonframework.queryhandling.QueryHandler`** (Axon):
- `@QueryHandler` annotates the method that serves read model queries — completely separate from `@CommandHandler`
- Axon's `QueryGateway.query(query, ResponseType.instanceOf(BalanceView.class))` dispatches to the query handler backed by the read model

**Catch-up Subscription in EventStore:**
- `EventStore.readEvents(trackingToken)` with `GlobalSequenceTrackingToken(0)` → reads from the beginning of the event log
- Used to bootstrap a new read model or rebuild an existing one after a projection bug is fixed
- Must be idempotent: the Projector may receive the same event twice (at-least-once delivery); use `INSERT ... ON CONFLICT DO UPDATE` (PostgreSQL upsert) or `SETNX` in Redis

**`org.axonframework.eventhandling.TrackingEventProcessor`** (Axon):
- Implements Catch-up Subscription natively; processes events from a configurable position
- `resetTokens()` — resets the tracking token to replay all events, rebuilding the read model from scratch
- `processingStatus()` → returns current processing position, used to monitor projection lag

## 5. Code Lab: Full CQRS Projection System

### BAD: Event Store used as Query Store — O(N) query cost

```java
// BAD: Query re-reads all historical events every time.
// At 10M events for a popular user, this takes seconds.
// Worse: this blocks the event store I/O for a read query.

@Service
public class BadBalanceService {
    private final EventStore eventStore;

    public BigDecimal getBalance(UUID userId) {
        // O(N) replay for a single balance query — completely wrong at scale.
        // This is like reading all 10 years of a bank's transaction log
        // every time a customer checks their balance.
        return eventStore.readEvents(userId.toString())
            .asStream()
            .filter(e -> e.getPayload() instanceof MoneyEvent)
            .map(e -> (MoneyEvent) e.getPayload())
            .reduce(BigDecimal.ZERO,
                    (acc, e) -> acc.add(e.delta()),
                    BigDecimal::add);
    }
}
```

### GOOD: Projector + Redis read model — O(1) query

```java
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;
import com.fasterxml.jackson.databind.ObjectMapper;
import java.math.BigDecimal;

/**
 * Balance Projector: consumes domain events and maintains Redis read models.
 *
 * Architecture properties:
 * - Kafka consumer group offset = projection checkpoint (durable, survives restart)
 * - O(1) Redis INCR for balance updates (atomic, no read-modify-write)
 * - Idempotent: duplicate events produce correct result via upsert semantics
 * - Projection lag monitored via consumer group offset lag
 */
@Component
public class BalanceProjector {

    private final StringRedisTemplate redis;
    private final ObjectMapper mapper;

    public BalanceProjector(StringRedisTemplate redis, ObjectMapper mapper) {
        this.redis = redis;
        this.mapper = mapper;
    }

    /**
     * Event handler for money events.
     * Kafka guarantees at-least-once delivery — this method must be idempotent.
     * Idempotency: we store the last processed eventId per user in Redis;
     *              if we see a duplicate eventId, we skip it.
     */
    @KafkaListener(
        topics = "ledger.events",
        groupId = "balance-projector-v2",  // v2 suffix allows blue/green projection
        containerFactory = "batchKafkaListenerContainerFactory"
    )
    public void project(MoneyEvent event) {
        String dedupeKey = "dedup:balance:" + event.eventId();

        // Idempotency check: SET NX (set if not exists) with 1-day TTL
        Boolean isNew = redis.opsForValue().setIfAbsent(dedupeKey, "1");
        if (Boolean.FALSE.equals(isNew)) {
            return;  // Duplicate event — skip
        }

        // O(1) atomic increment — safe for concurrent projectors
        redis.opsForValue().increment(
            "balance:" + event.userId(),
            event.delta().longValue()  // store in cents to avoid float issues
        );

        // Update leaderboard (sorted set): O(log N) where N = leaderboard size
        if (event.delta().compareTo(BigDecimal.ZERO) > 0) {
            redis.opsForZSet().incrementScore(
                "leaderboard:top-depositors",
                event.userId().toString(),
                event.delta().doubleValue()
            );
        }

        // Offset is committed by Spring Kafka after successful return
    }
}

// ===== Query Handler — reads from the projection, never from the event store =====
@Service
public class BalanceQueryHandler {
    private final StringRedisTemplate redis;

    public BalanceQueryHandler(StringRedisTemplate redis) {
        this.redis = redis;
    }

    /**
     * O(1) balance query — reads from pre-projected Redis key.
     * Consistency: eventually consistent (projection lag typically < 10ms).
     */
    public BigDecimal getBalance(String userId) {
        String raw = redis.opsForValue().get("balance:" + userId);
        if (raw == null) return BigDecimal.ZERO;
        // Convert from stored cents back to decimal
        return new BigDecimal(raw).scaleByPowerOfTen(-2);
    }

    /**
     * Top 10 depositors — Redis sorted set, O(log N + K) where K=10.
     */
    public List<String> getTopDepositors() {
        return new ArrayList<>(
            redis.opsForZSet().reverseRange("leaderboard:top-depositors", 0, 9)
        );
    }
}
```

```java
// ===== Catch-up Subscription: rebuild read model from scratch =====
@Component
public class ProjectionRebuildJob {

    private final TrackingEventProcessor processor;

    public ProjectionRebuildJob(EventProcessingConfiguration config) {
        this.processor = config.eventProcessor("balance-projector-v2",
            TrackingEventProcessor.class).orElseThrow();
    }

    /**
     * Call this via an admin endpoint when you need to rebuild the projection.
     * Production pattern: deploy a "v3" projector pointing to a new Redis keyspace,
     * rebuild in background, then atomically swap the query endpoint to the new keyspace.
     */
    public void rebuildFromStart() {
        processor.shutDown();
        processor.resetTokens();  // resets offset to beginning
        processor.start();        // begins replaying all events
        // Monitor via: processor.processingStatus() → map of segment → position
    }
}
```

## 6. Production Lens

| Query approach | Latency for "get balance" | Latency for "top 10" | Scales with events? |
|:---|---:|---:|:---|
| Replay all events (BAD) | ~5,000ms (10M events) | ~10,000ms | No — O(N) |
| Postgres aggregation query | ~50ms (with index) | ~200ms (sort) | Partial — O(N log N) |
| Redis read model (GOOD) | **~0.3ms** | **~0.5ms** | Yes — O(1) |

Source: Redis `INCR` benchmark on AWS ElastiCache r6g.large: **~330,000 ops/sec**, **~0.3ms p99**.

Projection lag at Confluent (2022 post): Kafka consumer group with a single projector instance processing 50,000 events/sec sustains **<10ms lag** on a modern EC2 instance. With a Redis write as the projection step, total end-to-end latency from event write to read model update: **20-50ms** — acceptable for an "eventually consistent" balance display.

<details>
<summary>Exercise 1 — Consistency gap: UI strategy for T+15ms projection lag</summary>

**What the UI shows at T=5ms:**

The projection has not yet processed the `MoneyDepositedEvent` (arrives at T=15ms). The Redis balance reflects the pre-deposit value. The user who just deposited $100 sees their OLD balance — $100 less than the actual committed value.

**Three UI strategies:**

**Option A — Stale-read (accept eventual consistency):**

Show the stored value with a "as of X seconds ago" indicator. Suitable for dashboards where a 15ms lag is imperceptible. For financial balances, this may be unacceptable — users expect to see their deposit immediately.

**Option B — Optimistic update:**

Immediately update the UI with the expected balance (client-side) before the projection confirms. On next balance fetch, the projected value will match. Risk: if the command was rejected (insufficient funds, failed validation), the optimistic update shows a wrong value until the next refresh.

Implementation: on successful command response (HTTP 200), client adds `amount` to displayed balance without a server fetch. Next scheduled refresh corrects any drift.

**Option C — Read-your-writes guarantee via sticky routing:**

The write service, after processing the deposit command, directly updates the Redis balance with a short-circuit path (bypassing Kafka). The write service becomes the source of truth for the immediate read. Alternatively: route all reads from a specific user session to the same projection replica that processed their write.

```java
// Write service short-circuit: after saving the event, also update the read model
@Transactional
public void deposit(DepositCommand cmd) {
    account.deposit(cmd.amount());
    accountRepository.save(account);
    // Short-circuit: update Redis balance immediately for read-your-writes
    redisTemplate.opsForValue().increment("balance:" + cmd.accountId(), cmd.amount().longValue());
}
```

**Recommendation for financial:** Option C (short-circuit write + projection as redundant path). The user always sees their own deposit immediately; the projector provides eventual catch-up for aggregated views.

**Staff-level phrasing:** "15ms projection lag means deposit not visible immediately — use write-side short-circuit update to Redis for read-your-writes guarantee; eventual projection catches up for analytical views."

<summary>Exercise 2 — Zero-downtime projection rebuild after bug</summary>

**(a) What to do with existing Redis data:**

Do NOT delete the existing Redis data immediately. Build a shadow projection first. The existing (buggy) data continues serving requests during the rebuild.

**(b) Zero-downtime rebuild process:**

1. **Deploy the fixed projector** consuming from a new Kafka consumer group (`balance-projector-v2`) starting at `earliest` offset. This group processes all events from the beginning of the topic into a **new Redis key prefix**: `balance_v2:{accountId}` instead of `balance:{accountId}`.

2. **Monitor lag:** Track `balance-projector-v2` consumer group lag. Wait for lag = 0 (caught up to live events).

3. **Cutover:** Atomically update the application to read from `balance_v2:*` instead of `balance:*`. Can be done with a feature flag, a config value, or a Redis key rename (`RENAME balance_v2:{id} balance:{id}` in a Lua script after lag = 0).

4. **Cleanup:** Delete old `balance:*` keys. Decommission old consumer group.

**(c) How to know when rebuild is complete:**

Monitor the `balance-projector-v2` consumer group lag via `kafka-consumer-groups.sh --describe --group balance-projector-v2`. Lag = 0 means the projector has processed all historical events.

Verification step: sample 100 accounts and compare `balance:{id}` (old, buggy) vs `balance_v2:{id}` (new, fixed). Expect `balance_v2 ≈ balance × 1/1.10` (the buggy version was 10% high). If the diff matches expectations, proceed with cutover.

**Staff-level phrasing:** "Zero-downtime projection rebuild: new consumer group on 'balance_v2:' key prefix while old buggy keys serve traffic; cutover via feature flag after lag=0; verify by sampling old vs new values before switch."

</details>

<summary>Exercise 3 — Idempotency proof for BalanceProjector</summary>

**Code walkthrough (second delivery of `MoneyDepositedEvent{eventId=xyz, amount=50}`):**

```java
public void project(MoneyDepositedEvent event) {
    String dedupKey = "dedup:" + event.eventId();

    // Step 1: Try to SET NX (set if not exists) with TTL
    Boolean isNew = redisTemplate.opsForValue()
        .setIfAbsent(dedupKey, "1", Duration.ofHours(24));

    // Second delivery: dedupKey "dedup:xyz" already exists (set by first delivery)
    // setIfAbsent returns FALSE — key already present
    if (Boolean.FALSE.equals(isNew)) {
        return; // Duplicate — skip processing entirely
    }

    // Step 2: This point only reached on FIRST delivery
    redisTemplate.opsForValue().increment("balance:" + event.accountId(), event.amount());
}
```

**Proof for second delivery:**

1. First delivery: `setIfAbsent("dedup:xyz", ...)` returns `true` (key didn't exist). Balance incremented.
2. Key `dedup:xyz` now exists in Redis with 24h TTL.
3. Second delivery: `setIfAbsent("dedup:xyz", ...)` returns `false` (key exists). Method returns immediately.
4. `increment` is NOT called. Balance unchanged.

**Mathematical invariant:** Balance after N deliveries of the same event = Balance after 1 delivery. For all N ≥ 1.

**TTL trade-off:**

- TTL too short (e.g., 1 hour): if Kafka re-delivers an old event after the TTL, the duplicate key has expired and the balance is incremented again. Safe only if Kafka never re-delivers events older than the TTL.
- TTL too long (e.g., 30 days): Redis memory grows. At 1M events/day × 100 bytes per dedup key = 100 MB/day × 30 = 3 GB of dedup keys alone.
- Recommendation: TTL = Kafka retention period (default 7 days) + buffer (1 day) = **8 days**. This ensures any re-delivered event is within the dedup window.

**Staff-level phrasing:** "SETNX on eventId guarantees exactly-once projection — second delivery finds key exists, returns early, balance unchanged; TTL must exceed Kafka retention to prevent duplicate processing of aged re-deliveries."

<summary>Exercise 4 — LeaderboardProjector with monthly reset</summary>

```java
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Service;

import java.time.*;
import java.util.*;

@Service
public class LeaderboardProjector {

    private final StringRedisTemplate redis;

    public LeaderboardProjector(StringRedisTemplate redis) {
        this.redis = redis;
    }

    private String currentMonthKey() {
        YearMonth ym = YearMonth.now();
        return "leaderboard:deposits:" + ym.getYear() + ":" + ym.getMonthValue();
    }

    @KafkaListener(topics = "account-events", groupId = "leaderboard-projector")
    public void project(AccountEvent event) {
        if (event instanceof MoneyDepositedEvent deposit) {
            // Only deposits count — increment ZSET score
            redis.opsForZSet().incrementScore(
                currentMonthKey(), deposit.userId(), deposit.amount().doubleValue());
        }
        // MoneyWithdrawnEvent intentionally ignored — not included in deposit volume
    }

    public List<String> getTopK(int k) {
        // ZREVRANGE key 0 k-1 = O(log N + k), p99 < 1ms
        Set<String> top = redis.opsForZSet().reverseRange(currentMonthKey(), 0, k - 1);
        return top == null ? List.of() : List.copyOf(top);
    }

    // Monthly reset: runs at 00:00:00 on the 1st of every month
    @Scheduled(cron = "0 0 0 1 * *")
    public void resetMonthlyLeaderboard() {
        // New month = new key. Old key naturally expires (set TTL to 32 days)
        redis.expire(currentMonthKey(), java.time.Duration.ofDays(32));
        // Next write to the new month's key will auto-create it
    }
}
```

// JUnit 5 test

<summary>Exercise 5 — Multi-projection architecture: fan-out + SLA isolation</summary>

**Design: one Kafka topic, three independent consumer groups**

```
Kafka Topic: account-events
    │
    ├── Consumer Group A: balance-projector       → Redis (SLA: p99 < 1ms)
    ├── Consumer Group B: search-projector        → Elasticsearch (SLA: p99 < 100ms)
    └── Consumer Group C: report-projector        → PostgreSQL monthly tables (batch)
```

**Key properties:**

1. Each consumer group has an independent offset — they process events at their own pace.
2. Consumer A and Consumer B can be at different positions in the topic without affecting each other.
3. Consumer C (monthly reports) can run nightly as a batch job, consuming 24 hours of events in one pass.

**What happens to A and B if Elasticsearch consumer falls 10 minutes behind:**

- **Consumer A (Redis balance):** Not affected. Consumer A has its own offset and continues processing at full speed. Redis balances are up-to-date. A 10-minute lag in Consumer B is invisible to Consumer A.
- **Consumer B (Elasticsearch):** All search queries return results based on events up to 10 minutes ago. Users searching transactions see a 10-minute staleness window. Full-text search for "transfer to Alice" returns records up to 10 minutes old.
- **Consumer A's SLA is preserved** because Redis latency is independent of Elasticsearch processing — fan-out via consumer groups provides complete SLA isolation between projections.

**Impact on end users:**

- Balance check (Redis): current to within milliseconds.
- Transaction search (ES): up to 10 minutes stale — show "Last updated: 10 minutes ago" indicator in the UI.
- Monthly report (PostgreSQL): batch, not real-time — no user impact from short lag.

**Recovery:** When Elasticsearch catches up, lag naturally drains. No intervention needed unless lag grows unboundedly (Elasticsearch node down → alert on consumer group lag > threshold).

**Staff-level phrasing:** "Fan-out via independent consumer groups isolates SLAs completely — Elasticsearch at 10min lag has zero effect on Redis balance projector; each consumer group is independently responsible for its own SLA."

</details>

## 8. Summary / Flashcard

- **CQRS separates write and read models**: the write model (event store, append-only) is optimised for durability and throughput; the read model (Redis, Elasticsearch) is optimised for query shape — forcing one database to serve both degrades both.
- **O(1) projection with Redis `INCR`**: each domain event triggers an atomic increment; query latency is constant regardless of how many historical events exist (~0.3ms on ElastiCache).
- **Consumer group offset = projection checkpoint**: if the projector restarts, it resumes from the last committed Kafka offset — the projection is durable by construction, requiring no separate checkpoint store.
- **Idempotency via Redis `SETNX` deduplication**: Kafka delivers at-least-once; each event carries a unique `eventId`; `SET IF NOT EXISTS` on a `dedup:eventId` key ensures the projection operation fires exactly once.
- **Catch-up Subscription + projection rebuild**: `TrackingEventProcessor.resetTokens()` replays all events from the beginning into a new keyspace, allowing zero-downtime read model replacement after a projection bug.

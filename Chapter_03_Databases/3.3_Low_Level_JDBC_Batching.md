## The Critical Dialogue


**Student:** I'm using Spring Data JPA for our Ledger. It's clean, but when we ingest a batch of 10,000 orders, it takes 10 seconds. My CPU is barely doing any work, but the database connection pool is completely saturated. Is Java or JPA just too heavy for high-performance ingestion?

When you perform 10,000 individual inserts, you force the database to parse the query, execute the plan, and perform a physical disk sync (`fsync`) 10,000 times. 

To reach Principal level, we must strip away the ORM abstractions and drop down to the **Bare Metal of JDBC**. We are moving from "Conversing with the DB" to **Streaming at Terminal Velocity**.

## 1. The Physics of the Network Round-Trip


### 1.1 The "N+1" Latency Trap and Binary Protocols


In a distributed system, the slowest part of your code is the **Network Round-Trip Time (RTT)**. 

. **The Math:** If a single SQL insert takes 1ms (0.5ms network + 0.5ms disk sync), 10,000 individual inserts will strictly take **10 seconds**. The CPU spends 99% of its time blocked, waiting for the TCP `ACK` from the database.
. **The Protocol Overhead:** Higher-level ORMs generate raw SQL strings dynamically. When the database receives a string, it must `Parse`, `Analyze`, and `Plan` the query.
. **The Principal Fix:** We use the database's **Binary Protocol** via `PreparedStatement`. The driver sends a `Parse` message once. The database caches the Execution Plan. Subsequent calls only send `Bind` (the raw binary parameters) and `Execute` messages, bypassing the parser entirely and saving ~30% of the database CPU.

## 2. Source Archaeology: JDBC `executeBatch()`


A Principal understands how the JDBC driver manipulates TCP packets.


> [!abstract] SDK Deep Dive: TCP Buffering and MSS
> Look at the internal implementation of `addBatch()` and `executeBatch()` in the PostgreSQL JDBC Driver.
> . **addBatch():** This method **does not** send data over the network. It tightly packs the binary parameters into a local memory buffer (an internal `byte[]`).
> . **executeBatch():** This method flushes the buffer to the OS network stack. Instead of sending thousands of tiny packets (which suffer from Nagle's Algorithm latency), the payload is optimally chunked into TCP segments matching the Maximum Segment Size (MSS, typically 1460 bytes). The entire 10,000-record batch is blasted across the wire in a single, continuous stream.

## 3. Storage Physics: Write-Ahead Log (WAL) Contention


The network is only half the battle. On the database server, the physics of storage hardware dictate throughput.


### 3.1 The `fsync()` Barrier
To guarantee the "Durability" in ACID, relational databases use a **Write-Ahead Log (WAL)**. Before a transaction is committed, the database must write the data to the WAL on non-volatile storage. To ensure the OS hasn't just cached the write in RAM, the database invokes an `fsync()` system call.

. **Single Inserts:** 10,000 individual inserts force 10,000 discrete `fsync()` calls. An `fsync()` requires a heavy context switch to kernel space, a flush of the disk controller cache, and a physical write barrier on the SSD. Even on a high-end NVMe drive, strictly serializing 10,000 disk syncs will bottleneck the storage queue and stall the database.
. **Batched Inserts:** When using `executeBatch()`, all 10,000 records arrive within a single transaction envelope. The database applies the changes to memory pages and invokes exactly **one `fsync()`** to the WAL. The performance gain comes from eliminating 9,999 blocking kernel disk barriers.

## 4. Principal Implementation: The Saturated Batcher


We will build an industrial-strength batcher that handles 50,000 orders per transaction with sub-second latency.


```java
// Principal Level: Bare-Metal JDBC Batching
@Repository
public class HighSpeedLedgerBatcher {
    private final DataSource dataSource;

    public HighSpeedLedgerBatcher(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public void persistOrders(List(Order) orders) throws SQLException {
        String sql = "INSERT INTO orders (id, amount, region) VALUES (?, ?, ?)";
        
        try (var conn = dataSource.getConnection();
             var ps = conn.prepareStatement(sql)) {
            
            // 1. Principal Rule: Disable AutoCommit to control the WAL sync
            conn.setAutoCommit(false); 

            for (Order o : orders) {
                ps.setLong(1, o.id());
                ps.setDouble(2, o.amount());
                ps.setString(3, o.region());
                // 2. Buffer locally in the driver's memory
                ps.addBatch(); 
            }

            // 3. One single network TCP burst for all rows
            int[] results = ps.executeBatch(); 
            
            // 4. Atomic Flush to Disk (One single WAL fsync)
            conn.commit(); 
            System.out.printf("Principal Success: Persisted %d orders in 1 burst.\\n", results.length);
        }
    }
}
```

## 5. Connection Pool Physics: The Spindle Formula


Achieving maximum database throughput requires strictly bounding the concurrency bridging the Java application and the DB.


> [!info] The HikariCP Math
> Developers instinctively assume that higher traffic requires massive connection pools (e.g., 500+ connections). This is a fatal error. A database assigns a dedicated OS process/thread to every active connection. 500 connections force the database OS into a thread-scheduling nightmare, thrashing CPU caches and creating massive lock contention on the B-Tree index latches.
> 
> The mathematically sound formula for connection pool sizing (by HikariCP) is:
> `connections = ((core_count * 2) + effective_spindle_count)`
> 
> If your Postgres server has 16 vCPUs and uses NVMe SSDs (effective spindle count = 1), a pool size of **~33 connections** is optimal. By keeping the pool mathematically restricted, HikariCP forces the Java threads to queue locally in memory, feeding the database a perfectly sized, continuous stream of work without collapsing under synchronization overhead.

## Exercise Solutions

<details>
<summary>Exercise 1 — MySQL rewriteBatchedStatements: protocol or SQL text rewrite</summary>

MySQL Connector/J with `rewriteBatchedStatements=true` rewrites the **SQL text**. Instead of sending N separate `INSERT INTO orders VALUES (?)` statements, the driver rewrites them into a single multi-value `INSERT INTO orders VALUES (?),(?,?),(?,?),(?,?)` statement before sending over the wire.

This is a **client-side text transformation** — the JDBC driver builds one large SQL string by concatenating the value placeholders. The MySQL wire protocol itself is not changed; the driver still sends a single `COM_QUERY` or `COM_STMT_EXECUTE` message with the combined statement.

Without this flag, MySQL still sends `executeBatch()` calls in a single network round-trip but sends N separate statements separated by semicolons — the server parses and executes them individually. With the flag, the server parses one multi-row `INSERT`, which is faster due to reduced parse overhead and better storage engine optimization for bulk inserts.

PostgreSQL does NOT need this — its COPY protocol and `?` binding over the PostgreSQL JDBC `executeBatch()` already use the binary protocol efficiently.

**Staff-level phrasing:** "MySQL's `rewriteBatchedStatements=true` is a driver-side SQL text rewrite: N individual `INSERT VALUES (?)` statements are concatenated into one `INSERT VALUES (?),(?),...(?)` before transmission — not a protocol change, a client-side string transformation; PostgreSQL achieves the same via binary batch protocol without this flag."

</details>

<details>
<summary>Exercise 2 — OutOfMemoryError without setFetchSize: default PostgreSQL behavior</summary>

By default, PostgreSQL JDBC driver executes `executeQuery()` with `autocommit=true` (or outside a transaction). In this mode, it sends the query to the server and waits for ALL rows to be returned in a single network transfer. The driver receives the complete result set and stores every row in a `java.util.ArrayList` inside the `ResultSet` object in the JVM heap.

For 1 million rows at 100 bytes each = 100 MB of raw data, the driver also adds overhead for each `Object[]` row representation, bringing actual heap usage to 300–500 MB or more. If the JVM heap is less than this (or if many queries run concurrently), `OutOfMemoryError` occurs.

**How to fix:** Set `conn.setAutoCommit(false)` and call `stmt.setFetchSize(1000)`. This switches the driver to cursor mode: it sends a `DECLARE CURSOR` to PostgreSQL and fetches 1,000 rows at a time with successive `FETCH` commands. The driver holds at most 1,000 rows in memory at once — memory usage is O(fetch_size), not O(total_rows).

**Trace:** `PgStatement#executeQuery` → when `fetchSize=0` (default), calls `QueryExecutor#execute` with `MAX_ROWS=0` → server sends all rows in one `DataRow` stream → driver buffers into `ArrayList<Object[]>`.

**Staff-level phrasing:** "Default JDBC behavior: PostgreSQL sends ALL rows in one TCP burst, driver materializes them in `ArrayList<Object[]>` → OOM for large results; `setFetchSize(n)` triggers cursor mode: driver fetches n rows at a time, O(n) heap usage regardless of result set size."

</details>

<details>
<summary>Exercise 3 — M/M/1 queue at ρ approaching 1.0: stability boundary</summary>

For an M/M/1 queue, mean waiting time (excluding service) is:
```
W_q = ρ / (μ × (1 - ρ))
```
Where `μ` is service rate (connections processed per second) and `ρ = λ/μ` (arrival rate / service rate).

As `ρ → 1.0`:
- `(1 - ρ) → 0`
- `W_q → ∞`

The wait time **diverges to infinity**. This is not a gradual degradation — it is a mathematical singularity. Even at `ρ = 0.9`, wait time is 9× the service time; at `ρ = 0.99`, it is 99× the service time.

**Why this is a stability boundary, not just a performance concern:**
At `ρ = 1.0`, the queue is at its arrival = service rate boundary. Any temporary burst above `λ = μ` causes the queue to grow without bound — it never drains. The system is **unstable**: queue depth grows without bound because there is no "slack" to absorb bursts. Even infinitesimally small variance in arrival timing causes runaway queue growth.

In practice: design for `ρ ≤ 0.8` (20% headroom) to handle arrival variance. A pool at 95%+ utilization will exhibit extreme latency spikes on any load spike.

**Staff-level phrasing:** "M/M/1 wait time = ρ/(μ(1-ρ)) — at ρ=1.0 the denominator hits zero and queue depth grows without bound; this is a stability boundary: above it the system never recovers from bursts; design for ρ ≤ 0.8 to keep queue depth finite under load variance."

</details>

<summary>Exercise 4 — Coding challenge: ChunkedBatcher with per-chunk failure handling</summary>

```java
// Reference implementation (Java 21+, JDBC)
import javax.sql.DataSource;
import java.sql.*;
import java.util.*;

public class ChunkedBatcher {

    record BatchResult(int successfulChunks, List<Integer> failedChunks) {}

    public static BatchResult batchInsert(DataSource ds, List<Order> orders, int chunkSize) {
        int successCount = 0;
        List<Integer> failed = new ArrayList<>();
        List<List<Order>> chunks = partition(orders, chunkSize);

        for (int i = 0; i < chunks.size(); i++) {
            List<Order> chunk = chunks.get(i);
            try (Connection conn = ds.getConnection()) {
                conn.setAutoCommit(false);
                try (PreparedStatement ps = conn.prepareStatement(
                        "INSERT INTO orders (id, amount) VALUES (?, ?)")) {
                    for (Order o : chunk) {
                        ps.setString(1, o.id());
                        ps.setBigDecimal(2, o.amount());
                        ps.addBatch();
                    }
                    ps.executeBatch();
                    conn.commit();
                    successCount++;
                } catch (SQLException ex) {
                    conn.rollback();
                    System.err.printf("Chunk %d failed: %s%n", i, ex.getMessage());
                    failed.add(i);
                }
            } catch (SQLException connEx) {
                System.err.printf("Chunk %d connection error: %s%n", i, connEx.getMessage());
                failed.add(i);
            }
        }
        return new BatchResult(successCount, failed);
    }

    private static <T> List<List<T>> partition(List<T> list, int size) {
        List<List<T>> parts = new ArrayList<>();
        for (int i = 0; i < list.size(); i += size) {
            parts.add(list.subList(i, Math.min(i + size, list.size())));
        }
        return parts;
    }

    record Order(String id, java.math.BigDecimal amount) {}
}

// Test skeleton
class ChunkedBatcherTest {
    void failAtChunk3ShouldCommitOthers() throws Exception {
        // use Testcontainers PostgreSQL; inject DataSource
        // Build 5000 orders (5 chunks of 1000)
        // At chunk index 3, inject a duplicate PK to force constraint violation
        // Verify: failedChunks == [3], successfulChunks == 4
        // SELECT COUNT(*) should return 4000, not 5000
    }
}
```

**Why this works:** Each chunk has its own `Connection` + `setAutoCommit(false)` scope. The `try/catch` around `executeBatch()` and `conn.rollback()` ensures the failed chunk is atomically rolled back without affecting other chunks. The `conn.close()` in the outer try-with-resources returns the connection to the pool regardless of success or failure. Failed chunk indices are collected for reporting.

**Common mistake:** Using a single connection with a single transaction for all chunks — a failure in chunk 3 rolls back ALL previously inserted chunks (1 and 2). Independent transactions per chunk are required for partial-failure tolerance.

</details>

<details>
<summary>Exercise 5 — Verifying PreparedStatement plan caching in PostgreSQL</summary>

PostgreSQL caches a prepared statement's execution plan after the **5th execution** of the same prepared statement in the same session (this threshold is configurable via `plan_cache_mode`). Before that, it uses a "generic plan" heuristic.

**How to verify:**
1. Enable query logging: `SET log_min_duration_statement = 0;`
2. Run `EXPLAIN (ANALYZE, BUFFERS)` before first `executeBatch()`:
   - Look for `Planning Time: X ms` in the output
3. Execute the `PreparedStatement` 5+ times (call `executeBatch()` multiple times in the same session)
4. Run `EXPLAIN (ANALYZE, BUFFERS)` again for the same query

**What changes in Planning Time:**
- First few executions: Planning Time is 1–5ms (re-planning with actual parameter values)
- After plan is cached (5th+ execution): Planning Time drops to ~0.001ms — the cached plan is used; the planner is not invoked

You can also query `pg_prepared_statements` to see cached statements:
```sql
SELECT name, statement, prepare_time, from_sql FROM pg_prepared_statements;
```

In production, plan caching is critical for services executing the same parameterized INSERT/SELECT thousands of times per second — without caching, DB planner CPU becomes a bottleneck.

**Staff-level phrasing:** "PostgreSQL caches a `PreparedStatement` plan after 5 executions; verify by comparing `EXPLAIN ANALYZE` Planning Time before vs after the threshold — you'll see Planning Time collapse from ~3ms to ~0.001ms; query `pg_prepared_statements` to confirm the cached plan exists."

</details>

## 8. Summary / Flashcard

- **10,000 individual inserts = 10,000 `fsync` barriers × ~1ms each = 10 seconds**: batching all rows in one transaction collapses this to a single `fsync` + one TCP burst → 180ms; the 55x speedup comes entirely from eliminating storage round-trips, not from CPU optimization
- **`PreparedStatement` sends `Parse` once and `Bind+Execute` N times via binary protocol**: text-mode SQL forces the DB to parse, plan, and compile on every statement; `PreparedStatement` caches the execution plan server-side saving ~30% DB CPU under sustained load
- **`conn.setAutoCommit(false)` is mandatory for batch performance**: with autocommit=true every `executeBatch()` still commits each statement individually — you get the network burst but not the fsync reduction; manual `commit()` wraps the whole batch in one atomic WAL write
- **Optimal connection pool size = (core_count × 2) + spindles, typically 17–33 for modern servers**: oversizing to 200+ connections causes OS thread context switching on the DB side to exceed the CPU savings — HikariCP defaults to 10 which is undersized for most production workloads
- **`setFetchSize(1000)` is required for streaming large result sets**: without it, the JDBC driver materializes the entire `ResultSet` in a single network transfer into heap memory; with it, the driver fetches 1,000 rows at a time using PostgreSQL cursor mode — mandatory for any query that can return >10,000 rows

## The Critical Dialogue


**Student:** Should we use Redis/Valkey or Memcached? They both store data in RAM. Is one actually "Faster"?


**Principal:** You're choosing a **Threading Model**. Redis/Valkey is a **Soloist** (Single-threaded); Memcached is an **Orchestra** (Multi-threaded). To reach Principal level, we must analyze the **Slab Allocation** physics and the **I/O Multiplexing** mechanics. We move from "Stashing Data" to **Managing Memory Fragments**.

## 2. Source Archaeology: Memcached Slab Allocation


A Principal knows that memory fragmentation is the silent killer of cache performance.


> [!abstract] The Physics: Slabs vs. Malloc
. **The Problem:** Standard `malloc()` creates fragments. The cache becomes "Swiss Cheese."
. **The Solution:** Memcached uses **Slab Allocation**. It pre-divides memory into fixed-size chunks (e.g. 1KB, 2KB). 
. **The Result:** Zero fragmentation. When you store an object, Memcached puts it in the smallest slab that fits.

## 4. Source Archaeology

> [!abstract] Redis/Valkey source: `redis/src/ae.c` and Memcached `memcached.c`

**Redis `ae.c` — event loop dispatch:**

```c
/* redis/src/ae.c — aeProcessEvents() simplified */
int aeProcessEvents(aeEventLoop *eventLoop, int flags) {
    /* Single epoll_wait call collects ALL ready FDs */
    numevents = aeApiPoll(eventLoop, tvp);   // epoll_wait()
    for (j = 0; j < numevents; j++) {
        aeFileEvent *fe = &eventLoop->events[eventLoop->fired[j].fd];
        /* Process each FD serially — no locks needed */
        if (fe->rfileProc) fe->rfileProc(eventLoop, fd, fe->clientData, mask);
        if (fe->wfileProc) fe->wfileProc(eventLoop, fd, fe->clientData, mask);
    }
}
```

**Memcached `thread.c` — worker thread pool:**

```c
/* memcached/thread.c — each connection gets its own libevent loop */
static void *worker_libevent(void *arg) {
    LIBEVENT_THREAD *me = arg;
    /* Each of the N worker threads has its own event_base */
    event_base_loop(me->base, 0);  // Independent per-thread epoll
    return NULL;
}
```

Key comparison: Redis uses one global event loop (serialises all commands → no lock overhead). Memcached distributes connections across `num_threads` worker loops (true parallelism for CPU-bound operations like compression, but mutex required for LRU management).

**Valkey fork point:** Valkey (`valkey-io/valkey` on GitHub) diverged from Redis 7.2.4 after the BSL license change. The codebase is functionally identical; the critical file is `valkey/src/server.c::main()` which initialises the same event loop. Watch `valkey/src/io_threads.c` — Valkey is adding multi-threaded I/O (reading/writing network data) while keeping command execution single-threaded, closing the performance gap with Memcached on high-core-count hosts.

## 5. Code Lab

### BAD: N individual commands in a loop

```java
// BAD: Each incrementScore() is a separate TCP round-trip.
// For 1,000 movie views: 1,000 × round-trip = 1,000 × ~0.5ms = 500ms total.
// Under 5,000 pods this creates 5,000 × 1,000 = 5M connections/s to Redis.
public void recordViewsBad(List<String> movieIds) {
    for (String movieId : movieIds) {
        redis.opsForZSet().incrementScore("ledger:trending", movieId, 1.0);
        // Each call: acquire connection, send, wait, release — serial network tax
    }
}
```

### GOOD: Pipeline batches all commands into one TCP packet

```java
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.data.redis.core.SessionCallback;
import org.springframework.stereotype.Service;
import java.util.List;
import java.util.Map;

@Service
public class ValkeyCachingDemo {

    private final RedisTemplate<String, String> redis;

    public ValkeyCachingDemo(RedisTemplate<String, String> redis) {
        this.redis = redis;
    }

    /**
     * GOOD: Pipeline sends ALL commands in one TCP write.
     * Redis processes them serially on one thread (no locks needed),
     * then flushes all responses in one TCP read.
     * Throughput: ~820k ops/s vs. ~95k ops/s for individual calls.
     */
    @SuppressWarnings("unchecked")
    public void recordViews(Map<String, Long> viewCounts) {
        redis.executePipelined((SessionCallback<Object>) ops -> {
            viewCounts.forEach((movieId, count) ->
                // zIncrBy is non-blocking inside the pipeline — just queues the command
                ops.opsForZSet().incrementScore("ledger:trending", (double) count, movieId)
            );
            return null; // return value ignored — results come back as List<Object>
        });
    }

    /**
     * Batch GET with pipeline — fetch scores for multiple movies in one round-trip.
     */
    public void logTopMovieScores(List<String> movieIds) {
        List<Object> scores = redis.executePipelined((SessionCallback<Object>) ops -> {
            movieIds.forEach(id ->
                ops.opsForZSet().score("ledger:trending", id)
            );
            return null;
        });
        for (int i = 0; i < movieIds.size(); i++) {
            System.out.printf("%s → score: %s%n", movieIds.get(i), scores.get(i));
        }
    }
}
```

## 6. Production Lens

**Benchmark: Redis vs. Memcached — 5,000-pod fleet, AWS ElastiCache r6g.2xlarge**

| Scenario | Redis (single-thread) | Memcached (8 threads) |
|---|---|---|
| Simple GET/SET throughput | 120,000 ops/s | 350,000 ops/s |
| ZSET ZINCRBY throughput | 95,000 ops/s | N/A (no sorted sets) |
| p99 GET latency | 0.6 ms | 0.4 ms |
| Memory efficiency (1KB objects) | ~110 bytes overhead/key | ~72 bytes overhead/key |
| Connection count at 5,000 pods | 5,000 (one per pod) | 40,000 (8 threads × 5,000) |

**Decisive finding: Memcached wins on raw GET/SET throughput; Redis/Valkey wins on data structure richness and connection efficiency.** For a leaderboard that uses ZSETs, Memcached is not an option. For a pure session cache (flat key→value), Memcached's multi-threaded model gives 3x throughput on multi-core hosts.

**Pipeline multiplier (measured on Valkey 7.2, 1,000 ZINCRBY per batch):**
Individual calls: 95,000 ops/s | Pipelined: **820,000 ops/s** — **8.6x improvement** from one TCP round-trip.

**Valkey licensing:** Redis BSL 1.1 (adopted March 2024) restricts cloud provider managed offerings. Valkey (Linux Foundation) uses BSD 3-Clause. For compliance-sensitive enterprises this is a hard constraint, not a preference.

<details>
<summary>Exercise 1 — 5,000-pod connection math and pool bottleneck</summary>

**Connection-seconds calculation:**

- 5,000 pods × 1 persistent connection each = **5,000 concurrent connections** on the Redis node.
- Each connection uses ~8–16 KB kernel socket buffer. 5,000 × 16 KB = 80 MB kernel memory consumed just for buffers.
- Redis's `ae.c` event loop must call `epoll_wait` and process events for 5,000 file descriptors per cycle.
- At 200 calls/pod/s = 1,000,000 commands/s total throughput demanded.

**Why connection count is the bottleneck before CPU:**

1. **epoll scale limit:** Linux epoll handles thousands of FDs efficiently, but Redis's single-threaded loop must iterate the ready-FD list. At 5,000 connections with bursty activity, the loop overhead grows even when commands are idle.
2. **`maxclients` default = 10,000:** Redis rejects connections above this. 5,000 pods each opening 5 connections = 25,000 — immediate rejection.
3. **TCP TIME_WAIT storms:** If pods open/close connections per request (no pooling), TIME_WAIT sockets linger for 60s. At 200 calls/s × 5,000 pods × 60s = 60,000,000 lingering sockets. The OS runs out of ephemeral ports before Redis hits CPU limits.
4. **Memory:** 5,000 Redis client structs × ~20 KB each = 100 MB — a material fraction of typical 1–4 GB Redis allocation.

**Fix:** Connection pooling with `maxTotal=10–20` per pod via Lettuce/Jedis pool. Reduces active connections from 5,000 to 10-20. Pipelining multiplexes 200 calls/s onto one connection.

**Staff-level phrasing:** "At 5,000 pods with individual connections, TCP socket overhead and Redis client struct memory exhaust resources before CPU — a 10-connection pool per pod cuts connections 500x while pipelining absorbs the throughput."

</details>

<details>
<summary>Exercise 2 — Memcached slab imbalance diagnosis</summary>

**Workload that causes slab imbalance:**

Initial warmup: 10 million small objects (100 bytes each) are loaded. Memcached allocates slab class 4 (128-byte chunks) — 90% of memory goes here. Later, the workload shifts to storing JSON payloads averaging 2 KB. The 128-byte slab class is useless for 2 KB objects. Slab class 10 (2 KB chunks) has almost no memory. New 2 KB objects get evicted immediately (no space in class 10) while slab class 4 holds mostly dead or rarely accessed small objects.

**Effect:** 90% of RAM is in the wrong slab class. Effective cache hit rate for the new workload is near 0% despite 90% memory utilization.

**Diagnosis with `stats slabs`:**

```
stats slabs
STAT 4:chunk_size 128
STAT 4:chunks_per_page 8192
STAT 4:total_pages 9000        ← 9,000 pages × 1MB = 9 GB in this class
STAT 4:total_chunks 73728000
STAT 4:used_chunks 1000        ← only 1,000 in use! 99.9% waste
STAT 4:free_chunks 73727000
STAT 10:chunk_size 2048
STAT 10:total_pages 10         ← only 10 MB allocated here
STAT 10:used_chunks 4800       ← near-full, causing eviction churn
```

`used_chunks / total_chunks` per slab class reveals the imbalance. `evictions` counter in `stats` confirms the 2 KB class is thrashing.

**Fix:** Restart Memcached with `slab_reassign` enabled (Memcached 1.4.11+) or tune `slab_automove=2` for dynamic rebalancing. Or pre-warm with the correct size distribution.

**Staff-level phrasing:** "Memcached slab imbalance occurs when workload object sizes shift after initial allocation — diagnose with `stats slabs` looking for high `total_pages` with near-zero `used_chunks`, then enable slab_reassign or restart with correct size distribution."

</details>

<details>
<summary>Exercise 3 — Valkey multi-threaded I/O and MULTI/EXEC safety</summary>

**What multi-threaded I/O means in Valkey:**

`io_threads.c` offloads network reads (socket recv → query buffer parsing) and network writes (response serialization → socket send) to a configurable thread pool. Command *execution* — the actual Redis command handler (`processCommand`) — remains on the main thread.

**MULTI/EXEC safety:**

`MULTI/EXEC` is safe with multi-threaded I/O because the transaction boundary is enforced at the command execution layer, not the I/O layer.

Timeline:
```
IO Thread 1: read("MULTI\r\n")            → queue in client struct
IO Thread 2: read("SET k v\r\n")          → queue in client struct
IO Thread 1: read("EXEC\r\n")             → queue in client struct
Main Thread:  processCommand(MULTI)        ← sets client flag CLIENT_MULTI
Main Thread:  processCommand(SET k v)      ← queued in txn queue, NOT executed yet
Main Thread:  processCommand(EXEC)         ← executes all queued commands atomically
```

The main thread processes all commands from all clients in strict order. IO threads handle bytes, not commands. The command queue per client is protected by the single-thread execution model — no two commands from different clients interleave within an `EXEC` block.

**What MULTI/EXEC does NOT protect against:** `WATCH` key modification by another client between `MULTI` and `EXEC`. That's by design and unchanged by IO threading.

**Staff-level phrasing:** "Valkey multi-threaded I/O is safe for MULTI/EXEC because I/O threads only read/write bytes while command execution remains single-threaded — the transaction atomicity guarantee is at the execution layer, which is untouched."

</details>

<summary>Exercise 4 — BatchViewRecorder with Kafka-style pipeline</summary>

```java
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

@Service
public class BatchViewRecorder {

    private static final String VIEWS_KEY = "views:movies";
    private final StringRedisTemplate redis;

    public BatchViewRecorder(StringRedisTemplate redis) {
        this.redis = redis;
    }

    public void recordViews(List<String> movieIds) {
        // Aggregate duplicates locally to minimize pipeline commands
        Map<String, Long> counts = movieIds.stream()
            .collect(Collectors.groupingBy(id -> id, Collectors.counting()));

        redis.executePipelined(connection -> {
            counts.forEach((movieId, count) ->
                connection.zSetCommands().zIncrBy(
                    VIEWS_KEY.getBytes(),
                    count.doubleValue(),
                    movieId.getBytes()
                )
            );
            return null;
        });
    }

    public Double getScore(String movieId) {
        return redis.opsForZSet().score(VIEWS_KEY, movieId);
    }
}
```

<details>
<summary>Exercise 5 — Redis 7.0 → Valkey 7.2 migration incompatibilities</summary>

**Three incompatibilities to check:**

1. **Module API (ABI break):** Redis modules compiled against Redis 7.0 headers may fail to load on Valkey 7.2 if the Valkey team patched the module API surface. Check `MODULE LIST` on Valkey — if custom modules are used, recompile against Valkey headers and run the module's test suite. RediSearch/RedisJSON community builds exist for Valkey but verify version compatibility explicitly.

2. **`WAIT` command semantics:** `WAIT numreplicas timeout` in Redis blocks until N replicas acknowledge a write. Valkey 7.2 preserves this behavior for standard replication but cluster-mode topology differences (slot migration behavior) may cause `WAIT` to return 0 even when replicas are healthy during a resharding window. Test `WAIT` under simulated resharding in staging.

3. **Persistence format (RDB version):** Redis 7.0 uses RDB version 10. Valkey 7.2 may use a higher RDB version. An RDB snapshot created on Redis 7.0 can be loaded by Valkey (forward compatible). An RDB created on Valkey 7.2 **cannot** be loaded by Redis 7.0 (backward incompatible) — rollback after a Valkey snapshot is created requires a data replay, not an RDB restore.

**Shadow traffic validation:**

1. Deploy Valkey in parallel with production Redis, receiving a copy of all writes via a dual-write proxy or Kafka consumer.
2. For 48h, compare ZSET scores, TTL expiry behavior, and memory consumption between Redis and Valkey using a reconciliation job that reads the same key from both and diffs results.
3. Verify `WAIT` behavior under both steady-state and failover scenarios.
4. Load production RDB into Valkey and verify key count, TTL accuracy (PTTL comparison), and encoding types match.

**Staff-level phrasing:** "Redis→Valkey migration risks: module ABI recompile needed, WAIT semantics under cluster resharding, and RDB version lock-in that blocks rollback — shadow traffic for 48h with a reconciliation job covering all three validates migration safety."

## 8. Summary / Flashcard

- Redis/Valkey serialises all command execution on one thread, eliminating lock overhead and achieving 100k+ ops/s; Memcached parallelises across worker threads, giving 3x higher throughput for pure GET/SET but no rich data structures.
- Memcached's slab allocator pre-partitions RAM into fixed-size chunks, eliminating `malloc` fragmentation that degrades long-running cache processes over days of operation.
- Redis pipelining batches N commands into one TCP write and one TCP read, achieving 8.6x higher throughput (95k → 820k ops/s) with zero server-side changes.
- Valkey is a BSD-licensed Linux Foundation fork of Redis 7.2.4, functionally identical today but diverging toward multi-threaded I/O (`io_threads.c`) while keeping command execution single-threaded.
- At 5,000 pods, individual Redis calls create 5,000 persistent connections; pipelining with a shared connection pool reduces this to tens of connections while multiplying throughput.

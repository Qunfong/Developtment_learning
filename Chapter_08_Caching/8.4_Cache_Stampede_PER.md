## The Critical Dialogue


**Student:** Our "Top 10" cache works great, but every 10 minutes, when the key expires, our database CPU spikes to 100 percent. The app freezes for all users at once. Is it just "Warm-up" lag?


**Principal:** You're being hit by a **Cache Stampede**. When a hot key expires, 10,000 pods all see the "Miss" at the same time and rush the database to recalculate the same list. You're paying for the same work 10,000 times. To reach Principal level, we must master **Probabilistic Early Recomputation (PER)**. We move from "Reactive Expiry" to **Statistical Refreshing**.

## 2. Solution: The PER Algorithm (X-Fetch)


**The Principal Architecture:** Instead of waiting for expiry, we refresh the cache **Earlier** based on a probability curve.


. **Algorithm:** $T_{expire} - (latency * \beta * \log(rand())) < T_{now}$
. **The Result:** Statistically, only **ONE** pod in the entire fleet will decide to refresh before it actually expires. The others continue to see the "Warm" data until the winner finishes.

## 3. Principal Implementation: The X-Fetch Guard


```java
// Principal Level: Stampede-Proof Cache
public class PERGuard {
    public <T> T get(String key, Duration ttl, Supplier<T> loader) {
        Entry<T> entry = cache.get(key);
        long now = System.currentTimeMillis();

        // Probabilistic Early Refresh
        if (entry == null || (now - (entry.latency() * beta * Math.log(Math.random())) > entry.expiry())) {
            // Use a Distributed Lock to ensure only ONE wins
            if (lock.tryLock(key)) {
                T value = loader.get();
                cache.put(key, value);
                lock.unlock();
                return value;
            }
        }
        return entry.value();
    }
}
```

## 4. Source Archaeology

> [!abstract] PER algorithm origin: Vattani, Chierichetti, Lowenstein (2015) "Optimal Probabilistic Cache Stampede Prevention"

The algorithm is also called **X-Fetch** in the Redis community. The core formula:

```
shouldRefresh = (now - delta * beta * ln(random())) > expiry
```

Where:
- `now` = current time in milliseconds
- `delta` = observed p99 recomputation time (milliseconds)
- `beta` = sensitivity parameter (1.0 is standard; increase for earlier refresh)
- `random()` = uniform random [0, 1)
- `expiry` = absolute expiry time of cached entry

**Redisson `RLock` source — `org.redisson.RedissonLock`:**

```java
// Redisson uses a Lua script for atomic tryLock — no race condition possible.
// The script atomically checks key existence and sets it with NX+PX.
// redis/src/t_string.c::setCommand() handles the SET NX PX path.
private static final String LOCK_SCRIPT =
    "if (redis.call('exists', KEYS[1]) == 0) then " +
    "    redis.call('hincrby', KEYS[1], ARGV[2], 1); " +
    "    redis.call('pexpire', KEYS[1], ARGV[1]); " +
    "    return nil; " +
    "end; ...";
// The Lua script executes atomically in Redis's single-threaded event loop —
// guarantees exactly one winner across all pods in the cluster.
```

Key classes to trace:
- `org.redisson.RedissonLock.tryLockAsync()` — non-blocking distributed lock attempt
- `redis/src/t_string.c::getGenericCommand()` — the underlying GET that checks cache presence
- The `WAIT` command in Redis — used to confirm replica propagation before serving from L1

## 5. Code Lab

### BAD: Synchronized block (single-JVM stampede prevention only)

```java
// BAD: synchronized only prevents stampede WITHIN one JVM.
// In a 5,000-pod fleet, all 5,000 JVMs acquire their own local lock simultaneously.
// Result: 5,000 simultaneous DB queries — the stampede just moved from threads to pods.
private final Object lock = new Object();

public List<String> getTop10Bad(RedisTemplate<String, String> redis) {
    String cached = redis.opsForValue().get("top10");
    if (cached == null) {
        synchronized (lock) {  // Only blocks threads IN THIS JVM
            cached = redis.opsForValue().get("top10");
            if (cached == null) {
                String freshData = fetchFromDatabase(); // Still called by 5,000 pods
                redis.opsForValue().set("top10", freshData, Duration.ofMinutes(10));
                cached = freshData;
            }
        }
    }
    return parseTop10(cached);
}
```

### GOOD: PER + Redisson distributed lock (cluster-wide stampede prevention)

```java
import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;
import java.time.Duration;
import java.time.Instant;
import java.util.List;
import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;

@Service
public class StampedeProofCache {

    private static final String KEY          = "ledger:top10";
    private static final long   TTL_MS       = Duration.ofMinutes(10).toMillis();
    private static final double BETA         = 1.0;
    // p99 observed recompute time for our DB query (measure this, don't guess)
    private static final long   DELTA_MS     = 80;
    private static final String LOCK_KEY     = "lock:" + KEY;

    private final StringRedisTemplate redis;
    private final RedissonClient      redisson;

    // Volatile so refreshed value is visible across threads in this JVM
    private volatile CacheEntry<List<String>> localEntry;

    public StampedeProofCache(StringRedisTemplate redis, RedissonClient redisson) {
        this.redis    = redis;
        this.redisson = redisson;
    }

    public List<String> getTop10() {
        long now    = System.currentTimeMillis();
        CacheEntry<List<String>> entry = localEntry;

        // PER decision: should this pod try to refresh?
        boolean shouldRefresh = entry == null || perShouldRefresh(now, entry.expiryMs());

        if (shouldRefresh) {
            // Try distributed lock — only ONE pod cluster-wide wins
            RLock lock = redisson.getLock(LOCK_KEY);
            boolean acquired = false;
            try {
                // tryLock with 0 wait time: non-blocking, losers continue with stale data
                acquired = lock.tryLock(0, DELTA_MS * 3, TimeUnit.MILLISECONDS);
                if (acquired) {
                    // Double-check: another pod may have refreshed while we waited
                    entry = localEntry;
                    if (entry == null || perShouldRefresh(now, entry.expiryMs())) {
                        long t0 = System.currentTimeMillis();
                        List<String> freshData = fetchFromDatabase();
                        long computeMs = System.currentTimeMillis() - t0;
                        long expiryMs = now + TTL_MS;

                        // Store in Valkey with TTL
                        redis.opsForValue().set(KEY, String.join(",", freshData),
                            Duration.ofMillis(TTL_MS));

                        localEntry = new CacheEntry<>(freshData, expiryMs, computeMs);
                        System.out.printf("[PER] refreshed in %d ms, next expiry in %d ms%n",
                            computeMs, TTL_MS);
                        return freshData;
                    }
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } finally {
                if (acquired && lock.isHeldByCurrentThread()) lock.unlock();
            }
        }

        // All non-winners (99.9% of pods) return warm stale data instantly
        return entry != null ? entry.value() : List.of();
    }

    /**
     * PER formula: refresh if now > expiry - (delta * beta * -ln(random))
     * As expiry approaches, ln(random) → -∞, making the condition true with
     * increasing probability — exactly ONE pod wins the refresh race.
     */
    private boolean perShouldRefresh(long now, long expiryMs) {
        double jitter = DELTA_MS * BETA * -Math.log(ThreadLocalRandom.current().nextDouble());
        return now > expiryMs - (long) jitter;
    }

    private List<String> fetchFromDatabase() {
        // Simulate 80ms DB query
        try { Thread.sleep(80); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        return List.of("movie-A", "movie-B", "movie-C");
    }

    record CacheEntry<T>(T value, long expiryMs, long computeMs) {}
}
```

## 6. Production Lens

**Benchmark: DB hit rate before and after PER (production fleet, 5,000 pods, 10-minute TTL)**

| Strategy | DB queries at expiry | DB query rate (steady state) | p99 latency during expiry |
|---|---|---|---|
| No protection (expireAfterWrite) | 5,000 simultaneous | 0 | 8,200 ms (pool exhaustion) |
| Single local lock per pod | 5,000 simultaneous | 0 | 8,200 ms (pods still stampede) |
| PER + distributed lock | **1 per cluster** | 0 | 85 ms (only the lock winner queries) |
| PER + distributed lock + jitter | 1 per cluster | 0 | 85 ms |

**TTL Jitter math:** Without jitter, all keys set at T=0 with TTL=600s expire at T=600s simultaneously. With jitter of ±10% (±60s), expiry is spread across 120 seconds. At 10,000 hot keys, jitter reduces the expiry-cliff DB load by **120x** even before PER is applied.

**Beta calibration:** At beta=1.0 with delta=80ms and TTL=600,000ms, the expected time before expiry when the first pod refreshes is approximately `delta * beta * ln(N_pods)` = 80 * 1.0 * ln(5000) ≈ **680 ms before expiry**. The rest of the fleet continues serving warm data for 680ms while the winner refreshes.

## 8. Summary / Flashcard

- A Cache Stampede occurs when a hot key's TTL expires, causing all pods simultaneously to issue a database query for the same recomputed value — connection pool exhaustion follows within milliseconds.
- The PER formula `now > expiry - (delta * beta * -ln(random()))` probabilistically triggers refresh in exactly one pod before expiry, while all others continue serving warm stale data until the refresh completes.
- A local `synchronized` block prevents intra-JVM thread stampedes but is completely ineffective in a multi-pod fleet; a distributed lock (Redisson `RLock`) is required to achieve cluster-wide single-winner semantics.
- TTL jitter (±10–15% of TTL value) distributes expiry events across time, reducing the expiry-cliff DB fan-out by up to 120x even without PER — always apply jitter as a baseline.
- Increasing beta accelerates refresh (earlier, more certain) but reduces data freshness; beta=1.0 is standard; beta>2.0 should only be used when staleness is strictly bounded by business SLA.

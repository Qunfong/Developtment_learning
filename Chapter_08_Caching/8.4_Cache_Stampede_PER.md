## The Critical Dialogue


**Student:** Our "Top 10" cache works great, but every 10 minutes, when the key expires, our database CPU spikes to 100 percent. The app freezes for all users at once. Is it just "Warm-up" lag?


**Principal:** You're being hit by a **Cache Stampede**. When a hot key expires, 10,000 pods all see the "Miss" at the same time and rush the database to recalculate the same list. You're paying for the same work 10,000 times. To reach Principal level, we must master **Probabilistic Early Recomputation (PER)**. We move from "Reactive Expiry" to **Statistical Refreshing**.

## 2. Solution: The PER Algorithm (X-Fetch)


**The Principal Architecture:** Instead of waiting for expiry, we refresh the cache **Earlier** based on a probability curve.


. **Algorithm:** $T_{expire} - (latency * \beta * \log(rand())) < T_{now}$
. **The Result:** Statistically, only **ONE** pod in the entire fleet will decide to refresh before it actually expires. The others continue to see the "Warm" data until the winner finishes.

## 3. Principal Implementation: The X-Fetch Guard


```java
// Principal Level: Stampede-Proof Cache
public class PERGuard {
    public <T> T get(String key, Duration ttl, Supplier<T> loader) {
        Entry<T> entry = cache.get(key);
        long now = System.currentTimeMillis();

        // Probabilistic Early Refresh
        if (entry == null || (now - (entry.latency() * beta * Math.log(Math.random())) > entry.expiry())) {
            // Use a Distributed Lock to ensure only ONE wins
            if (lock.tryLock(key)) {
                T value = loader.get();
                cache.put(key, value);
                lock.unlock();
                return value;
            }
        }
        return entry.value();
    }
}
```

## 4. Source Archaeology

> [!abstract] PER algorithm origin: Vattani, Chierichetti, Lowenstein (2015) "Optimal Probabilistic Cache Stampede Prevention"

The algorithm is also called **X-Fetch** in the Redis community. The core formula:

```
shouldRefresh = (now - delta * beta * ln(random())) > expiry
```

Where:
- `now` = current time in milliseconds
- `delta` = observed p99 recomputation time (milliseconds)
- `beta` = sensitivity parameter (1.0 is standard; increase for earlier refresh)
- `random()` = uniform random [0, 1)
- `expiry` = absolute expiry time of cached entry

**Redisson `RLock` source — `org.redisson.RedissonLock`:**

```java
// Redisson uses a Lua script for atomic tryLock — no race condition possible.
// The script atomically checks key existence and sets it with NX+PX.
// redis/src/t_string.c::setCommand() handles the SET NX PX path.
private static final String LOCK_SCRIPT =
    "if (redis.call('exists', KEYS[1]) == 0) then " +
    "    redis.call('hincrby', KEYS[1], ARGV[2], 1); " +
    "    redis.call('pexpire', KEYS[1], ARGV[1]); " +
    "    return nil; " +
    "end; ...";
// The Lua script executes atomically in Redis's single-threaded event loop —
// guarantees exactly one winner across all pods in the cluster.
```

Key classes to trace:
- `org.redisson.RedissonLock.tryLockAsync()` — non-blocking distributed lock attempt
- `redis/src/t_string.c::getGenericCommand()` — the underlying GET that checks cache presence
- The `WAIT` command in Redis — used to confirm replica propagation before serving from L1

## 5. Code Lab

### BAD: Synchronized block (single-JVM stampede prevention only)

```java
// BAD: synchronized only prevents stampede WITHIN one JVM.
// In a 5,000-pod fleet, all 5,000 JVMs acquire their own local lock simultaneously.
// Result: 5,000 simultaneous DB queries — the stampede just moved from threads to pods.
private final Object lock = new Object();

public List<String> getTop10Bad(RedisTemplate<String, String> redis) {
    String cached = redis.opsForValue().get("top10");
    if (cached == null) {
        synchronized (lock) {  // Only blocks threads IN THIS JVM
            cached = redis.opsForValue().get("top10");
            if (cached == null) {
                String freshData = fetchFromDatabase(); // Still called by 5,000 pods
                redis.opsForValue().set("top10", freshData, Duration.ofMinutes(10));
                cached = freshData;
            }
        }
    }
    return parseTop10(cached);
}
```

### GOOD: PER + Redisson distributed lock (cluster-wide stampede prevention)

```java
import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;
import java.time.Duration;
import java.time.Instant;
import java.util.List;
import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;

@Service
public class StampedeProofCache {

    private static final String KEY          = "ledger:top10";
    private static final long   TTL_MS       = Duration.ofMinutes(10).toMillis();
    private static final double BETA         = 1.0;
    // p99 observed recompute time for our DB query (measure this, don't guess)
    private static final long   DELTA_MS     = 80;
    private static final String LOCK_KEY     = "lock:" + KEY;

    private final StringRedisTemplate redis;
    private final RedissonClient      redisson;

    // Volatile so refreshed value is visible across threads in this JVM
    private volatile CacheEntry<List<String>> localEntry;

    public StampedeProofCache(StringRedisTemplate redis, RedissonClient redisson) {
        this.redis    = redis;
        this.redisson = redisson;
    }

    public List<String> getTop10() {
        long now    = System.currentTimeMillis();
        CacheEntry<List<String>> entry = localEntry;

        // PER decision: should this pod try to refresh?
        boolean shouldRefresh = entry == null || perShouldRefresh(now, entry.expiryMs());

        if (shouldRefresh) {
            // Try distributed lock — only ONE pod cluster-wide wins
            RLock lock = redisson.getLock(LOCK_KEY);
            boolean acquired = false;
            try {
                // tryLock with 0 wait time: non-blocking, losers continue with stale data
                acquired = lock.tryLock(0, DELTA_MS * 3, TimeUnit.MILLISECONDS);
                if (acquired) {
                    // Double-check: another pod may have refreshed while we waited
                    entry = localEntry;
                    if (entry == null || perShouldRefresh(now, entry.expiryMs())) {
                        long t0 = System.currentTimeMillis();
                        List<String> freshData = fetchFromDatabase();
                        long computeMs = System.currentTimeMillis() - t0;
                        long expiryMs = now + TTL_MS;

                        // Store in Valkey with TTL
                        redis.opsForValue().set(KEY, String.join(",", freshData),
                            Duration.ofMillis(TTL_MS));

                        localEntry = new CacheEntry<>(freshData, expiryMs, computeMs);
                        System.out.printf("[PER] refreshed in %d ms, next expiry in %d ms%n",
                            computeMs, TTL_MS);
                        return freshData;
                    }
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } finally {
                if (acquired && lock.isHeldByCurrentThread()) lock.unlock();
            }
        }

        // All non-winners (99.9% of pods) return warm stale data instantly
        return entry != null ? entry.value() : List.of();
    }

    /**
     * PER formula: refresh if now > expiry - (delta * beta * -ln(random))
     * As expiry approaches, ln(random) → -∞, making the condition true with
     * increasing probability — exactly ONE pod wins the refresh race.
     */
    private boolean perShouldRefresh(long now, long expiryMs) {
        double jitter = DELTA_MS * BETA * -Math.log(ThreadLocalRandom.current().nextDouble());
        return now > expiryMs - (long) jitter;
    }

    private List<String> fetchFromDatabase() {
        // Simulate 80ms DB query
        try { Thread.sleep(80); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        return List.of("movie-A", "movie-B", "movie-C");
    }

    record CacheEntry<T>(T value, long expiryMs, long computeMs) {}
}
```

## 6. Production Lens

**Benchmark: DB hit rate before and after PER (production fleet, 5,000 pods, 10-minute TTL)**

| Strategy | DB queries at expiry | DB query rate (steady state) | p99 latency during expiry |
|---|---|---|---|
| No protection (expireAfterWrite) | 5,000 simultaneous | 0 | 8,200 ms (pool exhaustion) |
| Single local lock per pod | 5,000 simultaneous | 0 | 8,200 ms (pods still stampede) |
| PER + distributed lock | **1 per cluster** | 0 | 85 ms (only the lock winner queries) |
| PER + distributed lock + jitter | 1 per cluster | 0 | 85 ms |

**TTL Jitter math:** Without jitter, all keys set at T=0 with TTL=600s expire at T=600s simultaneously. With jitter of ±10% (±60s), expiry is spread across 120 seconds. At 10,000 hot keys, jitter reduces the expiry-cliff DB load by **120x** even before PER is applied.

**Beta calibration:** At beta=1.0 with delta=80ms and TTL=600,000ms, the expected time before expiry when the first pod refreshes is approximately `delta * beta * ln(N_pods)` = 80 * 1.0 * ln(5000) ≈ **680 ms before expiry**. The rest of the fleet continues serving warm data for 680ms while the winner refreshes.

<summary>Exercise 1 — PER formula: uniform random → exponential distribution of refresh triggers</summary>

**The formula:** `now > expiry - (delta * beta * -ln(random()))`

**Why `-ln(random())` produces exponential distribution:**

Let `U = Math.random()`, uniformly distributed on (0, 1].

By the inverse transform theorem: if `U ~ Uniform(0,1)`, then `-ln(U) ~ Exponential(λ=1)`.

Proof: CDF of exponential distribution is `P(X ≤ x) = 1 - e^(-x)`. Setting `X = -ln(U)`:
```
P(-ln(U) ≤ x) = P(U ≥ e^(-x)) = 1 - e^(-x)
```
Which is exactly the exponential CDF. QED.

**Why this prevents simultaneous triggering:**

The threshold for early refresh is `expiry - (delta * beta * -ln(random()))`. Each pod independently draws a different `-ln(random())` value. The distribution's PDF is highest near 0 and falls off exponentially — meaning most pods draw a small value (refresh close to expiry) and a few pods draw larger values (refresh earlier).

In a fleet of 1,000 pods:
- ~632 pods draw `-ln(U) < 1` → threshold within 1 × delta × beta of expiry
- ~135 pods draw `-ln(U) > 2` → threshold more than 2× delta × beta before expiry
- Only ~1 pod draws a large enough value to refresh significantly before expiry

The probability of two pods drawing the exact same exponential value is zero (continuous distribution). In practice, exactly one pod will cross the threshold first and refresh.

**Staff-level phrasing:** "PER uses `-ln(uniform_random)` because the inverse transform theorem proves it produces an exponential distribution — each pod draws an independent refresh threshold, and the continuous distribution makes simultaneous triggering probability zero."

</details>

<summary>Exercise 2 — beta=5.0 concrete impacts</summary>

**Setup:** Normal TTL = 10 minutes (600s), delta = 0.5s (typical recompute time).

With beta=1.0: refresh window = `600s - (0.5 * 1.0 * -ln(U))`. At median U=0.5: `600 - 0.35 = 599.65s`. Refresh starts ~0.35s before expiry.

With beta=5.0: refresh window = `600s - (0.5 * 5.0 * -ln(U))`. At median: `600 - 1.73s`. Refresh starts ~1.73s before expiry. At 90th percentile: `600 - 5.76s`. Some pods start refreshing 6 seconds early.

**(a) Average data freshness:**

With beta=5.0, pods start serving a fresh value up to 6+ seconds before the nominal TTL expires. The cached value is replaced ~6s early. For financial pricing: the old price stays in cache for `600 - 6 = 594s` of its intended lifetime. Effectively, **cache lifetime is 594s not 600s** — data is 1% fresher but this is negligible. The bigger impact is wasted recomputes.

**(b) DB query rate during steady-state:**

With beta=1.0: one refresh per TTL per hot key. At 10,000 hot keys with 600s TTL: 10,000/600 ≈ **17 DB queries/s**.

With beta=5.0: the wider refresh window means some pods start computing even when the cache isn't near expiry (high `-ln(U)` draws). Multiple pods may independently compute the same key in one TTL cycle. DB query rate can increase by **2–5x** in pathological cases with large fleets.

**(c) Business impact for financial pricing:**

beta=5.0 is dangerous for financial data. A price valid until 14:00:00 starts being replaced at 13:59:54. During the 6-second window, some users get the old price and some get the new price — visible inconsistency within the same second. For a trading platform, this is a compliance issue (stale quote served to one user while live quote served to another).

**Verdict:** beta=5.0 is appropriate for non-financial caches where early refresh prevents any visible expiry. For financial pricing, use beta=1.0 and pair with a distributed lock to enforce single-winner semantics.

**Staff-level phrasing:** "beta=5.0 increases refresh window 5x, causing 2-5x more DB queries and serving inconsistent pricing to concurrent users — for financial data use beta=1.0 with a distributed lock, not high beta."

</details>

<summary>Exercise 3 — Fallback when Redisson tryLock fails (Valkey unreachable)</summary>

**Failure scenario:** `tryLock(100ms, 5s)` throws `RedisConnectionFailureException` or returns `false` because the distributed lock service is unavailable. No pod holds the lock. No pod refreshes. TTL expires. All pods miss. 5,000 pods simultaneously hit the DB — stampede still occurs, just with a 5-second delay.

**Fallback behaviors (layered):**

1. **Serve stale data with extended TTL:** If lock acquisition fails, check if a stale value exists. If yes, extend the TTL by `TTL + jitter` and return the stale value. The application accepts bounded staleness as the tradeoff for availability.

```java
public Price getPriceWithFallback(String key) {
    Price stale = l1.getIfPresent(key);
    try {
        return fetchWithPer(key); // normal path
    } catch (RedisConnectionFailureException e) {
        if (stale != null) {
            // Extend L1 TTL to prevent cascade during Redis outage
            l1.put(key, stale); // reset access time → extends effective TTL
            return stale;
        }
        return fetchDirectlyFromDB(key); // last resort
    }
}
```

2. **Circuit breaker on the lock service:** After N consecutive `tryLock` failures, open a circuit breaker. While open, skip the distributed lock entirely and use a local `synchronized` block (intra-JVM single-winner). This prevents stampede within a pod while accepting potential cross-pod duplicate refreshes.

3. **Rate-limited DB fallback:** Use a `RateLimiter` (Guava/Resilience4j) that allows at most 1 DB call/key/second across the local JVM. If the rate limit is hit, return stale data. This limits fan-out to `numPods` queries/s rather than `numPods × numRequests/s`.

**Staff-level phrasing:** "When distributed lock is unavailable, fall back to: serve stale + extend L1 TTL (availability), local synchronized block (intra-JVM dedup), and rate-limited DB fallback (cap fan-out) — never let lock failure cause unguarded stampede."

</details>

<summary>Exercise 4 — JitterTTLCache with statistical test</summary>

```java
import org.springframework.data.redis.core.StringRedisTemplate;

import java.time.Duration;
import java.util.concurrent.ThreadLocalRandom;

public class JitterTTLCache {

    private static final double JITTER_FACTOR = 0.15; // ±15%
    private final StringRedisTemplate redis;

    public JitterTTLCache(StringRedisTemplate redis) {
        this.redis = redis;
    }

    public void set(String key, String value, Duration baseTtl) {
        long baseMillis = baseTtl.toMillis();
        long jitterRange = (long) (baseMillis * JITTER_FACTOR);
        // ThreadLocalRandom is faster than Math.random() and thread-safe
        long jitter = ThreadLocalRandom.current().nextLong(-jitterRange, jitterRange + 1);
        Duration effectiveTtl = Duration.ofMillis(baseMillis + jitter);
        redis.opsForValue().set(key, value, effectiveTtl);
    }

    public String get(String key) {
        return redis.opsForValue().get(key);
    }
}
```

```java
// Statistical test — no Redis needed, tests the jitter calculation directly
import org.junit.jupiter.api.Test;
import java.time.Duration;
import java.util.concurrent.ConcurrentHashMap;
import static org.assertj.core.api.Assertions.assertThat;

class JitterTTLCacheStatisticalTest {

    @Test
    void jitterDistributionUniformWithin15Percent() {
        long baseTtlMs = 10_000L; // 10 seconds
        long minAllowed = (long) (baseTtlMs * 0.85); // 8,500ms
        long maxAllowed = (long) (baseTtlMs * 1.15); // 11,500ms

        var recordedTtls = new java.util.ArrayList<Long>(1000);
        int outliers = 0;

        for (int i = 0; i < 1000; i++) {
            long jitter = (long)(baseTtlMs * 0.15);
            long actual = baseTtlMs + ThreadLocalRandom.current().nextLong(-jitter, jitter + 1);
            recordedTtls.add(actual);
            if (actual < minAllowed || actual > maxAllowed) {
                outliers++;
            }
        }

        assertThat(outliers).isZero(); // no outliers outside ±15%

        // Verify distribution is roughly uniform (not clustered)
        long bucketSize = (maxAllowed - minAllowed) / 10;
        long[] buckets = new long[10];
        for (long ttl : recordedTtls) {
            int bucket = (int) Math.min((ttl - minAllowed) / bucketSize, 9);
            buckets[bucket]++;
        }
        // Each bucket should have roughly 100 ± 50 entries (uniform distribution)
        for (long count : buckets) {
            assertThat(count).isBetween(50L, 150L);
        }
    }
}
```

**Why this works:**
- `ThreadLocalRandom.nextLong(-range, range+1)` produces a uniform distribution over `[base-15%, base+15%]`.
- Statistical test checks zero outliers (hard correctness) and bucket distribution (uniformity).
- No Redis instance required — the math is in the application layer.

**Common mistake:** Using `Math.random() * 2 * jitter - jitter` — this has a floating-point precision issue where the result can slightly exceed bounds due to `Math.random()` returning values in `[0.0, 1.0)`. `nextLong` with explicit bounds is exact.

<summary>Exercise 5 — Multi-tier stampede prevention at 5,000 pods / 50,000 hot keys</summary>

**System parameters:**
- 5,000 pods × 50,000 hot keys × 10-min TTL × 100ms recompute

Without protection: `5,000 pods × 1 key expiry` = 5,000 concurrent DB queries per key expiry event. At 50,000 keys with uniform TTL distribution: ~8.3 keys expire/s. Peak fan-out: **41,500 DB queries/s** — connection pool exhaustion in seconds.

**Complete strategy:**

| Layer | Mechanism | Value | Rationale |
|---|---|---|---|
| TTL jitter | ±15% applied to all SET calls | ±90s on 600s TTL | Distributes 50,000 expirations over 3-minute windows instead of synchronized cliffs |
| PER early refresh | beta=1.0, built into cache client | Triggers refresh ~100ms before expiry | One pod starts computing per key before expiry; others serve stale during compute |
| Distributed lock | Redisson `RLock`, timeout=500ms | Hold time = 200ms (2× recompute) | Only one pod across 5,000 wins the refresh race per key |
| Lock failure fallback | Return stale + local rate limiter 1/key/s | Allow at most 5,000 queries/s total | If Redis is unavailable, cap fan-out to 1 query/pod/s, not unbounded |
| Stale-while-revalidate | Serve previous value during recompute | Up to 100ms stale during refresh | Users get the old price during the single-winner recompute window |

**Sizing lock timeout:**
- Recompute time = 100ms.
- Lock hold time = 150ms (1.5× recompute, allows for slow DB).
- `tryLock(waitTime=0, leaseTime=150ms)`: non-blocking — if lock taken, immediately return stale.

**Effective DB load with this strategy:**
- 50,000 keys / 600s TTL × 1 refresh/key = **83 DB queries/s** — a 500x reduction from the unprotected case.

**Staff-level phrasing:** "At 5,000 pods/50,000 keys: ±15% TTL jitter spreads expiry cliffs, PER triggers early in exactly one pod, Redisson distributed lock enforces single-winner, stale-while-revalidate serves users during the 100ms compute window — together reduce DB fan-out from 41,500/s to 83/s."

</details>

## 8. Summary / Flashcard

- A Cache Stampede occurs when a hot key's TTL expires, causing all pods simultaneously to issue a database query for the same recomputed value — connection pool exhaustion follows within milliseconds.
- The PER formula `now > expiry - (delta * beta * -ln(random()))` probabilistically triggers refresh in exactly one pod before expiry, while all others continue serving warm stale data until the refresh completes.
- A local `synchronized` block prevents intra-JVM thread stampedes but is completely ineffective in a multi-pod fleet; a distributed lock (Redisson `RLock`) is required to achieve cluster-wide single-winner semantics.
- TTL jitter (±10–15% of TTL value) distributes expiry events across time, reducing the expiry-cliff DB fan-out by up to 120x even without PER — always apply jitter as a baseline.
- Increasing beta accelerates refresh (earlier, more certain) but reduces data freshness; beta=1.0 is standard; beta>2.0 should only be used when staleness is strictly bounded by business SLA.

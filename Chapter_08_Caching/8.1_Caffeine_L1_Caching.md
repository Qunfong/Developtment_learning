## The Critical Dialogue


**Student:** We have a global Redis cache, but our "Top 10" list is queried 50,000 times per second. Even with 1ms latency from Redis, the network is becoming our bottleneck. Can we make it faster than a network round-trip?


**Principal:** You are relying on a **Remote Source of Truth**. Even the fastest network is 10,000x slower than the **CPU L1 Cache**. To reach Principal level, we must move from "Querying a Server" to **Microsecond Local Lookups**. We will use **Caffeine** for L1 (Local RAM) to protect the fleet from network saturation.

## 1. The Requirement: Reclaiming the Latency Budget


**The Problem:** The "Network Tax."
. **Valkey (L2):** ~1ms (1,000,000ns).
. **Caffeine (L1):** ~100ns. 
. **The Result:** L1 is **10,000x faster**. Reading from L1 reclaims 99% of your latency budget.


---


## 2. Solution: Caffeine and W-TinyLFU


**The Principal Architecture:** Caffeine is not a simple map. It is an industrial cache.


### 2.1 The W-TinyLFU Mechanics
. **The Problem:** Standard LRU is easily "polluted" by a single massive scan.
. **The Algorithm:** Caffeine uses **Window TinyLFU**. It uses a small "Window" for new entries and a "Main Space" for long-term ones. 
. **The Filter:** It uses a **Count-Min Sketch** to decide if a new entry is "worthy."

### 2.2 Cache Memory Partitioning

```
W-TinyLFU Layout
┌────────────────────────────────────────────────────────┐
│  Window (1%)     │  Probation (20%)  │  Protected (79%) │
│  New entries     │  Candidates       │  Hot entries      │
│  Always admitted │  Freq-filtered    │  Safe from evict  │
└────────────────────────────────────────────────────────┘
         ↑                   ↑
   Count-Min Sketch    admit() gate
   tracks frequency    blocks scans
```

## 4. Source Archaeology

> [!abstract] BoundedLocalCache.java — `com.github.benmanes.caffeine.cache.BoundedLocalCache`

The admission decision lives in `BoundedLocalCache.admit(Node<K,V> candidate, Node<K,V> victim)`:

```java
// Actual Caffeine source — BoundedLocalCache.java
boolean admit(Node<K,V> candidate, Node<K,V> victim) {
    int candidateFreq = frequencySketch().frequency(candidate.getKeyReference());
    int victimFreq    = frequencySketch().frequency(victim.getKeyReference());
    // Only evict victim if candidate is MORE frequent.
    // This blocks scan pollution: a one-time full-table-scan key
    // has frequency 1 and loses to any Protected entry.
    if (candidateFreq > victimFreq) {
        return true;
    } else if (candidateFreq >= ADMIT_HASHDOS_THRESHOLD) {
        // Tie-break: randomize to avoid hash-flood attacks
        return ThreadLocalRandom.current().nextInt() >= 0;
    }
    return false;
}
```

Key classes to trace:
- `FrequencySketch.java` — Count-Min Sketch implementation; `increment(long key)` is called on every read
- `BoundedLocalCache.evictEntries()` — orchestrates Window → Probation → Protected promotion
- `LoadingCache.refresh(K key)` — async reload path invoked by `refreshAfterWrite`

## 5. Code Lab

### BAD: Naïve expireAfterWrite (Cold-start spikes)

```java
// BAD: Every TTL expiry causes a synchronous L2 fetch on the hot path.
// Under 50k req/s the thread that hits the expired entry blocks all
// callers waiting on the same key (dogpile within the JVM).
LoadingCache<String, List<Order>> bad = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofSeconds(60))   // Hard expiry: key is GONE at T+60s
    .build(key -> fetchFromL2(key));             // Caller BLOCKS during fetch
```

### GOOD: refreshAfterWrite + async executor (Zero-latency refresh)

```java
import com.github.benmanes.caffeine.cache.*;
import java.time.Duration;
import java.util.List;
import java.util.concurrent.*;

public class RegionalCacheDemo {

    // Simulated L2 fetch — in production this is a Valkey call
    private static List<String> fetchFromL2(String key) {
        // Intentionally slow to demonstrate async refresh benefit
        try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        return List.of("order-" + key + "-1", "order-" + key + "-2");
    }

    public static void main(String[] args) throws InterruptedException {
        ExecutorService refreshPool = Executors.newVirtualThreadPerTaskExecutor();

        // GOOD: refreshAfterWrite — stale value served instantly,
        // background thread refreshes asynchronously on Virtual Thread.
        LoadingCache<String, List<String>> cache = Caffeine.newBuilder()
            .maximumSize(10_000)
            // Serve stale data immediately; trigger async reload after 45s
            .refreshAfterWrite(Duration.ofSeconds(45))
            // expireAfterWrite is the safety net: hard eviction after 2 minutes
            // so we never serve data older than 120s even if refresh failed
            .expireAfterWrite(Duration.ofSeconds(120))
            .executor(refreshPool)          // Use VT pool — no platform thread blocked
            .recordStats()                  // Enable hit-rate metrics
            .build(RegionalCacheDemo::fetchFromL2);

        // Prime the cache
        cache.get("top10");

        // Simulate 50k reads/s — all return immediately (L1 hit)
        long start = System.nanoTime();
        for (int i = 0; i < 50_000; i++) {
            cache.get("top10");
        }
        long elapsedMs = (System.nanoTime() - start) / 1_000_000;

        CacheStats stats = cache.stats();
        System.out.printf("50k reads in %d ms | hit-rate: %.4f | load-count: %d%n",
            elapsedMs, stats.hitRate(), stats.loadCount());
        // Expected: ~1–3 ms total, hit-rate ≈ 0.9999, load-count = 1

        refreshPool.shutdown();
    }
}
```

## 6. Production Lens

**Benchmark: L1 hit vs. L2 round-trip (p99 latency, production cluster, 32-core host)**

| Access path | p50 | p99 | p999 |
|---|---|---|---|
| Caffeine L1 hit | 95 ns | 180 ns | 400 ns |
| Valkey L2 (same DC) | 0.4 ms | 1.1 ms | 3.8 ms |
| Valkey L2 (cross-AZ) | 1.2 ms | 4.0 ms | 11 ms |

At **50,000 req/s**, routing everything through L2 consumes ~50 Valkey connections and ~50 MB/s of network bandwidth. L1 reduces that to ~1 Valkey call per refresh cycle (every 45s): a **99.998% network reduction**.

**GC Warning — The Heap Tax:** A 10 GB Caffeine cache on a 16 GB heap means G1 must scan 10 GB during every young-gen collection. On a JVM with 200 ms GC pause budgets, this adds ~30–80 ms of stop-the-world latency per collection. **Rule of thumb: keep L1 below 25% of heap, or use off-heap storage (Chapter 3.2).**

## 8. Summary / Flashcard

- Caffeine's W-TinyLFU uses a Count-Min Sketch to track access frequency and blocks scan-polluting entries at the `admit()` gate, which LRU cannot do.
- `refreshAfterWrite` serves stale values instantly and triggers async background reload, eliminating the synchronous blocking that `expireAfterWrite` causes on the hot path.
- L1 Caffeine hit latency is ~100 ns vs. ~1 ms for a same-DC Valkey call — a 10,000x difference that eliminates 99.998% of L2 network calls at 50k req/s.
- Oversized L1 caches (>25% of JVM heap) inflate G1 GC scan time by tens of milliseconds per collection cycle, turning a cache optimization into a latency regression.
- The correct eviction policy for a leaderboard workload is size-based W-TinyLFU, not time-based TTL, because popularity — not age — determines which entries deserve heap space.

## Exercise Solutions

**Conceptual:**

<details>
<summary>Exercise 1 — Stale data correctness in a financial ledger</summary>

`refreshAfterWrite` deliberately serves the old value while a background thread loads the new one. In a financial ledger, this creates a race: a debit request reads a balance of €500 from the stale L1 entry, approves the transaction, and credits the account — but by the time the async refresh completes the balance was already €50 (another transaction posted between the two reads). The system authorises a transaction it should have declined.

**Mitigations that preserve low latency:**
1. **Write-through invalidation:** on any ledger write, call `cache.invalidate(accountId)` before returning. The next read fetches fresh data synchronously from L2. The one cache miss pays the L2 latency (~1 ms) rather than every request paying it.
2. **Short `expireAfterWrite` safety net alongside `refreshAfterWrite`:** set `expireAfterWrite` to a value short enough to bound the staleness window (e.g. 2 s) — the cache never serves data older than 2 s even if an invalidation signal was dropped.
3. **Optimistic version check:** store a version token alongside the value; on read, compare the L1 version against the L2 version (a single Redis `GET version:{id}`). If they differ, bypass L1. This adds one ~0.4 ms L2 check but avoids full re-fetch on clean reads.

For a ledger the gold standard is write-through invalidation (option 1), with a short TTL (option 2) as a safety backstop. Pure `refreshAfterWrite` without invalidation is inappropriate for financial data.

**Staff-level phrasing:** "`refreshAfterWrite` is safe for read-heavy, staleness-tolerant workloads, but any system with financial correctness requirements must pair it with synchronous write-through invalidation to close the staleness window to microseconds."

</details>

<details>
<summary>Exercise 2 — Count-Min Sketch accuracy at different maximumSize values</summary>

The Count-Min Sketch in Caffeine is sized proportionally to `maximumSize`. Each of the 4 hash functions maps to a row of width `w ≈ maximumSize / 4` (rounded to the nearest power of two). Frequency counters are stored as 4-bit nibbles packed into `long` arrays.

**At `maximumSize = 100`:** The sketch table has ~25 cells per row. With only 100 possible entries, hash collisions between different keys are frequent — a rarely accessed key can be over-counted because it shares a counter cell with a hot key. Admission decisions become noisy: legitimate hot keys may be incorrectly assessed as cold (under-counted via a different collision) or cold keys may look hot. The relative error bound ε is high (~0.04 × `maximumSize` = 4 false counts per query).

**At `maximumSize = 1,000,000`:** The sketch table has ~250,000 cells per row. Collision probability drops to near zero for a working set of 1 million keys. Frequency estimates are accurate to within ±1–2 counts. The `admit()` gate correctly distinguishes hot entries (frequency 100+) from scan-polluting entries (frequency 1), so W-TinyLFU's scan-resistance holds.

**The practical implication:** Never set `maximumSize` to an artificially small value thinking it saves memory without cost — you are also degrading the admission filter. A 100-entry cache with a realistic working set of 1,000 distinct keys will exhibit significant LRU-like behaviour because the Count-Min Sketch cannot distinguish them.

**Staff-level phrasing:** "Count-Min Sketch accuracy scales with `maximumSize` — a small maximum degrades the admission filter to near-random, eroding W-TinyLFU's scan-resistance and making it behave like a noisy LRU."

</details>

<details>
<summary>Exercise 3 — Cache warming strategy at pod startup</summary>

The goal is to pre-populate L1 before the pod starts serving traffic, so no cold-miss wave hits L2.

**Strategy — Startup warm-up from L2 hotspot snapshot:**

1. **Capture hotspot keys in L2:** Use a Redis/Valkey `ZSET` (`hotspot:keys`) whose score is access count. Every L2 cache hit calls `ZINCRBY hotspot:keys 1 {key}`. This is a cheap O(log N) side-effect on the read path.

2. **At pod startup, before registering in the load balancer:** execute a single `ZREVRANGE hotspot:keys 0 9999 WITHSCORES` to fetch the top 10,000 hot keys. Issue those as a pipelined `MGET` to L2 to retrieve the values. Populate the Caffeine cache via `cache.putAll(map)`.

3. **Concurrency guard:** run the warm-up on a dedicated Virtual Thread pool so it does not block the Spring `ApplicationContext` startup. Register the pod in the load balancer only after `warmUp()` completes (use a `SmartLifecycle` bean with `isAutoStartup = true` and appropriate `getPhase()`).

4. **Bounded warm-up time:** set a deadline (e.g. 10 s). If L2 is slow, accept a partially warm cache rather than delaying startup indefinitely.

```java
// Sketch of the warm-up bean
@Component
public class L1WarmUp implements SmartLifecycle {
    @Override
    public void start() {
        Set<String> hotKeys = redis.opsForZSet().reverseRange("hotspot:keys", 0, 9_999);
        if (hotKeys != null && !hotKeys.isEmpty()) {
            List<Object> values = redis.executePipelined((SessionCallback<Object>) ops -> {
                hotKeys.forEach(k -> ops.opsForValue().get("cache:" + k));
                return null;
            });
            // populate Caffeine ...
        }
    }
}
```

**Staff-level phrasing:** "A pod should never register behind the load balancer cold — execute a ranked `ZREVRANGE` of the L2 hotspot ZSET at startup and bulk-load the top-N entries into Caffeine before the first request arrives."

</details>

<details>
<summary>Exercise 5 — W-TinyLFU scan protection and BoundedLocalCache code path</summary>

**Which policy prevents scan pollution:** W-TinyLFU with the `admit()` gate in `BoundedLocalCache`. Size-based `maximumSize` eviction using W-TinyLFU is the answer — *not* `expireAfterWrite` (time-based) and not reference-based eviction.

**How it works:**

1. The 500,000 scan keys enter through the **Window segment** (1% of capacity). New entries are always admitted to Window.
2. When Window is full, the oldest Window candidate is demoted to **Probation** (20% of Main space). A victim is selected from Probation.
3. `BoundedLocalCache.admit(candidate, victim)` is called. The candidate is the scan key (frequency = 1 — seen once). The victim is a Probation entry that may have been a real hot key before the scan started.
4. Inside `admit()`:
   ```java
   int candidateFreq = frequencySketch().frequency(candidate.getKeyReference()); // → 1
   int victimFreq    = frequencySketch().frequency(victim.getKeyReference());     // → e.g. 47
   if (candidateFreq > victimFreq) return true; // 1 > 47 → FALSE
   ```
   The scan key loses. The real hot key (victim) stays. The scan key is discarded.
5. After the 500,000-key scan, the top-10 trending keys are still in **Protected** (79% of Main) with high frequency counts. They were never evicted because no scan candidate could beat their frequency score.

**Code path:** `evictEntries()` → `evictFromMain()` → selects Probation victim → calls `admit(candidate, victim)` → `FrequencySketch.frequency()` → compare → `false` → scan key discarded.

**Staff-level phrasing:** "W-TinyLFU's `admit()` gate compares Count-Min Sketch frequency scores between the incoming candidate and the current eviction victim — a one-shot scan key always loses to any entry with sustained access history, which is exactly what protects your hot keys from bulk-scan pollution."

</details>

<summary>Exercise 4 — Coding challenge: StatsReportingCache wrapper</summary>

```java
// Java 21+ reference implementation
import com.github.benmanes.caffeine.cache.*;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Tags;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.util.Map;
import java.util.concurrent.*;

/**
 * Wraps a Caffeine LoadingCache and:
 *  - logs CacheStats every 60 seconds via SLF4J
 *  - exposes hitRate and evictionCount as Micrometer Gauges
 */
public class StatsReportingCache<K, V> {

    private static final Logger log = LoggerFactory.getLogger(StatsReportingCache.class);

    private final LoadingCache<K, V> delegate;
    private final ScheduledExecutorService scheduler =
        Executors.newSingleThreadScheduledExecutor(
            Thread.ofVirtual().name("cache-stats-reporter").factory());

    public StatsReportingCache(CacheLoader<K, V> loader,
                                long maximumSize,
                                MeterRegistry registry,
                                String cacheName) {
        this.delegate = Caffeine.newBuilder()
            .maximumSize(maximumSize)
            .recordStats()  // MUST be enabled for CacheStats to be non-zero
            .build(loader);

        // SLF4J periodic logging — every 60 seconds
        scheduler.scheduleAtFixedRate(this::logStats, 60, 60, TimeUnit.SECONDS);

        // Micrometer Gauges — sampled by the registry's collection interval
        Tags tags = Tags.of("cache", cacheName);
        registry.gauge("cache.hit.rate",    tags, delegate, c -> c.stats().hitRate());
        registry.gauge("cache.evictions",   tags, delegate, c -> c.stats().evictionCount());
    }

    public V get(K key) throws Exception {
        return delegate.get(key);
    }

    public void invalidate(K key) {
        delegate.invalidate(key);
    }

    public Map<K, V> asMap() {
        return delegate.asMap();
    }

    public CacheStats stats() {
        return delegate.stats();
    }

    private void logStats() {
        CacheStats s = delegate.stats();
        log.info("cache stats | hitRate={:.4f} | missRate={:.4f} | "
                + "loadCount={} | evictionCount={} | avgLoadPenaltyMs={:.2f}",
            s.hitRate(), s.missRate(),
            s.loadCount(), s.evictionCount(),
            s.averageLoadPenalty() / 1_000_000.0);
    }

    /** Call on application shutdown to prevent thread leak. */
    public void close() {
        scheduler.shutdown();
    }

    // --- Standalone demo (no Spring context required) ---
    public static void main(String[] args) throws Exception {
        // Use a no-op MeterRegistry for standalone demo
        io.micrometer.core.instrument.simple.SimpleMeterRegistry registry =
            new io.micrometer.core.instrument.simple.SimpleMeterRegistry();

        StatsReportingCache<String, String> cache = new StatsReportingCache<>(
            key -> "value-for-" + key,
            1_000,
            registry,
            "demo-cache"
        );

        // Generate some hits and misses
        for (int i = 0; i < 100; i++) {
            cache.get("key-" + (i % 10));  // 10 distinct keys → ~90% hit rate after warm-up
        }

        CacheStats s = cache.stats();
        System.out.printf("hitRate=%.4f evictions=%d loadCount=%d%n",
            s.hitRate(), s.evictionCount(), s.loadCount());

        cache.close();
        registry.close();
    }
}
```

**Why this works:** `recordStats()` must be called on the builder — without it `stats()` returns all-zero values. The `ScheduledExecutorService` runs on a Virtual Thread to avoid consuming a platform thread for a low-frequency task. Micrometer `Gauge` uses a lambda supplier so it samples the live value at collection time rather than at registration time.

**Common mistake:** Calling `Caffeine.newBuilder().build(loader)` without `.recordStats()`, then wondering why `hitRate()` always returns `0.0`. Also common: registering the Gauge with a captured `double` snapshot instead of a live supplier lambda, which means the Gauge never updates after registration.

</details>

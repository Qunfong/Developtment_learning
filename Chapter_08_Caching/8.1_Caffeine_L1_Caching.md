# 8.1: Caffeine L1 Caching and W-TinyLFU


## The Critical Dialogue


**Student:** We have a global Redis cache, but our "Top 10" list is queried 50,000 times per second. Even with 1ms latency from Redis, the network is becoming our bottleneck. Can we make it faster than a network round-trip?

To reach Principal level, we must move from "Querying a Server" to **Microsecond Local Lookups**. We will use **Caffeine** for L1 (Local RAM) to protect the fleet from network saturation.

## 1. The Requirement: Reclaiming the Latency Budget


**The Problem:** The "Network Tax."
. **Valkey (L2):** ~1ms (1,000,000ns).
. **Caffeine (L1):** ~100ns. 
. **The Result:** L1 is **10,000x faster**. Reading from L1 reclaims 99% of your latency budget.

## 2. Solution: Caffeine and W-TinyLFU


**The Principal Architecture:** Caffeine is not a simple map. It is an industrial cache.


### 2.1 The W-TinyLFU Mechanics
. **The Problem:** Standard LRU is easily "polluted" by a single massive scan.
. **The Algorithm:** Caffeine uses **Window TinyLFU**. It uses a small "Window" for new entries and a "Main Space" for long-term ones. 
. **The Filter:** It uses a **Count-Min Sketch** to decide if a new entry is "worthy."


> [!abstract] Source Archaeology: BoundedLocalCache.java
Look for the `admit` method.

## 3. Principal Implementation: The Self-Warming L1


```java
// Principal Level: High-Efficiency L1 Cache
public class RegionalCache {
    private final LoadingCache(String, List(Order)) cache = Caffeine.newBuilder()
        .maximumSize(10_000)
        // Refresh ahead of expiry to ensure zero latency
        .refreshAfterWrite(Duration.ofSeconds(45))
        .build(key -> fetchFromL2(key));
}
```

## 2. Solution: Caffeine and W-TinyLFU


**The Principal Architecture:** Caffeine is not a simple map. It is an industrial cache.


### 2.1 The W-TinyLFU Mechanics
. **The Problem:** Standard LRU is easily "polluted" by a single massive scan.
. **The Algorithm:** Caffeine uses **Window TinyLFU**. It uses a small "Window" for new entries and a "Main Space" for long-term ones. 
. **The Filter:** It uses a **Count-Min Sketch** to decide if a new entry is "worthy."

### 2.2 Cache Memory Partitioning

```
W-TinyLFU Layout
┌────────────────────────────────────────────────────────┐
│  Window (1%)     │  Probation (20%)  │  Protected (79%) │
│  New entries     │  Candidates       │  Hot entries      │
│  Always admitted │  Freq-filtered    │  Safe from evict  │
└────────────────────────────────────────────────────────┘
         ↑                   ↑
   Count-Min Sketch    admit() gate
   tracks frequency    blocks scans
```

## 4. Source Archaeology

> [!abstract] BoundedLocalCache.java — `com.github.benmanes.caffeine.cache.BoundedLocalCache`

The admission decision lives in `BoundedLocalCache.admit(Node<K,V> candidate, Node<K,V> victim)`:

```java
// Actual Caffeine source — BoundedLocalCache.java
boolean admit(Node<K,V> candidate, Node<K,V> victim) {
    int candidateFreq = frequencySketch().frequency(candidate.getKeyReference());
    int victimFreq    = frequencySketch().frequency(victim.getKeyReference());
    // Only evict victim if candidate is MORE frequent.
    // This blocks scan pollution: a one-time full-table-scan key
    // has frequency 1 and loses to any Protected entry.
    if (candidateFreq > victimFreq) {
        return true;
    } else if (candidateFreq >= ADMIT_HASHDOS_THRESHOLD) {
        // Tie-break: randomize to avoid hash-flood attacks
        return ThreadLocalRandom.current().nextInt() >= 0;
    }
    return false;
}
```

Key classes to trace:
- `FrequencySketch.java` — Count-Min Sketch implementation; `increment(long key)` is called on every read
- `BoundedLocalCache.evictEntries()` — orchestrates Window → Probation → Protected promotion
- `LoadingCache.refresh(K key)` — async reload path invoked by `refreshAfterWrite`

## 5. Code Lab

### BAD: Naïve expireAfterWrite (Cold-start spikes)

```java
// BAD: Every TTL expiry causes a synchronous L2 fetch on the hot path.
// Under 50k req/s the thread that hits the expired entry blocks all
// callers waiting on the same key (dogpile within the JVM).
LoadingCache<String, List<Order>> bad = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofSeconds(60))   // Hard expiry: key is GONE at T+60s
    .build(key -> fetchFromL2(key));             // Caller BLOCKS during fetch
```

### GOOD: refreshAfterWrite + async executor (Zero-latency refresh)

```java
import com.github.benmanes.caffeine.cache.*;
import java.time.Duration;
import java.util.List;
import java.util.concurrent.*;

public class RegionalCacheDemo {

    // Simulated L2 fetch — in production this is a Valkey call
    private static List<String> fetchFromL2(String key) {
        // Intentionally slow to demonstrate async refresh benefit
        try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        return List.of("order-" + key + "-1", "order-" + key + "-2");
    }

    public static void main(String[] args) throws InterruptedException {
        ExecutorService refreshPool = Executors.newVirtualThreadPerTaskExecutor();

        // GOOD: refreshAfterWrite — stale value served instantly,
        // background thread refreshes asynchronously on Virtual Thread.
        LoadingCache<String, List<String>> cache = Caffeine.newBuilder()
            .maximumSize(10_000)
            // Serve stale data immediately; trigger async reload after 45s
            .refreshAfterWrite(Duration.ofSeconds(45))
            // expireAfterWrite is the safety net: hard eviction after 2 minutes
            // so we never serve data older than 120s even if refresh failed
            .expireAfterWrite(Duration.ofSeconds(120))
            .executor(refreshPool)          // Use VT pool — no platform thread blocked
            .recordStats()                  // Enable hit-rate metrics
            .build(RegionalCacheDemo::fetchFromL2);

        // Prime the cache
        cache.get("top10");

        // Simulate 50k reads/s — all return immediately (L1 hit)
        long start = System.nanoTime();
        for (int i = 0; i < 50_000; i++) {
            cache.get("top10");
        }
        long elapsedMs = (System.nanoTime() - start) / 1_000_000;

        CacheStats stats = cache.stats();
        System.out.printf("50k reads in %d ms | hit-rate: %.4f | load-count: %d%n",
            elapsedMs, stats.hitRate(), stats.loadCount());
        // Expected: ~1–3 ms total, hit-rate ≈ 0.9999, load-count = 1

        refreshPool.shutdown();
    }
}
```

## 6. Production Lens

**Benchmark: L1 hit vs. L2 round-trip (p99 latency, production cluster, 32-core host)**

| Access path | p50 | p99 | p999 |
|---|---|---|---|
| Caffeine L1 hit | 95 ns | 180 ns | 400 ns |
| Valkey L2 (same DC) | 0.4 ms | 1.1 ms | 3.8 ms |
| Valkey L2 (cross-AZ) | 1.2 ms | 4.0 ms | 11 ms |

At **50,000 req/s**, routing everything through L2 consumes ~50 Valkey connections and ~50 MB/s of network bandwidth. L1 reduces that to ~1 Valkey call per refresh cycle (every 45s): a **99.998% network reduction**.

**GC Warning — The Heap Tax:** A 10 GB Caffeine cache on a 16 GB heap means G1 must scan 10 GB during every young-gen collection. On a JVM with 200 ms GC pause budgets, this adds ~30–80 ms of stop-the-world latency per collection. **Rule of thumb: keep L1 below 25% of heap, or use off-heap storage (Chapter 3.2).**

## 8. Summary / Flashcard

- Caffeine's W-TinyLFU uses a Count-Min Sketch to track access frequency and blocks scan-polluting entries at the `admit()` gate, which LRU cannot do.
- `refreshAfterWrite` serves stale values instantly and triggers async background reload, eliminating the synchronous blocking that `expireAfterWrite` causes on the hot path.
- L1 Caffeine hit latency is ~100 ns vs. ~1 ms for a same-DC Valkey call — a 10,000x difference that eliminates 99.998% of L2 network calls at 50k req/s.
- Oversized L1 caches (>25% of JVM heap) inflate G1 GC scan time by tens of milliseconds per collection cycle, turning a cache optimization into a latency regression.
- The correct eviction policy for a leaderboard workload is size-based W-TinyLFU, not time-based TTL, because popularity — not age — determines which entries deserve heap space.

## The Critical Dialogue

**Student:** We use HTTPS for our public API. But for internal calls, we just use plain HTTP because it's "Inside the network."

**Principal:** You are relying on the **Wall of Hubris**. In a modern fleet, the "Internal Network" is the most dangerous place because one compromised pod can sniff all traffic. To reach Principal level, we must master **Mutual TLS (mTLS)** and the **SPIFFE/SPIRE** framework. We move from "Network Trust" to **Cryptographic Proof of Identity**.

## 1. The Physics of mTLS

In standard TLS, the client verifies the server. In **mTLS**, the server *also* verifies the client.
- **The Perimeter:** Security moves from the firewall (L3/4) to the **Identity Layer (L7)**.
- **The Tax:** The initial handshake is expensive (~3ms for TLS 1.3 + certificate validation), but subsequent packets use **AES-NI** hardware acceleration (~0.001ms/packet).

## 2. Source Archaeology: SPIFFE and SPIRE

> [!abstract] The Mechanics: SVID
> - **SVID:** A short-lived X.509 certificate, valid for 1 hour by default.
> - **SPIRE Agent:** Lives on every node. It verifies the pod's identity (using K8s UID) and issues an SVID automatically.
> - **Rotation:** SVIDs are rotated every hour. If a pod is compromised, the cert is useless within minutes.

**`io.spiffe.workloadapi.WorkloadApiClient`** (`spiffe-lib-java`, `io.spiffe:java-spiffe-core`):
- `newClient(WorkloadApiClient.ClientOptions.defaultOptions())` → connects to the SPIRE Agent Unix Domain Socket at `unix:///tmp/spire-agent/public/api.sock`
- `fetchX509Context()` → returns `X509Context` containing the pod's SVID chain and trust bundles
- `watchX509Context(Watcher<X509Context>)` → **push-based rotation**: the SPIRE Agent streams new SVIDs before expiry, no polling required

**`io.spiffe.svid.x509svid.X509Svid`**:
- `getSpiffeId()` → returns the SPIFFE URI, e.g. `spiffe://ledger.prod/order-service`
- `getChain()` → the `List<X509Certificate>` to present during mTLS handshake
- `getPrivateKey()` → the `PrivateKey` for the handshake (never persisted to disk — lives in process memory only)

**`io.spiffe.bundle.x509bundle.X509BundleSet`**:
- Used as `TrustManager` — contains the SPIFFE Trust Domain CAs; only SVIDs signed by these CAs are accepted
- Peer's SPIFFE ID is validated against a policy (e.g. only `spiffe://ledger.prod/*` is allowed to call the order service)

**Certificate chain validation in Java:**
- `sun.security.ssl.X509TrustManagerImpl.checkClientTrusted()` is called during the server-side TLS handshake; SPIRE's `X509BundleSet` effectively replaces the default trust store
- Java's `SSLContext.init(KeyManager[], TrustManager[], SecureRandom)` is the integration point

### GOOD: SPIRE SVID-backed mTLS with automatic rotation watcher

```java
import io.grpc.*;
import io.grpc.netty.shaded.io.netty.handler.ssl.SslContext;
import io.grpc.netty.shaded.io.grpc.netty.GrpcSslContexts;
import io.spiffe.workloadapi.*;
import io.spiffe.svid.x509svid.X509Svid;
import io.spiffe.bundle.x509bundle.X509BundleSet;
import java.util.concurrent.atomic.AtomicReference;
import javax.net.ssl.SSLException;

/**
 * mTLS gRPC client backed by SPIRE X.509 SVIDs.
 *
 * Key properties:
 * - SVID loaded from SPIRE Agent Unix socket — never from disk or env vars
 * - Rotation watcher: new SVID is applied before expiry (no restart needed)
 * - Peer identity validated: only spiffe://ledger.prod/* accepted
 */
public class SecureOrderServiceClient implements AutoCloseable {

    private final WorkloadApiClient spireClient;
    private final AtomicReference<ManagedChannel> channelRef = new AtomicReference<>();

    public SecureOrderServiceClient() throws Exception {
        // 1. Connect to SPIRE Agent via Unix Domain Socket
        this.spireClient = WorkloadApiClient.newClient(
            WorkloadApiClient.ClientOptions.defaultOptions()
        );

        // 2. Fetch initial SVID and build channel
        X509Context ctx = spireClient.fetchX509Context();
        channelRef.set(buildChannel(ctx));

        // 3. Watch for SVID rotation — SPIRE pushes new cert before expiry
        spireClient.watchX509Context(new Watcher<>() {
            @Override
            public void onUpdate(X509Context newCtx) {
                // Swap channel atomically — in-flight RPCs complete on old channel
                ManagedChannel old = channelRef.getAndSet(buildChannel(newCtx));
                old.shutdown();  // graceful — waits for in-flight calls
                System.out.println("SVID rotated, new SPIFFE ID: "
                    + newCtx.getDefaultSvid().getSpiffeId());
            }

            @Override
            public void onError(Throwable e) {
                System.err.println("SPIRE watch error: " + e.getMessage());
                // Production: implement exponential backoff reconnect here
            }
        });
    }

    private ManagedChannel buildChannel(X509Context ctx) {
        X509Svid svid = ctx.getDefaultSvid();
        X509BundleSet bundles = ctx.getX509BundleSet();

        try {
            SslContext sslCtx = GrpcSslContexts.forClient()
                // Present our SVID as client certificate
                .keyManager(svid.getPrivateKey(),
                            svid.getChain().toArray(new java.security.cert.X509Certificate[0]))
                // Trust SPIFFE bundle CAs only — no system trust store
                .trustManager(bundles.getBundles().values().stream()
                    .flatMap(b -> b.getX509Authorities().stream())
                    .toArray(java.security.cert.X509Certificate[]::new))
                .build();

            return ManagedChannelBuilder
                .forAddress("order-service.internal", 443)
                .useTransportSecurity()
                .overrideAuthority("spiffe://ledger.prod/order-service")
                .build();
        } catch (SSLException e) {
            throw new RuntimeException("Failed to build mTLS channel", e);
        }
    }

    public ManagedChannel channel() { return channelRef.get(); }

    @Override
    public void close() {
        spireClient.close();
        channelRef.get().shutdown();
    }
}
```

## 5. Production Lens

| Phase | Latency | Notes |
|:---|---:|:---|
| TLS 1.3 full handshake | ~3 ms | One-time per new connection |
| TLS 1.3 session resumption | ~0.5 ms | `session_ticket` reuse |
| AES-NI data encryption (1KB) | ~0.001 ms | Hardware-accelerated, amortized to zero |
| SVID fetch from SPIRE Agent | ~2 ms | Unix socket, negligible on hot path |
| SVID rotation (push-based) | 0 ms hot-path | Background watcher handles it |

At Uber's scale (2021 blog post), enforcing mTLS across ~4,000 internal services via Envoy sidecars added **~2ms per new connection** but reduced their blast radius per compromised pod from "entire internal network" to "single SVID's TTL window (1 hour)." The security improvement was worth more than the 2ms cost on connection establishment.

SVID rotation every 1 hour: if a pod's SVID is stolen, the attacker has at most **60 minutes** before the credential is worthless — versus static TLS certificates that can be valid for 1–2 years.

<summary>Exercise 1 — mTLS handshake cost: batch job + HTTP/2 multiplexing</summary>

**(a) Total CPU time per minute for 10,000 handshakes:**

10,000 connections/minute × 3ms/handshake = **30,000ms = 30 CPU-seconds/minute** spent on TLS handshakes.

With a single-core CPU: 30 out of 60 seconds = **50% of one CPU core** consumed purely by TLS handshakes. On a 4-core pod: 12.5% CPU overhead.

The 3ms per TLS 1.3 handshake includes: ClientHello, ServerHello, certificate exchange, ECDHE key generation (the dominant cost), and Finished messages. RSA-based handshakes take 10–30ms. ECDH (P-256) is ~1ms for the key math; the rest is network round-trips.

**(b) HTTP/2 multiplexing saving:**

Without HTTP/2: 10,000 connections × 3ms = 30 CPU-seconds.

With HTTP/2: `10,000 requests / 100 requests per connection = 100 connections`. 100 × 3ms = **300ms = 0.3 CPU-seconds/minute**.

Saving: 29.7 CPU-seconds/minute. Latency per request: each of the 10,000 requests no longer incurs a handshake — only 100 connections do. The other 9,900 requests skip directly to stream creation (~0.1ms).

**Practical implication:** For a batch job making 10,000 calls to the same service, HTTP/2 connection pooling (with persistent connections) reduces TLS overhead by 100x. This is why gRPC (HTTP/2 by default) is preferred for high-RPC internal communication.

**Staff-level phrasing:** "10k new mTLS connections at 3ms each = 30 CPU-seconds/minute; HTTP/2 multiplexing 100 RPCs per connection collapses this to 100 handshakes = 0.3 CPU-seconds — a 100x reduction in crypto overhead."

<summary>Exercise 2 — SVID expiry: error chain and production detection</summary>

**Error chain when gRPC call fails with expired SVID:**

```
io.grpc.StatusRuntimeException: UNAVAILABLE: Network closed for unknown reason
  Caused by: javax.net.ssl.SSLHandshakeException: PKIX path validation failed
    Caused by: java.security.cert.CertPathValidatorException: timestamp check failed
      Caused by: java.security.cert.CertificateExpiredException:
                 NotAfter: Mon Jan 20 14:00:00 UTC 2025
```

The chain: gRPC wraps all transport exceptions as `StatusRuntimeException(UNAVAILABLE)`. The root cause is the TLS layer rejecting the certificate during the handshake's certificate validation step. Java's `CertPathValidator` checks `notAfter` against the current time and throws `CertificateExpiredException`.

**Note:** The peer may also reject YOUR certificate (client-side SVID) during mTLS — same chain but the error originates from the server's validation of your presented client certificate.

**Production detection before outage:**

```java
// Micrometer gauge exposing SVID expiry time
@Configuration
public class SvidMetricsConfig {

    @Bean
    public Gauge svidExpiryGauge(MeterRegistry registry,
                                  WorkloadApiClient spireClient) {
        return Gauge.builder("spire.svid.seconds_until_expiry",
                spireClient,
                client -> {
                    try {
                        var bundle = client.fetchX509Context();
                        var cert = bundle.getDefaultSvid().getChain().get(0);
                        long expiryMs = cert.getNotAfter().getTime();
                        return (expiryMs - System.currentTimeMillis()) / 1000.0;
                    } catch (Exception e) {
                        return -1.0; // signal unknown state
                    }
                })
            .description("Seconds until SPIRE SVID expires")
            .register(registry);
    }
}
```

**Prometheus alert rule:**
```yaml
- alert: SvidExpiryImminent
  expr: spire_svid_seconds_until_expiry < 300
  for: 1m
  labels:
    severity: critical
  annotations:
    summary: "SVID expiring in less than 5 minutes — rotation may have failed"
```

**Staff-level phrasing:** "Expired SVID surfaces as SSLHandshakeException → CertificateExpiredException in the gRPC error chain — expose expiry as a Prometheus gauge and alert at <300s remaining to catch rotation failures before they cause outages."

```yaml
# SPIRE OPA/Envoy authorization policy (pseudo-YAML)
# Applied at the Envoy sidecar as RBAC filter

authorization_policy:
  name: "ledger-prod-isolation"

  rules:
    - name: "allow-order-to-payment"
      effect: ALLOW
      source:
        principal: "spiffe://ledger.prod/order-service"
      destination:
        principal: "spiffe://ledger.prod/payment-service"
      conditions:
        - method_matches: "^/payment.*"   # restrict to payment API paths only

    - name: "deny-staging-to-prod"
      effect: DENY
      source:
        principal_match:
          prefix: "spiffe://ledger.staging/"
      destination:
        principal_match:
          prefix: "spiffe://ledger.prod/"
      # No conditions — deny all staging→prod calls regardless of method

    - name: "default-deny"
      effect: DENY
      source:
        principal: "*"
      destination:
        principal: "*"
      # Catch-all: deny everything not explicitly allowed
```

**Implementation note:** In real SPIRE + Envoy RBAC, this is expressed as an Envoy `RBAC` network filter policy applied at the downstream proxy. The SVID subject URI is extracted from the mTLS client certificate's SAN field and matched against the policy rules. The `deny-staging-to-prod` rule must appear before the default-deny but after any explicit allows — Envoy evaluates DENY rules first.

**Staff-level phrasing:** "SPIRE policy isolates staging from prod by matching the SVID trust domain prefix (spiffe://ledger.staging/) — deny rules on trust domain prefix are evaluated before allow rules and enforce hard environment boundaries."

<summary>Exercise 4 — SvidExpiryMonitor implementation</summary>

```java
import io.spiffe.workloadapi.WorkloadApiClient;
import io.spiffe.workloadapi.DefaultWorkloadApiClient;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.time.Instant;
import java.time.temporal.ChronoUnit;

public class SvidExpiryMonitor {

    private static final Logger log = LoggerFactory.getLogger(SvidExpiryMonitor.class);
    private static final long WARN_THRESHOLD_SECONDS = 300; // 5 minutes

    private final WorkloadApiClient workloadApiClient;

    public SvidExpiryMonitor() throws Exception {
        this.workloadApiClient = DefaultWorkloadApiClient.newClient(
            DefaultWorkloadApiClient.ClientOptions.builder()
                .spiffeSocketPath(System.getenv().getOrDefault(
                    "SPIFFE_ENDPOINT_SOCKET",
                    "unix:///tmp/spire-agent/public/api.sock"))
                .build()
        );
    }

    public double secondsUntilExpiry() {
        try {
            var context = workloadApiClient.fetchX509Context();
            var cert = context.getDefaultSvid().getChain().get(0);
            Instant notAfter = cert.getNotAfter().toInstant();
            long seconds = ChronoUnit.SECONDS.between(Instant.now(), notAfter);
            return (double) seconds;
        } catch (Exception e) {
            log.error("Failed to fetch SVID from SPIRE agent: {}", e.getMessage());
            return -1.0;
        }
    }

    public void checkAndWarn() {
        double remaining = secondsUntilExpiry();
        if (remaining < 0) {
            log.warn("SVID expiry unknown — SPIRE agent may be unreachable");
        } else if (remaining < WARN_THRESHOLD_SECONDS) {
            log.warn("SVID expires in {:.0f} seconds — rotation may be delayed. " +
                     "Check SPIRE agent logs at /var/log/spire-agent.log", remaining);
        }
    }

    // For background monitoring (Spring @Scheduled or standalone thread)
    public void startMonitoring() {
        Thread.ofVirtual().name("svid-expiry-monitor").start(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                checkAndWarn();
                try {
                    Thread.sleep(10_000); // check every 10 seconds
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        });
    }
}
```

**Common mistake:** Calling `workloadApiClient.fetchX509Context()` on every health check tick — this creates a gRPC call to the SPIRE agent per tick. Prefer `watchX509Context(Watcher)` (push-based) so the agent streams new SVIDs automatically, and the monitor only reads the latest cached value.

<summary>Exercise 5 — eBPF vs mTLS: why payload is opaque + tracing alternative</summary>

**Why eBPF cannot inspect mTLS payload:**

eBPF hooks at the kernel networking layer — specifically at the `tc` (traffic control) ingress/egress points, socket buffer, and XDP (eXpress Data Path). At these hook points, the data is already encrypted:

```
Application → TLS Library (OpenSSL/BoringSSL) → Encrypted bytes → Kernel socket buffer → eBPF hook
```

eBPF sees the encrypted ciphertext in the kernel socket buffer. The TLS encryption/decryption happens in **userspace** (the TLS library). The kernel never sees plaintext. eBPF operates in kernel space — it cannot reach into userspace memory to read the pre-encryption data (that would require `bpf_probe_read_user`, which is a tracing primitive, not a network hook).

Cilium Hubble sees TCP/IP metadata (source IP, destination IP, port, packet size, connection state) but cannot decode HTTP methods, paths, or payload content. Pixie uses `uprobe` (userspace eBPF probe) to hook into OpenSSL's `SSL_write`/`SSL_read` functions — this CAN see plaintext, but only for known TLS library symbols.

**Non-breaking way to get request tracing inside mTLS:**

Use **OpenTelemetry instrumentation at the application layer**, not the network layer:

1. **OTel Java agent** instruments HTTP/gRPC calls and injects trace context into request headers before encryption.
2. The downstream service receives the traceparent header (inside the mTLS-encrypted payload), and OTel agent extracts it.
3. Traces are reported out-of-band to the OTel Collector via a separate mTLS connection — not inspected in-path.

This gives full distributed tracing (method, path, status, latency) without breaking encryption, because tracing happens in the application process above the TLS layer.

For network-level visibility without breaking mTLS: use **Envoy access logs** — Envoy terminates mTLS and logs request metadata (URL, method, status code, latency) before re-encrypting for the upstream. Access logs go to a SIEM without exposing payload content.

**Staff-level phrasing:** "eBPF operates in kernel space where data is already encrypted — TLS encryption happens in userspace OpenSSL; use OTel instrumentation above the TLS layer for request tracing, or Envoy access logs for network-level metadata without payload decryption."

</details>

## 7. Summary / Flashcard

- **mTLS shifts the trust perimeter** from the network (L3/L4 firewall) to cryptographic identity (L7 SVID); a compromised pod inside the network cannot impersonate another service because it lacks a valid SPIRE-issued SVID.
- **`WorkloadApiClient.watchX509Context(Watcher)`** is the push-based rotation API; the SPIRE Agent streams a new SVID before the current one expires, enabling zero-restart, zero-downtime certificate rotation.
- **SVID TTL of 1 hour** limits the blast radius of a credential theft to 60 minutes; contrast with traditional TLS certs (1-2 year validity) where a stolen cert enables impersonation for years.
- **TLS 1.3 handshake costs ~3ms** one-time per connection; amortized over HTTP/2 multiplexed requests (e.g. 100 RPCs per connection) the per-request overhead is ~0.03ms — negligible vs the security guarantee.
- **eBPF cannot inspect mTLS payload** because encryption occurs in the kernel's TLS implementation (or in Netty's JDK SSL engine) before eBPF's socket-level hooks; the correct approach for observability is distributed tracing with propagated headers at the application layer.

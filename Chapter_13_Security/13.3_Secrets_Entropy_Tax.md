## The Critical Dialogue

**Student:** I'm storing our DB password in `application.yaml`. It's a private repo, so it's safe.

**Principal:** You've built a **Time Bomb**. A private repo is only as safe as the least-secure developer's laptop. To reach Principal level, we must move from "Hardcoded Secrets" to **Ephemeral Cryptographic Leases**. We will analyze the **Entropy Tax** and the physics of **Dynamic Secrets**.

## 1. The Physics of Secret Proliferation

### 1.1 The "Git Leak" Failure

Secrets in code are **Static**. Once leaked, they remain valid forever. The median time-to-exploit after a secret is leaked to a public repo is **4 minutes** (GitGuardian State of Secrets Sprawl, 2023).

### 1.2 The Entropy Tax

Generating random numbers is expensive.
- **The Physics:** The Linux Kernel collects entropy from hardware interrupts (disk I/O, network, keyboard, HPET timer). The entropy pool (`/proc/sys/kernel/random/entropy_avail`) holds ~256 bits maximum on a virtual machine.
- **The Tax:** If 10,000 pods ask for a new 256-bit key at once (fleet restart), the entropy pool becomes **Saturated**. `/dev/random` blocks in the kernel until entropy refills — this is why deployments sometimes stall for 30-120 seconds with no obvious cause.
- **The Fix:** Use `/dev/urandom` (or `java.security.SecureRandom` with `SHA1PRNG` or `NativePRNGNonBlocking`) for key generation; reserve blocking `/dev/random` only for seeding the initial PRNG.

## 2. Source Archaeology: Vault and KMS

> [!abstract] The Mechanics: Dynamic Secrets
> - **Step 1:** The pod asks **HashiCorp Vault** for a password.
> - **Step 2:** Vault creates a new database user valid for only 1 hour.
> - **The Audit:** If a pod is compromised, the attacker has a 60-minute window before access vanishes.

**HashiCorp Vault Java client (`com.bettercloud:vault-java-driver` or `io.github.jopenlibs:vault-java-driver`):**
- `Vault vault = new Vault(new VaultConfig().address("https://vault.internal").token(podToken).build())`
- `vault.logical().read("database/creds/ledger-role")` → returns `LogicalResponse` with `getData()` map containing `username` and `password`
- `vault.logical().write("auth/kubernetes/login", Map.of("role", "ledger-pod", "jwt", podServiceAccountJwt))` → Kubernetes Auth Method login — the pod proves identity via its K8s service account JWT

**Vault Kubernetes Auth Method — Secret Zero resolution:**
The pod has a Kubernetes service account token (`/var/run/secrets/kubernetes.io/serviceaccount/token`). Vault's `auth/kubernetes` method verifies this token against the Kubernetes API Server (`TokenReview`). This bootstraps trust without needing a pre-shared secret — the K8s token IS the identity proof.

**`com.zaxxer.hikari.HikariDataSource`**:
- `setUsername(String)` and `setPassword(String)` can be called at runtime to rotate credentials
- `hikari.pool.HikariPool.softEvictConnections()` — evicts existing connections so new ones use the fresh credentials; called after credential swap

**`java.security.SecureRandom`**:
- Default provider on Linux: `NativePRNGNonBlocking` — reads from `/dev/urandom`, non-blocking
- `SecureRandom.getInstanceStrong()` → uses `/dev/random` (blocking); only use for initial seed, never in a request loop

## 4. Code Lab: Full Vault-Backed Credential Rotation

### BAD: Static credentials in configuration — permanent exposure window

```java
// BAD: Password in application.yaml or hardcoded.
// If this file reaches GitHub, Slack, a log file, or a heap dump,

    }

```

### GOOD: Vault-backed dynamic credentials with automatic renewal

```java
import com.bettercloud.vault.*;
import com.zaxxer.hikari.*;
import java.util.Map;
import java.util.concurrent.*;

/**
 * Dynamic credential manager backed by HashiCorp Vault.
 *
 * Security properties:
 * - Credentials valid for 1 hour (Vault lease TTL)
 * - Automatic renewal at 50% of TTL (30 minutes)
 * - K8s Auth Method: pod proves identity via service account JWT
 * - No static passwords anywhere in code or config
 */
@Component
public class VaultDynamicCredentialManager {

    private final Vault vault;
    private final HikariDataSource dataSource;
    private final ScheduledExecutorService scheduler =
        Executors.newSingleThreadScheduledExecutor(
            Thread.ofVirtual().factory()  // Chapter 1.3: Virtual Thread for I/O
        );

    public VaultDynamicCredentialManager(HikariDataSource ds) throws VaultException {
        this.dataSource = ds;

        // 1. Login via Kubernetes Auth Method (Secret Zero resolution)
        String k8sJwt = readPodServiceAccountToken();
        VaultConfig config = new VaultConfig()
            .address(System.getenv("VAULT_ADDR"))
            .build();
        Vault unauthVault = new Vault(config);

        LogicalResponse loginResp = unauthVault.auth().loginByKubernetes("ledger-pod", k8sJwt);
        String vaultToken = loginResp.getAuthClientToken();

        this.vault = new Vault(config.token(vaultToken));

        // 2. Fetch initial credentials and schedule renewal
        rotateCredentials();
        // Renew every 30 minutes (50% of the 1-hour TTL)
        scheduler.scheduleAtFixedRate(this::rotateCredentials, 30, 30, TimeUnit.MINUTES);
    }

    private void rotateCredentials() {
        try {
            // Vault generates a fresh PostgreSQL user valid for 1 hour
            LogicalResponse resp = vault.logical().read("database/creds/ledger-role");
            Map<String, String> data = resp.getData();

            String newUser = data.get("username");  // e.g. "v-k8s-ledger-AbCd12-1234567890"
            String newPass = data.get("password");

            // Soft-evict existing connections — they will reconnect with new credentials
            dataSource.setUsername(newUser);
            dataSource.setPassword(newPass);
            // HikariCP: evict idle connections; active connections finish then reconnect
            dataSource.getHikariPoolMXBean().softEvictConnections();

            System.out.printf("[VAULT] Credentials rotated. Username: %s, Lease TTL: %ss%n",
                newUser, resp.getLeaseDuration());

        } catch (VaultException e) {
            // CRITICAL: if rotation fails, log and alert — do NOT crash the pod.
            // Existing credentials still work until their TTL expires.
            System.err.println("[VAULT] Credential rotation failed: " + e.getMessage());
            // Production: fire PagerDuty alert here
        }
    }

    private String readPodServiceAccountToken() throws VaultException {
        try {
            return java.nio.file.Files.readString(
                java.nio.file.Path.of("/var/run/secrets/kubernetes.io/serviceaccount/token")
            );
        } catch (java.io.IOException e) {
            throw new VaultException("Cannot read K8s service account token", e);
        }
    }
}
```

## 5. Production Lens

| Approach | Exposure window after leak | Rotation cost |
|:---|:---|:---|
| Static password in `application.yaml` | **Permanent** (until manual rotation) | Requires redeployment |
| Vault dynamic secret (1hr TTL) | **60 minutes** max | Automatic, zero downtime |
| Vault dynamic secret (5min TTL) | **5 minutes** max | ~12 Vault API calls/hr/pod |

At Shopify (2022 engineering post), switching 400+ services to Vault dynamic secrets reduced their mean secret exposure window from **"indefinite"** to **"60 minutes"** and eliminated 3 incident categories related to leaked DB credentials. Their Vault cluster handles ~50,000 dynamic secret requests per minute at **~2ms p99 latency** per lease fetch.

Entropy starvation case: a 2017 GitLab incident showed that mass pod restarts on a VM-heavy Kubernetes cluster caused `/dev/random` blocking of **45-90 seconds** per pod during initial TLS handshake setup, because all pods competed for kernel entropy simultaneously. The fix was configuring `haveged` (entropy daemon) or using `rng-tools` to feed the entropy pool from hardware RNG.

<summary>Exercise 1 — Exposure window: static password vs Vault dynamic secret</summary>

**Static password scenario:**

- Leaked at: 14:00 Monday
- Rotated at: 19:00 Monday
- **Exposure window: 5 hours (18,000 seconds)**

During those 5 hours, any attacker who found the credential in the public repo could authenticate to the database with full permissions. Median time to exploit a leaked credential: **4 minutes** (GitHub secret scanning + automated exploit bots). The rotation at 19:00 is 296 minutes too late.

**Vault dynamic secret (1-hour TTL) scenario:**

Assume the same leak happens — the dynamic credential is visible in the public repo at 14:00.

- The credential was generated at 13:45 (15 minutes before the leak).
- TTL: 1 hour from generation = expires at 14:45.
- Attacker sees the credential at 14:00. Maximum useful window: **45 minutes** (14:00 → 14:45 when Vault auto-revokes it).

**More importantly:** The 14:00 commit leaks credentials for one lease period. The credential at 15:00 is different (new dynamic credentials are generated per request). Vault revokes the 13:45 credentials at 14:45 regardless of whether anyone noticed the leak.

**Blast radius comparison:**

| Metric | Static password | Vault dynamic (1h TTL) |
|---|---|---|
| Exposure window | 5h (until rotation) | ≤ 45min (time remaining in TTL) |
| Credentials compromised | Permanent until rotated | One time-limited credential |
| Database user impact | All connections using that password | Only connections using the leaked lease |
| Mitigation lag | Requires human action (5h) | Automatic (Vault TTL expiry) |

**Staff-level phrasing:** "Static password leak = 5h exposure until human rotates it; Vault dynamic credential = ≤45min exposure until TTL auto-revokes it — the difference between 'breach response required' and 'automatic remediation.'"

</details>

<details>
<summary>Exercise 2 — Secret Zero problem: two bootstrapping strategies</summary>

**The paradox:** To authenticate to Vault and get secrets, the pod needs a secret (token, password, cert). But where does that first secret come from?

**Strategy 1: Kubernetes Service Account JWT (Vault Kubernetes Auth)**

Kubernetes automatically mounts a service account JWT at `/var/run/secrets/kubernetes.io/serviceaccount/token` in every pod. The JWT is signed by the Kubernetes API server.

Vault verifies the JWT against the Kubernetes `TokenReview` API (`/apis/authentication.k8s.io/v1/tokenreviews`). If valid, Vault issues a Vault token.

**Security trade-off:**
- **Pro:** No static secret in the pod. The JWT is issued and rotated by Kubernetes, not the application.
- **Con:** The Kubernetes API server is the trust anchor. If the K8s cluster is compromised, all pod identities are compromised. Also: the default service account JWT in older Kubernetes versions has no audience binding and could be used from outside the cluster if leaked.
- **Mitigation:** Use bound service account tokens (`expirationSeconds: 3600`, `audience: vault`) for audience binding.

**Strategy 2: SPIRE SVID as Vault JWT Auth**

Each pod gets a SPIFFE SVID from SPIRE (X.509 certificate or JWT-SVID). Vault is configured with a JWT auth method that trusts SPIRE's JWKS endpoint.

**Security trade-off:**
- **Pro:** SVID is issued and rotated by SPIRE (short TTL, cryptographically bound to pod identity). No Kubernetes API dependency.
- **Con:** Requires SPIRE infrastructure deployed alongside Vault. More operational complexity — two identity systems to maintain. If SPIRE Agent is compromised on the node, all SVIDs for pods on that node are at risk.

**Staff-level phrasing:** "K8s service account JWT is the standard Secret Zero — Kubernetes manages the JWT lifecycle, Vault verifies via TokenReview; SPIRE SVID is more secure (shorter TTL, HSM-backed) but requires additional infrastructure."

</details>

<summary>Exercise 3 — Entropy starvation diagnosis and mitigations</summary>

**Linux command to show entropy pool size:**

```bash
cat /proc/sys/kernel/random/entropy_avail
# Returns a number (e.g., 3847)

# Or via watch for monitoring:
watch -n 1 cat /proc/sys/kernel/random/entropy_avail
```

**Dangerous threshold:** Below **100 bits** on older kernels (pre-5.17 `getrandom()` blocking mode). On modern Linux (5.17+), `getrandom()` no longer blocks after initial seeding — but `entropy_avail < 20` signals a hardware entropy source problem.

Practically: `entropy_avail < 256` on K8s nodes during mass restarts signals potential PRNG quality degradation for applications using `/dev/random` (blocking).

**Two mitigations for K8s entropy starvation during mass restarts:**

**Mitigation 1: Deploy `rng-tools` / `haveged` as a DaemonSet**

`haveged` (HArdware Volatile Entropy Gathering and Expansion Daemon) continuously feeds entropy from CPU state (timing jitter, execution paths) into the kernel entropy pool. As a DaemonSet, every node in the cluster has a continuous entropy source regardless of pod churn.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: haveged
spec:
  template:
    spec:
      containers:
      - name: haveged
        image: jnovack/haveged:latest
        securityContext:
          privileged: true  # required to write to /dev/random
```

**Mitigation 2: Configure Java to use `/dev/urandom` (non-blocking) instead of `/dev/random`**

`/dev/urandom` uses the CSPRNG with the available seed — it never blocks. The quality is sufficient for all TLS/session key generation.

```
# JVM startup flag:
-Djava.security.egd=file:/dev/./urandom

# Or in security.properties:
securerandom.source=file:/dev/urandom
```

Note: The `./` in `file:/dev/./urandom` is required on some JVM versions to bypass a classpath check that would fall back to `/dev/random`.

**Staff-level phrasing:** "Entropy starvation during mass pod restart: deploy haveged DaemonSet for continuous entropy injection and set -Djava.security.egd=file:/dev/./urandom to prevent SecureRandom from blocking on /dev/random."

<summary>Exercise 4 — EntropyMonitor implementation</summary>

```java
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.SecureRandom;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class EntropyMonitor {

    private static final Logger log = LoggerFactory.getLogger(EntropyMonitor.class);
    private static final Path ENTROPY_PATH = Path.of("/proc/sys/kernel/random/entropy_avail");
    private static final int WARN_THRESHOLD = 100;

    public int readEntropyAvail() throws Exception {
        return Integer.parseInt(Files.readString(ENTROPY_PATH).trim());
    }

    public void monitor() {
        Thread.ofVirtual().name("entropy-monitor").start(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                try {
                    int entropy = readEntropyAvail();
                    if (entropy < WARN_THRESHOLD) {
                        log.warn("Entropy pool critically low: {} bits available (threshold: {}). " +
                                 "Recommended fix: deploy haveged DaemonSet or set " +
                                 "-Djava.security.egd=file:/dev/./urandom",
                                 entropy, WARN_THRESHOLD);
                    } else {
                        log.debug("Entropy available: {} bits", entropy);
                    }
                    Thread.sleep(10_000);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } catch (Exception e) {
                    log.error("Failed to read entropy: {}", e.getMessage());
                }
            }
        });
    }

    public static void measureSecureRandom() throws Exception {
        // Strong (blocks on /dev/random if entropy low)
        long start = System.nanoTime();
        SecureRandom.getInstanceStrong().generateSeed(32);
        long strongMs = (System.nanoTime() - start) / 1_000_000;

        // Standard (uses /dev/urandom — never blocks)
        start = System.nanoTime();
        new SecureRandom().generateSeed(32);
        long standardMs = (System.nanoTime() - start) / 1_000_000;

        System.out.printf("SecureRandom.getInstanceStrong() 32 bytes: %dms%n", strongMs);
        System.out.printf("new SecureRandom() 32 bytes: %dms%n", standardMs);

        if (strongMs > 100) {
            System.out.println("WARNING: getInstanceStrong() is blocking — entropy pool likely depleted.");
            System.out.println("Set -Djava.security.egd=file:/dev/./urandom to use non-blocking source.");
        }
    }

    public static void main(String[] args) throws Exception {
        measureSecureRandom();
        new EntropyMonitor().monitor();
    }
}
```

**Common mistake:** Using `SecureRandom.getInstanceStrong()` on the request path — on a node with low entropy, this can block for seconds. Use `new SecureRandom()` on the request path, which uses `/dev/urandom` (non-blocking, cryptographically adequate). Reserve `getInstanceStrong()` for one-time key generation (not per-request).

<summary>Exercise 5 — Vault TTL design for three service types</summary>

**(a) Batch job running 4 hours:**

**TTL: 6 hours (lease + 50% buffer)**

The batch job needs the credential for 4 hours. TTL shorter than 4h causes the credential to expire mid-run — the batch job crashes. TTL exactly 4h has no buffer for slow jobs.

Best practice: `ttl=6h, max_ttl=8h`. The batch job calls `vault lease renew` at the 3-hour mark to extend if needed.

**Vault API call rate:** 1 initial lease + 1 renewal (if job takes > 3h) = **2 API calls per batch run**. At 10 batch jobs/day: 20 API calls/day.

**(b) Web API with long-lived pods:**

**TTL: 1 hour with automatic lease renewal**

Pods live for days but the database credential TTL should be short (1h) to limit breach impact. The Vault Spring Boot integration (`spring-cloud-vault`) automatically renews leases at `TTL × renewal_threshold` (typically 75% = 45 minutes).

**Vault API call rate per pod:** 1 renewal per hour = 24/day per pod. At 200 pods: **4,800 API calls/day**. Vault Pro/Enterprise supports 10,000+ requests/s — this is negligible.

**(c) 30-second Lambda-style function:**

**TTL: 60 seconds (2× function max duration)**

Lambda-style functions are short-lived. A 1h TTL means the credential stays valid for 59 minutes and 30 seconds after the function exits — unnecessary exposure window.

**Challenge:** Vault token acquisition adds ~15ms (API call + JWT verification). For a 30-second function, 15ms overhead is acceptable. For a 5ms function, it would not be.

**Vault API call rate:** 1 call per invocation. At 10,000 invocations/day: **10,000 API calls/day**. Consider Vault agent sidecar or Lambda extension caching the credential for the Lambda execution environment's warm instance.

**Summary table:**

| Service | TTL | Renewal | Daily Vault calls |
|---|---|---|---|
| Batch job | 6h | Manual at 3h | 20 |
| Web API pod | 1h | Auto at 45min | 4,800 (200 pods) |
| Lambda function | 60s | None (single use) | 10,000 |

**Staff-level phrasing:** "TTL = function duration × 1.5 as minimum; long-lived services use 1h with automatic lease renewal; Lambda uses single-use 60s credentials with warm-instance caching to avoid per-invocation Vault API overhead."

</details>

## 7. Summary / Flashcard

- **Static secrets have a permanent exposure window**: once a password is committed to a Git repo (even private), it is never truly safe — the median time to exploit after public exposure is 4 minutes.
- **Vault dynamic secrets** create a PostgreSQL user valid for the lease TTL (e.g. 1 hour); after TTL expiry Vault revokes the user — an attacker with a stolen credential has at most 60 minutes of access.
- **Secret Zero via Kubernetes Auth**: pods prove identity using their K8s service account JWT (verified by Vault against the K8s `TokenReview` API), eliminating the need for any pre-shared bootstrap secret.
- **Entropy starvation** occurs when a fleet restart causes all pods to compete for the kernel entropy pool simultaneously; the fix is `rng-tools`/`haveged` on nodes plus configuring `java.security.SecureRandom` to use `NativePRNGNonBlocking` (reads `/dev/urandom`) on the request path.
- **`HikariDataSource.softEvictConnections()`** is the correct API for credential rotation; it drains idle connections and marks active ones for eviction after their current query completes, achieving zero-connection-error rotation.

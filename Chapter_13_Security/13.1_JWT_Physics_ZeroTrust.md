## 1. The Physics of the Token

### 1.1 The Signature Tax

- **RSA-2048:** On a standard core, one verification takes **~1ms**.
- **Impact:** In a Ledger doing 1M RPS, you need **1,000 dedicated CPU cores** just for math.
- **The Principal Fix:** Use **EdDSA** (Ed25519). It is 10x faster (~0.09ms/verify) and has smaller keys (32 bytes vs 256 bytes), reclaiming 90% of your security budget.

---

## 2. Source Archaeology: JWKS and Rotation

A Principal never hardcodes a public key. We use **JWKS (JSON Web Key Set)** for hitless rotation.

> [!abstract] The Mechanics: Key Discovery
> - **Step 1:** The Identity Provider (IDP) publishes keys at `/.well-known/jwks.json`.
> - **Step 2:** Pods fetch and cache these in a **Caffeine L1 Cache**, keyed by `kid`.
> - **Step 3:** Tokens are verified against the cached key ID (`kid`).

**`com.nimbusds.jose.JWSVerifier`** (Nimbus JOSE+JWT, `com.nimbusds:nimbus-jose-jwt`):
- `Ed25519Verifier` implements `JWSVerifier` for EdDSA verification
- `JWSAlgorithm.Ed25519` — the algorithm constant; reject anything else at the parser level
- `JWTClaimsSet.getExpirationTime()` — always validate `exp` after signature; a valid signature on an expired token is still invalid

**`com.nimbusds.jose.jwk.source.RemoteJWKSet`**:
- Constructor: `new RemoteJWKSet(new URL("https://idp/.well-known/jwks.json"))` — fetches and caches the JWKS endpoint
- `get(JWKSelector, SecurityContext)` → returns matching keys by `kid`; handles key rotation transparently by re-fetching on cache miss

**`com.nimbusds.jose.proc.DefaultJWTProcessor`**:
- `setJWSKeySelector(new JWSVerificationKeySelector<>(JWSAlgorithm.Ed25519, jwkSource))` — binds algorithm + key source; rejects `alg:none` attacks automatically when algorithm is explicitly constrained

**Algorithm confusion attack:** If you accept both RS256 and HS256 in the same validator, an attacker can sign a token with HS256 using the public key as the HMAC secret. Always use `JWSAlgorithm.Ed25519` (or a single explicit algorithm) in `JWSVerificationKeySelector`.

## 3. Principal Implementation: The Identity Guard

```java
// Principal Level: Zero-Trust Identity Guard
public class IdentityGuard {
    // 1. L1 Cache for Public Keys
    private final LoadingCache<String, PublicKey> keyCache = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofHours(1))
        .build(kid -> fetchFromIdp(kid));

    public boolean verify(String jwt) {
        String kid = extractKid(jwt);
        PublicKey key = keyCache.get(kid);

        // 2. Perform Math on a Virtual Thread
        return crypto.verify(jwt, key);
    }
}
```

## 4. Code Lab: Full Principal-Grade Implementation

### BAD: Vulnerable JWT verification — accepts any algorithm, no audience check

```java
// BAD: Three critical vulnerabilities in 10 lines.
import com.auth0.jwt.JWT;
import com.auth0.jwt.algorithms.Algorithm;

public class InsecureJwtVerifier {
    private static final String PUBLIC_KEY = "-----BEGIN PUBLIC KEY-----\n...";

    public boolean verify(String token) {
        // VULNERABILITY 1: alg:none — if the token says "alg":"none",
        // some old libraries skip verification entirely.
        // VULNERABILITY 2: No 'aud' claim check — any token signed by this
        // IDP is accepted, even tokens meant for a different service.
        // VULNERABILITY 3: Hardcoded key — no rotation possible without redeployment.
        try {
            JWT.require(Algorithm.RSA256(loadPublicKey(PUBLIC_KEY), null))
               .build()
               .verify(token);
            return true;
        } catch (Exception e) {
            return false;
        }
    }
}
```

### GOOD: Nimbus-based EdDSA verifier with JWKS rotation and full claim validation

```java
import com.nimbusds.jose.*;
import com.nimbusds.jose.crypto.Ed25519Verifier;
import com.nimbusds.jose.jwk.*;
import com.nimbusds.jose.jwk.source.RemoteJWKSet;
import com.nimbusds.jose.proc.*;
import com.nimbusds.jwt.*;
import com.nimbusds.jwt.proc.*;
import java.net.URL;
import java.util.Date;

/**
 * Production-grade Zero-Trust JWT verifier.
 *
 * Key properties:
 * - EdDSA (Ed25519): ~0.09ms/verify vs ~1ms for RSA-2048 (11x faster)
 * - JWKS with automatic key rotation via RemoteJWKSet
 * - alg:none rejected at algorithm selector level
 * - Audience + expiry + issuer validated
 */
public class ZeroTrustIdentityGuard {

    private final DefaultJWTProcessor<SecurityContext> processor;

    public ZeroTrustIdentityGuard(String jwksUrl, String expectedIssuer,
                                   String expectedAudience) throws Exception {
        // 1. JWKS source — RemoteJWKSet caches keys and re-fetches on kid miss
        RemoteJWKSet<SecurityContext> jwkSource =
            new RemoteJWKSet<>(new URL(jwksUrl));

        // 2. Algorithm selector — ONLY Ed25519 accepted
        //    Rejects alg:none and RS256/HS256 confusion attacks
        JWSKeySelector<SecurityContext> keySelector =
            new JWSVerificationKeySelector<>(JWSAlgorithm.Ed25519, jwkSource);

        // 3. Claims verifier — exp, nbf, iss, aud all checked
        DefaultJWTClaimsVerifier<SecurityContext> claimsVerifier =
            new DefaultJWTClaimsVerifier<>(
                new JWTClaimsSet.Builder()
                    .issuer(expectedIssuer)
                    .audience(expectedAudience)
                    .build(),
                java.util.Set.of("exp", "iat", "sub")  // required claims
            );

        this.processor = new DefaultJWTProcessor<>();
        this.processor.setJWSKeySelector(keySelector);
        this.processor.setJWTClaimsSetVerifier(claimsVerifier);
    }

    /**
     * Returns the verified claims set, or throws BadJWTException.
     * Call from a Virtual Thread (Chapter 1.3) to avoid blocking carrier threads.
     */
    public JWTClaimsSet verify(String rawJwt) throws Exception {
        // DefaultJWTProcessor handles parse + signature + claims in one call
        return processor.process(rawJwt, null);
    }
}
```

## 5. Production Lens

| Algorithm | Verify time (single core) | CPU cores for 1M RPS |
|:---|---:|---:|
| RSA-2048 | ~1.0 ms | 1,000 cores |
| RSA-4096 | ~3.5 ms | 3,500 cores |
| ECDSA P-256 | ~0.2 ms | 200 cores |
| **Ed25519** | **~0.09 ms** | **90 cores** |

Source: OpenSSL speed benchmarks on a single Graviton2 vCPU (AWS r6g). A 10,000-pod fleet switching from RSA-2048 to Ed25519 reclaims ~91% of signature-verification CPU — equivalent to decommissioning ~900 pods at ~$70/pod/month = **$63,000/month** saved.

Token size impact: a JWT with 20 claims averages 800 bytes. At 10M RPS, that is **800 MB/s of auth headers** on every internal service mesh link. Trimming to 5 essential claims (~300 bytes) saves **500 MB/s per service hop** — directly reducing egress costs.

## Exercise Solutions

**Conceptual:**

<details>
<summary>Exercise 1 — CPU budget calculation</summary>

**(a)** Total JWT verifications per second: 500 pods × 2,000 RPS = **1,000,000 verifications/sec**

**(b)** CPU cores consumed by RSA-2048 verification: 1,000,000 verifications/sec × 1ms/verification = 1,000,000 ms of CPU per second = **1,000 dedicated CPU cores**

**(c)** Ed25519 verification time is ~0.09ms, so: 1,000,000 × 0.09ms = 90,000 ms/sec = **90 CPU cores**. Savings: 1,000 − 90 = **910 cores reclaimed** (~91% reduction).

**Staff-level phrasing:** "At 1M RPS, RSA-2048 consumes 1,000 CPU cores purely on modular exponentiation; switching to Ed25519 reclaims 910 of those cores — equivalent to decommissioning nearly a full rack of servers."

</details>

<details>
<summary>Exercise 2 — Key rotation drill</summary>

**Exact sequence:**

1. The IDP generates a new key pair, adds the new entry to `jwks.json` keyed by a new `kid` (e.g. `kid-2`), and keeps the old entry (`kid-1`) in the JWKS response during a transition window.
2. New tokens are issued signed with `kid-2`. Old tokens still in flight carry `kid-1`.
3. A pod receives a token with `kid-2`. `RemoteJWKSet` looks up `kid-2` in its local cache — **cache miss**.
4. `RemoteJWKSet.get()` makes an HTTP GET to `/.well-known/jwks.json` and re-fetches the full JWKS document. The response now contains both `kid-1` and `kid-2`.
5. The new keys are cached. The token with `kid-2` is verified successfully. Tokens with `kid-1` continue to resolve from the cache until they expire.

**Worst-case verification latency during rotation:** cache miss latency = HTTP round-trip to the IDP endpoint. On an internal network this is typically **5–50ms**. During this window, the verifying thread blocks on the HTTP call. This is why the reference implementation calls `verify()` from a Virtual Thread (Chapter 1.3) — blocking a Virtual Thread is free, whereas blocking a carrier thread starves the ForkJoinPool.

**Staff-level phrasing:** "Key rotation with `RemoteJWKSet` is hitless because the JWKS endpoint is additive — old kids remain valid during the transition window — and the only user-visible cost is a single HTTP round-trip on the first cache miss per pod."

</details>

<details>
<summary>Exercise 3 — Attack analysis</summary>

**`alg:none` attack:** An attacker strips the signature from a valid JWT and sets the header field `"alg": "none"`, causing some libraries to skip signature verification entirely and accept the forged token as valid.

**Why `JWSVerificationKeySelector` with `JWSAlgorithm.Ed25519` prevents it:** `JWSVerificationKeySelector` only returns key candidates whose algorithm matches the selector's configured algorithm. A token claiming `alg:none` has no algorithm, so `JWSVerificationKeySelector.selectJWSKeys()` returns an empty list. `DefaultJWTProcessor` treats an empty key list as a verification failure and throws `BadJOSEException` — the method that rejects the malformed token is `DefaultJWTProcessor.process()`, before any signature math is attempted.

**Staff-level phrasing:** "The defense against `alg:none` is to never allow the token to self-describe its algorithm — by binding the key selector to a single explicit `JWSAlgorithm`, the processor rejects any token whose algorithm field doesn't match before signature verification is even attempted."

</details>

<details>
<summary>Exercise 5 — Token bloat audit</summary>

**Approximate serialized size:** Claims like `sub`, `iss`, `aud`, `exp`, `iat`, `jti` add ~150 bytes. `email` (~30 bytes), `given_name` + `family_name` (~40 bytes), `locale` (~15 bytes), `org_id` (~30 bytes), `roles` array (5 entries, ~80 bytes), `permissions` array (20 entries, ~300 bytes) — plus Base64-URL encoding overhead (~33%). Rough total: **~900–1,000 bytes** per token.

**Claims to remove and justifications:**

- **`given_name`, `family_name`**: Display names belong in a user-profile service, not in every auth token on every internal service hop — any service that needs the user's name should look it up, not receive it on every request.
- **`locale`**: A UI preference has no authorization semantics and bloats every token for a concern only the frontend needs.
- **`permissions` (array of 20)**: Fine-grained permissions should be resolved by the resource server at decision time using the `sub` + `org_id` as a lookup key — embedding 20 permissions in the token creates a stale-cache problem the moment permissions change.
- **`roles` (array of 5)**: Keep at most a single coarse-grained role claim; the full role set should be fetched from a policy engine (e.g. OPA) per-request if needed.
- **`email`**: Useful for audit logging but not for authorization; pass it only in tokens consumed by user-facing services, not on every internal mesh call.

**After pruning to `sub`, `iss`, `aud`, `exp`, `iat`, `jti`, `org_id`:** ~250–300 bytes — a **65% size reduction**, saving ~600 MB/s per service hop at 10M RPS.

**Staff-level phrasing:** "A JWT is a broadcast — every claim you put in it travels to every downstream service on every request hop; audit the authorization semantics of each claim and remove anything that can be looked up lazily, because token bloat is a distributed systems tax, not just a security concern."

</details>

**Coding:**

<details>
<summary>Exercise 4 — Coding challenge: BloomFilter blacklist</summary>

```java
// Java 21+ reference implementation
import com.google.common.hash.BloomFilter;
import com.google.common.hash.Funnels;
import java.nio.charset.StandardCharsets;

/**
 * O(1) in-memory JWT revocation blacklist using a Bloom filter.
 *
 * Sizing for 1M revoked tokens at 0.1% (0.001) false-positive rate:
 *   m = -n * ln(p) / (ln(2))^2
 *     = -(1_000_000) * ln(0.001) / (0.693)^2
 *     = 1_000_000 * 6.908 / 0.480
 *     ≈ 14,400,000 bits ≈ 1.8 MB
 *
 * Guava's BloomFilter uses ~14.4 bits per element at 0.1% FPR,
 * so memory footprint ≈ 14,400,000 bits / 8 = ~1.8 MB.
 */
public class BloomFilterBlacklist {

    private static final int EXPECTED_INSERTIONS = 1_000_000;
    private static final double FALSE_POSITIVE_PROBABILITY = 0.001; // 0.1%

    private final BloomFilter<String> filter;

    public BloomFilterBlacklist() {
        this.filter = BloomFilter.create(
            Funnels.stringFunnel(StandardCharsets.UTF_8),
            EXPECTED_INSERTIONS,
            FALSE_POSITIVE_PROBABILITY
        );
    }

    /**
     * Mark a JWT as revoked by its unique jti claim.
     * This operation is irreversible — Bloom filters do not support deletion.
     */
    public void revoke(String jti) {
        if (jti == null || jti.isBlank()) {
            throw new IllegalArgumentException("jti must not be null or blank");
        }
        filter.put(jti);
    }

    /**
     * Returns true if the jti is definitely revoked, or possibly revoked
     * (false positive). Returns false only if the jti is definitely NOT revoked.
     *
     * False-positive rate: ~0.1% at 1M insertions.
     * A false positive means a valid token is incorrectly rejected —
     * the caller should treat this as a hard rejection (fail-closed).
     */
    public boolean isRevoked(String jti) {
        return filter.mightContain(jti);
    }

    /**
     * Reports the current approximate false-positive probability.
     * As more elements are inserted beyond EXPECTED_INSERTIONS,
     * this value rises above the configured 0.001 target.
     */
    public double falsePositiveProbability() {
        return filter.expectedFpp();
    }

    /**
     * Memory footprint calculation:
     *   bits = -n * ln(p) / (ln(2))^2 = 14,377,588 bits ≈ 1.8 MB
     */
    public long approximateMemoryBitsUsed() {
        // Guava exposes this via its internal array; approximate via formula
        long n = EXPECTED_INSERTIONS;
        double p = FALSE_POSITIVE_PROBABILITY;
        return (long) Math.ceil(-n * Math.log(p) / (Math.log(2) * Math.log(2)));
    }

    public static void main(String[] args) {
        BloomFilterBlacklist blacklist = new BloomFilterBlacklist();

        // Revoke 1M tokens
        for (int i = 0; i < 1_000_000; i++) {
            blacklist.revoke("jti-" + i);
        }

        // Check a revoked token
        System.out.println("jti-42 revoked: " + blacklist.isRevoked("jti-42")); // true

        // Check a never-revoked token
        System.out.println("jti-never revoked: " + blacklist.isRevoked("jti-never")); // false (probably)

        // Report false-positive rate
        System.out.printf("Current FPP: %.4f%%%n", blacklist.falsePositiveProbability() * 100);
        System.out.printf("Memory: ~%.1f MB%n",
            blacklist.approximateMemoryBitsUsed() / 8.0 / 1_024 / 1_024);
    }
}
```

**Why this works:** A Bloom filter maps each element to `k` bit positions via `k` independent hash functions. `mightContain` returns false only if at least one of the `k` bits is 0 — meaning the element was definitively never inserted. This gives O(1) lookup with zero network I/O, at the cost of a tunable false-positive rate (valid tokens occasionally rejected).

**Common mistake:** Calling `BloomFilter.create()` inside a request handler (creating a new filter per request) rather than injecting a singleton. Another common mistake is using `filter.mightContain()` and treating a `false` result as "valid" — this is correct — but then treating a `true` result as "definitely revoked" — this is wrong because of false positives. The correct mental model: `false` = definitely clean, `true` = revoked OR false positive (both must be rejected, fail-closed).

</details>

## 7. Summary / Flashcard

- **Ed25519 vs RSA-2048**: Ed25519 verifies in ~0.09ms vs ~1ms for RSA-2048 — an 11x speedup that reduces verification CPU from 1,000 cores to 90 cores at 1M RPS.
- **`RemoteJWKSet` + `JWSVerificationKeySelector`** implement JWKS-backed key rotation: on `kid` cache miss, the JWK set is re-fetched from the IDP endpoint, making key rotation hitless without redeployment.
- **Algorithm confusion attack** is prevented by binding `JWSVerificationKeySelector` to a single explicit `JWSAlgorithm`; accepting both RS256 and HS256 in the same validator allows an attacker to sign with HS256 using the public key as the HMAC secret.
- **`alg:none` attack** is defeated by `DefaultJWTProcessor` when the `JWSKeySelector` is non-null — a token claiming `alg:none` has no matching key selector entry and is rejected before signature verification is attempted.
- **Bloom filter revocation** provides O(1) in-memory blacklist checks with tunable false-positive rates; a 1M-entry filter at 0.1% FPR requires ~14.4 MB — far cheaper than a Redis roundtrip (~0.3ms) on every request.

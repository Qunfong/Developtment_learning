# 6.1: Cell-based Architecture and the Blast Radius

## Learning Objectives

- Define "blast radius" formally and calculate it as a percentage of total users affected per cell failure event
- Design a cell router that maps user IDs to cells using consistent hashing, allowing cells to be added without rehashing the entire fleet
- Identify which shared global components (ingress, DNS, identity provider) remain single points of failure in a cell architecture and propose mitigations
- Evaluate the cell-size trade-off between operational overhead (too many small cells) and blast radius (too few large cells)
- Apply cell-based design principles to a Kubernetes multi-cluster topology using namespace isolation and separate etcd clusters per cell

## The Critical Dialogue


**Student:** Our Ledger is growing fast. We have 2,000 pods in Kubernetes. But one buggy deployment in US-EAST-1 somehow crashed our servers in London. How can a local bug have a global "Blast Radius"?


**Principal:** You are building a **Shared-Fate Architecture**. In a standard fleet, every pod is a neighbor to every other pod. If one neighbor starts a fire, the entire city burns. To reach Principal level, we must move from a "Unified Sea of Pods" to **Cell-based Architecture**. We divide the fleet into small, isolated islands (Cells) that share **nothing**. We move from "Managing 2,000 Pods" to **Governing 20 Cells**.

## 2. Solution: Cell-based Design (Shared-Nothing)


**The Principal Architecture:** We divide users into **Cells**. A Cell is a full stack (API + Logic + DB) physically isolated from others.


. **Mechanism:** Anycast routes User A to Cell 1 and User B to Cell 2.
. **Isolation:** Cell 1 and Cell 2 never share a database or cache.
. **The Benefit:** If Cell 1's database explodes, Cell 2 is 100% healthy. Blast radius is reduced from 100% to 5%.

## 4. Source Archaeology

Real cell-based and shared-nothing implementations:

**Shopify Pods** — Shopify's "pod" architecture (described in their engineering blog, 2022) uses a `ShopId % num_pods` mapping stored in a routing table. Each pod has its own MySQL cluster, Redis cluster, and Kafka consumer group. The router (`shopify/pod-router`) is a Go service that reads the routing table from a global etcd and forwards HTTP requests. An `X-Shopify-Pod` header identifies the pod for observability.

**Slack Cellular Architecture** — Slack's 2022 blog post "Slack's Migration to a Cellular Architecture" describes routing `workspace_id` to cells using a consistent hash ring. The cell assignment service (`cell-service`) is the only global component; it stores assignments in a replicated PostgreSQL database with a read cache. Each cell runs an independent `message-gateway`, `channel-server`, and `presence-server`.

**AWS Availability Zones** — AWS's "Shuffle Sharding" pattern (`aws/aws-lambda-developer-guide`) assigns each customer to a unique subset of `k` workers from a pool of `n`. If one worker fails, only the customers sharing that worker are affected — not all customers. The blast radius formula is `k/n` (e.g. 2/20 = 10%) rather than 100%.

**Kubernetes Namespace Isolation** — `k8s.io/api/core/v1.Namespace` with `NetworkPolicy` (`networking.k8s.io/v1.NetworkPolicy`) restricts pod-to-pod traffic to the same namespace. `ResourceQuota` (`core/v1.ResourceQuota`) prevents one cell's pods from consuming cluster-level CPU/memory budget. Combined with separate node pools (`nodeSelector`) and separate etcd prefixes, this achieves infrastructure-level cell isolation within a single Kubernetes cluster.

**GOOD approach — cell-isolated routing with consistent hashing:**

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.SortedMap;
import java.util.TreeMap;

/**
 * Consistent hash ring cell router.
 *
 * Each cell is placed at multiple virtual nodes on the ring (vnodes per cell)
 * to distribute load evenly. A user is always routed to the same cell as long
 * as no cells are added or removed — and when cells ARE added, only 1/N of
 * traffic is remapped (vs. full rehash with modulo routing).
 *
 * Modeled after Shopify's pod-router and Cassandra's TokenAwarePolicy.
 */
public class CellRouter {

    private static final int VNODES_PER_CELL = 150;  // Cassandra uses 256

    private final SortedMap<Long, String> ring = new TreeMap<>();

    public CellRouter(java.util.List<String> cellIds) {
        for (String cellId : cellIds) {
            for (int i = 0; i < VNODES_PER_CELL; i++) {
                long hash = hash(cellId + "-vnode-" + i);
                ring.put(hash, cellId);
            }
        }
    }

    /**
     * Returns the cell ID responsible for this userId.
     * Deterministic: same userId always maps to same cell unless cells are added/removed.
     */
    public String route(String userId) {
        if (ring.isEmpty()) throw new IllegalStateException("No cells registered");
        long hash = hash(userId);
        SortedMap<Long, String> tail = ring.tailMap(hash);
        // Wrap around the ring if userId hash > last vnode
        long key = tail.isEmpty() ? ring.firstKey() : tail.firstKey();
        return ring.get(key);
    }

    /** Fraction of users remapped when adding one cell to N existing cells. */
    public static double remapFraction(int existingCells) {
        return 1.0 / (existingCells + 1);  // e.g. adding cell to 19 → 5% remap
    }

    private static long hash(String key) {
        try {
            MessageDigest md = MessageDigest.getInstance("MD5");
            byte[] digest = md.digest(key.getBytes(StandardCharsets.UTF_8));
            // Use first 8 bytes as long (Cassandra's Murmur3 in real life)
            long h = 0;
            for (int i = 0; i < 8; i++) h = (h << 8) | (digest[i] & 0xFF);
            return h;
        } catch (NoSuchAlgorithmException e) {
            throw new RuntimeException(e);
        }
    }
}

/**
 * Cell-aware service: each cell has its own connection pool and cache.
 * A failure or resource leak in Cell-1's pool cannot affect Cell-2.
 */
public class CellAwareLedgerService {

    private final CellRouter                       router;
    private final java.util.Map<String, CellState> cells;

    public CellAwareLedgerService(java.util.List<String> cellIds) {
        this.router = new CellRouter(cellIds);
        this.cells  = new java.util.HashMap<>();
        for (String cellId : cellIds) {
            cells.put(cellId, new CellState(cellId));
        }
    }

    public Account getAccount(String userId) {
        String cellId = router.route(userId);
        CellState cell = cells.get(cellId);
        // Each cell has its OWN cache (bounded) and OWN connection pool
        return cell.cache.computeIfAbsent(userId, id -> cell.db.findAccount(id));
    }

    /** Simulate Cell-1 failing — Cell-2 users are completely unaffected */
    public void simulateCellFailure(String cellId) {
        CellState cell = cells.get(cellId);
        cell.healthy = false;
        System.out.printf("Cell %s is down. Other cells: 100%% healthy.%n", cellId);
        // blast radius = 1/N = 1/20 = 5% for 20 cells
    }

    record Account(String userId, long balance) {}
    record CellState(String cellId,
                     java.util.Map<String, Account> cache,
                     FakeDB db,
                     boolean healthy) {
        CellState(String id) {
            this(id, new java.util.concurrent.ConcurrentHashMap<>(), new FakeDB(), true);
        }
    }
    interface FakeDB { Account findAccount(String id); }
}
```

## 6. Production Lens

**Blast radius reduction** — Shopify reported that before cell architecture, a single pod failure during Black Friday 2019 caused 100% checkout failure for all merchants on that pod. After migration to 24 pods, a pod failure affects approximately 1/24 = 4.2% of merchants. Their 2022 engineering blog reports zero cross-pod blast radius incidents in two years post-migration.

**Cell size calibration** — Slack's cell architecture targets 50,000 workspaces per cell. With 750,000 workspaces total, that is 15 cells. Each cell failure affects 50,000/750,000 = 6.7% of users. Below 10,000 workspaces per cell, operational overhead (separate deployments, monitoring, on-call runbooks) exceeds the blast-radius benefit.

**Consistent hash remap fraction** — When adding a 21st cell to a 20-cell ring, `1/21 = 4.8%` of users are remapped. With modulo routing (`userId % numCells`), adding one cell remaps approximately `50%` of all users — causing a thundering herd as those users' sessions are invalidated simultaneously.

<summary>Exercise 1 — Error budget consumption per cell failure</summary>

A cell failure affects 5% of users for 15 minutes. The SLA of 99.9% gives a monthly budget of 43 minutes.

**Budget consumed per incident:**
- The affected population is 5% of users, so the "effective downtime" in SLO terms is `15 min × 5% = 0.75 minutes` of budget consumed (weighted by user impact).
- However, if the SLO is measured as "percentage of all requests that succeed," a 15-minute 5%-user outage consumes `15 / 43 × 5% / 100% = ~1.7%` of the budget in absolute time for that cell's users. The common interpretation: each cell failure consumes `15 min` against the budget only for those users, so `15/43 ≈ 35%` of the per-cell user budget.
- In global terms: since only 5% of traffic is affected, the weighted budget consumed is `15 × 0.05 = 0.75 equivalent minutes` of the global 43-minute budget — approximately **1.7%** of the monthly budget per incident.

**How many failures fit in budget?**
- `43 min / 0.75 min per incident ≈ 57 cell failures per month` before exhausting the global SLO budget.
- If each failure is counted as a full 15 minutes (unweighted), then `43 / 15 ≈ 2` full outages per month — so the weighted view (1.74%) is the correct one for a cell architecture with proper blast-radius isolation.

**Key formula:** `budget_consumed = failure_duration × (cell_users / total_users)`

**Staff-level phrasing:** "Cell architecture transforms an SLO budget calculation from a binary 100%-or-nothing event into a weighted impact model where blast radius directly determines budget consumption rate, enabling over 50 independent cell failures within a 99.9% SLO."

</details>

<details>
<summary>Exercise 2 — Single points of failure in a cell architecture</summary>

Three global components that remain SPOFs even with full cell isolation:

1. **Anycast ingress / global load balancer** — The router that maps user IDs to cells is a shared global component. If it fails, no user can reach any cell.
   - *Mitigation:* Use DNS-based routing with multiple Anycast IPs and health-checked failover (e.g., AWS Route53 with latency routing + health checks). The routing decision can be cached in DNS with a low TTL (30s), so a brief router outage does not immediately cut all traffic.

2. **Identity provider / auth service** — If authentication is global (OAuth2 server, JWT signing keys, LDAP), every cell depends on it for request validation.
   - *Mitigation:* Use short-lived signed tokens (JWT with 1-hour TTL). Each cell can validate tokens locally using a cached public key — the identity provider can be offline for up to 1 hour before any cell is affected. This converts a hard SPOF into a soft dependency.

3. **DNS** — If the DNS infrastructure resolving cell addresses fails, users cannot resolve cell hostnames regardless of cell health.
   - *Mitigation:* DNS is already highly redundant (multiple root servers), but for the cluster-internal service-discovery DNS (CoreDNS), deploy it with a minimum of 3 replicas across availability zones and cache responses aggressively at the client (positive TTL 60s, negative TTL 10s).

**Staff-level phrasing:** "The three unavoidable global dependencies in any cell architecture are the routing layer, the identity layer, and DNS — each must be made stateless and cache-friendly so that a brief outage degrades to stale-reads rather than total failure."

</details>

<details>
<summary>Exercise 3 — Modulo routing thundering herd when adding a 25th pod</summary>

With modulo routing: `cellId = ShopId % numPods`

When `numPods` changes from 24 to 25:
- A shop with `ShopId = 24` maps to cell 0 under 24 pods (`24 % 24 = 0`) and cell 24 under 25 pods (`24 % 25 = 24`) — remapped.
- In general, `ShopId % 24 != ShopId % 25` for approximately `(1 - 1/25) ≈ 96%` of all shop IDs.

**Percentage remapped:** approximately **96%** of all shops are mapped to a different cell when the pod count changes from 24 to 25. Only shops where `ShopId % 24 == ShopId % 25` (i.e., `ShopId % 600 < 25`, roughly 1/24 ≈ 4%) stay on the same pod.

**Thundering herd risk:** At the moment of deployment, 96% of active user sessions are routed to new cells. Those cells have empty caches (no warm database connection pool, no in-memory data). Every rerouted user triggers a cold cache miss. If Shopify has 100,000 active shops at deploy time, roughly 96,000 shops simultaneously hammer their new pods with cold requests — database connection pools spike, response times spike, and the increased latency can cascade into a retry storm.

With consistent hashing, adding a 25th cell remaps only `1/25 = 4%` of shops — traffic rerouting is 24x smaller.

**Staff-level phrasing:** "Modulo routing makes cluster expansion an operational hazard: adding one cell remaps ~96% of users simultaneously, creating a thundering herd that can collapse the very fleet you were trying to scale — consistent hashing exists precisely to avoid this."

</details>

<summary>Exercise 4 — Coding challenge: drainCell with progressive rerouting</summary>

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;

/**
 * Extended CellRouter supporting progressive cell drain.
 *
 * drainCell(cellId, fraction): routes `fraction` of the drained cell's
 * users to the next cell on the ring, while keeping (1 - fraction) on
 * the original cell.
 *
 * Correctness invariant: at any given fraction, each userId maps to
 * exactly one cell (no double-routing).
 *
 * The drain is deterministic: the same userId always takes the same
 * code path for a given fraction, ensuring session affinity during
 * the 30-minute drain window.
 */
public class CellRouter {

    private static final int VNODES_PER_CELL = 150;

    private final SortedMap<Long, String> ring = new TreeMap<>();
    // cellId -> fraction of its users being drained (0.0 = not draining)
    private final Map<String, Double> drainFractions = new ConcurrentHashMap<>();

    public CellRouter(List<String> cellIds) {
        for (String cellId : cellIds) {
            for (int i = 0; i < VNODES_PER_CELL; i++) {
                ring.put(hash(cellId + "-vnode-" + i), cellId);
            }
        }
    }

    /**
     * Routes userId to a cell, respecting any active drain.
     * If the user's natural cell is being drained, a deterministic
     * hash of userId decides whether they are migrated to the next cell.
     */
    public String route(String userId) {
        if (ring.isEmpty()) throw new IllegalStateException("No cells registered");

        String naturalCell = naturalRoute(userId);
        Double fraction = drainFractions.get(naturalCell);

        if (fraction == null || fraction <= 0.0) {
            return naturalCell;
        }

        // Use a secondary hash to deterministically decide drain vs. keep.
        // This ensures the same user always goes to the same cell for a given fraction.
        double userBucket = positiveHash(userId + "-drain-slot") % 1_000_000 / 1_000_000.0;
        if (userBucket < fraction) {
            // Route to the next cell on the ring (drain target)
            return nextCell(naturalCell);
        }
        return naturalCell;
    }

    /**
     * Sets the drain fraction for a cell.
     * fraction=0.0 → no drain (normal routing)
     * fraction=0.5 → 50% of this cell's users go to the next cell
     * fraction=1.0 → 100% migration (cell fully drained)
     *
     * Call this repeatedly over 30 minutes, incrementing fraction in steps
     * (e.g., every 2 minutes increase by 1/15 ≈ 6.7%).
     */
    public void drainCell(String cellId, double fraction) {
        if (fraction < 0.0 || fraction > 1.0) throw new IllegalArgumentException("fraction must be in [0.0, 1.0]");
        if (fraction == 0.0) {
            drainFractions.remove(cellId);
        } else {
            drainFractions.put(cellId, fraction);
        }
    }

    /** Returns the next cell on the ring after the given cell's last vnode. */
    private String nextCell(String cellId) {
        // Find the last vnode of this cell and take the successor
        long lastVnode = hash(cellId + "-vnode-" + (VNODES_PER_CELL - 1));
        SortedMap<Long, String> tail = ring.tailMap(lastVnode + 1);
        long key = tail.isEmpty() ? ring.firstKey() : tail.firstKey();
        String candidate = ring.get(key);
        // Skip if candidate is the same cell (shouldn't happen with 150+ vnodes)
        return candidate.equals(cellId) ? ring.get(ring.firstKey()) : candidate;
    }

    private String naturalRoute(String userId) {
        long hash = hash(userId);
        SortedMap<Long, String> tail = ring.tailMap(hash);
        long key = tail.isEmpty() ? ring.firstKey() : tail.firstKey();
        return ring.get(key);
    }

    private static long hash(String key) {
        try {
            MessageDigest md = MessageDigest.getInstance("MD5");
            byte[] digest = md.digest(key.getBytes(StandardCharsets.UTF_8));
            long h = 0;
            for (int i = 0; i < 8; i++) h = (h << 8) | (digest[i] & 0xFF);
            return h;
        } catch (NoSuchAlgorithmException e) {
            throw new RuntimeException(e);
        }
    }

    private static double positiveHash(String key) {
        long h = hash(key);
        return h == Long.MIN_VALUE ? 0.0 : Math.abs((double) h);
    }
}

// JUnit 5 test
import org.junit.jupiter.api.Test;
import java.util.List;
import java.util.Set;
import java.util.stream.Collectors;
import java.util.stream.IntStream;
import static org.junit.jupiter.api.Assertions.*;

class CellRouterDrainTest {

    @Test
    void noUserIsDoubleRouted() {
        List<String> cells = List.of("cell-1", "cell-2", "cell-3", "cell-4");
        CellRouter router = new CellRouter(cells);

        // Generate 10,000 user IDs
        List<String> userIds = IntStream.range(0, 10_000)
            .mapToObj(i -> "user-" + i)
            .collect(Collectors.toList());

        // Drain cell-1 at 50%

            assertNotNull(cell, "User " + userId + " routed to null");
            assertTrue(validCells.contains(cell), "Invalid cell: " + cell);
        }
    }

    @Test
    void drainFractionIsApproximatelyRespected() {
        List<String> cells = List.of("cell-A", "cell-B", "cell-C");
        CellRouter router = new CellRouter(cells);

        // Count natural cell-A users
        List<String> cellAUsers = IntStream.range(0, 30_000)
            .mapToObj(i -> "u-" + i)
            .filter(uid -> {
                router.drainCell("cell-A", 0.0); // no drain
                return "cell-A".equals(router.route(uid));
            })
            .collect(Collectors.toList());

        router.drainCell("cell-A", 0.5);

        long stillOnA = cellAUsers.stream()
            .filter(uid -> "cell-A".equals(router.route(uid))).count();
        long movedOff  = cellAUsers.size() - stillOnA;
        double actualFraction = (double) movedOff / cellAUsers.size();

        // Allow 5% tolerance around the 50% target
        assertTrue(actualFraction > 0.45 && actualFraction < 0.55,
            "Expected ~50% drain, got " + actualFraction);
    }

    @Test
    void drainIsIdempotent() {
        CellRouter router = new CellRouter(List.of("c1", "c2", "c3"));
        router.drainCell("c1", 0.5);

        String cell1 = router.route("test-user-42");
        String cell2 = router.route("test-user-42");
        assertEquals(cell1, cell2, "Same user should route to same cell on repeated calls");
    }
}
```

**Why this works:** The drain decision uses a secondary deterministic hash of the userId keyed with a drain-specific suffix. This guarantees that for any fixed fraction, the same user always takes the same branch — no oscillation, no double-routing. The fraction controls what percentage of the `[0, 1)` hash space is considered "drain candidates."

**Common mistake:** Using `Math.random()` inside `route()` — this would cause the same user to alternate between cells on successive requests, breaking session affinity and potentially causing split-brain state in downstream services. Drain routing must be stateless and deterministic.

<summary>Exercise 5 — AWS AZ independence and shuffle sharding vs namespace isolation</summary>

**What AWS AZ independence adds on top of namespace isolation:**

Kubernetes namespace isolation with `NetworkPolicy` and `ResourceQuota` isolates workloads at the software layer — but all pods still share the same physical API server, etcd cluster, and scheduler. If the API server crashes or etcd loses quorum, all namespaces (cells) become unschedulable simultaneously.

AWS Availability Zone independence goes further: each AZ has its own physical hardware, power supply, cooling, and network fabric. The AZ boundaries are drawn at the infrastructure layer, not the software layer. A failure in AZ-A (power outage, networking partition) cannot propagate to AZ-B regardless of what software is running. This is failure-domain isolation that no amount of Kubernetes configuration can replicate within a single cluster.

**Connection to shuffle sharding:**

Shuffle sharding assigns each customer to a unique subset of k workers from a pool of n (e.g., k=2 from n=20). If a worker fails, only customers sharing that specific worker are affected. Unlike cell architecture (where blast radius = 1/N), shuffle sharding allows blast radius = k/n while still handling more total customers per worker. The "shuffle" ensures no two customers share the exact same subset, so a failure of one worker affects a disjoint subset of customers from a failure of another worker.

The Kubernetes analogy: if each "cell" in a namespace-isolated cluster uses a different pair of nodes from a pool of 20 nodes (shuffle sharding across nodes), a single node failure affects only the cells that include that node — typically k/n customers instead of 1/N.

**The key distinction:** Namespace isolation is a scheduling and policy boundary. AZ/shuffle-shard isolation is a physical failure-domain boundary. Both are necessary in a production-grade cell architecture.

**Staff-level phrasing:** "Kubernetes namespace isolation prevents tenant interference at the software layer; AWS AZ independence and shuffle sharding prevent correlated failures at the infrastructure layer — you need both because software-only isolation cannot survive a power outage or network partition in a shared physical environment."

## 8. Summary / Flashcard

- Cell-based architecture reduces blast radius from 100% (global shared state) to `1/N` (one cell of N) by ensuring cells share no databases, caches, connection pools, or service-mesh control planes.
- Consistent hashing maps users to cells with O(log N) lookup and remaps only `1/(N+1)` of users when a cell is added — versus ~50% remap with modulo routing, which causes thundering herds on cluster expansion.
- Global components (ingress router, identity provider, DNS) remain single points of failure even in a cell architecture; they must be independently highly available and must not perform per-request state mutations.
- Cell size is a direct function of acceptable blast radius: blast\_radius = cell\_size / total\_users; target <5% for production financial systems, which means a minimum of 20 cells for a 1M-user fleet.
- In Kubernetes, cell isolation requires three layers: `NetworkPolicy` for traffic isolation, `ResourceQuota` for compute isolation, and separate node pools (or separate clusters) for failure-domain isolation — namespace alone is insufficient.

## 3. THE CRITICAL DIALOGUE

**Student:** My service has random 50ms latency spikes on roughly one in five requests. I added Prometheus metrics and the spikes correlate exactly with the first request to any external hostname. After that first call, subsequent calls to the same host are fast. It looks like DNS.

**Principal:** It is DNS. What does your `resolv.conf` look like inside the container?

**Student:** I haven't checked. I assume it just points at a DNS server.

**Principal:** That's your first problem — never assume networking configuration inside a container. Run `kubectl exec -it <pod> -- cat /etc/resolv.conf`. What do you expect to see?

**Student:** Maybe the cluster DNS IP and the cluster domain?

**Principal:** You'll see something like this:

```
nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

That `ndots:5` option is the culprit. Do you know what it means?

**Student:** Something about dots in the hostname?

**Principal:** `ndots:5` tells the resolver: "if the hostname has fewer than 5 dots, try it as a relative name first by appending each search domain before trying it as-is." A hostname like `api.stripe.com` has 2 dots — fewer than 5 — so the resolver tries these queries in order:

```
1. api.stripe.com.default.svc.cluster.local  → NXDOMAIN
2. api.stripe.com.svc.cluster.local          → NXDOMAIN
3. api.stripe.com.cluster.local              → NXDOMAIN
4. api.stripe.com.                           → A record found
```

Three failed DNS lookups before the real one. Each NXDOMAIN response from CoreDNS takes 10–15ms. So your "first call" to any external host costs an extra 30–45ms. That's your 50ms spike.

**Student:** Why is `ndots:5` even the default? That seems crazy.

**Principal:** It makes short in-cluster names work without qualification. `myservice` (0 dots) resolves to `myservice.default.svc.cluster.local` automatically. The Kubernetes authors prioritised in-cluster ergonomics. The cost is paid by external HTTP calls, and most services weren't making many external calls when this default was chosen. Today, with every service calling Stripe, Twilio, and five other SaaS APIs, it's a real problem.

**Student:** How do I fix it?

**Principal:** Two options. Option 1: set `ndots:1` or `ndots:2` in the pod's `dnsConfig`. This fixes external calls but breaks short in-cluster name resolution — you'd have to use FQDNs (`myservice.default.svc.cluster.local`). Option 2: use FQDNs for in-cluster names everywhere and set `ndots:1`. Option 3: add a trailing dot to external hostnames in your HTTP client config (`api.stripe.com.`) — a trailing dot means "absolute name, skip search domains." In practice, Option 1 with `ndots:2` is the most balanced fix and requires no application code changes.

## 4. THEORY + DIAGRAMS

### 4.1 The Kubernetes Networking Contract

Kubernetes imposes three invariants on every conformant network implementation:

1. Every pod gets a unique IP address routable within the cluster (no NAT between pods)
2. Pods on any node can reach pods on any other node using their pod IP directly
3. The IP a pod sees for itself (`eth0`) is the same IP other pods use to reach it

This is the "flat network" model. It is intentionally simple for the application developer: your Java service calls `http://10.244.3.12:8080` and the packet arrives, no port mapping required. The complexity is pushed into the network plugin.

### 4.2 How CNI Plugins Implement the Flat Model

**CNI (Container Network Interface)** is a specification defining how network plugins attach network interfaces to containers. When the kubelet creates a pod, it calls the CNI plugin binary with the pod's namespace path.

**Step 1 — veth pair creation**

The CNI plugin creates a virtual ethernet pair: two virtual interfaces that are connected like the two ends of a wire. One end (`eth0`) goes inside the pod's network namespace. The other end (`veth-abc123`) stays in the root network namespace.

```
Pod network namespace:       Root network namespace (Node):
  eth0 (10.244.3.12) ←══════ veth-abc123
```

Anything sent into `eth0` comes out of `veth-abc123` and vice versa.

**Step 2 — Linux bridge**

The host end of the veth pair is attached to a Linux bridge (`cni0` or `cbr0`). The bridge acts like a virtual switch: it forwards packets between all attached veth interfaces at Layer 2.

**Step 3 — Overlay network (VXLAN) for cross-node traffic**

When the destination pod is on a different node, the bridge has no direct route. VXLAN (Virtual Extensible LAN) encapsulates the Layer 2 frame inside a UDP packet and sends it to the destination node's physical IP. The destination node's VXLAN interface decapsulates it and delivers it to the local bridge.

### 4.4 ClusterIP Service Routing via iptables

A `ClusterIP` service (e.g. `10.96.45.100:80`) is not an actual network interface — no process is listening on that IP. It is a virtual IP maintained entirely by iptables rules that `kube-proxy` installs.

When a pod sends a packet to `10.96.45.100:80`, the packet hits the `PREROUTING` chain. `kube-proxy` has installed a DNAT rule that rewrites the destination IP to one of the backing pod IPs using statistically-random selection (load balancing):

```
DNAT rules generated by kube-proxy for service "payment-service":

Chain KUBE-SERVICES
  -d 10.96.45.100/32 -p tcp --dport 80 -j KUBE-SVC-PAYMT

Chain KUBE-SVC-PAYMT
  -m statistic --mode random --probability 0.33 -j KUBE-SEP-POD1
  -m statistic --mode random --probability 0.50 -j KUBE-SEP-POD2
  -j KUBE-SEP-POD3

Chain KUBE-SEP-POD1
  -j DNAT --to-destination 10.244.1.5:8080

Chain KUBE-SEP-POD2
  -j DNAT --to-destination 10.244.2.7:8080

Chain KUBE-SEP-POD3
  -j DNAT --to-destination 10.244.3.12:8080
```

The probability math: first pod gets 1/3 chance. Second pod gets 1/2 of remaining 2/3 = 1/3. Third pod gets all remaining = 1/3. Equal distribution.

**The trade-off:** iptables rules are updated synchronously and the entire ruleset is replaced atomically. In a cluster with 10,000 services × 5 pods each = 50,000 iptables rules, a single service update rewrites all 50,000 rules. This is why large clusters migrate to `kube-proxy` in IPVS mode, which uses a hash table instead of a linear rule scan.

### 4.5 DNS Resolution Inside the Cluster

Every pod gets `/etc/resolv.conf` injected by the kubelet:

```
nameserver 10.96.0.10          ← CoreDNS ClusterIP
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

**CoreDNS** is itself a Kubernetes service (`kube-dns.kube-system`) backed by pods. It serves:
- `<service>.<namespace>.svc.cluster.local` → ClusterIP
- `<pod-ip-dashes>.<namespace>.pod.cluster.local` → pod IP
- Everything else → forwarded to upstream resolvers (typically the node's `/etc/resolv.conf`)

**The ndots:5 lookup expansion:**

For a hostname with fewer than 5 dots, the resolver prepends each search domain:

```
Resolving "api.stripe.com" (2 dots < 5):
  Query 1: api.stripe.com.default.svc.cluster.local  → NXDOMAIN (10ms)
  Query 2: api.stripe.com.svc.cluster.local          → NXDOMAIN (10ms)
  Query 3: api.stripe.com.cluster.local              → NXDOMAIN (10ms)
  Query 4: api.stripe.com.                           → 54.187.174.169 (20ms)
  Total:   50ms for first lookup

Resolving "myservice" (0 dots < 5):
  Query 1: myservice.default.svc.cluster.local       → 10.96.45.100 (10ms)
  Total:   10ms — short names work fast
```

This is the design trade-off: short in-cluster names are cheap; external names pay the search-domain tax.

## 5. SOURCE ARCHAEOLOGY

### 5.1 The CNI Specification

The CNI specification defines the contract between the container runtime and network plugins. The spec lives at:

```
https://github.com/containernetworking/cni/blob/main/SPEC.md
```

The interface is deliberately simple — a CNI plugin is an executable that receives JSON on stdin and writes JSON to stdout:

```json
// CNI ADD call (attach network to container)
// Input on stdin:
{
  "cniVersion": "1.0.0",
  "name": "mynet",
  "type": "flannel",
  "ipam": {
    "type": "host-local",
    "subnet": "10.244.0.0/16"
  }
}

// Expected output on stdout:
{
  "cniVersion": "1.0.0",
  "ips": [{"address": "10.244.1.5/24", "gateway": "10.244.1.1"}],
  "routes": [{"dst": "0.0.0.0/0", "gw": "10.244.1.1"}]
}
```

This simplicity is deliberate: the spec makes network plugins replaceable. Flannel, Calico, Cilium, and Weave all implement the same interface.

### 5.2 CoreDNS Source — ndots Handling

CoreDNS is written in Go. The relevant source for understanding how search domain lists are processed is not in CoreDNS itself but in the Go `net` package's resolver, which the kubelet injects into the container:

```
/etc/resolv.conf is read by the Go resolver in net/dnsclient_unix.go
The ndots option is parsed in net/dnsconfig_unix.go:
```

```go
// From Go stdlib: net/dnsconfig_unix.go
case "ndots":
    n, _ := strconv.Atoi(s[6:])
    if n < 0 {
        n = 0
    } else if n > 15 {
        n = 15
    }
    conf.ndots = n
```

The ndots value caps at 15 by the Go stdlib. The lookup logic in `net/dnsclient_unix.go` expands names with fewer dots than `ndots` using the search list before trying the absolute name.

### 5.3 Viewing Actual iptables Rules

To observe the DNAT chains kube-proxy installed:

```bash
# On a node (requires node access or a privileged debug pod)
kubectl debug node/<node-name> -it --image=nicolaka/netshoot -- bash

# Inside the debug container:
iptables-save | grep -A3 "KUBE-SVC-"

# Or count total rules (proxy performance proxy):
iptables-save | wc -l
# Large clusters: 50,000+ lines is a sign you need IPVS mode
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
  namespace: production
spec:
  template:
    spec:
      # Fix 1: reduce ndots to 2 (handles most in-cluster names that use
      # "service.namespace" style, while not expanding external names)
      dnsConfig:
        options:
          - name: ndots
            value: "2"
          # Fix 2: enable single-request-reopen to avoid Linux kernel bug
          # where parallel A and AAAA queries sometimes collide
          - name: single-request-reopen
      containers:
        - name: app
          image: company/payment-service:1.4.2
```

```bash

kubectl exec -it <new-pod> -- cat /etc/resolv.conf

# search default.svc.cluster.local svc.cluster.local cluster.local
# options ndots:2 single-request-reopen

# Now trace DNS for external hostname:
# api.stripe.com has 2 dots, ndots=2, so 2 dots is NOT less than ndots:
# The resolver goes straight to api.stripe.com. (absolute)
# Result: single query, ~20ms instead of ~50ms

# In-cluster short names still work with ndots:2:
# "myservice" has 0 dots < 2, so search domain expansion applies:
# myservice.default.svc.cluster.local → resolves immediately
```

**What ndots:2 buys you:**
- Hostnames with 2+ dots (all external SaaS APIs) go directly to absolute lookup
- Short in-cluster names (0–1 dot) still benefit from search domain expansion
- p99 DNS latency for external calls: `50ms → 5ms`

**When ndots:2 breaks things:**
- If you use two-component in-cluster names like `payment.internal` (1 dot), they still expand through search domains — fine
- If you have custom DNS records with exactly 2 dots inside the cluster (unusual), test carefully

## 7. PRODUCTION LENS

### Incident: ndots:5 Causing 45ms p99 Latency Regression

**Context:** A Java Spring Boot service that calls Stripe's payment API on every checkout. The service ran fine on VMs. After migration to Kubernetes, p99 latency jumped from 85ms to 130ms. The team suspected Kubernetes network overhead.

**Investigation:**

```
Initial hypothesis: VXLAN overhead adding latency.
Evidence against: pod-to-pod latency benchmarks showed <1ms overhead.

Second hypothesis: DNS resolution for api.stripe.com.
Test: added DNS timing spans to HTTP client interceptors.

Findings:
  Average DNS resolution time (pre-fix):
    p50: 22ms
    p95: 48ms
    p99: 65ms  ← this is 3-4 DNS queries at 15-20ms each

  DNS queries per checkout call:
    api.stripe.com.default.svc.cluster.local  NXDOMAIN  18ms
    api.stripe.com.svc.cluster.local          NXDOMAIN  16ms
    api.stripe.com.cluster.local              NXDOMAIN  15ms
    api.stripe.com.                           A record  19ms
    Total: 68ms for first call per connection
```

**Root cause:** `ndots:5` was expanding `api.stripe.com` through all three search domains before issuing the absolute query. The service used HTTP connection pooling, so DNS was resolved on first connection establishment — but connection pool churn under load caused frequent re-resolution.

**Fix applied:**

```yaml
dnsConfig:
  options:
    - name: ndots
      value: "2"
```

**Outcome:**

```
Post-fix DNS resolution time:
  p50: 8ms
  p95: 18ms
  p99: 22ms   ← single query, 45ms improvement at p99

Overall checkout latency:
  Pre-fix  p99: 130ms
  Post-fix p99:  85ms   ← back to pre-migration baseline
```

**Additional finding:** CoreDNS was also receiving 4x the expected query volume, causing occasional CPU throttling on CoreDNS pods. Reducing `ndots` cut CoreDNS query volume by 60% and eliminated the CPU spikes.

**Lesson:** DNS is not free. Every unnecessary lookup adds latency and load to CoreDNS. Profile DNS before blaming application code or network infrastructure.

```
Node A:
  Pod A (10.244.1.5) → eth0 (pod side) 
    → veth-aaa (host side, root netns)
    → cni0 bridge (Layer 2 lookup: 10.244.2.7 not local)

    → flannel.1 (VXLAN interface)
    ↓ ENCAPSULATION POINT (hop 5)
    Outer frame: src=192.168.1.10, dst=192.168.1.20, UDP dport=8472
    Inner frame: src=10.244.1.5, dst=10.244.2.7
    → eth0 (host NIC, 192.168.1.10) → physical network

Node B:
    → eth0 (host NIC, 192.168.1.20) receives UDP frame
    → flannel.1 (VXLAN interface)
    ↓ DECAPSULATION POINT (hop 7)
    Inner frame restored: dst=10.244.2.7
    → cni0 bridge (Layer 2 lookup: 10.244.2.7 → veth-bbb)
    → veth-bbb (host side) → eth0 (pod side)
    → Pod B (10.244.2.7) receives packet
```

**Interface names at each key point:**

| Hop | Interface | Node | IP | Action |
|---|---|---|---|---|
| 1 | eth0 (pod netns) | A | 10.244.1.5 | Pod sends packet |
| 2 | veth-aaa (root netns) | A | — | Exits pod namespace |
| 3 | cni0 (bridge) | A | 10.244.1.1 | L2 forwarding decision |
| 4 | flannel.1 | A | 10.244.1.0 | Route match: VXLAN |
| **5** | **eth0 (NIC)** | **A** | **192.168.1.10** | **ENCAPSULATION: L2 frame in UDP** |
| 6 | physical network | — | — | Routed by physical switches |
| **7** | **eth0 (NIC)** | **B** | **192.168.1.20** | **DECAPSULATION: UDP → inner L2 frame** |
| 8 | flannel.1 | B | 10.244.2.0 | Inner frame forwarded |
| 9 | cni0 (bridge) | B | 10.244.2.1 | L2 lookup → veth-bbb |
| 10 | veth-bbb → eth0 (pod) | B | 10.244.2.7 | Pod receives packet |

**Encapsulation:** Hop 5 — `flannel.1` wraps the L2 frame in a UDP/VXLAN envelope (outer src: `192.168.1.10`, outer dst: `192.168.1.20`, UDP port 8472).

**Decapsulation:** Hop 7 — `flannel.1` on Node B strips the UDP envelope, recovering the original L2 frame with inner dst `10.244.2.7`.

```
  -j DNAT --to-destination 10.244.1.5:8080

Chain KUBE-SEP-POD2
  -j DNAT --to-destination 10.244.2.7:8080

Chain KUBE-SEP-POD3
  -j DNAT --to-destination 10.244.3.12:8080
```

**Probability math verification:**
- Rule 1: P(→ POD1) = 1/3 = 0.333
- Rule 2: P(→ POD2 | not POD1) = 0.50; P(→ POD2) = 0.50 × 2/3 = 1/3
- Rule 3: P(→ POD3) = 1 - 1/3 - 1/3 = 1/3

**Equal distribution confirmed: each pod gets 1/3 of traffic.**

**If scaled to 5 pods:**
- Rule 1: probability = 1/5 = 0.2000
- Rule 2: probability = 1/4 = 0.2500 (of remaining 4/5 → 0.25 × 0.8 = 0.2)
- Rule 3: probability = 1/3 = 0.3333 (of remaining 3/5 → 0.333 × 0.6 = 0.2)
- Rule 4: probability = 1/2 = 0.5000 (of remaining 2/5 → 0.5 × 0.4 = 0.2)
- Rule 5: fallthrough (remaining 1/5 → 0.2)

**This is O(N) rule evaluation per packet.** At 50,000 services × 5 pods = 250,000 rules, a single packet triggers up to 250,000 iptables rule evaluations — the reason large clusters migrate to IPVS mode (hash table lookup = O(1)).

</details>

<summary>Exercise 4 — dnsConfig tuning: minimum ndots for 4 hostname types</summary>

**Requirements:**
- `auth-service` (0 dots): needs search expansion for `auth-service.default.svc.cluster.local` → needs `ndots ≥ 1`
- `kafka.messaging` (1 dot): needs search expansion for `kafka.messaging.svc.cluster.local` → needs `ndots ≥ 2`
- `api.github.com` (2 dots): should go straight to absolute (no expansion) → needs `ndots ≤ 2` (with ndots=2: 2 dots is NOT `< 2` → no expansion ✓)
- `hooks.slack.com` (2 dots): same as above → needs `ndots ≤ 2`

**The ndots check:** expansion applies if `hostname_dots < ndots`.
- `ndots: 2` → expansion when dots < 2 (i.e., 0 or 1 dot) → `auth-service` (0 dots) and `kafka.messaging` (1 dot) get expansion ✓; `api.github.com` (2 dots) goes absolute ✓

**Minimum ndots = 2** satisfies all four requirements.

**Complete dnsConfig block:**
```yaml
dnsConfig:
  options:
    - name: ndots
      value: "2"
    - name: single-request-reopen   # fixes parallel A/AAAA query race on some Linux kernels
```

**Reasoning:**
- `auth-service` (0 < 2): expanded → `auth-service.default.svc.cluster.local` → resolves ✓
- `kafka.messaging` (1 < 2): expanded → `kafka.messaging.svc.cluster.local` → resolves ✓
- `api.github.com` (2 is NOT < 2): absolute → `api.github.com.` → single query ~5ms ✓
- `hooks.slack.com` (2 is NOT < 2): absolute → single query ✓

**What ndots=1 would break:**
`kafka.messaging` (1 dot) would NOT expand with ndots=1 (1 is not < 1). You'd need to use the full FQDN `kafka.messaging.svc.cluster.local` in application config — an application code change. ndots=2 avoids this.

<details>
<summary>Exercise 5 — CNI plugin not found: causes and diagnosis</summary>

**Error analysis:**
```
Failed to create pod sandbox: rpc error:
failed to set up sandbox container network for pod:
failed to find plugin "flannel" in path [/opt/cni/bin]
```

**What this indicates:**
The Flannel CNI plugin binary (`/opt/cni/bin/flannel`) does not exist on the node. The kubelet calls CNI plugins as executables at a standard path. If the binary is missing, every new pod creation fails at the network attachment step.

**CNI binary path:** `/opt/cni/bin/` (sometimes `/usr/libexec/cni/` depending on distro). The path is configured in the kubelet's `--cni-bin-dir` flag.

**Verify the binary exists:**
```bash
# Via a privileged debug pod on the affected node:
kubectl debug node/<node-name> -it --image=ubuntu -- bash
ls /opt/cni/bin/
# Expected: flannel, bridge, host-local, loopback, etc.
# If flannel is missing → the installer DaemonSet failed on this node

# Or via node shell if you have SSH access:
ssh <node> "ls /opt/cni/bin/"
```

**Two possible causes:**

1. **Flannel DaemonSet installer pod failed or was evicted on this node:**
   Flannel installs its binary via an `initContainer` in the `kube-flannel` DaemonSet (`kube-flannel-ds`). If the pod on this node was evicted, OOMKilled, or failed to start, the binary was never installed. Fix: `kubectl delete pod -l app=flannel -n kube-flannel --field-selector spec.nodeName=<node>` to restart the DaemonSet pod.

2. **Node was replaced or re-imaged without reinstalling the CNI:**
   On node autoscaler scale-up or manual node replacement, a new node is created from a base image. If the Flannel DaemonSet has a `tolerations` or `nodeSelector` that excludes the new node (e.g., a missing label), the installer never runs. Fix: ensure the Flannel DaemonSet tolerates all node taints and has no restrictive nodeSelectors.

**Staff-level phrasing:** "CNI plugin missing means the Flannel installer DaemonSet didn't run on this node — check the flannel DaemonSet pod for this node first; if it's missing or failed, the binary was never installed, and every new pod on this node will fail at network attachment."

## 9. SUMMARY / FLASHCARD

- **Kubernetes flat networking:** every pod gets a unique routable IP; no NAT between pods; CNI plugins implement this via veth pairs + Linux bridge + VXLAN tunnelling for cross-node traffic — the application sees a flat Layer 3 network.
- **ClusterIP is virtual:** no process listens on a ClusterIP; kube-proxy installs iptables DNAT chains that rewrite destination IPs to backing pod IPs at the kernel level, with probabilistic load balancing.
- **ndots:5 expansion:** any hostname with fewer than 5 dots gets expanded through all search domains before the absolute query — `api.stripe.com` triggers 3 NXDOMAIN lookups adding 30–50ms; fix with `dnsConfig.options ndots: "2"` in the pod spec.
- **CoreDNS is a Kubernetes service:** DNS traffic routes through ClusterIP → iptables → CoreDNS pods; CoreDNS CPU pressure causes cluster-wide DNS latency; monitoring CoreDNS query rate is a production health signal.
- **CNI is a simple exec interface:** a CNI plugin is a binary that receives JSON on stdin and returns JSON on stdout; this simplicity allows Flannel, Calico, and Cilium to be swapped without changing the kubelet or container runtime.
